# ADR-0033: 采用静默写入且不参与裁决的分级记忆

## 状态

Accepted (2026-08-25 实现)

## 日期

2026-08-24

## 背景

Forge 今天唯一像记忆的东西是 `FORGE.md` (ADR-0018 §5): 每轮现读, 单文件 32 KiB,
总计 64 KiB, 渲染成 `WORKSPACE_INSTRUCTIONS` 块. 但它是**人写的** —— Agent 在一次
会话里弄清楚"这个项目的测试命令是 `make test` 而不是 `pytest`", 下一次会话它一无
所知, 只能重新试一遍.

`docs/02-detailed-design.md` §7 画过一份草稿 (`memory/project.md` +
`memory/user.json`), 写于 ADR-0026 统一 JSON 之前, 且从未实现. **本 ADR 取代它.**

### 为什么不把学到的东西写进 `FORGE.md`

这是设计时认真考虑过并否决的方案. 它有一个很强的优点 (只有一份真相, 用户能看能改
能进 git review), 但三条否决理由更硬:

1. **不是所有用户都会建 `FORGE.md`.** Agent 自己创建一个用户没要求过的文件, 是对
   工作区的意外改动.
2. **`FORGE.md` 在 git 里, 写它就是写进别人的工作区.** 团队协作时每个人的 Agent
   都往同一个文件里写自己学到的东西, 产生的 diff 噪音和冲突要由整个团队承担.
3. **人写的约定和机器推断的事实混在一个文件里, 之后分不开** —— 而它们的信任级别
   不一样 (决策 8).

### 一条必须先说清的边界

记忆会进系统提示词, 所以它天然是一个跨会话的注入面: 一个被污染的仓库文件被模型读到,
判断成"项目事实", 写进记忆, 下个会话它以提示词的身份出现.

**这个风险的承重缓解不是写入审批, 是"记忆不参与安全裁决" (决策 3).** 记忆进不了
裁决链, 最坏情况就是模型照着一条被污染的记忆去请求一个动作 —— 然后照常撞上
ADR-0013 / ADR-0020 / ADR-0027 那整条链, 该问人的还是问人. 爆炸半径由现有架构框住.

ADR-0009 §背景里有一条被划掉的话记着同一件事: *"项目记忆里说, 模型大概率不会请求
该动作; 但这属于'影响尝试', 安全边界仍以规则为准"*. 本 ADR 把它重新钉死, 并且钉成
机器守得住的.

## 决策

### 决策 1: 三类记忆分开, 只有两类归本 ADR

| 类别 | 谁写 | 存哪 | 归谁管 |
|---|---|---|---|
| 人写的项目约定 | 用户 | 工作区 `FORGE.md` | ADR-0018, 不变 |
| Agent 学到的项目事实 | 模型 | `~/.forge/projects/<id>/memory.json` | 本 ADR |
| 用户偏好 | 模型 | `~/.forge/memory.json` | 本 ADR |

分级判据取自 ADR-0001 补充条款: **生命周期**. 项目事实跟项目走, 输出偏好跟人走,
所以它们不能同一个文件.

### 决策 2: 静默自动写入, 不设人工审批

模型判断某件事值得记就直接写, 不弹审批, 不打断.

理由是决策 3 已经把爆炸半径框住了: 在"记忆进不了裁决"成立的前提下, 写入审批是第二道
弱得多的闸, 却要在每次写入时付 UX 代价. 而记忆的全部价值就在于它是**无感积累**的 ——
一个每次都要人点确认的记忆系统, 用户会在第三次的时候关掉它.

**显式接受的残余风险**: 被污染的仓库内容可能进入记忆, 并在后续会话里影响模型的判断
(不是它的权限). 缓解手段是决策 3 的禁令 + 决策 7 的来源可追 + 决策 4 那条"删掉文件即可重来",
不是事前审批. 这是本项目在 MVP 阶段的取舍.

### 决策 3: `memory ⇏ security`, 写成机器判据

记忆**在任何情况下都不参与安全裁决**: 不进 `PolicyContext`, 不影响 mode 能力矩阵,
不影响学习规则匹配, 不作为审批展示的依据.

按 ADR-0028 规则 A1, 边界必须是机器守得住的 —— 写在注释里不算. 因此
`scripts/check_arch.py` 的 `SIBLING_BANS` 新增两条:

```python
(
    "application.memory",
    "application.security",
    "记忆不参与任何安全裁决 (ADR-0033 决策 3)",
),
(
    "application.agent_loop",
    "application.memory",
    "AgentLoop 不读写长期记忆 (ADR-0010)",
),
```

### 决策 4: 两级存储, 单文件, 不做版本历史

```
~/.forge/memory.json                         用户偏好
~/.forge/projects/<project_id>/memory.json   项目事实
```

**不做 revision 历史.** 记忆写坏的后果上限很低: 它进不了裁决 (决策 3), 所以最坏是
模型基于一条错事实做了个错判断 —— 比如照着过期的记忆跑 `pytest`, 而项目已经换成
`uv run pytest`. 那一步会当场失败, 用户看得见, 模型下一轮就能改.

而 revision 历史要连带解决"旧版本什么时候清理", 那本身是一整套也会出错的机制. 用一套
会出错的机制去兜一个后果很轻的错误, 不划算. 真需要历史的时候再引入不迟 —— 那时
ADR-0022 计划的 `r<N>.json` 形状现成可抄.

记忆写坏的恢复路径是**删文件**. `project_id` 形如 `ForgeCLI-a1b2c3d4`
(`generate_project_id` 拿目录名做前缀, 见 `domain/workspace/project.py:74`), 所以
用户找得到那个文件, 删掉即可重新开始. 这不是一个功能, 是写在这里让人知道文件在哪 ——
`~/.forge/` 是 ADR-0015 恢复机制**有意**排除的区域, `/recovery` 救不回记忆.

不落工作区: 与 `plans/` 同一条理由 (ADR-0022 决策 5) —— 落工作区会污染用户仓库,
还会被下一轮 Agent 当成项目内容读回上下文. 附带后果是 `fs.*` 工具够不到它, 这正是
想要的隔离.

### 决策 5: 记什么, 不记什么, 以及写入过滤

**允许**: 可验证的项目事实 (测试命令, 构建命令, 目录含义, 架构事实), 用户明确说过
的偏好.

**禁止**: 推断与猜测; 进度与决定 ("我们决定先改 A 再改 B" —— 那是计划, 归
ADR-0022); 任何凭证.

判据是 **"脱离产生它的那段对话之后, 这句话还成不成立"**. 这条正好和 ADR-0022 给
计划定"会话级"的判据互补: 计划失真所以不跨会话, 记忆不失真才配跨会话.

**凭证过滤是强制的.** 静默写入意味着一条 API key 可能被无声写进
`~/.forge/projects/<id>/memory.json` 并在此后每一轮进提示词. 写入侧按已知形状
(`sk-`, `ghp_`, `AKIA`, PEM 头, 高熵长串) 拒绝并回一条明确的 observation, 不静默
截断.

**这份过滤不能复用 `application/agent_run/scrubbing.py`.** 那份注释明写*"不做脱敏"*,
理由是工具入参是用户判断要不要放行的依据, 挡掉一部分只会让他在看不全的信息上做决定.
记忆的取舍正好相反: 静默写入, 长期读取, 没有人在看. 同一个仓库里出现两份文本处理
不是重复, 是两个不同的取舍 —— 这一段写在这里, 是为了下一个想合并它们的人.

### 决策 6: 同 key 覆盖, 不是 append

记忆是 `key -> {value, provenance}` 的映射, 不是流水.

静默写入加只增不改等于**错误单调累积**: 项目从 `pytest` 换到 `uv run pytest` 之后,
旧那条永远在, 而模型会看到两条互相矛盾的记忆并自己挑一条. 同 key 写入直接覆盖,
旧值直接丢弃 —— 决策 4 不留历史.

### 决策 7: 每条记忆带来源

每条记录 `{session_id, turn_id, created_at, derived_from}`.

这不是为了审批 (决策 2 已经否掉了), 是为了排查: 没有来源的坏记忆无法调试 ——
"模型为什么突然认为测试命令是 X" 这个问题只有来源能回答.

**session_id 与 turn_id 由 `MemoryService.begin_turn` 带进来, 不走 `ToolPlan`**
(2026-08-25 实现时补充). 工具的 `perform` 只拿得到 ToolPlan 与 ExecutionContext,
两者都不带会话身份; 塞进 `normalized_input` 是能拿到, 但那会进 `plan_hash`, 于是
"两次内容完全相同的调用得到同一个 plan_hash"这条不变量就破了
(见 `ToolPlan._hash_source` 的注释). 所以由 AgentTurnService 在每轮开始时推进一个
进程内标记, 形状与 `ProjectContext` 一样.

### 决策 8: 注入通道与信任标注

新增 `PromptBlockId.MEMORY_STATE`, 由 `SystemPromptBuilder` 渲染, 读取时机与
`project_instructions` / `planning` 完全一致 (`AgentTurnService._compile_prompt`
每轮现读, 轮内冻结).

**放在缓存断点之后**, 与 `PLAN_STATE` / `TODO_STATE` 同侧: 记忆可能在会话中途被
模型改写, 进稳定前缀就等于前缀不再稳定, 而这件事没有任何一层会说话
(`domain/prompt/blocks.py` 的模块注释).

**块正文必须标注来源与信任级别**: 这些是从过往对话推断出来的事实, 不是用户下达的
指令. 与 `FORGE.md` 冲突时以 `FORGE.md` 为准.

**逐条冲突检测没有做, 只保留无条件的优先级声明** (2026-08-25 实现时修订). 原文要求
"冲突要在块里显式写出来". 实现时发现"这条记忆与 `FORGE.md` 矛盾吗"需要语义比较, 而
机械可做的两种近似都不成立: 按 key 字面匹配几乎永不命中 (key 是 `test_command` 这样的
slug, 而 `FORGE.md` 写的是中文散文), 按 value 匹配测出来的是**一致**而不是冲突.

所以块正文无条件声明优先级, 由模型自己判. 这满足了原文真正要的那一半 —— 不静默取一个,
两边都摆出来 —— 而摆一个几乎不会响的逐条提示反而更糟: 它不响的时候, 读代码的人会
以为"没提示就是没冲突".

块正文与标注文案按 ADR-0031 进 `domain/prompt/text.py`, 受 `PROMPT_TEXT_VERSION`
管辖 (ADR-0031 把原来的 `MAIN_AGENT_PROMPT_VERSION` 接续成了它, 本 ADR 初稿写的是
旧名).

### 决策 9: 写入走工具管线, 新增 `MEMORY_WRITE` 能力

新增工具 `memory.write` / `memory.forget`, 按 ADR-0029 归到同一个动作模块.

走工具管线的收益是**全套机制免费继承**: `TOOL_REQUESTED` / `TOOL_COMPLETED` 审计,
运行事件, 目录谓词, mode 门 —— 不用为记忆再造一套.

`Capability` 闭集新增 `MEMORY_WRITE`. **它不进 `MUTATING_CAPABILITIES`** —— 写的是
Forge 自己的状态目录, 碰不到工作区也碰不到工作区之外的用户文件, 所以不触发审批,
这正是决策 2 要的静默. 先例是 `PLAN_ONLY`: `plan.write` 同样写 `~/.forge/` 下的文件,
同样不算 mutating.

不复用 `PLAN_ONLY` 而新增一个值: 复用会让安全模块的能力矩阵里"计划"和"记忆"变成同一
件事, 而将来任何一条只想管其中一个的规则都写不出来.

**`CAPABILITY_VOCABULARY_VERSION` 不升, 已有的 `always` 学习规则与风险缓存不失效.**

`domain/tool/capability.py` 的模块注释今天写着"新增或改写词汇需要 ADR 或显式版本升级,
并使下游缓存与学习规则失效". 本 ADR 把这句拆成两种情况, 并同步改掉那段注释:

- **增量扩词汇** (加一个新值, 不动任何已有值的含义): **不需要失效**.
  `CAPABILITY_VOCABULARY_VERSION` 全库只有一个消费方 —— `ToolPlan` 的同名字段默认值
  (`domain/tool/plan.py:192`), 它进 `_hash_source` 因而进 `plan_hash`. 加一个新枚举值
  不改变任何已有 plan 的哈希: 老规则是给不声明 `MEMORY_WRITE` 的工具记的, 照常匹配;
  `memory.write` 是新工具, 没有旧规则指着它. 升版本反而会把每一个 `plan_hash` 打乱,
  让用户为一件与他无关的事重新批准一遍.
- **语义改动** (改写或复用一个已有值): **必须升版本并失效**. 那时一条老规则可能匹配
  上一件它当初没批准过的事, 而这是静默的.

这条区分本来就隐含在"失效是为了防止旧授权匹配新语义"这个理由里, 只是原注释没分开写.
`memory.write` 是第一个增量扩词汇的案例, 所以在这里补清楚.

### 决策 10: 入口不给 `AgentLoop`

`MemoryService` 是记忆对外的唯一入口, **只注入 `AgentTurnService`**.

ADR-0010 §影响明写: *"`AgentLoop` 只能产出意图, 不能直接写文件, 执行 shell, 写事件
或**读写长期记忆**"*. 把入口给循环是字面违反.

从功能上讲循环也用不着: 记忆是提示词块, 按 ADR-0018 每轮冻结, 读取只发生在
`_compile_prompt` 那一刻 —— 与 `ProjectInstructionReader` 和 `PlanningService`
完全同构, 而那两个就是注入 `AgentTurnService` 的. 写入走决策 9 的工具管线, 同样
不经过循环.

**这样"记忆与循环解耦"完成得比给它一个端口更彻底**: 循环对记忆的依赖数是 0.

## 备选方案

- **写进 `FORGE.md` 的受管区段**: 单一真相, 可 review, 可进 git. 因背景里的三条
  理由否决.
- **写入需人工审批**: 更保守, 但决策 3 已经把爆炸半径框住, 这道闸的边际收益小而
  UX 代价每次都付.
- **保留 revision 历史与 `/memory` 查看回退**: 写坏时能精确回退, 但要连带设计旧版本
  的清理, 而它兜的那个错误后果很轻 (决策 4).
- **回合结束后由 Forge 抽取记忆, 不做成工具**: 模型不会忘记调用, 但每轮多一次 LLM
  调用 (成本), 且绕开工具管线要自建一套审计.
- **记忆与计划共用 `PLAN_ONLY` 能力**: 少加一个枚举值, 但安全矩阵从此分不开这两件事;
  而按决策 9, 增量扩词汇的成本本来就接近零.
- **只做用户偏好, 不做项目事实**: 风险最小, 但把最有价值的那一半 (省掉每次会话重新
  摸索项目) 丢掉了.

## 影响

- 跨会话不再从零摸索项目, 但引入一条模型可写, 且不经人确认的提示词输入.
- `Capability` 闭集多一个值, 但 `CAPABILITY_VOCABULARY_VERSION` 不升, 已有 `always`
  规则与风险缓存不失效; `capability.py` 的模块注释补上增量与语义改动之分.
- `SystemPromptBuilder` 增加一个块, `AgentTurnService` 增加一个依赖.
- `scripts/check_arch.py` 增加两条 `SIBLING_BANS`.
- `docs/02-detailed-design.md` §7 由本 ADR 取代.
- 决策 8 的逐条冲突检测在实现时取消, 只保留无条件的优先级声明.
- `~/.forge/` 下新增两个 JSON 文件, 无版本历史也无自动回收. 记忆写坏时唯一的恢复
  路径是用户手动删文件, 产品内没有查看与删除入口 —— 这是本 ADR 明确接受的简化.

## 验收标准

- `application/memory` 对 `application/security` 的任何 import 都会让
  `make arch` 失败.
- `application/agent_loop` 对 `application/memory` 的任何 import 都会让
  `make arch` 失败.
- 模型写入一条项目事实后不产生任何审批提示, 且下一个新会话的系统提示词里能读到它.
- 同 key 二次写入后, 提示词里只出现新值.
- 新增 `MEMORY_WRITE` 之后, 已有的 `always` 学习规则仍然匹配 —— 任何已有工具的
  `plan_hash` 都不变.
- 含 `sk-` 前缀或 PEM 头的内容写入被拒绝, 模型收到明确 observation.
- 记忆块无条件声明这些内容是推断而来, 不是用户指令, 并写明与项目指令冲突时以项目
  指令为准.
- 记忆块位于缓存断点之后, `PromptSnapshot._assert_cache_partition` 通过.
- 记忆相关正文全部位于 `domain/prompt/text.py`, `check_prompt_text.py` 通过.
- `make ci` 全绿.
