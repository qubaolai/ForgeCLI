# ADR-0064：把项目级配置按归属拆成三处存储

## 状态

Proposed

## 日期

2026-10-09

## 背景

当前项目身份与项目配置主要写在 `~/.forge/projects/<project-id>/forge.json`，由多个写入方各写各的键（读出后局部修改再写回，靠 round-trip 保留其余内容）：

| 内容 | 键 | 写入方 |
| --- | --- | --- |
| 项目状态 | `project_id`、`trusted`、`primary_workspace_root`、`workspace_roots`、`created_at`、`updated_at` | `project/json_store.py` 的 `JsonProjectConfigStore.save` |
| 模型选择 | `model.provider`、`model.name` | `settings/keys.py` 的项目级键，经 `settings/config_service.py` 路由；在 `runtime/project_runtime.py` 绑定当前项目的 forge.json |
| 按用途模型覆盖 | `model_overrides.<origin>` | `llm/overrides_store.py` |
| 权限规则 | `permissions.*` | `security/settings_store.py` |
| 沙箱 | `sandbox.*` | `security/settings_store.py` |
| auto 分类器规则 | `autoMode.*` | `security/settings_store.py` |

（ADR-0054 提到的 `hooks` 段与 `lsp.enabled` 已于 2026-09-18 撤销，不在当前配置面内。）

这些内容同处一个文件的后果是：**其中一部分描述"这个项目"，另一部分描述"这台机器上的这个人"，而文件位置只服务于后者。**

具体地说：

- `project_id` 由本机绝对路径的 sha256 生成（`project/model.py` 的 `generate_project_id`）；`primary_workspace_root` / `workspace_roots` 是本机绝对路径；`trusted` 是本机的人做过的决定；`model.*` 是这台机器上想用哪个模型。这些放在用户级 Forge home 下是对的，它们本就不该跨机器复制。
- 但 `permissions.*`（"这个仓库里 `git push` 先问"、"别碰 `./generated`"）、`sandbox.*`（"这个仓库的构建要访问 registry.npmjs.org"、"`dist/` 是可写产物"）、`autoMode.*`（"这个仓库里哪些目录是一次性的"）是**关于这个仓库的约定**，应该跟着仓库走，让同一个仓库的协作者共享。

现有代码已经把 `sandbox` 与 `permissions` 当作项目级处理：读侧把用户级与项目级合并（`runtime/tool_wiring.py` 的沙箱段与 autoMode 段），写侧"允许并写进项目设置"把域名追加进项目级设置文件（`runtime/sandbox_wiring.py` 的 `add_sandbox_allowed_domain`），`permissions` 同样有用户级与项目级两个来源（`security/permission_setup.py`）。也就是说这些内容本就是按项目归置的，只是项目级那一份落在了本机的 `forge.json` 里。

现状使项目约定无法被表达：一个人的仓库约定只存在于他自己的 `~/.forge/projects/<本机路径 hash>/forge.json` 里，另一个人克隆同一个仓库会得到另一个 project-id 和另一份互不相干的配置。仓库因此没有任何地方可以写下自己的约定，也无法把它交给协作者。

ADR-0008 决定项目级配置与状态不写入项目目录，理由是避免污染用户仓库、避免被误提交。这条理由对*状态*成立，对一个仓库自身的约定不成立。ADR-0063 已为 skills 开了同一个口子（`<workspace-root>/.forge/skills/`），本 ADR 把边界扩展到配置。

## 决策

### 1. 按归属分成三个存储位置

分桶判据是"这条信息描述项目，还是描述本机/本人"，不是"它属于哪一级"。

**存储一：本机项目状态与模型偏好，留在 `~/.forge/projects/<project-id>/forge.json`。**

| 键 | 为什么留 |
| --- | --- |
| `project_id` | 由本机绝对路径的 sha256 生成，换机器、换路径即不同 |
| `trusted` | 坐在这台机器前的人做的决定 |
| `primary_workspace_root`、`workspace_roots` | 本机绝对路径，含个人目录信息 |
| `created_at`、`updated_at` | 本机记账 |
| `model.provider`、`model.name` | 当前机器在本项目使用的默认模型 |
| `model_overrides.<origin>` | 当前机器按用途选择模型 |

**存储二：团队共享设置，写到 `<workspace-root>/.forge/settings.json`。**

| 键 | 为什么 |
| --- | --- |
| `permissions.allow`、`deny`、`ask`、`additionalDirectories` | 团队共享的仓库权限约定。`allow` 仅包含团队明确写入共享文件的规则；Forge 从审批卡片生成的个人 allow 规则另存本机文件 |
| `permissions.defaultMode`、`disableBypassPermissionsMode`、`disableAutoMode` | 这个仓库的默认提问档位与档位开关，即"在这个仓库里默认怎么问" |
| `sandbox.*` | 这个仓库的执行环境需求：要访问的域名、可写与禁读的路径、要排除的命令 |
| `autoMode.allow`、`autoMode.soft_deny`、`autoMode.environment` | 本身就是一句话描述"这个项目/环境的事实"，天生长在项目上 |

`permissions` 与 `sandbox` 的团队约定整体归属仓库；Bash 审批生成的个人 allow 规则是例外，写到本机项目设置。

**存储三：本机项目设置覆盖，写到 `<workspace-root>/.forge/settings.local.json`。**

该文件保存当前用户在本项目的个人授权习惯及对共享设置的本机覆盖，不提交到版本库。Forge 首次向其中写入时，将 `/.forge/settings.local.json` 幂等追加到项目根目录 `.gitignore`；不因首次信任而创建 `.forge/` 或修改 `.gitignore`。

| 键 | 为什么不进仓库 |
| --- | --- |
| Forge 审批流程生成的 `permissions.allow` Bash 命令规则 | 这是用户对常用命令的个人授权习惯，不应随仓库共享 |
| 对共享 `settings.json` 同名标量项的覆盖 | 允许用户在本机调整项目策略而不改团队文件 |

### 2. 本机覆盖与权限规则合并

`settings.local.json` 中同名标量设置优先于 `settings.json`；用户可在本机覆盖团队共享默认值。权限规则列表按来源分别保留并共同参与裁决，不用本机列表整体替换共享列表：

- Bash 审批卡片生成的持久 allow 规则写入 `settings.local.json`，作为本机规则追加到共享规则集合；相同规则去重，不会替换共享 allow 列表。
- `deny` 仍高于 `allow`，不因增加本机来源而改变；本机 allow 不能绕过任何 deny。
- `ask`、`additionalDirectories` 与 sandbox 路径列表等集合字段按字段定义合并，不能用“local 优先”整段替换，也不能借本机配置绕过既有路径边界。

### 3. 共享仓库设置的信任边界

`<workspace-root>/.forge/settings.json` 来自仓库，对克隆它的人而言是不可信输入。它生效的前提是这个人已经在这台机器上信任过这个目录：

- 只有已信任项目才会被激活为 `ProjectRuntime`：`runtime/project_runtime.py` 的 `ProjectRuntimeRegistry.activate` 经 `ProjectService.get` 取项目，未信任时返回 `None`。
- 只有存在当前项目时才读取项目级设置：`security/permission_setup.py` 在 `project_id is None` 时直接跳过项目来源。
- 共享规则按 `PROJECT_SETTINGS`、本机规则按 `PROJECT_LOCAL_SETTINGS` 来源分别标注，界面显示规则来自仓库文件还是本机覆盖；两者仍受既有的 deny 优先与策略内置规则约束（`PermissionRuleSource.POLICY_SETTINGS` 不可被其他来源覆盖）。

共享文件允许包含项目需要的权限与沙箱配置，包括可能放宽操作的 `permissions.allow`、`permissions.defaultMode`、`sandbox.enabled=false` 与 `allowUnsandboxedCommands`。这是明确的产品取舍：信任项目也表示接受该仓库的共享权限与沙箱约定。来源标注帮助用户检查规则，但本身不是执行前的额外授权。Bash 审批时生成的个人 allow 规则仍写入 `settings.local.json`。

### 4. 何时创建 `.forge/`

不因"首次信任目录"而创建。只在真的有仓库侧或本机项目设置要写入时（用户显式编辑共享设置，或 Forge 首次保存个人 Bash allow 规则）才创建 `<workspace-root>/.forge/`。只有首次写入本机设置时才自动更新项目根目录 `.gitignore`。

理由与 2026-06-26 的"不因信任而污染仓库"同源：仅仅信任一个目录不是写入它的理由，否则每个被信任的仓库根目录都会被凭空塞一个 `.forge/`。

### 5. 提交还是忽略

`<workspace-root>/.forge/settings.json` 是团队共享的项目约定，应纳入版本库。`settings.local.json` 是个人项目配置，由 Forge 自动加入 `.gitignore`。项目身份与模型选择继续留在 `~/.forge/projects/<project-id>/forge.json`，天然不进任何仓库。

这样团队约定与个人项目习惯各有明确文件；`.gitignore` 只排除本机覆盖，不排除团队共享设置。

## 落地要点

- 新增共享设置文件 `settings.json` 与本机覆盖文件 `settings.local.json`；两者复用现有 `permissions` / `sandbox` / `autoMode` 段结构。标量键本机优先，规则集合按来源合并。
- `security/settings_store.py` 的 `project_settings_file(project_id)` 只接收 project_id，拼不出 `<workspace-root>/.forge/`，需要把工作区根一并传下去。调用方：`security/permission_setup.py`、`security/permission_update.py`、`runtime/tool_wiring.py`（沙箱、autoMode、沙箱运行期与权限施加器）、`runtime/sandbox_wiring.py`。
- Bash 审批生成的 `permissions.allow` 建议必须以本机项目设置为目标：将 `PermissionUpdateDestination.PROJECT_SETTINGS` 与 `PROJECT_LOCAL_SETTINGS`（或等价目标）区分，调整 `tools/builtin/Bash/bash_permissions.py` 和 `security/shell_rule_matching.py`。来源显示也要区分共享规则与本机规则。
- 首次写入 `settings.local.json` 时，安全地创建或更新主工作区根的 `.gitignore`（不存在时创建），只增加根锚定规则 `/.forge/settings.local.json`，保留其他内容与换行；已有文件若已被 Git 跟踪，不自动执行取消跟踪操作。
- `settings/config_service.py` 的 `ConfigLevel`（定义在 `settings/keys.py`）不需要改：它的项目级键是 `model.provider` / `model.name`，仍落本机 `forge.json`。
- `sandbox` 的 `denyRead` / `denyWrite` / `allowWrite` 常是本机绝对路径。共享文件里用相对主工作区根的路径；写侧只有能无歧义、安全地表达为相对路径时才可写共享层，否则保留在本机层。
- 文案区分团队共享 `settings.json` 与本机 `settings.local.json`；审批卡片说明 Bash allow 只保存到本机项目设置。

## 备选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 全部留在 `forge.json`（现状） | 只有一个文件，读写路径简单 | 项目约定无法随仓库共享；两个协作者各自维护一份 |
| 全部项目级内容都进仓库 `.forge/` | 概念最整齐 | 状态是本机的，进仓库会被误提交；`trusted` 更不能由仓库自己声明 |
| 项目约定进仓库但靠 `.gitignore` 区分 | 不必拆文件 | 文件在仓库外，"忽略其中几段"无从表达 |
| 放宽项留本机、其余随仓库 | 仓库无法替人放宽 | `permissions` 与 `sandbox` 各被拆到两处，读写都要按来源分流；"问不问"的约定无法随仓库共享 |
| 共享 `settings.json` + 被忽略的 `settings.local.json` + Forge home 项目状态/模型文件（选定） | 团队策略与个人授权习惯分开；Bash 审批生成的 allow 不会被提交；身份和模型偏好仍留本机 | 增加一层本机覆盖；规则要按来源合并；首次本机写入需维护 `.gitignore` |

## 影响

**收益**

- 一个仓库可以携带团队共享的权限、沙箱与 autoMode 约定，协作者克隆后即可生效。
- 人类审批时生成的 Bash allow 规则保留为本机项目习惯，不会随仓库共享。
- 项目状态仍留在本机，不产生跨机器复制未信任状态的问题。

**代价**

- 仓库文件可设置放宽方向的键：一份克隆下来的仓库，作者能替协作者设定 `defaultMode`、`sandbox.enabled=false` 等。项目 trust 同时代表接受共享策略；这是本 ADR 明知的取舍。
- 本机设置首次写入要自动更新 `.gitignore`；如果该文件此前已被 Git 跟踪，新增 ignore 规则不会将它自动取消跟踪。
- `sandbox` 的路径类键常是本机绝对路径，需要相对路径化，否则仓库会带上个人目录结构。
- `project_settings_file(project_id)` 的签名与全部调用方要改。
- 相关界面文案要把"项目 forge.json"改指仓库文件。

**兼容性**

- 本 ADR 部分取代 ADR-0008 中"Forge 不在被信任项目根目录下自动创建 `.forge/`"这一条，以及 `docs/roadmap/mvp/2026-06-26/README.md` 中对应的验收项（"确认当前项目根目录下没有自动创建 `.forge/`"）。取代范围仅限配置写入：仍然不允许因"信任目录"而写仓库。
- 迁移前写在 `forge.json` 的项目规则原本是本机数据，且无法可靠区分手动规则与审批生成规则。迁移默认放入 `settings.local.json`，保持当前用户行为且不意外共享；提供显式操作将选定规则提升到 `settings.json`。不能安全转换成相对路径的 sandbox 条目继续留在本机层。

## 验收标准

- `forge.json` 只保留本机项目身份、工作区路径与模型选择。
- `<workspace-root>/.forge/settings.json` 承载团队共享的 `permissions.*`、`sandbox.*`、`autoMode.*`；`settings.local.json` 承载本机覆盖与审批生成的 Bash allow。
- `settings.local.json` 标量设置优先于 `settings.json`；规则来源保持可见，deny 始终高于 allow。
- 首次写入 `settings.local.json` 自动将 `/.forge/settings.local.json` 加入主工作区根 `.gitignore`，不重复、不覆盖其他内容，也不忽略整个 `.forge/`。
- 首次信任目录不创建 `<workspace-root>/.forge/`。
- 共享文件里的 `permissions.allow` 只在目录已被本机信任时生效；审批生成的 Bash allow 只写本机文件。
- 仓库文件设置的 `permissions.defaultMode` / `sandbox.enabled` 等对协作者生效；信任提示说明接受仓库的共享策略。
- `sandbox` 路径类键在仓库文件里以相对工作区根的路径表达。
- 相关界面文案把"项目 forge.json"改指仓库文件。
