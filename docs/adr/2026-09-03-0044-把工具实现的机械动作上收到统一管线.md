# ADR-0044: 把工具实现的机械动作上收到统一管线

## 状态

Proposed

本 ADR 只动"工具实现里重复了 N 遍的那部分代码由谁执行", 不动 ADR-0004 §2 的两段接口,
不动 ADR-0013 的裁决口径, 也不新增任何绕过 `ToolRequestCoordinator` 的执行路径.

## 日期

2026-09-03

## 背景

### 先说清楚不动什么: 两段接口是承重的

`prepare` / `perform` 分段常被当成"写一个工具太重"的原因. 它不是. `ToolPlan` 从产出到
执行之间有六个消费方:

| 消费方 | 读 `ToolPlan` 做什么 |
| --- | --- |
| `CapabilityAnalyzerRegistry` | 按 `capabilities` 分派分析器, 回写 `effective_plan` |
| `PolicyEngine` | 出 ALLOW / ASK / DENY |
| `approval_flow.build_view` | 把 `content_previews` 与目标集合摊开给人看 |
| `RecoveryFlow.begin` | 按 `mutates_workspace` 决定建不建快照 |
| `ToolAuthorizationService.issue` | 把 `plan_hash` 绑进 `ExecutionAuthorization` |
| `ToolRuntime.execute` | 四道校验 + `file_state_bindings` 复核 |

合成单段 `run(arguments, context)` 之后这六个消费方全部没有输入: 审批界面只剩原始 JSON
可展示, `plan_hash` 无从算起, ADR-0027 决策 2 的执行前复核失去比较基准. 分段是这套安全
模型的唯一可能形状.

真正过重的是另一件事: **每个工具都要把同一批机械动作重抄一遍**, 而其中两件是安全性质,
它们今天的执行方式是纪律, 不是机制.

### 数字

`src/forgecli/application/tools/builtin/` 现有 5083 行, 10 个 `Tool` 实现:

- 10 个 `prepare`, **全部**以 `invalid = validate_arguments(_SPEC, request.arguments)`
  开头, 零例外.
- 11 个 `ToolPlan` 构造点, 其中 `plan_id` / `tool_name` / `spec_hash` /
  `execution_context` / `declaration_confidence` 五个字段逐字相同.
- 20 个 `ToolResult` 构造点, 其中 `invocation_id` / `tool_name` / `status` 三个字段逐字
  相同.
- 7 个工具 (`memory_write`, `memory_forget`, `plan_read`, `plan_write`, `todo_write`,
  `todo_set_status`, `artifact_read`) 的 `ToolPlan` 除 `normalized_input` 外整份是常量:
  `effects` 为空, `STATIC`, `IN_WORKSPACE`, 固定 capability. 它们的 `prepare` 是 23-34
  行仪式, 没有一行是这个工具自己的判断.

行数本身不值得写 ADR. 值得写的是下面这条.

### 同一条 TOCTOU 性质今天有两套实现

ADR-0027 决策 2 要求"需要执行一致性的文件以 `FileStateBinding` 进入 `ToolPlan`, 由
`ToolRuntime` 在 `perform` 前统一复核". 这条今天只兑现了一半:

| | `FileStateBinding` | `path_state_token` |
| --- | --- | --- |
| 存放位置 | `ToolPlan.file_state_bindings` | 塞在 `normalized_input` 里 |
| 复核方 | `ToolRuntime._verify_file_state` 一处 | 4 个工具各在 `perform` 开头手写一段 |
| 谁在填 | 只有 `executable_binding` / `script_binding` 两个安全分析器 | `fs_read`, `find_definition`, `search_text`, `fs_apply_patch` |
| 覆盖字段 | realpath, file_identity, size, mtime_ns, content_hash | exists, realpath, kind, is_symlink, link_target, file_identity, size, mtime_ns, mode |
| 性质 | 机制: 漏了也验 | 纪律: 漏写不报错 |

`fs_*` 没走中心那条的原因看得很清楚: `FileStateBinding` 强制要 `content_hash`, 而
`search_text` 一次要绑几百个文件, 全读一遍算哈希不可行. 于是它们各自发明了一个不含内容
哈希的令牌, 并各自手写复核. 两套实现的字段集还不一样 —— 中心那条反而少了
`link_target` 与 `mode`.

## 决策

### 1. 入参 schema 校验由管线执行, 工具不再自己调

`ToolRequestCoordinator._prepare` 在调用 `tool.prepare` **之前**按
`registry.describe(name).input_schema` 校验一次, 不通过直接产出既有的
`ObservationKind.PREPARATION_FAILED`. `base.validate_arguments` 随之删除.

三条理由:

1. **两个入参协调器全都拿得到**: schema 在注册表里, 原始入参在 `ToolRequest` 里. 这件事
   本来就不需要工具参与.
2. **纪律换成机制**: 今天没有任何东西保证一个新工具记得校验, 漏了就是拿着未校验的入参
   往下走到 `ToolPlan`.
3. **`prepare` 的第一条语句从此是这个工具自己的逻辑**, 而不是十份相同的样板.

边界要写清楚: 校验只保证入参**符合 `input_schema`**, 不保证语义有效. 路径存不存在,
正则编不编得过, `scope` 取值合不合法, 仍然是 `prepare` 的事 —— 它们要 `ExecutionContext`,
JSON Schema 表达不了.

未注册的工具已经在 `_check_availability` 挡下, 所以 `describe` 在这一步不会抛
`UnknownToolError`.

### 2. 文件状态复核统一由 `ToolRuntime` 执行, 绑定分三档

`FileStateBinding` 加一个校验级别, 字段集取现有两套的并集:

| 档 | 期望 | 复核内容 |
| --- | --- | --- |
| `ABSENT` | 这条路径当时不存在 | 仍然不存在 |
| `IDENTITY` | 同一个文件 | realpath, kind, is_symlink, link_target, file_identity, size, mtime_ns, mode |
| `CONTENT` | 同一份内容 | `IDENTITY` 全部字段 + 重读比对 `content_hash` |

字段一个都不能少: 少了 `link_target`, 把原文件换成一个指向别处的符号链接复核不出来;
少了 `content_hash`, ADR-0027 决策 2 对可执行文件与脚本的保证就没了.

谁给哪一档:

- `executable_binding` / `script_binding`: `CONTENT`, 与今天一致.
- `fs_read`: 单个目标 `IDENTITY`.
- `find_definition` / `search_text`: 展开出的文件集合 `IDENTITY`. 不给 `CONTENT` 是刻意的
  取舍 —— 几百个文件全部算内容哈希不可行, 而它们要的性质只是"还是我展开时看到的那些
  文件".
- `fs_apply_patch`: update / delete / move 用 `IDENTITY`, create 用 `ABSENT`.

复核只发生在 `ToolRuntime._verify_file_state` 一处, `perform` 之前. `base.path_state_token`
与四段手写复核一并删除.

三处需要一并改到的既有实现:

- `_verify_file_state` 现在无条件要求 `facts.is_regular_file`
  (`application/tools/runtime.py:154`), 这会把 `ABSENT` 判成变化, 必须按档分支.
- `validate_narrowing` 要求 `effective_plan` 只能新增绑定不能移除
  (`domain/tool/authorization.py:113`). `fs_*` 的绑定来自 `prepare`, 属于 `original`
  一侧, 分析器仍然只做新增, 这条约束不变.
- 绑定已经进 `plan_hash` (`domain/tool/plan.py:242`), 而 `path_state_token` 今天塞在
  `normalized_input` 里也进 `plan_hash`. 换过去之后进入哈希的事实没有增减, 但**值会变**.

`plan_hash` 变化不影响存量 learned rules: `can_learn` 要求 `executable_identity_hash`
非空, 而只有 shell 分析器给得出它 (`domain/security/rules.py:173`), 所以今天能落成规则的
只有 `shell_run` —— 它的 `normalized_input` 里没有 `path_state_token`, 本 ADR 一个字段
都没碰它.

### 3. `ToolPlan` 与 `ToolResult` 的机械字段由构造器补齐

- `ExecutionContext.plan_for(spec, request, *, capabilities, effects, ...)` 补上五个逐字
  相同的字段; 其余字段仍由工具显式给出, 且**必须允许覆盖** —— `shell_run` 的
  `OPAQUE` / `UNKNOWN` / `WorkspaceScope.OUTSIDE` 表达不出来的话这个构造器就是错的.
- `ToolPlan.ok(...)` 与 `ToolPlan.failed(code=..., message=...)` 补上 `invocation_id` /
  `tool_name` / `status`.

这一条是纯重构, 但收益不只是行数: `spec_hash` 抄错今天只在
`application/tools/runtime.py:85` 运行期被抓到, 走构造器就没有抄错的余地.

### 4. `ToolPlan` 为常量的工具用统一基类

新增 `ConstantPlanTool`: 子类声明 capability 并实现 `run(...) -> ToolResult`, 基类实现
`prepare` 产出那份常量计划. 名字按**判据**取, 不按用途取 —— 判据是"这个工具的
`ToolPlan` 除 `normalized_input` 外是常量", 那是可以逐条对照检查的.

这**不是**快速通道: 这些工具照样走完整条管线, 照样受 `ToolSpec` 上界与
`ExecutionAuthorization` 校验, 照样写 `TOOL_REQUESTED` / `TOOL_COMPLETED`. 少的只有手抄
plan 那一段. ADR-0004 §3 口径 2 (没有 `requires_authorization`) 完全保留.

ADR-0043 的 `ask_user` 是第 8 个这样的工具, 也是本 ADR 最直接的检验: 一个"阻塞问一句话"
的工具如果要写 120 行而其中 100 行是 plan 仪式, 那就是这套设计过重的证据.

### 5. 协调器的阶段通知收敛为一次扇出

`application/tool_request/coordinator.py` 739 行里有 35 处遥测调用 (21 处 `_log.`,
9 处 `_observer.`, 5 处 `_audit.`), 每个阶段向三个 sink 各喊一遍, payload 高度重叠,
`_resolve` 读起来一半是流程一半是日志.

改为一个按阶段扇出的 `PipelineTrace`: 每个阶段记一次, 由它分发到日志, `ToolRunObserver`
与 `ToolAuditSink`. **落盘事件的名称与字段一个都不变** —— 变的只是谁来调用.

顺序约束仍然是安全约束, 必须在 `PipelineTrace` 里显式保留: 写前审计落盘先于
`tool_started` (`coordinator.py` 的既有注释), 恢复屏障先于 `issue` (ADR-0015 §1).

## 备选方案

- **方案 A: 合并 `prepare` / `perform` 为单段 `run()`.** 拒绝. 背景第一节的六个消费方
  全部失去输入, 审批界面退化成展示原始 JSON, ADR-0027 的执行前复核没有比较基准.
- **方案 B: 反过来, 删掉 `FileStateBinding`, 统一用 `path_state_token`.** 拒绝. 那是把
  机制换成纪律: ADR-0027 决策 2 对可执行文件与脚本的复核会退回到每个工具自觉, 而这条
  性质恰恰是不能靠自觉的.
- **方案 C: 给 `ToolSpec` 加 `requires_validation` 之类的开关, 让工具选择走不走统一校验.**
  拒绝. 与 ADR-0004 §3 口径 2 同一条理由: 让工具作者决定自己受不受管, 等于没管.
- **方案 D: 维持现状, 只在工程规范里写一条"记得校验, 记得复核".** 拒绝. 那条规范今天
  事实上已经存在 (`base.py` 的模块说明), 而两套 TOCTOU 实现正是在它下面长出来的.

## 影响

### 收益

- 入参校验与文件状态复核从"每个工具记得做"变成"管线一定做", 两条安全性质各只剩一个
  执行点.
- `FileStateBinding` 的字段集补齐 `link_target` 与 `mode`, 中心复核不再弱于工具自己写的
  那一份.
- 新增一个工具的成本落到"这个工具自己的逻辑"上: 常量 plan 的工具不写 `prepare`, 其余
  工具的 `prepare` 第一行就是自己的判断.
- `coordinator._resolve` 恢复成一段可以一眼读完的流程.

### 代价

- **有一处模型可见的行为变化, 不是无损重构**: 四个 `fs_*` 工具的复核失败, 返回形状从
  `ToolResult(TOOL_ERROR, code="target_changed", retryable=True)` 变成
  `AuthorizationError` -> `ObservationKind.EXECUTION_ENVIRONMENT_CHANGED`
  (`can_retry=True`). 分类因此更准确 —— 目标在裁决后被替换本来就不是"工具坏了" ——
  但终端文案与模型看到的 observation kind 都会变.
- `plan_hash` 的值会因绑定位置变化而改变一次. 存量 learned rules 不受影响 (决策 2),
  但任何按 `plan_hash` 做的缓存都会失配一次.
- 改动触及 10 个工具的公共路径, 而 `tests/` 现在总共 1931 行, 工具层几乎没有行为覆盖.

**前置条件**: 先补一组 `prepare` -> `evaluate` -> `perform` 的管线测试, 再动上述任何一
项. 没有这组测试, 重构完只能靠肉眼确认没退化.

### 已知边界

- `IDENTITY` 档不读内容, 因此挡不住"内容变了而 size 与 mtime_ns 被刻意保持不变"的替换.
  这是明知的取舍, 需要内容级保证的路径 (可执行文件, 脚本) 仍走 `CONTENT`, 与 ADR-0027
  决策 2 一致.
- 复核仍然发生在 `perform` 之前, 不是把已打开的 fd 交给工具. ADR-0027 已知边界里那条很窄
  的宿主并发窗口继续存在, 本 ADR 不缩小它.
- ASK 路径上 `prepare` 会跑第二遍 (`coordinator.py:491` 的 `_revalidate`), 因此 `prepare`
  必须又幂等又便宜. 这条约束今天没有写在任何地方, 本 ADR 把它记下来但不加强制检查 ——
  当前唯一接近上限的是 `search_text.prepare` 的 glob 展开, 而它不命中 ASK.

## 验收标准

- `application/tools/builtin/` 下不再出现 `validate_arguments` 调用, 由
  `scripts/check_arch.py` 加一条断言守住 (与 ADR-0004 §13 的既有断言同一个脚本).
- `application/tools/builtin/` 下不再出现 `path_state_token` 及其手写复核, 该函数从
  `base.py` 删除.
- 四个 `fs_*` 工具各有一个用例: 计划生成后替换目标文件, 结果是
  `execution_environment_changed` 而不是执行.
- `fs_apply_patch` 的 create 用例: 计划生成后该路径被别的进程创建出来, 复核失败.
- 7 个常量 plan 工具的实现里不出现 `ToolPlan` 构造; `ask_user` 落地时同样不出现.
- 一个故意不校验入参的测试工具, 在管线里仍然被 `PREPARATION_FAILED` 挡下.
- 存量 learned rules 在升级后仍然命中 (`shell_run` 的 `plan_hash` 不受本 ADR 影响).
- `make ci` 通过.
