# ADR-0008：区分应用配置与项目配置存储

## 状态

Accepted

## 日期

2026-06-23

## 背景

ForgeCLI 同时有两类配置和状态：

- 应用级配置：跟用户使用 ForgeCLI 的偏好相关，跨项目复用，例如 UI 主题、LLM 供应商和模型配置。
- 项目级配置：跟某个被信任目录绑定，例如日志级别、Agent 可操作目录列表、会话状态、JSONL 对话事件和项目产物。

如果继续把所有信息都放在同一个配置文件中，会导致几个问题：

- `workspace.dir` 这类单值配置无法表达多工作区目录。
- 用户在一个项目里添加的可操作目录可能影响另一个项目。
- 会话事件和状态如果落在应用配置目录，会让项目恢复、审计和清理边界不清晰。
- 首次信任目录的决策没有项目级持久化位置，导致每次启动都可能重复询问。
- 如果直接在每个项目目录下创建 `.forge/`，会污染用户仓库，也容易被误提交到 Git。

## 决策

1. Forge 使用用户级 Forge home 作为本机持久化根目录，默认是 `~/.forge`，当前实现可继续通过 `FORGE_CONFIG_DIR` 覆盖。

   应用级配置包括：

   - UI 主题。
   - LLM 供应商配置和模型参数。
   - 其它跨项目复用的 ForgeCLI 偏好。

2. 项目由“被信任的目录”区分，但项目级配置和运行状态不写入项目目录，而是存储在用户级 Forge home 下：

   ```text
   ~/.forge/
     config.toml
     llm.toml
     projects/
       index.toml
       <project-id>/
         project.toml
         sessions/
         artifacts/
   ```

   - `projects/index.toml` 记录已信任项目根目录到 `project-id` 的映射。
   - `projects/index.toml` 使用已信任项目根目录作为 key，不使用 `[[projects]]` array-of-tables。
   - `project-id` 使用目录名加规范路径 hash 生成，例如 `ForgeCLI-a1b2c3d4`，避免同名目录冲突。
   - `project.toml` 保存该项目自身配置和状态。
   - Forge 不在被信任项目根目录下自动创建 `.forge/`。

   `projects/index.toml` 示例：

   ```toml
   [trusted_roots."/Users/almond/Documents/git_repostory/ForgeCLI"]
   project_id = "ForgeCLI-a1b2c3d4"
   trusted = true
   created_at = "2026-06-26T10:00:00+08:00"
   updated_at = "2026-06-26T10:00:00+08:00"

   [trusted_roots."/Users/almond/Documents/git_repostory/AnotherProject"]
   project_id = "AnotherProject-f6e7d8c9"
   trusted = true
   created_at = "2026-06-26T11:00:00+08:00"
   updated_at = "2026-06-26T11:00:00+08:00"
   ```

   使用 table 而不是 `[[projects]]` 的原因是：项目根路径在本机天然唯一，按路径作为 key 可以让新增项目只追加一组配置，更新信任状态时也不需要在数组中查找和去重。

   `projects/ForgeCLI-a1b2c3d4/project.toml` 示例：

   ```toml
   project_id = "ForgeCLI-a1b2c3d4"
   trusted = true
   primary_workspace_root = "/Users/almond/Documents/git_repostory/ForgeCLI"
   workspace_roots = [
     "/Users/almond/Documents/git_repostory/ForgeCLI",
     "/Users/almond/Documents/git_repostory/SharedTools",
   ]

   [logging]
   level = "info"
   ```

3. 项目级配置包括：

   - 当前项目是否已被信任。
   - `primary_workspace_root`。
   - `workspace_roots` 列表。
   - 项目级日志级别等只对当前项目生效的配置。
   - 后续 session state、`events.jsonl`、对话内容、artifacts 和项目记忆。

4. 启动 `forge` 时通过用户级项目索引查找项目根。

   查找规则：

   - 规范化当前目录路径。
   - 读取 `~/.forge/projects/index.toml`。
   - 使用当前目录去匹配 `trusted_roots` 中的已信任项目根目录。
   - 如果当前目录等于某个已信任项目根，或当前目录是某个已信任项目根的子目录，应直接命中该项目，不再重复询问信任。
   - 子目录判断必须使用路径边界匹配，不能用简单字符串前缀匹配。
   - 如果命中多个项目，选择路径最长的已信任项目根。
   - 额外添加的 `workspace_roots` 只表示 Agent 可操作目录，不参与启动时的项目身份匹配。
   - 如果没有命中已信任项目，必须询问用户是否信任当前目录。

   用户选择信任后：

   - 只信任当前目录，不自动信任父级目录。
   - 当前目录成为 `primary_workspace_root`。
   - 在用户级 Forge home 下创建项目目录和 `project.toml`。
   - 在 `projects/index.toml` 中新增一组 `trusted_roots."<canonical-root>"` 配置，写入该规范路径到 `project-id` 的映射。
   - `workspace_roots` 初始值只包含 `primary_workspace_root`。

   用户选择不信任时，进程直接退出，不创建项目配置，不进入 REPL。

   后续在该项目根目录或其子目录启动 `forge` 时，应复用已信任项目，不再重复询问信任。

5. 工作区不再是单个可修改的 `workspace.dir` 配置项。

   - 工作区是 `workspace_roots` 列表。
   - `primary_workspace_root` 是首次信任的项目根目录，不能通过 `/config` 修改。
   - 用户只能通过显式命令添加或删除额外可操作目录。
   - 删除目录不能移除 `primary_workspace_root`。

6. `/config` 不再提供“工作区目录”修改项。

   `/config` 可以继续管理应用级配置，也可以在后续阶段展示项目级配置，但不得把工作区作为单个路径值编辑。

7. `/status` 使用 `cwd:` 字段展示当前可操作工作区目录列表，而不是展示单个当前工作目录。

## 备选方案

- 继续使用单个 `workspace.dir`：实现简单，但无法表达多个可操作目录，也不适合权限和审计。
- 所有配置都放在用户级 `.forge` 的同一个文件：跨项目复用方便，但项目状态、会话和信任边界不清晰。
- 项目状态放在项目根目录 `.forge/project/`：项目隔离清晰，但会污染仓库目录，并可能被误提交。
- 每次启动都询问信任：安全但打扰用户，且不能支持恢复已信任项目。
- 使用显式项目选择器：可以脱离目录选择项目，但会让“进入目录即进入项目”的心智模型复杂化，MVP 暂不采用。

## 影响

该决策把应用偏好和项目状态分开，使后续工具权限、session 恢复、审计和多目录读取有明确边界，同时避免在用户仓库中自动创建 Forge 运行时目录。

代价是配置解析需要分成应用配置、项目索引和项目配置三条路径；`ConfigService` 或等价应用服务需要显式合并这几类视图，并且 `/config` 菜单需要移除“工作区目录”选项。

本 ADR 部分取代 ADR-0005 中关于单一项目配置文件路径和单值 workspace 配置的描述。ADR-0005 中 TOML、敏感信息不落盘、不可变 `EffectiveConfig` 等原则继续有效。

## 验收标准

- 首次信任目录后在用户级 Forge home 下创建 `projects/<project-id>/project.toml`。
- 首次信任目录不会在项目根目录下创建 `.forge/`。
- `projects/index.toml` 可以通过规范路径找到已信任项目。
- 已信任项目再次启动不重复询问信任。
- 在已信任项目子目录启动不重复询问信任。
- `/config` 不再展示或修改“工作区目录”。
- 工作区以 `workspace_roots` 列表存储，至少包含 `primary_workspace_root`。
- `/add-dir` 可以添加额外可操作目录。
- 删除目录不能删除 `primary_workspace_root`。
- `/status` 的 `cwd:` 展示工作区目录列表。
- 会话 state、JSONL 事件和对话内容在后续实现中落入 `projects/<project-id>/`。
