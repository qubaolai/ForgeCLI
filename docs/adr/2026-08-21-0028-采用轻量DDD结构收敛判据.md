# ADR-0028：采用轻量 DDD 结构收敛判据

## 状态

Accepted (2026-08-21 实现; 2026-08-24 订正 import 环判据)

## 日期

2026-08-21

## 背景

ADR-0002 定下的是**轻量** DDD。八个月之后, 实现已经在四个方向上偏离了"轻量"这个词,
而每一处偏离单独看都有理由:

### 1. 每个中间阶段各定义一个大 DTO, 并重复携带相同字段

一次工具调用的事实链是:

```text
ToolPlan -> AnalysisFindings -> AuthorizationDecision
         -> ApprovalPresentation + ApprovalBinding
         -> ExecutionAuthorization -> ToolObservation
```

七个类。其中 `executable_identity_hash`, `executable_names`, `script_snapshots` 三项,
在 `PolicyEngine.decide` 的六个返回分支里**各抄了一遍**, 一共十八处赋值, 全部形如
`executable_identity_hash=findings.executable_identity_hash`。

抄写本身不出错, 出错的是**下一个分支**: 新增一条裁决路径时漏抄一项, 结果是审批界面少
一段信息或学习规则绑不住可执行文件身份, 而类型检查不会报错。

### 2. `plan_hash` 已覆盖的内容又在多个绑定中重复保存

`ToolPlan._hash_source` 已经包含 `tool_name`, `spec_hash`,
`capability_vocabulary_version`, `target_set_hash`。`ApprovalBinding` 又把这四项单独
存了一份, 并在 `differences()` 里逐项比对。

这不是纵深防御。四项中任何一项变化, `plan_hash` 必然跟着变, 所以第二次比对恒为冗余;
它唯一的作用是让"哪一项变了"的提示更具体, 而代价是一个十字段的绑定类和一个必须与
`_hash_source` 保持同步的字段清单 —— 同步失败不会报错。

### 3. 只有一个生产实现, 却同时存在抽象接口、注册表、服务包装器和 wiring 工厂

`src/` 有 48 个 ABC / Protocol, 其中 28 个只有一个实现。这 28 个里, 有 10 个的实现与
抽象**在同一层**, 因而不承担任何依赖倒置作用:

`AgentLoop`, `ToolDispatcher`, `ToolRunObserver`, `ToolAuditSink`, `TokenEstimator`,
`LlmGateway`, `BudgetGuard`, `GatewayObserver`, `LlmCacheController`,
`ProviderHealthRegistry`。

同类问题还有服务包装器: `ConfigBackedSelectionResolver` 每次调用都重建一个
`DefaultModelSelectionResolver` 再委托过去, 模块注释自己写着"解析语义与
`DefaultModelSelectionResolver` 完全一致"。两个类, 一套语义。

### 4. 为未来沙箱、远程目标、凭证范围预留字段, 但没有真实生产方或消费方

`ApprovalPresentation` 有 30 个字段。其中十个 —— `credential_scopes`,
`resolved_remote_targets`, `executable_realpath`, `executable_identity_hash`,
`interpreter_chain`, `isolation_level`, `recovery_scope`, `checkpoint_id`,
`recovery_strategy`, `invalidated_by` —— 全库 grep 找不到任何生产方或消费方。

它们不是无害的。十个字段全部进 `presentation_hash`, 也就是说人类批准的那份视图哈希里,
有十项内容是恒为空的占位。更实际的伤害是: 读代码的人会以为凭证范围和远端目标已经接线,
而审批界面上根本不会出现它们。

### 5. 职责过载的两个类

- `ShellCapabilityAnalyzer` 677 行, 同时负责命令解析调度、写删移效果推导、可执行文件
  身份绑定、网络目标识别和审批文案措辞。
- `ToolRequestCoordinator` 716 行, 承担能力门、prepare、裁决、审批、重验、恢复事务、
  签发、执行、审计九段流程分支, 已经接近一个手写的工作流引擎。

### 6. 为了 raw shell 的少量自动放行, 维护巨大的命令语义表

命令知识分散在四个文件: `effects.py` (262 个命令名), `wrappers.py` (211),
`arguments.py` (69), `builtins.py` (102)。同一条命令的知识被切成"效果是什么"、
"参数怎么读"、"是不是解释器"三份, 键集大量重叠但没有单一记录 —— 加一条命令要改三处,
漏一处的后果是静默的。

**这一项最值得权衡**: 表越详细, ADR-0024 的只读快速放行覆盖越广, 用户被打断得越少;
但表越大, 维护成本和安全审计成本上升得越快。而这两者不对称 —— 覆盖面的收益是线性的
(少问几次), 审计成本的增长不是。

## 决策

**保留轻量 DDD 的分层方向与安全纵深, 删掉不承重的结构。** 判据四条, 后续每一处删改都
必须能指到其中一条; 指不到就不改。

### 规则 A：抽象保留判据

一个 ABC / Protocol 只在满足以下**任一**条件时保留:

- **A1 依赖倒置**: 删掉它会让上游包依赖一个更靠外的包。两种形态都算:
  - 跨层: 抽象在 `application`, 实现在 `infrastructure` 或 `interfaces`。所有
    `*Store`, `FileSystemView`, `CommandExecutor`, `ModelProvider`,
    `ApprovalService`, `UserOutput` 一类都因此保留。
  - 跨包: `application` 内部由 `scripts/check_arch.py` 的 `SIBLING_BANS` 守住的边界,
    例如 `tools` 与 `security` 互不相识。`ToolRunObserver` 与 `ToolAuditSink` 属于
    这一类 —— 删掉它们, `tool_request` 就要认识 `agent_run` 的事件总线与
    `session` 的写入口, 而那正是这两个抽象存在的理由。

  **边界必须是机器守得住的**: 一条只写在注释里的"依赖方向"不构成 A1。所以本次把
  `tool_request ⇏ agent_run`、`tool_request ⇏ session` 与
  `security / agent_loop ⇏ llm.gateway.default_gateway` 补进 `SIBLING_BANS`,
  并把 `SessionToolAudit` 移到它真正写入的那一侧 (`application/session/`)。

  两个按"只有一个实现"本该删掉、复核后保留的端口, 记在这里而不是含糊过去 ——
  规则 A 的意图是删掉不承重的抽象, 不是把行数当目标:

  - `LlmGateway`: `DefaultLlmGateway` 拖着 provider 注册表、凭证池、重试环与治理件。
    让 `security` 或 `agent_loop` 直接依赖它, 一个分类器用例就要装配整个 LLM 子系统。
  - ~~`ModelSelectionResolver`~~: **这一条判错了, 2026-08-24 已删除该端口**, 见下面
    的"import 环订正"。当时给的理由是"删掉端口会形成
    `gateway -> runtime_resolver -> catalog_builder -> gateway` 的 import 环",
    而那个环本身才是缺陷 —— 拿它当保留抽象的理由, 等于用一层间接把结构问题盖住。

  `LlmGateway` 这一处说明规则 A 需要一条机器判据: 光看"几个实现"会把承重的抽象一起
  删掉。`scripts/check_abstractions.py` 因此维护一份 `INVERTED_PACKAGE_BOUNDARIES`
  白名单, 每一项都要能指出它挡住的那条 `SIBLING_BANS` 边界。**白名单项的理由必须是
  一条机器守得住的边界, 不能是"删了会出环"** —— 后者说明该修的是环。
- **A2 多实现**: 有两个及以上**真实运行时实现**。`Null*` / `Noop*` 空实现**不算**
  第二个实现 —— 它表达的是"这个协作件可以不接", 而 `X | None` 或让真实实现自己处理
  `enabled=False` 表达得更直接, 少一个类和一层分派。
- **A3 开放扩展点**: `Tool`, `CommandHandler`, `CapabilityAnalyzer`, `UserIntent`,
  `ModelSelection`。它们的实现数量本身就是存在理由 —— 新增一个实现不该改任何既有代码。

不满足则删除抽象, 调用点直接依赖具体类。

**测试需要替身不构成保留理由。** Python 不需要 ABC 才能替换; 而且多数情况下, 更下层
已经有一个更合适的接缝 —— `LlmGateway` 的替身应该走 `DefaultLlmGateway` 加现成的
`FakeModelProvider`, 那样测的是真实的网关逻辑, 而不是一个与生产实现无关的假类。

判据由 `scripts/check_abstractions.py` 静态检查, 进 `make ci`。

### 规则 B：一个事实只存一次

- 事实存在**计算出它的那个类**上。下游需要它就持有那个类的引用, 不逐字段抄写。
- `ToolPlan._hash_source` 已覆盖的字段, 不得再单独出现在任何绑定类或展示类里。
- 派生值 (`target_set_hash`, `plan_hash`, `envelope_hash`, 审批视图哈希) 只有一个
  计算点。

**这不是删防线。** 批准后的全量重验仍然逐项比对, 只是比对对象从"十个抄来的字段"变成
"一个 `plan_hash` 加四项 plan 之外的环境事实"(工具目录快照、执行画像、策略版本、
mode) 加一份审批视图哈希。覆盖范围完全相同, 而漏同步的可能性消失了。

### 规则 C：字段必须同时有生产方与消费方

没有真实生产方或消费方的字段一律删除。**不为将来的沙箱、远端目标、凭证范围预留占位。**

加一个字段是十行改动; 而一个假装已经接线的字段, 会让读代码的人以为某处支持它, 也会让
审计的人以为某项事实已经展示给用户看过了。需要时按新 ADR 加回来。

一条例外: `IsolationLevel` 的三档枚举保留。ADR-0014 已经论证过为什么它不能只留
`NO_SANDBOX` 一档 —— 那会让"探测不出来"和"确认无隔离"变成同一个值, 而这两者的安全
含义相反。**例外的判据是"合并会制造非法状态或让失败方向反转", 不是"将来可能用得上"。**

### 规则 D：命令表按方向分类, 放行方向收到最小核心集

命令表分两类, 判据是**漏一条会朝哪个方向错**:

- **放行方向** (进表 = 更可能自动放行): 只有一张, 即 ADR-0024 快速放行依赖的只读命令
  集合。漏一条 = 多问一次人; 多一条 = 少一道闸门。**收到约 25 条高频只读命令**, 小到
  可以一次审计完。表外命令一律退回 ASK。
- **风险方向** (进表 = 更可能被拦, 或目标清单展示得更准): 解释器、提权前缀、间接执行、
  写删移动、参数结构。漏一条 = 退回 ASK 且清单少一项, 不会放行。**保留全部条目**, 但
  合并到单一模块, 每条命令一条记录。

原 `_KNOWN_READERS` 中被移出核心集的命令不是被删除: 它们仍然按"位置参数是读取目标"
解释, 审批清单照常准确, 只是不再享受快速放行。

**这条决策的取舍要写明白**: 用户会因此多看到一些审批框 (`wc`, `sort`, `xxd` 一类)。
换来的是一张能在一次代码评审里读完的表 —— 而 ADR-0024 的整个前提, 正是"人类真的在看"。
一张没人审计得动的放行表, 与没有审计的区别只在文档里。

## 备选方案

- **方案 A：维持现状, 只写一份"注意不要再加抽象"的工程规范。** 成本最低。但现有的
  10 个空抽象和 10 个死字段不会自己消失, 而规范约束不了已经写下的代码。不采用。
- **方案 B：只删死字段和空抽象, 不动 DTO 链与命令表。** 收益立竿见影且风险极低。但
  它不解决规则 B 指向的那类问题 —— 六个分支各抄一遍字段, 下次仍然会漏。作为本 ADR
  的一个子集被采纳 (Phase 4/5), 不作为全部。
- **方案 C：推倒重来, 按"一个用例一个服务"重写 application 层。** 能得到最干净的结构,
  但会同时丢掉 ADR-0013 到 ADR-0027 沉淀的全部安全判据 —— 那些判据的价值恰恰在于它们
  是被真实缺陷打磨出来的。不采用。
- **方案 D：命令表保留全量, 只做结构拆分。** 体验完全不变, 维护成本降一半。但审计成本
  几乎不降 —— 262 条命令的表, 拆不拆都没有人能一次读完。不采用。

## 影响

### 收益

- 一次工具调用的事实链从七个类收到五个, 且没有任何字段在两个类里各存一份。
- 新增裁决分支不再需要抄八个字段, 因而不会漏抄: `PolicyEngine.decide` 只有一处构造。
- 抽象数量 48 -> 40; 剩下的每一个都能指到 A1 / A2 / A3, 且由 `make arch` 守住。
- 审批视图的每个字段都能指出生产方与消费方; 视图哈希不再包含恒为空的占位。
- 命令知识每条只登记一次, 放行方向的表收到 29 条命令名, 可以一次审计完。
- 三个职责过载的类各自拆开: `shell_analyzer` 677 -> 299,
  `coordinator` 716 -> 553, `ApprovalPresentation` + `HitlApprovalView` 两个类
  30 个字段 -> `ApprovalView` 一个类 9 个字段。

### 代价

- `POLICY_VERSION` 递增, 已沉淀的 learned allow rules 全部失效, 用户需要重新批准一次。
- 部分只读命令 (`wc`, `sort`, `xxd`, `strings` 等) 退回 ASK, 交互次数增加。
- 删除 `LlmGateway` 一类抽象后, 现有基于假网关的测试要改成基于 `FakeModelProvider`。
  按既定原则, 旧测试跟随重写, 不为兼容旧测试保留抽象。
- `BudgetGuard` 与 `TokenizerRegistry` 整体删除, 将来接入预算或精确分词器时要重新设计
  接入点。这是规则 C 的预期代价。

### 兼容性

- **恢复点与会话记录格式不变。** `/undo` 与 `/resume` 对本次改动之前建立的 checkpoint
  与 session 照常工作。
- `llm.json` 的 `[llm.cache]` 与 `[llm.circuit_breaker]` 配置键行为不变。
- learned allow rules 因 `POLICY_VERSION` 递增而失效, 这是有意的 —— 绑定字段集变了,
  沿用旧规则等于用旧口径的绑定去满足新口径的裁决。

### 后续约束

- 新增 ABC 前必须能指到 A1 / A2 / A3 之一, 否则 `make ci` 不通过。
- 新增字段必须同时给出生产方与消费方。
- 往放行方向的命令表里加条目需要在 PR 说明里单独指出, 不能混在一批改动里。

## 验收标准

- `scripts/check_abstractions.py` 通过并进入 `make ci`。
- `ApprovalBinding` 的字段集与 `ToolPlan._hash_source` 的字段集无交集。
- 审批视图的每个字段都能指出至少一个生产方与一个消费方。
- `PolicyEngine.decide` 中只有一处构造 `AuthorizationDecision`。
- 每条命令的效果与参数结构只在一个模块里登记。
- `ShellCapabilityAnalyzer` 不再同时承担路径推导与可执行文件身份绑定, 两段各在
  独立模块且各自独立测试。
- `ToolRequestCoordinator` 不再承担审批视图构造与恢复事务登记。

  行数只是这两条的代理指标, 不单独作为验收项。协调器剩下的是链路顺序本身 ——
  再拆下去只能靠回调把 prepare 与 evaluate 传进审批模块, 那既违反规则 A, 也让
  "批准后必须重新 prepare 与 evaluate"这条安全约束从一处变成两处。
- ADR-0013 的裁决优先级 (Hard Deny > Mandatory Ask > 模式预算 > Ask > Allow) 分支顺序
  一字不改, 有测试逐条钉住。
- ADR-0024 的八条判据本身不变, 只有其依赖的命令表收窄; 收窄后 `ls`, `grep`, `find`
  仍自动放行, `ls > out.txt`, `cat a | sh` 仍触发审批。
- `make ci` 全绿, 且 `make arch` 含 `scripts/check_abstractions.py`。

## 实测结果 (2026-08-21)

| 项 | 前 | 后 |
|---|---|---|
| 抽象 (ABC / Protocol) | 48 | 40 |
| `ApprovalPresentation` + `HitlApprovalView` | 2 类 / 30 字段 (10 个无生产方) | `ApprovalView` 1 类 / 9 字段 |
| `ApprovalBinding` | 10 项 (4 项已在 plan_hash 内) | 6 项, 与 `_hash_source` 无交集 |
| `PolicyEngine.decide` 构造点 | 6 处, 18 处抄字段 | 1 处 |
| `shell_analyzer.py` | 677 行 | 299 + 262 + 184 (三个职责各一个模块) |
| `coordinator.py` | 716 行 | 553 + 92 + 101 |
| 命令表 | 四个文件, 键集重叠 | `commands.py` 一条命令一条记录 |
| 只读快速放行覆盖 | 85 条命令 | 29 条命令名 + git 只读子命令 |
| 测试 | 865 | 872 |

**源码总行数只从 41149 降到 41056。** 这个数字要如实记下来: 本次删掉的结构大多被
同等体量的代码加上说明它们为什么这样切的注释替代了。规模不是这次的目标, 也不该被
当成验收项 —— 目标是"改一处只改一处"和"每个字段都有人生产、有人消费"。

## import 环订正 (2026-08-24)

### 症结

上面 `ModelSelectionResolver` 那一条把因果搞反了. 当时的观察没错: 删掉端口, 整套测试
在收集阶段就起不来. 错在结论 —— 把"会出环"当成保留抽象的理由, 于是那个环留在原地,
只是被一层间接挡住不再显形.

真正的成因不在解析器, 在两处结构:

1. **`application/llm/gateway/__init__.py` 是一个急切转导出的包门面** (184 行, 30 条
   import, 其中一条是 `default_gateway`). Python 在 import 任何子模块前先执行包的
   `__init__`, 所以 `import ...gateway.errors` —— 一个零内部依赖的叶子模块 —— 也会
   连带装配整个 LLM 子系统. 图上的每一条门面 import 都是真实的边.
2. **`catalog.py` 与 `in_memory_catalog.py` 住在 `gateway/` 里, 而目录不是调用切片的
   内部构件**. 消费它的有四方: 配置服务 (写 `llm.json` 前先合并校验), thinking 覆盖层,
   计量的 `CostEstimator`, 选择解析 —— 只有最后一个属于 gateway. 于是
   `catalog_builder` 这个**上游生产方**要反过来 import 下游包, 加上第 1 条就闭合成环.

### 改动

| 原位置 | 现位置 | 理由 |
|---|---|---|
| `gateway/catalog.py` + `gateway/in_memory_catalog.py` | `llm/catalog.py` (合一) | 目录是 llm 切片的共享词汇, 四个消费方里三个不在 gateway |
| `gateway/default_selection_resolver.py` + `llm/runtime_resolver.py` | `llm/selection.py` (合一) | 纯函数与"现读哪三个来源"的类是一件事的两半 |
| `gateway/selection_resolver.py` (`ModelSelectionResolver` ABC) | 删除 | 规则 A: 单实现, 不跨层, 不跨任何机器守得住的边界 |
| `gateway/__init__.py` 的 30 条转导出 | 删除 | 唯一走门面的是 `llm_wiring.py` 一处 |

`DefaultLlmGateway.__init__` 的 `resolver` 参数改为具体类型
`ConfigBackedSelectionResolver`. 装配点只有 `llm_wiring.py` 一处, 没有测试构造网关,
因此改动不波及测试替身.

### 顺带发现: 同样的环还有八个

把判据写成脚本之后才看清楚, 这不是一个孤例. `scripts/check_arch.py` 首次跑出 **9 个
import 环**, 每一个都是同一个形状 —— 急切转导出的包门面 + 子模块之间的横向 import:

```text
application.llm.gateway
application.manual_shell
application.planning
application.project
application.session
application.slash_commands
application.tools.builtin
infrastructure.execution.sandbox
infrastructure.session
```

九个都靠 import 顺序活着: 只要第一个 import 它们的入口不变, `__init__` 不动, 就永远
不炸. 这已经是第三次遇到 (`application/llm/config` 一次, `gateway` 一次, 这批八个).
**顺序是运气, 不是设计**, 所以这次不只是修, 是把它变成 `make ci` 的一道闸门.

### 新增判据: 无 import 环

`scripts/check_arch.py` 加第 4 条规则, 用 Tarjan 求强连通分量. 关键是建图方式:
`import a.b.c` 记成同时指向 `a`, `a.b`, `a.b.c` **三条边** —— 因为 Python 确实会依次
执行三个 `__init__`. 这样"包门面必须是惰性的"就不再是一条约定, 而是环检查的推论:
一个只有 docstring 的 `__init__` 没有出边, 不可能出现在任何环里.

判据本身也验过会响: 把 `default_gateway` 那一条 import 加回 `gateway/__init__.py`,
检查立刻报出跨 9 个模块的环并以 1 退出.

### 结果

- 9 个 import 环 -> 0 个 (325 个模块)
- `INVERTED_PACKAGE_BOUNDARIES` 从 4 项减到 3 项, 剩下的每一项都能指出一条
  `SIBLING_BANS` 边界
- 8 个包门面转为 docstring-only, 74 处调用点改从子模块 import
- `make ci` 全绿 (890 项测试, mypy 329 文件)
