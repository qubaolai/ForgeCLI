# ADR-0009：采用模式策略驱动 Agent 处理流程

## 状态

Proposed

## 日期

2026-06-29

## 背景

ForgeCLI 需要从 REPL 直接响应用户输入，演进为由 `AgentTurnService` 管理一次完整 Agent turn。用户通过自然语言提出需求，Agent 根据当前模式决定应该解释、澄清、生成计划，还是尝试执行改动。

模式不是简单的 UI 状态，而是 Agent 行为边界。它必须决定 Agent 在当前 turn 中能做什么、不能做什么，以及什么时候必须询问人类。

因此需要明确：LLM 或 workflow 只产出候选动作，ForgeCLI 根据当前 mode 和 policy 决定候选动作是否允许执行、是否需要询问人类、是否必须转为只读回复。

## 决策

1. LLM / workflow 只能产出候选动作，不能直接执行副作用。

   候选动作包括：

   - 回复用户。
   - 生成计划。
   - 请求编辑文件。
   - 请求执行 shell。
   - 请求调用工具。
   - 请求继续下一步。
   - 请求用户补充信息。

   这些动作必须交给 `AgentTurnService` 和策略组件裁决。LLM 不能自行绕过 ForgeCLI 的模式、审批和工具边界。

2. `AgentTurnService` 是模式裁决的主控边界。

   `AgentTurnService` 负责：

   - 读取当前 session mode。
   - 加载 `ModePolicy` 和 `ApprovalPolicy`。
   - 调用 workflow 或 LLM 取得候选动作。
   - 判断动作是否允许执行。
   - 判断是否需要人类确认。
   - 调用 ToolRuntime 或文件编辑适配器执行副作用。
   - 写入 session events 和 state snapshot。

   Workflow 和 LLM provider 不得直接写文件、执行 shell、调用外部工具或写 `events.jsonl`。

3. 模式语义由 policy 固定，UI 名称可以后续打磨。

   MVP 当前已有 `/chat`、`/plan`、`/act`。后续可以增加或重命名模式，但底层策略语义应保持稳定：

   | 策略语义 | 行为 |
   | --- | --- |
   | `chat` | 默认对话。可以解释、问答、澄清需求；不主动写文件。 |
   | `plan` | 只读计划。不得编码、写文件、执行有副作用的 shell 或工具，只能生成计划、风险和待确认事项。 |
   | `ask` / `approval` | 询问权限模式。所有写操作、shell 写操作和工具副作用都必须询问人类。 |
   | `edit` / `act` | 允许编辑模式。普通代码编辑可以执行；敏感写操作仍必须询问人类。 |
   | `auto` | 自动执行模式。在预算和安全边界内可以连续执行普通开发动作，不需要每一步人工介入；敏感、破坏性、外部发布类动作仍必须询问人类或直接拒绝。 |

   当前 `/act` 可以先映射到 `edit` 语义；`auto` 可以作为后续模式加入，不要求在 2026-06-29 切片实现。

4. 权限判断按动作风险分级。

   动作至少分为：

   - `read`: 只读文件、查看状态、读取配置。
   - `write`: 创建或修改工作区内普通文件。
   - `shell`: 执行 shell 命令。
   - `tool`: 调用内置工具、MCP 工具或外部适配器。
   - `sensitive`: 删除文件、大范围覆盖、改权限、修改凭证相关文件、安装依赖、网络访问、git push、发布、写工作区外路径、执行破坏性命令。

   策略要求：

   - `plan`: 只允许 `read` 和计划输出。
   - `ask` / `approval`: `write`、`shell`、`tool`、`sensitive` 都需要人类确认。
   - `edit` / `act`: 普通 `write` 可执行；`shell`、`tool` 按风险判断；`sensitive` 必须确认。
   - `auto`: 普通 `write`、低风险 `shell` 和低风险 `tool` 可在预算内连续执行；`sensitive` 不允许自动越权。

5. `plan` 模式必须强制只读。

   在 `plan` 模式下，即使 LLM 产出了编辑、shell 或工具副作用候选动作，`AgentTurnService` 也不得执行。它应把候选动作转为计划说明、风险说明或待确认事项。

6. `auto` 模式不等于无限授权。

   `auto` 只表示普通开发动作可以在预算内连续推进，不表示 LLM 可以绕过敏感操作审批。安全下限由 policy 强制执行，不由 prompt 约束替代。

## 备选方案

- 让 LLM 自行决定是否编码和是否执行工具：灵活但不安全，会破坏权限边界和可测试性，不采用。
- 只保留一个 `act` 模式：简单但表达力不足，无法区分“每步询问”“允许普通编辑”“自动连续执行”的不同安全等级，不采用。
- 只用 prompt 约束 Agent 行为：实现成本低，但无法作为可靠安全边界，也难以测试和验收，不采用。
- 把模式判断放在 CLI 层：短期简单，但会让 Typer/Rich/REPL 代码承载业务规则，破坏 application 层边界，不采用。

## 影响

收益：

- 用户入口保持自然：通过对话表达需求，通过模式控制执行边界。
- 权限边界清晰：LLM 产出候选动作，ForgeCLI 策略决定是否执行。
- `plan`、`ask`、`edit`、`auto` 的差异可以通过单元测试验证。
- REPL 保持轻量，只负责输入、输出和分派。

代价：

- 需要实现明确的 `ModePolicy`、`ApprovalPolicy` 和动作风险分类。
- `AgentTurnService` 会成为关键编排点，需要较完整的单元测试。
- 需要把工具、shell、文件编辑等副作用统一表达为可裁决的候选动作。

兼容性：

- 现有 `/chat`、`/plan`、`/act` 可以继续保留。
- `/act` 可先映射到 `edit` 策略语义。
- `auto`、`ask` 或 `approval` 可以作为后续模式或策略选项加入，不要求立刻改变现有 CLI 命令。

## 验收标准

- 自然语言输入通过 `AgentTurnService` 处理，不由 REPL 直接决定业务执行。
- Workflow / LLM provider 不直接写文件、执行 shell、调用工具或写 session events。
- `plan` 模式下不会执行编码、文件写入或有副作用工具。
- 询问权限模式下，所有写操作和工具副作用都必须产生人类确认流程。
- 允许编辑模式下，普通编辑可执行，敏感写操作必须确认。
- 自动执行模式不得绕过敏感、破坏性、外部发布类安全边界。
- 模式判断逻辑位于 application 层，不落在 REPL 或 CLI 渲染层。
