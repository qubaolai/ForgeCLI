# ADR-0014：采用启动探测与按执行实例创建的跨平台沙箱架构

## 状态

Accepted（2026-08-10 重写）

## 日期

2026-07-29（2026-07-30 修订，2026-08-10 按当前实现重写）

## 背景

ForgeCLI 允许 Agent 执行 Shell、Python、Node、构建工具和项目自定义脚本。规则引擎可以在
执行前识别已知风险，但无法仅靠字符串或 AST 证明任意程序没有文件、网络、进程和资源
副作用，因此裁决通过后仍需要操作系统级 containment。

沙箱同时带来一个产品语义问题：代码生成器如果只修改临时工作区，执行结束后生成的代码会被
销毁；如果直接让沙箱写真实工作区，又失去了临时层、差异审查和恢复保护。Forge 必须明确区分：

```text
在沙箱中运行并产生候选变更
                ≠
把候选变更应用到真实工作区
```

前者是受限进程执行，后者是一个新的真实工作区写入事务，必须单独形成计划、裁决、审批和
恢复绑定。

## 目标与非目标

### 目标

- 所有 Agent Shell 使用同一执行入口，不存在“沙箱失败后直接跑宿主 Shell”的隐藏分支。
- 只有经过行为自测的能力才能进入执行画像。
- 沙箱策略在会话中保存，实例按执行临时创建。
- 默认关闭网络、隐藏非必要环境变量，并把工作区写入导向临时层。
- 授权绑定实际 Provider、能力和策略，禁止授权后静默降级。
- 为沙箱内生成代码提供安全、可审计、可恢复的后续 materialize 设计。
- 在无法提供系统沙箱的平台如实标记 `NO_SANDBOX`，由规则引擎和人工审批收紧。

### 非目标

- Forge 不在用户态重新实现内核、namespace、Seatbelt 或虚拟机。
- 沙箱不替代 Hard Deny、模式策略、LLM Safety Classifier、人工审批或恢复机制。
- 沙箱不承诺完全不消耗或影响宿主 CPU、内存、磁盘，也不防御全部内核漏洞和侧信道。
- 第一阶段不自动把沙箱内所有文件递归复制回真实工作区。

## 决策

### 1. 权限裁决、沙箱隔离和工作区写回是三个独立层次

完整目标链路为：

```text
Agent / 用户请求
  ↓
ToolRequestCoordinator
  ↓
ShellCapabilityAnalyzer / ScriptAnalyzer
  ↓
PolicyEngine / Human Approval
  ↓
ExecutionAuthorization
  ↓
ShellTool
  ↓
SandboxManager
  ↓
SandboxInstance
  ↓
Shell / Python / Node / 其他进程
  ↓
CommandOutcome + 候选 SandboxChangeSet
  ↓
销毁 SandboxInstance
  ↓
MaterializationCoordinator（仅在请求写回时）
  ↓
新的 ToolPlan / Policy / Approval / Recovery binding
  ↓
安全写回真实工作区
```

职责边界如下：

- `PolicyEngine` 回答“本次动作是否允许、拒绝或需要询问”。
- `SandboxProvider` 回答“获准进程在操作系统层面能触达什么”。
- `ArtifactCollector` 回答“临时层中产生了哪些可安全保存的候选内容”。
- `MaterializationCoordinator` 回答“哪些候选变更可以应用到哪里”。
- ADR-0015 的恢复层回答“真实工作区变更如何建立 preimage 和恢复能力”。

任一层不能用自己的成功覆盖其他层的拒绝。尤其是：Shell 已获准执行不等于其临时变更已获准
写回；沙箱成功也不能把 `ASK` 或 `DENY` 提升为 `ALLOW`。

### 2. Forge 启动时探测 Provider，但不创建永久实例

启动顺序为：

```text
构造会话级 SandboxPolicy
  ↓
按平台构造 Provider 候选
  ↓
执行最小文件系统和网络行为自测
  ↓
选择第一个实际可用 Provider
  ↓
生成 SandboxProbe
  ↓
冻结到 ExecutionProfile
  ↓
初始化 SandboxManager
```

启动阶段不会创建长期 Bash、固定 mount namespace 或永久临时工作区。Provider 探测结果可以
在会话内缓存；每次执行仍读取当时的 `SandboxPolicy` 并创建新的 `SandboxInstance`。

当前组合根创建的默认策略为：

```text
policy_version = 1
workspace_roots = 当前项目工作区
external_dirs = none
network_enabled = false
ephemeral_workspace = true
max_processes = 64          # 已建模，尚未实施硬限制
max_memory_bytes = 1 GiB    # 已建模，尚未实施硬限制
```

当前策略对象为会话内快照，尚未接入完整持久化和 `/add-dir` 修改流程。

### 3. 所有 Shell 都必须通过 SandboxManager

`ShellTool` 只依赖 `CommandExecutor`。组合根向其注入 `SandboxManager`，而不是直接注入
`LocalCommandExecutor`：

```text
ShellTool
  → SandboxManager.run(request)
  → selected_provider.create(current_policy, request)
  → SandboxInstance.run()
  → SandboxInstance.close()
```

没有系统隔离能力时也使用显式 `NoSandboxProvider`。因此代码路径仍然统一，但环境画像明确为
`NO_SANDBOX`。

Manager 在每次运行时：

1. 读取当前策略；
2. 创建一次性实例；
3. 执行冻结的 `CommandRequest`；
4. 在 `finally` 中关闭实例；
5. 删除该实例拥有的临时资源。

Provider 创建失败返回结构化执行失败。已经按某个 Provider 画像签发的授权不得在同一次调用中
回退到下一个 Provider，因为那会形成“按强环境裁决、按弱环境执行”的授权错配。

### 4. Provider 可用性必须通过行为自测

检查 `sandbox-exec` 或 `bwrap` 文件存在只能说明它可能可调用，不能证明当前宿主允许创建
所需边界。Provider 至少实际验证：

- 指定临时目录可以写入；
- 边界外目标不能写入；
- 默认禁网时不能连接宿主临时监听端口。

探测输出 `SandboxProbe`：

```text
provider
available
filesystem_isolation
network_isolation
process_isolation
resource_limits
overlay_or_temp_workspace
provider_version
detail
```

隔离等级由已证明的能力计算：

- `STRONG_SANDBOX`：文件、网络、进程、资源限制和临时层全部经验证。
- `PARTIAL_SANDBOX`：至少有一项真实隔离能力，但未满足全部强能力。
- `NO_SANDBOX`：没有系统隔离，或平台 Provider 行为自测失败。

当前内置 Provider 都不会产生 `STRONG_SANDBOX`：Seatbelt 没有独立进程 namespace，
bubblewrap 尚未实施并证明 CPU、内存和进程数硬上限。

### 5. 执行画像和策略必须绑定一次性授权

`ExecutionProfile` 至少冻结：

```text
platform / isolation_level
sandbox_provider / provider_version
filesystem_isolation / network_isolation / process_isolation
resource_limits / overlay_or_temp_workspace
sandbox_policy_hash
trusted_path / shell_launch
environment_allowlist
protected_roots_hash
profile_version
```

完整 profile 计算 `execution_profile_hash`，进入 `ExecutionAuthorization` 的签名材料。
Provider、策略、受控 PATH、Shell 启动方式或环境净化规则改变后，旧授权不能继续使用。

当前运行时会验证授权携带的 profile hash 与本次执行上下文一致。未来接入可变策略时，策略更新
必须同步重建 profile 和 policy context，不能只替换 `SandboxManager` 的 policy provider。

### 6. 工作区默认复制到单次临时层

`WorkspaceMirror` 当前使用 `mkdtemp` 创建精确实例根，并使用 `copytree` 完整复制每个授权
工作区：

```text
forge-sandbox-<random>/
  workspaces/<index>/
  home/
  tmp/
```

复制保留符号链接本身，不展开链接目标。实例环境中的 `HOME`、`USERPROFILE`、`TMPDIR`、
`TMP` 和 `TEMP` 指向实例私有目录。

当前行为按 Provider 区分：

- bubblewrap 将临时副本挂载到真实工作区原绝对路径；相对和绝对工作区路径看到同一副本。
- Seatbelt 以临时副本为 cwd；相对路径写入副本，真实工作区绝对路径保持只读。绝对路径写入
  不会自动重定向，而会失败。
- NoSandbox 不创建 `WorkspaceMirror`，命令直接使用真实 cwd，写入会落到物理工作区。

实例关闭时只删除由该实例 `mkdtemp` 创建的精确目录。受隔离实例中的新文件和修改目前不会自动
写回真实项目。

### 7. macOS 使用 SeatbeltProvider

Seatbelt profile 由 Forge 代码生成，不读取工作区配置，默认 `deny default`：

- 允许启动进程、必要的系统服务和运行时读取；
- 允许读取系统运行目录、真实工作区和授权外部目录；
- 只允许写入本次临时实例根；
- `network_enabled=false` 时不授予网络；
- `network_enabled=true` 时当前授予全部网络，不支持目标级过滤。

Seatbelt 不提供独立 PID namespace，系统运行服务权限也受 macOS 版本影响，因此最多为
`PARTIAL_SANDBOX`。

当前 Seatbelt Provider 尚未把 `DirectoryGrant.READ_WRITE` 映射为外部目录写权限；外部目录在
Seatbelt 中实际仍只读。该行为在补齐前必须作为能力不足处理，不能在 UI 中声称已经授予写入。

### 8. Linux 和 WSL2 使用 BubblewrapProvider

Bubblewrap 实例当前使用：

```text
--die-with-parent
--new-session
--unshare-all
--ro-bind / /
```

随后把工作区临时副本、实例 HOME/TMP 和已授权外部目录 bind 到 namespace。网络默认处于新的
network namespace；只有策略允许网络时才 `--share-net`。

外部目录授权映射为：

- `READ_ONLY` → `--ro-bind`；
- `READ_WRITE` → `--bind`。

当前宿主根整体以只读方式可见，因此可以阻止普通宿主写入，但不能隐藏全部宿主可读文件；设备
视图也仍使用 bubblewrap 提供的标准 `/dev`。加上资源硬限制尚未完成，当前最多为
`PARTIAL_SANDBOX`。

WSL2 对 Python 进程表现为 Linux，使用同一 Provider。Windows 主机挂载目录如果进入 WSL 文件
系统视图，必须作为外部目录单独授权和测试，不能因“运行在 WSL”自动成为可信工作区。

### 9. 原生 Windows 当前使用 NoSandboxProvider

原生 Windows 没有内置的 Partial/Strong Provider。`NoSandboxProvider` 仍经过统一 Manager，
但不实施文件、网络或进程访问边界，传入的 `SandboxPolicy` 不会转化为 OS 限制。

`NO_SANDBOX` 下由以下控制共同收紧：

- Shell/脚本确定性分析和 Hard Deny；
- auto 解析不完整时的隔离 LLM Safety Classifier；
- 模式能力预算和人工审批；
- 受控 PATH、非交互 Shell 和净化环境；
- 执行超时、输出上限和进程组回收。

这些控制不能被表述为系统沙箱。人工批准的 Shell 在 `NO_SANDBOX` 下会真实修改宿主文件；UI 必须
明确显示当前隔离等级。

### 10. 网络默认关闭，资源边界按真实能力报告

网络策略当前是二值的：关闭全部网络，或允许 Provider 所能提供的全部网络。域名、IP、端口和协议
级授权尚未实现。

`LocalCommandExecutor` 当前提供：

- 每条请求的 wall-clock timeout；
- stdout/stderr 大小上限；
- 独立进程组；
- 超时或取消时整组终止和回收。

`SandboxPolicy.max_processes` 和 `max_memory_bytes` 尚未映射到 rlimit、cgroup、Job Object 或
等效平台机制，所以 `resource_limits=false`。不能因为存在字段就报告资源隔离已经生效。

### 11. 沙箱生成代码必须先形成不可变候选变更集

为了把沙箱中的生成代码安全应用到真实项目，实例执行前后需要建立可比较的工作区清单。后续实现
必须在销毁实例之前完成：

```text
记录临时副本基线 manifest
  ↓
执行获准命令
  ↓
扫描执行后 manifest
  ↓
计算 SandboxChangeSet
  ↓
ArtifactCollector 安全收集候选内容
  ↓
把 bundle 封存到 Forge 受保护临时区/状态区
  ↓
销毁 SandboxInstance
```

`SandboxChangeSet` 至少表达：

```text
created / modified / deleted
source_relative_path / proposed_target_path
object_type / size / mode
before_hash / after_hash
base_workspace_view_hash
sandbox_policy_hash / execution_profile_hash
producer_plan_hash / tool_invocation_id
```

移动不能仅凭相同内容 hash 武断推断；无法证明移动身份时按删除加新建展示。字段名称可以演进，
但来源、基线、目标、内容 hash 和执行画像必须可审计。

当前 `SandboxInstance.run()` 只返回 `CommandOutcome`，`SandboxManager` 随后立即关闭实例。因此
实现该流程时必须扩展实例/Manager 契约，让 Collector 在 `close()` 之前读取临时层，或让 Provider
在返回前生成已经封存且不依赖实例目录的 bundle；不得把已经销毁的临时路径交给后续流程。

### 12. ArtifactCollector 不能递归信任沙箱输出

Collector 把沙箱内容视为不可信数据，不能直接 `copytree` 到真实工作区。默认规则为：

- 只处理工作区相对路径，规范化后必须仍位于对应工作区根内；
- 拒绝绝对路径、`..` 越界、设备文件、FIFO、socket 和挂载点；
- 默认拒绝符号链接、硬链接、junction 和 reparse point；未来支持时必须使用独立策略；
- 限制候选文件数、单文件大小、总大小、目录深度和扫描时间；
- 不自动收集 `.git`、Forge 配置/状态/凭证目录和其他受保护路径；
- 记录内容 hash 和元数据，不把不必要的文件正文写入事件日志或 LLM transcript；
- 二进制文件只展示类型、大小和 hash，除非工具提供安全预览器；
- 扫描失败、对象在扫描中变化或 bundle 封存失败时，不得 materialize 部分结果。

构建缓存、覆盖率、依赖目录和其他可再生输出可以通过版本化 ArtifactPolicy 排除；具体目录示例不是
永久硬编码名单。

### 13. Materialize 是新的工具计划，不继承 Shell 授权

候选 bundle 创建完成后，Forge 可以向用户或 Agent 提供“查看候选变更”和“请求应用”的能力。
真正写回必须创建新的 materialization plan：

```text
sealed artifact bundle
  ↓
选择候选变更
  ↓
生成精确 MaterializationPlan
  ↓
重新解析真实目标与受保护路径
  ↓
PolicyEngine / mode policy
  ↓
显示 diff、删除和元数据变化
  ↓
必要时人工批准
  ↓
建立 RecoveryStore binding，或使用 ADR-0020 的人类本次直接授权
  ↓
原子写回
  ↓
记录 postimage 和最终 MutationSet
```

原 Shell 的 `ExecutionAuthorization` 只允许沙箱执行，不能自动授权 materialize。即使用户批准了
Shell，也必须让审批展示明确包含后续写回计划；当前实现不支持在一个 Shell 审批中隐式授权未来
未知的变更集。

MaterializationPlan 至少绑定：

- bundle hash 和生产它的 Shell plan hash；
- 每个目标的操作类型、目标路径和 after hash；
- 真实工作区执行前的 base/preimage hash；
- 删除、覆盖、权限变化和其他不可从正文 diff 表达的副作用；
- 当前 mode、策略版本和 execution profile；
- 恢复绑定或人工一次性批准的 view hash。

LLM 可以建议选择哪些候选变更，但不能修改 sealed bundle、扩大目标路径或自行批准。

### 14. 写回前必须处理并发修改和恢复

沙箱副本建立后，用户、IDE 或其他进程可能继续修改真实工作区。materialize 前必须逐目标比较：

```text
当前真实对象 hash/身份
        vs
沙箱基线 manifest 中的 before hash/身份
```

不一致时标记冲突，禁止静默覆盖。后续可以提供三方合并，但合并结果必须形成新的内容 hash 和新的
审批视图，不能继续使用旧授权。

自动 materialize 必须先由 ADR-0015 RecoveryStore 建立 `TARGETED` 恢复事务。若 RecoveryStore
不可用，可以根据 ADR-0020 请求人类“仅本次直接应用”；UI 必须明确该操作会修改真实工作区且不
保证可恢复。Hard Deny、受保护路径、计划/view hash 变化和执行画像绑定仍不可被人工批准覆盖。

删除和覆盖必须保存 preimage；新建文件至少记录 `existed_before=false`。写回使用受控文件 API、
临时文件加原子 rename 和 no-follow/最终目标校验，不调用新的通用 Shell 来复制产物。

### 15. `/add-dir` 改变后续策略，不扩大正在运行实例

后续 `/add-dir` 规范语义为：

```text
/add-dir <path>             # 默认只读
/add-dir <path> --write     # 明确请求读写
/add-dir --list
/add-dir --remove <path>
```

它只能由用户显式发起。路径必须经过 realpath、符号链接/重解析点和受保护路径检查；策略更新递增
`policy_version`，只影响之后创建的实例。正在运行的实例不会动态获得新增权限。

读写授权不能暗示允许 materialize 到该目录；外部目录写回仍需单独的 MaterializationPlan、策略
裁决和恢复/人工批准。

当前代码已经建模 `DirectoryGrant.READ_ONLY/READ_WRITE`，但尚未实现完整命令和持久化流程。

### 16. 临时工作区、真实工作区和直接文件工具的语义必须向用户明确

当前行为矩阵为：

| 执行路径 | 系统隔离有效时 | NO_SANDBOX 时 | 当前是否自动写回 |
|---|---|---|---|
| `shell.run` 相对路径写入 | 写临时副本 | 写真实工作区 | 否 |
| `shell.run` 绝对工作区路径 | bubblewrap 写副本；Seatbelt 拒绝真实写入 | 写真实工作区 | 否 |
| `fs.write_file` | 直接写真实工作区，不经过 Shell 沙箱 | 同左 | 本身即真实写入 |
| 未来 `workspace.materialize` | 经独立写回计划应用 | 同左 | 是，但需新授权 |

终端状态和审批 UI 至少展示 `isolation_level` 和 Provider。不能只显示“沙箱已启用”，也不能把
临时层中的成功写入描述为已经修改项目文件。

## 备选方案

### 方案 A：启动一个永久沙箱和持久 Shell

优点是连续 `cd`、环境变量和命令启动成本较低。缺点是策略变化后难以证明旧进程没有保留权限，
临时层和挂载生命周期也更复杂。

当前不采用。未来如实现持久 Shell，只保存可恢复的逻辑 cwd/环境；策略版本变化时销毁并重建实例。

### 方案 B：Provider 失败后直接执行宿主 Shell

可以提高命令成功率，但会使授权画像和真实执行环境不一致。

不采用。运行期失败返回结构化错误，重新探测和降级必须触发新的裁决。

### 方案 C：让沙箱直接读写真实工作区

实现简单，生成代码立即可见，但脚本误写、删除和动态目标会直接影响用户文件，无法在执行后先审查
差异。

不作为默认路径。只有明确的真实写入计划、适用的恢复保障或人类本次直接批准才能写真实工作区。

### 方案 D：命令结束后把整个临时工作区复制回去

会覆盖并发用户修改、复制缓存和敏感输出、跟随恶意链接，并把删除语义变得不明确。

不采用。必须先生成 sealed change set，再按精确目标 materialize。

### 方案 E：使用第三方统一 SRT

可以减少 Provider 维护，但引入额外运行时、安装、供应链和平台成熟度耦合。

当前不采用。Forge 自己拥有 Provider 契约、可信策略、自测和生命周期，底层复用 Seatbelt、
bubblewrap 等操作系统能力。

### 方案 F：远程执行节点或虚拟机

隔离更强，也更适合不可信依赖和高资源任务，但引入调度、同步、凭证和成本问题。

MVP 不采用，保留为需要 Strong 隔离时的后续 Provider。

## 影响

### 收益

- Shell 执行入口统一，Provider 失效不会形成宿主旁路。
- 能力画像来自行为自测，不会因二进制存在而虚报 Strong。
- 每次执行使用新实例和当前策略，权限生命周期清晰。
- 受隔离 Shell 的普通写入不会直接破坏真实工作区。
- 生成代码可以先形成候选差异，再决定是否应用。
- materialize 与 Shell 授权分离，便于审计、恢复和冲突处理。

### 代价

- 当前完整复制工作区会增加启动延迟和磁盘占用。
- 每次命令后丢弃实例，不保留 Shell 进程状态。
- 生成代码在 ArtifactCollector 落地前无法从沙箱自动带回项目。
- Materialize 需要额外扫描、hash、diff、审批和恢复事务。
- 多平台 Provider 的能力和路径语义不完全一致。
- `NO_SANDBOX` 仍需依赖概率分类、规则和人工判断，安全能力明显更弱。

## 当前限制与后续顺序

建议按以下顺序继续实现：

1. 定义 `SandboxExecutionResult`、基线 manifest、`SandboxChangeSet` 和 sealed bundle。
2. 在实例关闭前实现带配额和对象类型检查的 ArtifactCollector。
3. 增加只读的 change/diff 展示，不写真实工作区。
4. 实现 `MaterializationPlan` 和独立 ToolSpec/Policy 流程。
5. 接入 ADR-0015 TARGETED RecoveryStore 与冲突检查。
6. 实现原子 materialize，并覆盖创建、修改、删除和失败回滚。
7. 最后再允许 auto 在恢复预算内自动应用低风险候选变更。
8. 优化 WorkspaceMirror 为 reflink、OverlayFS 或其他经自测的 Copy-on-Write Provider。

在第 1–6 步完成前，受隔离 Shell 的变更必须继续视为临时结果，不得在 UI 或模型 observation 中
声称“代码已经写入项目”。

## 验收标准

### 当前实现应持续满足

- 所有 `shell.run` 都经过 `SandboxManager` 和某个显式 Provider。
- Provider 只因行为自测成功才报告对应能力。
- Seatbelt/bubblewrap 缺失或自测失败时显式选择 NoSandbox。
- Provider 创建失败不在同一授权下回退到更弱 Provider。
- 每次执行创建一个实例，并在成功、失败或取消后关闭。
- 临时工作区关闭后被删除，真实工作区内容不因副本内相对路径写入而改变。
- NoSandbox 不伪装文件、网络、进程或资源隔离。
- 网络默认关闭，环境变量和 PATH 使用净化快照。
- timeout、输出上限和进程组回收有效。
- Provider 能力和 policy hash 进入 `execution_profile_hash`。
- `fs.write_file` 不能借 Shell 的 ephemeral binding 绕过真实写入恢复策略。
- Hard Deny 和人工审批不会因沙箱存在而被跳过。

### Materialize 切片完成后必须新增满足

- 实例销毁前产生绑定基线、生产 plan、策略和画像的 sealed `SandboxChangeSet`。
- Collector 拒绝链接、设备、socket、FIFO、越界和受保护路径，并实施数量/大小预算。
- Shell 授权不能直接复用为 materialization 授权。
- UI 完整展示创建、修改、删除、二进制和元数据变化。
- materialize 前检测真实工作区并发修改，冲突时不静默覆盖。
- 自动 materialize 具备 ADR-0015 recovery binding；无恢复时只能走明确的人类本次直接批准。
- 目标、内容或审批视图变化会使旧授权失效。
- 写回使用安全文件 API 和原子替换，不调用通用 Shell 复制候选产物。
- 成功、拒绝、冲突、部分失败和恢复结果均产生可审计事件。
