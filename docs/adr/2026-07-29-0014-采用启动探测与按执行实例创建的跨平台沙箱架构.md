# ADR-0014：采用启动探测与按执行实例创建的跨平台沙箱架构

## 状态

Proposed

## 日期

2026-07-29

## 背景

ForgeCLI 需要为 Agent 发起的 Shell、Python、Node 和其他脚本执行提供跨平台的 containment。
沙箱的目标不是创建一台完整虚拟机，而是在可使用受控宿主资源的前提下，限制进程能够访问的文件、
网络、进程、设备和资源，并降低错误或恶意脚本对宿主机的真实影响。

不同平台的沙箱能力不同：macOS 和 Linux 可以使用平台适配器；Windows 非 WSL2 环境可能没有
等价的统一沙箱能力。运行期还可能通过 `/add-dir` 为当前会话增加宿主机目录，因此沙箱的固定
持久化进程和动态权限扩展需要明确区分。

## 决策

### 1. Forge 启动时初始化 SandboxManager，不创建固定永久沙箱

Forge 启动时完成沙箱能力探测，并初始化 `SandboxManager`：

```text
Forge 启动
  ↓
检测平台和沙箱实现
  ↓
执行最小隔离自测
  ↓
生成 ExecutionEnvironmentProfile
  ↓
初始化 SandboxManager
```

启动阶段不创建一个固定挂载列表和固定 Bash 进程作为全局沙箱。具体 Shell 执行时，使用当时最新
的策略创建沙箱实例。

### 2. 持久化策略，临时化沙箱实例

沙箱相关状态分为两类：

```text
SandboxPolicy       持久化或会话级保存
SandboxInstance     单次执行或短期会话级存在
```

`SandboxPolicy` 包含允许访问的目录、网络、进程和资源限制；`SandboxInstance` 是根据某一版本
策略创建的实际执行环境。

推荐生命周期：

```text
读取当前 SandboxPolicy
  ↓
创建 SandboxInstance
  ↓
启动 Bash / Python / 其他进程
  ↓
收集输出和产物
  ↓
销毁 SandboxInstance
```

### 3. ShellTool 必须通过 SandboxProvider 执行

所有 Shell 执行都必须进入统一执行器：

```text
ShellTool
  ↓
Command Security Pipeline
  ↓
SandboxProvider
  ↓
SandboxInstance
  ↓
Shell 进程
```

平台实现包括：

- macOS：Seatbelt Provider。
- Linux：bubblewrap Provider。
- Windows WSL2：按 Linux 执行环境选择对应 Provider，并显式处理 Windows 主机挂载。
- Windows 非 WSL2：使用 `NoSandboxProvider`，由规则引擎、操作系统权限和风险分类器控制。

没有可用沙箱时不能绕过 `SandboxProvider` 直接执行宿主 Shell。

### 4. 启动探测必须验证能力，而不只是检查可执行文件

`SandboxManager` 必须生成 `ExecutionEnvironmentProfile`：

```text
platform
sandbox_provider
sandbox_available
filesystem_isolation
network_isolation
process_isolation
resource_limits
overlay_or_temp_workspace
profile_version
```

能力等级至少包括：

```text
STRONG_SANDBOX
PARTIAL_SANDBOX
NO_SANDBOX
```

只有在实际自测确认文件、网络和进程边界有效时，才可标记为 `STRONG_SANDBOX`。仅发现
`bubblewrap` 或 Seatbelt 相关命令存在，不足以证明沙箱可用。

### 5. 沙箱限制访问对象和副作用，不承诺绝对不影响宿主资源

沙箱应限制：

- 可读路径。
- 可写路径。
- 网络访问和目标。
- 子进程创建。
- 设备访问。
- CPU、内存、运行时间、进程数和输出大小。
- 可见环境变量。

沙箱可以使用受控的宿主 CPU、内存和磁盘资源，但不应表述为“完全不会影响宿主机”。资源耗尽、
内核漏洞、平台实现缺陷和侧信道不属于普通沙箱保证范围；需要更强隔离时应使用虚拟机或独立执行节点。

### 6. 脚本执行优先使用临时可写层

对 Python、Node、Shell heredoc 和其他任意脚本执行，推荐使用：

```text
工作区源内容只读挂载
        +
临时可写层 / Copy-on-Write Overlay
```

测试生成的临时文件、缓存、覆盖率报告和构建产物写入临时层。执行完成后由 Forge 收集必要产物，
再销毁临时层。

如果命令需要直接修改真实工作区，则必须根据当前模式和命令决策结果单独授权，不能因为脚本已经在
沙箱中运行就自动获得真实工作区写权限。

### 7. `/add-dir` 使用命令式资源授权，不动态扩大已有实例权限

`/add-dir` 采用命令式语法，是对宿主机资源的授权变更，不是对当前沙箱进程的直接挂载操作：

```text
/add-dir <path>
/add-dir <path> --write
/add-dir --list
/add-dir --remove <path>
```

其中：

- `/add-dir <path>` 默认授予只读访问。
- `/add-dir <path> --write` 请求读写访问，必须显式确认。
- `/add-dir --list` 展示当前会话已经授权的目录和访问模式。
- `/add-dir --remove <path>` 撤销目录授权，并使后续执行使用新的策略版本。

交互式确认可以作为 `--write` 或高风险路径的审批界面保留，但不再作为 `/add-dir` 的主要输入形式。
命令的参数、访问模式和最终授权结果应结构化保存，便于审计、恢复和自动化。

`/add-dir` 只能由用户显式发起。LLM 可以建议用户执行该命令，但不得自行调用 `/add-dir` 扩大自身
的宿主机访问范围。

处理流程为：

```text
/add-dir <path> [--write]
  ↓
路径规范化、符号链接解析和保护路径检查
  ↓
确定只读或读写范围
  ↓
必要时请求用户确认
  ↓
更新 SandboxPolicy
  ↓
递增 policy_version
  ↓
后续执行创建新 SandboxInstance
```

默认规则为：

- `/add-dir <path>` 默认只读。
- `/add-dir <path> --write` 需要显式确认。
- 凭证、系统目录、Forge 自身数据目录和其他受保护路径不得通过 `/add-dir` 授权。
- 新目录只对新创建的沙箱实例生效。
- 正在运行的命令和旧沙箱实例不会获得新增目录访问权。
- 目录撤销同样更新策略版本，并使后续执行不再获得该目录。

### 8. 持久 Shell 会话保存逻辑状态，策略变化时重建执行环境

如果产品需要保持：

```bash
cd project
export MODE=test
```

则可以保留会话级 `ShellSession`，但不要求其底层沙箱实例永久不变。

当 `/add-dir` 或其他安全策略变化导致 `policy_version` 更新时：

```text
保存允许恢复的 cwd 和环境变量
  ↓
停止旧 Shell / SandboxInstance
  ↓
根据新策略创建实例
  ↓
恢复 cwd 和必要环境
```

不允许通过已有 Shell 进程自行修改挂载边界，也不允许沙箱内进程请求 Forge 直接增加宿主机访问权限。

### 9. 网络默认关闭，资源扩展必须显式授权

强沙箱默认配置：

```text
network = disabled
workspace = read-only 或临时可写层
external_dirs = none，除非已授权
credentials = hidden
privileged_devices = none
```

需要访问网络、工作区外目录、设备或真实工作区写入时，必须更新策略并重新计算命令裁决；不能只依赖
已有沙箱实例继续执行。

### 10. 无沙箱环境自动收紧 auto 能力

当 `ExecutionEnvironmentProfile` 为 `NO_SANDBOX` 时：

- `plan` 和 `accept_edits` 的脚本执行仍按各自规则处理。
- `auto` 对新脚本、变更脚本和未知脚本调用 Background Safety Classifier。
- 低风险、意图匹配且范围可证明受控时可以自动执行。
- 分类器超时、异常或不确定时进入 `ASK`。
- Hard Deny 在所有环境中保持有效。

无沙箱环境的 `auto` 自动执行能力不得强于 `STRONG_SANDBOX` 环境。

## 备选方案

### 方案 A：Forge 启动时创建一个永久沙箱

优点是启动后执行路径简单，可能减少创建开销。

缺点是工作区和 `/add-dir` 目录动态变化时难以安全更新；不同平台难以保持一致；长期运行进程的
状态和权限边界难以审计。

不采用。

### 方案 B：每次执行 Shell 都完全重新初始化 Forge 和沙箱管理器

优点是边界清晰。

缺点是重复探测和初始化成本较高，无法自然支持持久化 Shell 会话。

不采用；改为启动时探测、执行时实例化。

### 方案 C：持久 Shell 进程中动态增加宿主目录

优点是无需重启 Shell。

缺点是依赖平台特有的动态挂载机制，权限扩大难以审计，容易产生旧进程状态和新安全策略不一致。

不采用。

### 方案 D：使用交互式 `/add-dir` 作为唯一授权接口

优点是能够在授权前逐步询问用户，交互引导较强。

缺点是参数不明确，不利于脚本化、恢复、审计和命令历史；读权限与写权限也容易在交互过程中混淆。

不采用作为规范接口。保留交互式确认作为高风险权限的审批环节，规范接口使用
`/add-dir <path> [--write]`。

### 方案 E：启动探测 + 策略版本化 + 按执行实例创建沙箱

优点是既支持命令式动态 `/add-dir`，又保持实例边界清晰；可以适配无沙箱平台，并支持持久 Shell
的逻辑状态恢复。

缺点是策略变化时需要重建 Shell 或执行实例，必须管理状态恢复和临时产物。

采用。

## 影响

### 收益

- 沙箱能力在 Forge 启动时可被明确探测和审计。
- 每次执行使用最新策略，避免固定沙箱权限过期。
- `/add-dir` 可以在运行期生效，同时不会影响当前正在执行的进程。
- 测试和任意脚本可以在临时可写层中运行，减少真实工作区破坏。
- 持久 Shell 会话可以通过保存逻辑状态支持策略重建。

### 代价

- 每次 Shell 执行存在沙箱实例创建和销毁成本。
- 持久 Shell 的策略变化需要重启底层执行进程。
- 需要维护多平台 Provider、能力探测和自测逻辑。
- 临时层中的测试产物需要显式收集和处理。
- 无沙箱 Windows 的 auto 依赖额外的 LLM 分析。

### 后续约束

- 沙箱实例不能绕过 `ShellTool` 和命令安全管线。
- 沙箱能力检测失败时必须明确降级，不得假设沙箱存在。
- 策略变化必须递增版本并使旧执行上下文失效或重建。
- `/add-dir` 默认只读，读写授权必须分开。
- `/add-dir` 的规范语法为 `/add-dir <path> [--write]`，并支持列出和撤销授权。
- LLM 不能自行发起 `/add-dir`。
- 不能将“沙箱存在”解释为绝对不会影响宿主机。

## 验收标准

- Forge 启动时能生成 `ExecutionEnvironmentProfile`。
- 能区分 `STRONG_SANDBOX`、`PARTIAL_SANDBOX` 和 `NO_SANDBOX`。
- ShellTool 在所有平台都经过 SandboxProvider 或 NoSandboxProvider。
- 强沙箱实例可以限制路径、网络、进程和资源。
- 脚本执行默认使用临时可写层或等效隔离策略。
- `/add-dir` 默认只读，并能更新 `SandboxPolicy` 和 `policy_version`。
- `/add-dir <path> --write` 会触发显式授权或审批。
- `/add-dir --remove <path>` 会撤销目录并更新策略版本。
- 新目录只对新创建的沙箱实例可见。
- 正在运行的旧实例不会因 `/add-dir` 自动获得新目录权限。
- 持久 Shell 会话可以在策略变化后恢复允许的 cwd 和环境变量。
- 无沙箱环境的 auto 对新脚本和变更脚本启用风险分类器。
- 沙箱能力探测失败、创建失败或运行时异常均有明确的安全降级行为。
- 沙箱、策略变更和执行实例生命周期均有审计事件。
