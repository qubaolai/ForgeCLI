# ADR-0039: 把模型可读正文改成 Jinja 模板

## 状态

Proposed

本 ADR 修订 ADR-0031 的决策 1, 4, 5: 正文的家从 `domain/prompt/text.py` 换成
`application/prompt/templates/`, 三道闸随之改写. ADR-0031 的其余部分 (收进来的判据,
一个版本号一个指纹, 归属检查进 `make ci`) 不变, 而且这次比原来严 —— 扫描不再有例外目录.

## 日期

2026-08-26

## 背景

### 1. 块的骨架只存在于控制流里

ADR-0031 把散在四个文件里的正文收进了 `domain/prompt/text.py`, 解决的是"看不出彼此矛盾".
但它没解决另一件事: **看不出一个块长什么样**. 工具契约那一块由六个常量
(`TOOL_CONTRACT`, `SECTION_TOOL_CHOICE`, `TOOL_TABLE_LEAD_WITH_SHELL` /
`TOOL_TABLE_LEAD_PLAIN`, `SHELL_BOUNDARY`, `SECTION_SEARCH_ORDER`, `SEARCH_STRATEGY`)
在 `_tool_contract` 的三个 `if` 与两处 `"\n\n".join` 里拼成. 想知道模型实际读到什么, 要
读两个文件, 并在脑子里跑一遍那几个 join.

两件事不是一件: 正文收在一处, 骨架仍然散在控制流里.

### 2. 一段有条件的正文没有位置可放

给工具契约加一节"任务拆解"需要三处改动: text.py 加一个常量, builder 加一个开关, builder
的 `sections` 列表里插一行. 三处分布在两个文件, 而它们表达的是同一件事 —— "这一节在有
待办工具的时候出现".

### 3. 拼装本身会静默出错

`_tool_table` 的注释里记着一次真实事故: 分隔符在一次重构里丢了, 渲染出来的是
`读取文件fs_read` 这样粘在一起的一行. 没有任何测试会红 —— 提示词照常渲染, 指纹照常稳定,
只是模型读到的工具表是一坨. 拼装代码越多, 这类缺陷的面积越大.

### 4. `text.py` 坐在 domain, 却没有一个 domain 消费方

ADR-0031 决策 1 给的理由是"只有 domain 能被四个消费方全部 import 而不撞 SIBLING_BANS".
事实上 `scripts/check_arch.py` 的 SIBLING_BANS 里没有任何一条涉及 `application.prompt`,
而八个消费方 (agent_loop, agent_turn, context ×2, tools ×2, llm.gateway, prompt) 全在
application, domain 里一个都没有. 那条理由不成立, 结果是一个纯 application 的东西长期
挂在 domain 上.

## 决策

### 决策 1: 正文只有一个家, 一份文件就是一段正文

`application/prompt/templates/`, 三类:

```text
blocks/<block_id>.md.j2   系统提示词的块正文. 有骨架: 哪几节, 什么条件下出现
headings.md.j2            八个块的标题, 一张表
notices/<group>.md.j2     回合中的引导, 收摊通知, 工具回执, 压缩占位. 一条一个 macro
```

`blocks/` 的文件名与 `headings.md.j2` 的键都**复用 `PromptBlockId` 的取值**; 不另立一份
模板 id 枚举 —— 那会是第二份要手工同步的表, 而漏同步不报错.

`domain/prompt/text.py` 随之删除. `domain/prompt/` 只剩 `blocks.py`: 缓存划分与派生指纹
这类不变量, 那才是 domain 该装的东西.

### 决策 2: 按组存, 不按条存

一份文件一组, 一条一个 `macro`: `render_notice("loop.halt")` 里 `loop` 是文件, `halt` 是
宏. 八个块标题同理, 合成 `headings.md.j2` 里的一张表.

一条一个文件试过, 五十几句话变成五十几份一行文件: 找是好找了, 但"这几句彼此矛盾没有"就
再也看不出来了 —— 而那正是 ADR-0031 当初收拢正文要解决的问题. 一组并排放着, 一眼扫得完;
八份各一行的标题文件, 谁也看不出这八个标题还成不成套.

孤儿检查随之按**宏**查而不是按文件查: 合并之后, 一份文件里死掉一条不会让文件本身变成孤儿.

### 决策 3: 条件写在模板里, builder 只算开关与槽位值

`{% if has_shell %}` / `{% if tool_table %}` / `{% if has_planning %}` 进模板. builder 的
职责收敛成三件: 出哪些块, 块序与 `cacheable` (编排), 开关, 槽位值.

### 决策 4: 措辞一律进模板, 包括标签词与查表

`自动放行` / `需人类确认` / `额外工作目录` / `项目事实` / `用户偏好` 这些标签是措辞, 不是
值, 全部进模板. 连能力名那张表也进 `blocks/runtime_facts.md.j2` —— builder 传能力**取值**
的集合, 模板按取值查名字, 顺序由模板里那张表定 (集合的迭代顺序不稳定, 拿它定顺序会毁掉
指纹的确定性).

只有两样留在 Python 里, 而且都不是措辞: `PROMPT_TEXT_VERSION` (一个数字), 与项目指令的
分隔行 `--- BEGIN/END WORKSPACE INSTRUCTIONS ---` (ASCII 结构标记, 必须与
`_escape_sentinels` 认的那一行逐字节相同, 所以留在转义器旁边).

### 决策 5: 模板与渲染器都在 `application/`, 不在 `infrastructure/`

仓库惯例是"真的去碰文件系统属 infrastructure" (FORGE.md 就是那么分的). 这里刻意不照办:
**内置模板是包内数据, 不是工作区状态** —— 它不随用户环境变化, 读它不需要工作区路径, 也没有
"读不到就降级"的余地. `check_arch.py` 的机器规则不禁止这条: jinja2 不在 `BANNED_THIRD_PARTY`
里, 也没有跨层 import.

### 决策 6: 不引入 `PromptTemplates` 端口

只有一个实现的 ABC 按 ADR-0028 规则 A 本来就该删, `scripts/check_abstractions.py` 就是查
这个的. 于是消费方直接调 `render_block` / `render_notice` / `render_heading`, 五个
`SystemPromptBuilder()` 构造点一个都不用动. 将来真要换引擎再抽象 —— 那时才有第二个实现,
规则 A2 才成立.

### 决策 7: 一次加载, 进程内冻结, 缺文件当场炸

`auto_reload=False` + `lru_cache`: 模板在会话中途被改写会让同一轮的提示词漂, 而 ADR-0018
要求提示词按 turn 冻结. 缺文件不降级, 直接抛 —— 与 FORGE.md 那条"读不到就跳过"相反: 内置
正文不是可选的, 悄悄渲染出一句空话比起不来更糟.

`StrictUndefined`: 漏一个槽位要抛异常, 不能静默渲染成空字符串.

### 决策 8: `{# #}` 注释不进指纹

每份模板的 `{# #}` 里写着它为什么这么措辞 —— 那是这套正文最值钱的部分, 也是从 text.py 的
行间注释原样搬过来的. 但注释一个字都不会进模型上下文, 让改一句注释也要升版本重钉指纹,
唯一的后果是没人再写注释. 指纹因此在算之前先把 `{# #}` 剥掉.

分组层面的理由 (五组 notices 各自的读者是谁) 放 `templates/README.md`.

### 决策 9: 三道闸改写

| 闸 | 改法 |
|---|---|
| `scripts/check_prompt_text.py` | `render_block` / `render_notice` / `render_heading` 进 SINKS; **例外目录取消** —— 原先 text.py 自己全是中文字面量要放行, 现在任何 .py 里都不该再有 |
| 半角标点 | 按文件参数化到整个 `templates/` |
| 指纹 | `templates_fingerprint()` 覆盖全目录; 改任一份模板都要升 `PROMPT_TEXT_VERSION` |

再加三条新的: 每个块都有正文模板, 也在标题表里有一行; 模板必须经 `importlib.resources`
读得到 (与 wheel 里的读法一致); 渲染结果里不残留 `{{` 或 `{%` (`StrictUndefined` 挡的是
"槽位没传值", 挡不住"标签写错了").

"无孤儿"那条也跟着换判据: 从"每个常量都有人引用"变成"每一个 notices 宏都有人
`render_notice`".

## 备选方案

- **方案 A: 在 text.py 里用 Section 元组表 + 自制渲染器.** 优点是不加依赖. 缺点是条件与
  循环一上来就要三种构造 (`if` / `for` / 槽位), 而自制模板引擎只会长大; 且 Section 的
  `repr` 进指纹, 改一个字段名就会改指纹, 而正文一个字都没动.
- **方案 B: 外部模板 + 端口 + infrastructure 实现.** 分层上最"正统", 但那个端口只有一个
  实现, 会被 `check_abstractions.py` 判死 —— 为了绕过它去凑第二个实现是本末倒置.
- **方案 C: 只搬块正文, 一行通知留在 `domain/prompt/text.py`.** 这是本 ADR 的第一版决策,
  被否掉了: 两个家就要有两套闸, 而漏掉的那一套迟早会有人从缝里塞一句话进去; 何况那个模块
  坐在 domain 却零 domain 消费方 (背景 4).
- **方案 D: 一条通知一个文件.** 第二版这么做过, 也被否掉了 —— 见决策 2. 通读成本是这套
  正文的核心资产, 不能为了"好找"把它花掉.

## 影响

**收益.** 一个块就是一份能从头读到尾的文件, 条件也在文件里. 新增一节正文从"三处改动, 两个
文件"变成"在模板里加一段". 拼装代码消失, 连带那类静默排版事故的面积一起消失. 正文归属检查
不再有例外目录, 比 ADR-0031 那版严.

**代价.**

- 新增运行时依赖 `jinja2`.
- 一行通知从"一个模块里的一行"变成"一份组文件里的一个宏". 同组之内并排可读, 跨组通读
  要 `cat templates/notices/*`, 比原先翻一个模块多一步.
- 模板是数据文件: 源码树里永远读得到, 装出来的 wheel 里只有 `pyproject.toml` 的 `include`
  说了算. 这类失败只在装好之后才现形, 所以配了一条走 `importlib.resources` 的用例, 以及
  `make verify-cli`.
- 每次渲染多一次模板查表. 一行通知的渲染在微秒级, 而且 Environment 缓存编译结果.

**约束.**

- `blocks/` 的文件名与 `headings.md.j2` 的键即 `PromptBlockId` 取值; `notices/` 的
  `<组>.<条>` 即 `render_notice` 的入参. 改任一边都要两边一起改, 有用例钉住.
- 搬家那一步必须**渲染逐字节不变**. 这是唯一能证明"只搬没改"的办法; 改措辞是下一步的事.

## 第一个用户: 工具契约的"任务拆解"一节

条件 `has_planning` (本轮目录里同时有 `todo_write` 与 `plan_write` 才渲染, 与 `shell_run`
那条"引导语跟着目录走"同一条规矩).

正文给**可数的判据**而不是形容词: "自主判断复杂度"这种话两头都会翻车 —— 给"改个错别字"
也建三项清单, 或者复杂任务照样不建. 所以写的是"要改 3 个以上文件 / 一句话里有多个可分
交付物 / 要跨改代码-跑测试-更新文档多个阶段 / 已经几轮还说不清剩几步", 并给出反例
(单文件小改, 纯问答, 只读探查不建).

另外两句是接口, 不说模型会自己脑补: **待办不必绑定计划** (ADR-0022 决策 4, `plan_id` 可空),
以及**提交计划会停下来等用户裁决** (ADR-0023), 拿到裁决之前不要按已批准处理.

## 验收标准

- 搬家那两步的渲染结果逐字节不变 (只有 `PROMPT_TEXT_VERSION` 让快照指纹变).
- 八个块各有一份正文模板, 且都能渲染出标题 —— 有用例.
- 每一个 notices 宏都有人 `render_notice` —— 有用例.
- 模板经 `importlib.resources` 读得到, 且在 `make package` 出的 wheel 里 —— 有用例 + 一次
  人工核对.
- 渲染结果里不残留 `{{` 或 `{%` —— 有用例, 且覆盖每一个条件性块与转义那条路径.
- 任何 .py 里往模型上下文传中文字面量都会被 `make ci` 拦下, 没有例外目录.
- 模板里出现全角标点会被用例拦下.
- 目录里有待办工具时提示词含"任务拆解"一节; 没有时整节不出现.
- `src/forgecli/domain/prompt/text.py` 不再存在, 全库零 `prompt_text` 引用.
- `make ci` 通过.
