# ADR-0038: 计划评审的"同意并执行"升档到 auto

## 状态

Proposed

本 ADR 修订 ADR-0023 决策 4 的一条: 升档的终点从 `ACCEPT_EDITS` 改为 `AUTO`. ADR-0023
的其余部分 (回合边界停顿, 四选一, 再入用 `InputOrigin.PROGRAM`) 不变, 整体仍是 Accepted.

## 日期

2026-08-26

## 背景

### 1. 那条约束是在能力预算表还在的时候定的

ADR-0023 决策 4 写死了两件事: 升档只允许 `PLAN -> ACCEPT_EDITS`, 且"绝不升到 `AUTO` 或
`FULL_ACCESS`". 写这条的时候, 模式的差别由 `domain/security/modes.py` 的能力预算表表达 ——
`EXECUTE_SHELL` 在 `accept_edits` 要问人, 在 `auto` 起自动放行. 多升一档就是真的多放一类
能力, 所以那条约束当时挡住的是一组能力.

### 2. ADR-0030 之后, `accept_edits` 与 `auto` 编译出的东西完全一样

围栏顶替预算表之后, 模式只在两处生效:

- `domain/execution/fence.py::fence_for`: 只有 `PLAN` 拿只读围栏 (`writable_roots` 为空),
  只有 `FULL_ACCESS` 拿 `network_allowed=True`.
- `application/tool_request/catalog_predicates.py::catalog_query_for_mode`: 只有 `PLAN`
  收窄工具目录.

`PolicyEngine` 除了把模式名打进 ASK 的 message 之外不读 mode; `budget.py` 的判据是围栏与
`confined`, 与模式无关. 于是 `accept_edits` 与 `auto` 今天产出逐字节相同的围栏和目录 ——
"绝不升到 `AUTO`"挡住的已经不是一组能力, 是一个标签.

### 3. 名实不符落在用户这边

`/mode` 面板给 `accept_edits` 的一句话说明是"放行低风险编辑, 命令仍逐次询问". 而用户刚刚
点的那一项叫"同意并执行", 表达的是"按这份计划自己做完". 他被送进一个说明文字与自己的决定
对不上的档位, 还要自己再敲一次 `/auto` —— 这正是 ADR-0023 背景里想消掉的那种手工步骤.

## 决策

### 决策 1: 唯一允许的升档边改为 `PLAN -> AUTO`

`_upgraded_mode` 的返回值改成 `SessionMode.AUTO`. 其余一律不变: 仍然只有
`approve_and_run` 触发, 仍然经 `SessionService.set_mode` 落盘并写 `mode_changed`, 与用户
在 plan 档手敲 `/auto` 完全等价, **不新增任何旁路**.

### 决策 2: 边的另一端仍然封死在 `FULL_ACCESS` 之前

`FULL_ACCESS` 放的是网络与跨工作区, 而那是今天围栏里真正还在起作用的一条差别
(`network_allowed = mode is FULL_ACCESS`). 这一档只能由人自己切, 任何评审动作都到不了.

### 决策 3: 计划正文不能成为提权的依据

`_upgraded_mode` 不接受参数, 也读不到 `PlanDocument`. 计划是模型产出的低信任文本, "计划里
写了什么能不能影响档位"这个问题在类型层面就没有入口. 这条与 ADR-0023 一字不改.

### 决策 4: 只有"同意并执行"改档

"同意"仍然只批准计划 + 播种待办, 不碰档位. 那条路径的用意是"先批准, 晚点再做", 提前放权
与它的用意相反.

### 决策 5: 升档仍然不等于授权

评审不走 `ApprovalService`, 不签发 `ExecutionAuthorization`, 不进 `RiskCache`, 不写
learned rule. 升档之后计划里的每一步仍逐次走完整裁决管线: 目录能力门 -> `prepare` ->
能力分析 -> `PolicyEngine` -> ASK / ALLOW / DENY -> 恢复屏障 -> `ExecutionAuthorization`.

## 备选方案

- **方案 A: 让升档终点变成一个配置项.** 优点是各人各取所需. 缺点是权限规则从代码常量变成
  配置数据, 而它一旦可写就是一个提权入口 —— 提权规则应当由 ADR 管辖, 不由某个键的当前值
  决定.
- **方案 B: 保持 `ACCEPT_EDITS`, 改档位说明让文案与实现一致.** 那修的是背景 3, 修不了
  背景 2: 用户做完"你自己做完"这个决定之后, 仍然停在一个语义上更保守的档上, 还是要自己
  再切一次.
- **方案 C: 升到 `FULL_ACCESS`.** 拒绝. 网络与跨工作区是围栏里真正还在起作用的一条边,
  它必须由人自己跨.

## 影响

**收益.** 用户点完"同意并执行"就在他以为自己在的那一档, 少一次手工切换. `auto` 与
`accept_edits` 将来若重新分开 (`auto` 恢复"低风险命令自动放行"的独立语义), 这条边已经落在
正确的一端, 不用再改一次权限规则.

**代价.**

- 学习规则按 mode 绑定 (`RuleMatch.mode`, `learned_rules.py::_match_of`). 升档之后, 早先在
  `accept_edits` 下学到的"始终允许"不再命中, 用户可能被再问一次. 方向是多问一次, 不是少问
  一次.
- 会话档位从 `plan` 一步跨两格. `mode_changed` 照写, 审计里看得见; 用户随时可以
  `/plan` 或 `/accept-edits` 切回去.

**约束.**

- **这次改动当下不放宽任何一条实际权限**: 围栏与工具目录在 `accept_edits` 与 `auto` 下相同
  (背景 2). 谁将来把这两档重新分开, 要一并复核这条边是否还该落在 `AUTO`.
- 新会话的默认档不变, 仍是 `accept_edits` (`SessionService`).

## 验收标准

- plan 档"同意并执行"产出 `upgraded_mode = AUTO`, 且会话模式与 `PLAN_REVIEWED` 事件里的
  `upgraded_mode` 都是 `auto` —— 有用例.
- 计划正文写满 `full_access` 字样也只升到 `AUTO`, 任何情况下都到不了 `FULL_ACCESS` ——
  有用例.
- 从 `accept_edits` / `auto` / `full_access` 批准计划不改档, 既不升也不降 —— 有用例.
- "同意" / "补充" / "拒绝"都不碰档位 —— 有用例.
- 评审仍然拿不出 `ExecutionAuthorization`, 也写不进 learned rule —— 沿用既有用例.
- 终端菜单与 Web 计划面板走完一次"同意并执行"之后, 显示的档位都是 `auto`.
- `make ci` 通过.
