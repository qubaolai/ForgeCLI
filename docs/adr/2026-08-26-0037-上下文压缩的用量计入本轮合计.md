# ADR-0037: 上下文压缩的用量计入本轮合计

## 状态

Proposed

## 日期

2026-08-26

## 背景

ADR-0032 决策 2 的二级压缩是**一次额外的模型调用**: 把一段历史喂给模型, 换回一段
交接说明. 那份 ADR 的注释里写着它"要钱, 要时间", 但代码里这笔钱一直没记到任何账上.

### 1. `response.usage` 被原地丢掉

`summarize()` 拿到响应之后只留了 `provider` 与 `model`, `usage` 整个扔了. 于是这次
调用既不产出 `UsageRecordDraft`, 也就不进 `events.jsonl` 的 `USAGE_RECORDED`, 更不进
终端与页面的本轮合计.

**量级不是零头.** 压缩调用的 input 大致等于被它压掉的那段历史 —— 一次把 40k 上下文
压到 6k 的操作, 自己就要烧掉 38k 左右的 input token. 一轮里发生一次压缩, 合计少报的
可能比报出来的还多.

### 2. 压缩这件事在运行事件流里根本不存在

`AgentRunEventKind` 里没有任何压缩相关的值, `_fit_context` 一条 `self._publish` 都
没有. 用户在界面上看到的是"卡了几秒", 而实际发生的是一次额外的模型调用把一段历史
换掉了. 它只落在 `events.jsonl` 里, 那是事后审计用的, 不是现场看的.

### 3. 两个方向相反的 token 数

`CompactionDraft` 里**已经有** `tokens_before` / `tokens_after` / `tokens_saved`, 但
那是「省下多少上下文」, 是 `ApproximateTokenEstimator` 对 transcript 的估算. 与「这次
压缩花了多少 token」方向正好相反. 展示层顺手拿它当用量, 就会把一笔支出显示成节省.

### 4. 空摘要的花费被提前返回吞掉

`AgentTurnService.compact()` 里 `if not result.drafts: return 0` 排在记账之前. 模型
回了一段空白照样计费, 而这恰恰是最该被看见的一种浪费.

## 决策

### 决策 1: 压缩的用量走与模型调用完全相同的那条路

`summarize()` 接一个可选的 `UsageMeter`, 产出 `UsageRecordDraft`;
`ContextFitResult` 带上 `usage_drafts`; 循环把它并进已有的 `_usage_drafts`;
`AgentTurnService` 照原有的 `for draft in outcome.usage_drafts` 落盘.

**不另开一条路**是这条决策的全部内容. 另开一条就意味着 `AgentTurnService` 要认识
"还有另一种 usage", 而它已经有一条了 —— 两条路迟早有一条漏掉某个字段.

`UsageMeter` 注入在 `ContextManager` 上而不是各调用方自己算: 自动压缩走 `AgentLoop`,
`/compact` 走 `AgentTurnService`, 两条路都要计量, 而只有 `ContextManager` 同时站在
这两条路上. 注入的是**与循环同一个** meter —— 各建一个迟早会出现两套单价.

### 决策 2: `ModelUsagePayload` 加 `origin`, 合计含压缩但标出来

合计必须含: 这是这一轮真实烧掉的 token, 不算进来就对不上账单.

标出来也必须: `模型 N 次` 数的是 `MODEL_STARTED` 事件, 而压缩不发那个事件. 混进去
不加标记的话, 用户看到的是"2 次模型调用烧了 48.9k", 拿去核账单会发现一次对不上的
调用. 终端写成 `用量(压缩)` 与 `48.9k tokens (含压缩 38.8k)`, 页面单列一格"压缩".

`origin` 取 `RequestOrigin` 的值, 不另造一个布尔标记: 用途本来就是封闭枚举, 而且
将来的 `title` / `review` 之类内部调用会走同一条判断.

### 决策 3: 新增 `CONTEXT_COMPACTED` 运行事件, 它只讲省下多少

payload 记级别, 压缩前后与省下的估算 token, 顶替了几条消息 / 改写了几段工具输出.

**不把花费也塞进这个 payload.** 花费走 `MODEL_USAGE`, 因为合计的加法只认那一种事件 ——
塞两处就要么重复计数, 要么让展示层去判断该信哪一个. 两条事件相邻发出, 界面上就是
"省下 34.8k / 花掉 38.8k"两行并排, 而这两个数并排才读得懂.

### 决策 4: 记账在判断压没压动之前

请求发出去了钱就花了, 与摘要好不好用无关. `summarize()` 在 `gateway.complete` 之后
立刻建草稿, 两条"没压动"的返回路径都带着它.

### 决策 5: token 数过千换 k

不足 1000 给整数, 到 1000 及以上换成一位小数的 k, 尾随的 `.0` 去掉: `999` /
`1k` / `1.2k` / `12.3k` / `156k`.

一位小数就够: 这个数字是拿来判断量级的 (这轮烧得多不多), 不是拿来对账的 —— 要对账
得看供应商账单, 而那里的口径本来就与本地估算不同. 需要精确值的地方 (页面上合计那格
的 tooltip, 处理过程那栏的悬停明细) 仍然给整数.

同一条规则两处各写一份: 终端在 `run_renderer._tokens`, 页面在 `runModel.formatTokens`.
它们跨语言, 没有共享的可能, 所以靠各自的用例钉住边界值.

### 决策 6: 不做跨轮与跨会话累计

范围只到"本轮合计"为止.

不做不是因为难: `USAGE_RECORDED` 事件从 ADR-0011 起就一直在写, 每条都带 origin 与
四档 token 数, 数据是全的 —— 缺的只是一个读者. 不做是因为它与本 ADR 要解决的问题
无关: 这里修的是"本轮合计漏了一块", 而跨会话累计是一个新功能, 它要先回答"按什么
分组, 从哪一刻算起, 在哪儿展示"这些本 ADR 没有答案的问题.

## 备选方案

- **方案 A: 把压缩的花费塞进 `CompactionDraft` 与 `CONTEXT_COMPACTED` payload.**
  优点是一次压缩只有一条记录. 缺点是那个结构里已经有一组方向相反的 token 数 (背景 3),
  再塞一组进去, 读的人必须先分清哪个是省下的哪个是花掉的 —— 而这正是最容易读错的地方.
- **方案 B: 压缩也发 `MODEL_STARTED` / `MODEL_COMPLETED`.** 优点是 `模型 N 次` 自动
  对得上. 缺点是那两个事件驱动终端活动区的"正在思考"与时间线上的模型步骤, 而压缩不是
  模型选择要做的一步; 混进去之后, 时间线上会多出一个用户没让它做的"模型调用".
- **方案 C: 只在日志里记, 不进展示.** ADR-0035 之后压缩确实已经进日志了
  (`context.summarized`). 但日志是排查时才翻的, 而"这一轮花了多少"是每一轮都要看的
  数字 —— 一个每次都要去翻日志才能算对的合计, 等于没有合计.

## 影响

**收益.** 本轮合计对得上账单. 压缩从"界面上看不见的一次卡顿"变成一条明确的记录,
省下多少与花掉多少并排可见. `/compact` 的花费第一次有了去处.

**代价.**

- 本轮合计的数字会明显变大 —— 它一直就该这么大, 之前是少报. 触发过压缩的长任务尤其
  明显.
- `ContextManager` 多一个可选协作件 (`UsageMeter`). 缺省为 None 时压缩照常跑, 只是
  不产出草稿, 与 `gateway` 缺省为 None 是同一条取舍.
- 一级降级不调模型, 所以它只发 `CONTEXT_COMPACTED`, 没有配套的用量事件. 展示层不能
  假设两者成对出现.

**约束.**

- `AgentRunEventKind` 的值进测试断言与序列化, `context_compacted` 一经加入不可随意改
  (ADR-0016 §4 的既有约束).
- 压缩用量的 `turn_id`: 自动压缩用当前轮, `/compact` 复用**上一轮**的编号 —— 手动压缩
  发生在两轮之间, 没有属于自己的 turn. 这与 `record_compaction` 一直以来的口径一致.

## 验收标准

- `ContextManager.fit` / `summarize_now` 都产出 `origin=compact` 的 `UsageRecordDraft`;
  摘要为空时同样产出.
- 循环把它并进 `usage_drafts`, 并发出 `CONTEXT_COMPACTED` 与 `MODEL_USAGE` 两条事件.
- 压缩的用量事件不会在页面时间线上变成一个只有用量, 没有开始也没有结束的"模型调用".
- 终端与页面的本轮合计含压缩, 且能单独看出压缩占了多少.
- token 显示口径的边界值 (999 / 1000 / 1234 / 156000) 两侧各有用例.
- `make ci` 通过.
