# ADR-0055: 完全仿照 Claude Code 重写权限模块

## 状态

Proposed (2026-09-15; 2026-09-16 起工作区里有一版实现, 见"影响"末段)

取代 ADR-0013 (分层 Shell 命令安全控制架构), ADR-0024 (已证明只读效果的 Shell 命令
快速放行), ADR-0027 (单一安全事实链与执行前状态复核), ADR-0046 (accept_edits 按调用
触达的事实裁决), ADR-0052 (Full Access 启动期声明与 Manual 档). 修订 ADR-0030: 围栏
保留, 作为 Claude Code 的 sandbox 使用; 围栏之上的"能力预算"删除. ADR-0043 (人机提示
通道) 不变. 与 ADR-0054 一起生效.

## 日期

2026-09-15

## 背景

借鉴对象与"完全仿照"的口径同 ADR-0054. 路径相对 `claude-code-analysis/src/`.

### 本仓库现状与要删掉的东西

本仓库的权限模块建在 `ToolPlan` 上: 分析器按能力分派 (`security/analyzers/`), 产出
`AnalysisFindings`, `PolicyEngine` 按 Hard Deny > Mandatory Ask > 围栏预算 > Ask >
Allow 裁决, 签发 `ExecutionAuthorization`; 学习规则绑可执行文件身份与 `plan_hash`;
模式是"隔离档 x 审批档"两轴 (`core/mode.py` `SessionMode`), 围栏按模式编译.

随 ADR-0054 删掉 `ToolPlan` 之后, 这一套没有输入了. 删除: `security/analyzers/`,
`security/shell/` 里为分析服务的 `command_plan.py` / `effects.py` / `wrappers.py`
(解析器 `parser.py` / `tokens.py` / `posix.py` / `powershell.py` 保留, 给 Bash 的
`bash_permissions.py` 当 AST 用), `policy_engine.py`, `budget.py`, `findings.py`,
`decision.py`, `context.py`, `vocabulary.py`, `rules.py`, `learned_rules.py`,
`authorization_service.py`, `approval.py` (`ApprovalView` / `ApprovalBinding`),
`executable_identity.py`, `executable_resolver.py`, `scripts.py`, `hard_deny.py`,
`protected_paths.py` / `protected_paths_builder.py` (内容变成决策 2 的 policy 规则),
`workspace_grants.py` (变成 `additional_working_directories`), `core/mode.py` 的
`SessionMode` / `SandboxLevel` / `ApprovalPolicy`.

## 决策

### 1. 模式: 与 Claude Code 同一组, 同一个循环, 同一道 bypass 门

```python
class PermissionMode(Enum):
    DEFAULT = "default"                      # 规则说了算, 其余问
    PLAN = "plan"                            # 裁决与 default 同; 系统提示词要求只出方案, 出 plan 时回 pre_plan_mode
    ACCEPT_EDITS = "accept_edits"            # 工作目录内的写自动放行
    BYPASS_PERMISSIONS = "bypass_permissions"  # 除 deny / 内容级 ask / 安全检查外全部放行
    DONT_ASK = "dont_ask"                    # ask 一律成 deny (无人值守)
```

对照现在的预设: `manual` -> `default` (Claude Code 的 default 不问工作目录内的读, 本仓库
照它), `plan` -> `plan`, `accept_edits` -> `accept_edits`, `full_access` ->
`bypass_permissions`, `auto` -> 没有对应的模式: 它的语义 ("围栏内自动") 变成沙箱设置
`sandbox.auto_allow_bash_if_sandboxed` (决策 7), 与模式正交. (ADR-0058 之后 `auto` 是第六档的名字: 分类器
模式, 与旧预设同名不同义.)

- Tab 循环 `get_next_permission_mode`: default -> accept_edits -> plan -> (bypass, 若可用)
  -> default. `/mode <name>` 直接切.
- `bypass_permissions` 的可用性是启动期事实: `forge --allow-full-access` 且一次性确认
  (ADR-0052 的 `full_access_consent.py` 保留, 改名 `bypass_consent.py`), 且设置里
  `permissions.disable_bypass_permissions_mode` 不是 `"disable"`
  (`bypassPermissionsKillswitch.ts`). 三者任一不满足, 菜单里没有这一档.
- `pre_plan_mode`: 进 plan 时记下来时的模式, 出 plan 恢复. 计划评审的"同意并执行"
  (ADR-0023 / ADR-0038) 从"升到 auto"改成"回到 `pre_plan_mode`, 没有就 `accept_edits`".
- `dont_ask` 只给无人值守的入口 (`forge run --print`); 交互会话切不到它.

### 2. 上下文与规则来源: `ToolPermissionContext`, 五个来源

```python
@dataclass(frozen=True)
class ToolPermissionContext:
    mode: PermissionMode
    additional_working_directories: Mapping[str, AdditionalWorkingDirectory]  # 路径 -> (路径, 来源)
    always_allow_rules: Mapping[PermissionRuleSource, tuple[str, ...]]        # 规则原文按来源分组
    always_deny_rules: Mapping[PermissionRuleSource, tuple[str, ...]]
    always_ask_rules: Mapping[PermissionRuleSource, tuple[str, ...]]
    is_bypass_permissions_mode_available: bool
    should_avoid_permission_prompts: bool = False     # 无界面: ask 直接成 deny
    pre_plan_mode: PermissionMode | None = None

class PermissionRuleSource(Enum):
    USER_SETTINGS = "user_settings"        # ~/.forge/config.json
    PROJECT_SETTINGS = "project_settings"  # ~/.forge/projects/<id>/forge.json
    POLICY_SETTINGS = "policy_settings"    # 代码里内置, 不可被其他来源覆盖 (差异表)
    CLI_ARG = "cli_arg"                    # --allowed-tools / --disallowed-tools
    SESSION = "session"                    # 审批时选"本会话", 只在内存
```

设置文件的形状与 Claude Code 的 `settings.json` 同:

```json
{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Read(~/notes/**)"],
    "deny":  ["Bash(curl:*)", "Read(./.env)"],
    "ask":   ["Bash(git push:*)"],
    "additionalDirectories": ["../shared"],
    "defaultMode": "accept_edits",
    "disableBypassPermissionsMode": "disable"
  }
}
```

`security/permission_setup.py::get_initial_permission_context()` 按 Claude Code 的
`permissionSetup.ts` 装: 五个来源的三张表合并 (不去重, 每条记来源), `defaultMode`
(命令行 `--permission-mode` 优先), `additionalDirectories` 展开成绝对路径.
`security/permission_update.py::apply_permission_update(update, context)` 施加
`PermissionUpdate` (`add_rules` / `replace_rules` / `remove_rules` / `set_mode` /
`add_directories` / `remove_directories`), 目标是 `user_settings` / `project_settings`
/ `session`; 前两者写回文件, 后者只改内存.

`/permissions` (取代 `/rules`) 列出三张表, 按来源分组, 可以删 `session` /
`project_settings` / `user_settings` 的规则 (`deletePermissionRule` 的语义);
`policy_settings` 只读. `shadowed_rule_detection.py`: 加载时发现 allow 规则被同工具的
deny 规则整个盖住, 记一条 warning.

### 3. 规则写法与匹配

`security/permission_rule_parser.py`: `"Bash(git commit:*)"` <->
`PermissionRuleValue(tool_name="Bash", rule_content="git commit:*")`; 括号里可以转义;
没有括号就是整工具. 工具名认 `aliases` (`file_read(...)` 解析成 `Read(...)`,
`legacy` 名字表就是 ADR-0054 决策 2 的别名表).

内容怎么比由**工具**决定 (`tool.prepare_permission_matcher`), 通用部分:

| 工具 | 内容 | 匹配 (`shell_rule_matching.py` / `filesystem.py`) |
|---|---|---|
| `Bash` | `npm test` 精确 | 子命令去掉包装器 (`env`, `timeout`, `nice`) 与前置赋值后, 整串相等 |
| `Bash` | `git commit:*` 前缀 | 子命令等于前缀, 或以 `前缀 + 空格` 开头 |
| `Bash` | `git *`, `npm run *:*` 通配 | `*` 匹配任意字符, `\*` 字面星号 |
| `Read` / `Edit` / `Write` / `Glob` / `Grep` / `LSP` | 路径 glob | `//x` 绝对; `~/x` 家目录; `/x` 相对该规则来源的根 (project 是项目目录, user 是家目录, session / cli 是启动时的 cwd); `x` 或 `./x` 相对当前 cwd; `**` 跨目录. 原路径与 realpath 都比 |
| 其余 | 无 | 只有整工具一档 |

`Edit` 的规则同时管 `Write`, `NotebookEdit` 一类写工具 (Claude Code 的 `'edit'`
操作类型); `Read` 的规则管全部读工具 (`'read'`). 复合命令: 任一子命令命中 deny 即
deny, 任一命中 ask 即 ask, 全部命中 allow 才 allow (`bashPermissions.ts:2369`).

### 4. 裁决顺序: `has_permissions_to_use_tool`, 与 `permissions.ts` 逐行对应

`security/permissions.py`:

```python
def has_permissions_to_use_tool(tool, input, context, parent_message, tool_use_id) -> PermissionDecision:
    result = _inner(tool, input, context)
    if result.behavior == "allow":
        return result
    if result.behavior == "ask" and context.permission.mode is DONT_ASK:
        return PermissionDeny(reason=ModeReason(DONT_ASK), message=DONT_ASK_REJECT_MESSAGE(tool.name))
    if result.behavior == "ask" and context.permission.should_avoid_permission_prompts:
        return PermissionDeny(reason=OtherReason("permission prompts are not available"), ...)
    return result
```

`_inner` (`hasPermissionsToUseToolInner`):

| # | 判据 | 结果 |
|---|---|---|
| 1a | 整工具 deny 规则 (`get_deny_rule_for_tool`) | deny, `RuleReason` |
| 1b | 整工具 ask 规则; 例外: `Bash` 且沙箱内自动放行开着且这条命令会进沙箱 -> 交给 1c | ask, `RuleReason` |
| 1c | `tool.check_permissions(parsed_input, context)`; 抛异常按 passthrough | |
| 1d | 工具说 deny | deny |
| 1e | `tool.requires_user_interaction()` 且工具说 ask | ask (bypass 也问) |
| 1f | 工具说 ask 且理由是内容级 ask 规则 | ask (bypass 也问) |
| 1g | 工具说 ask 且理由是 `SafetyCheckReason` | ask (bypass 也问) |
| 2a | 模式是 `bypass_permissions`, 或 `plan` 且 bypass 可用 | allow, `ModeReason`, 入参取工具给的 `updated_input` |
| 2b | 整工具 allow 规则 (`tool_always_allowed_rule`) | allow, `RuleReason` |
| 3 | passthrough -> ask; 工具给的 ask 原样 | ask, 带工具给的 `suggestions` |

`PermissionDecisionReason` 的六种: `RuleReason(rule)`, `ModeReason(mode)`,
`SubcommandResultsReason(mapping)`, `HookReason(name, reason)`, `SafetyCheckReason(reason)`,
`WorkingDirReason(reason)`, `SandboxOverrideReason(kind)`, `OtherReason(reason)`.
`PermissionAsk` 带 `message`, `suggestions: tuple[PermissionUpdate, ...]`, `blocked_path`;
`PermissionAllow` 带 `updated_input`, `user_modified`; `PermissionDeny` 带 `message`.

ask 的去向: `can_use_tool` 的实现 (`security/interactive.py`, 对应
`useCanUseTool` 那条路) 经 `HumanPromptService` 摆卡片 (ADR-0043), 卡片上是工具的
`user_facing_name`, 入参展示 (Edit 是 diff, Bash 是命令加 `get_destructive_command_warning`
的提醒), 以及 `suggestions` 逐项变成的按钮: "Yes", "Yes, and don't ask again for
`<rule>` in this project" (`add_rules` -> `project_settings`), "add `<dir>` as a working
directory", "switch to accept_edits"; "No, and tell Claude what to do differently" 带
一句话回给模型. 用户改了入参 (Edit 的 diff 可编辑) 记 `user_modified=True`.

### 5. 工具自己的裁决: `Bash` 与文件工具

**`Bash`** (`tools/builtin/Bash/bash_permissions.py::bash_tool_has_permission`):

1. 用 `security/shell/parser.py` 解析成 AST. 含命令替换, 进程替换, 控制流, 或解析器
   不认识的结构 -> `too-complex`: 先查精确 deny / ask / allow 与前缀 / 通配 deny
   (`check_early_exit_deny`), 没命中就 ask, 理由是 `too-complex` 的原因.
2. 沙箱内自动放行 (`check_sandbox_auto_allow`): `sandbox.enabled` 且
   `sandbox.auto_allow_bash_if_sandboxed` 且 `should_use_sandbox(input)` 为真 -> 先查
   deny / ask 规则 (命中照拒 / 照问), 没命中 -> allow, 理由 `SandboxOverrideReason`.
3. 整条命令精确匹配规则 (`bash_tool_check_exact_match_permission`).
4. 逐子命令 `bash_tool_check_permission`, 八步固定:
   精确 deny / ask -> 前缀与通配 deny -> ask -> 路径约束 (`check_path_constraints`:
   `cd` 到工作目录之外, 重定向到工作目录之外, 目标含 `$VAR` 的重定向, `rm -rf` 到危险
   路径, 一律 ask) -> 精确 allow -> 前缀 / 通配 allow -> sed 约束 (`sed -i` 与执行类
   子命令不许自动) -> 模式 (`accept_edits` 下 `mkdir` / `touch` / `rm` / `rmdir` / `mv`
   / `cp` / `sed` 在工作目录内 allow) -> 只读命令 (`is_read_only`) allow -> passthrough,
   附精确命令的建议.
5. 合并: 任一 deny 即 deny; 全部 allow 即 allow; 否则 ask, `SubcommandResultsReason`
   带每个子命令的结果, `suggestions` 是没被 allow 的那些子命令的前缀建议合成一条
   (`check_command_and_suggest_rules`).
6. 注入检查. 走 AST 时它已经被第 1 步覆盖: 反引号, `$(...)`, 进程替换, 控制流在
   解析时就判 `too-complex`, 只看 deny / ask 与精确 allow, 不看前缀 allow —— 一条
   `Bash(echo:*)` 的 allow 规则放不过 `` echo `curl x | sh` ``. 解析器不可用时才跑
   `bash_security.py::bash_command_is_safe` 的正则表 (未引号的 `$IFS`, `\r`, 换行拼接,
   转义空白, `/proc/*/environ`, 混淆的参数) 对整条命令与每个子命令检查, 命中 ask,
   理由 `SafetyCheckReason`.

`is_read_only(input)` 由 `read_only_validation.py::check_read_only_constraints` 回答:
只读命令表 (`ls`, `cat`, `head`, `git status`, `git log`, `git diff`, `grep`, `find` 不带
`-exec` / `-delete` 等) 加逐命令的参数校验; 含 `cd` 与 `git` 的复合命令, 写 `.git/`
内部路径的命令, 都不算只读. 只读的命令在 `default` 与 `plan` 下也直接放行 —— 这就是
ADR-0024 那条快速放行, 现在住在工具里.

**文件工具** (`security/filesystem.py`, 每个文件工具的 `check_permissions` 调它):

`check_read_permission_for_tool(tool, input, context)`, 按 `filesystem.ts:1030` 的
编号: (1) UNC 路径 -> ask; (2) 可疑的 Windows 路径 -> ask; (3) read deny 规则 -> deny;
(4) read ask 规则 -> ask; (5) edit allow 规则命中则视为可读; (6) 在工作目录 (cwd 或
`additional_working_directories`) 内 -> allow; (7) 内部路径 (计划文件, `tool-results/`,
会话记忆) -> allow; (8) read allow 规则 -> allow; (12) 其余 ask, 建议 `add_directories`.

`check_write_permission_for_tool(tool, input, context)`, 按 `filesystem.ts:1205`:
(1) edit deny 规则 -> deny; (1.5) 内部可写路径 (计划文件, scratchpad) -> allow;
(1.6) `~/.forge/**` 只认 `session` 来源的 allow 规则; (1.7) 安全检查
(`check_path_safety_for_auto_edit`: `.git` / `.vscode` / `.idea` / `.forge` 目录, shell
配置文件 `.bashrc` / `.zshrc` / `.profile` 等, UNC 路径) -> ask, `SafetyCheckReason`,
bypass 也问; (2) edit ask 规则 -> ask; (3) `accept_edits` 且在工作目录内 -> allow;
(4) edit allow 规则 -> allow; (5) 其余 ask, 建议: `default` / `plan` 下 `set_mode
accept_edits`, 目标在工作目录外时 `add_directories`.

`Glob` / `Grep` / `LSP` 对 `path` / `filePath` 调读检查; `TodoWrite`, `AskUserQuestion`
与本仓库自有工具用缺省 allow.

### 6. 建议与"始终允许"

ask 决定的 `suggestions` 是 `PermissionUpdate` 列表, 由工具的 `check_permissions` 算
(`suggestion_for_exact_command`, `suggestion_for_prefix`, `generate_suggestions`):

- `Bash`: 子命令有第二个词的给 `Bash(<argv0> <argv1>:*)` 前缀 (`git commit:*`), 否则
  精确命令; 复合命令合成一条含多个规则的 `add_rules`. 没有危险前缀过滤 —— Claude Code
  只在进 auto 时剥 (差异表).
- 文件工具: 读在工作目录外 -> `add_directories`; 写 -> `set_mode accept_edits`
  (只在 `default` / `plan` 下), 工作目录外再加 `add_directories`.

用户选"don't ask again" 时 `apply_permission_update` 写到 `project_settings`
(Claude Code 写 `localSettings`; 本仓库没有仓库内的本地设置文件, 项目设置本来就在
`~/.forge/projects/<id>/`). 没有学习规则的哈希绑定: 规则就是一行文字, 下次同前缀的
命令直接命中. 规则文件在 `~/.forge` 之下, 模型写不了 (决策 5 的 1.6).

### 7. 沙箱: 围栏保留, 按 Claude Code 的 sandbox 设置驱动

ADR-0030 的 `FencePolicy` 与 `CommandExecutor` 就是 Claude Code `utils/sandbox/` 的
对应物 (Seatbelt / bubblewrap), 保留. 变的是它从哪来: 不再按模式编译, 改由设置
`sandbox` 段驱动, 键与 Claude Code 同:

```json
{"sandbox": {"enabled": true, "autoAllowBashIfSandboxed": true,
             "excludedCommands": ["docker *"], "network": {"allowUnixSockets": [], "allowLocalBinding": false},
             "allowUnsandboxedCommands": false}}
```

- `enabled` 且 `should_use_sandbox(input)` 才进围栏: `dangerously_disable_sandbox`
  且 `allowUnsandboxedCommands` 为真, 或命令含 `excludedCommands`, 不进.
- `autoAllowBashIfSandboxed` 是决策 5 第 2 步的开关. 现在的 `auto` 预设就是它.
- 围栏的写白名单 = cwd + `additional_working_directories` + 沙箱设置里的
  `filesystem.allowWrite`; 反过来, 沙箱允许写的路径在路径裁决里也算可写
  (`pathValidation.ts::isPathInSandboxWriteAllowlist`).
- `~/.forge` 与设置文件被强制加进 `denyWrite` (Claude Code 对 `.claude/settings.json`
  的做法).
- 围栏立没立起来 (`confined`) 只影响 `should_use_sandbox`: 没立起来就等于
  `enabled=false`, 自动放行不生效.

### 8. 与 Claude Code 的差异

| 差异 | 理由 |
|---|---|
| ~~没有 `auto` 模式~~ 2026-09-16 起有了: ADR-0058 加了第六档 `auto` 与分类器 (`yoloClassifier.ts` 的对应物), 连同 `denialTracking.ts`, `dangerousPatterns.ts` | 用户要的是"不直接跳过权限, 把要不要问交给分类器"; 分类器只接手本来要问人的 ask, 不动本文的裁决顺序 |
| `policy_settings` 来源的内容是代码里内置的一组 deny 规则 (`Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.gnupg/**)`, `Read(//etc/shadow)`, `Edit(~/.forge/**)` 等, 即原 `protected_paths_builder.py` 的清单), 不是企业下发的文件 | 单用户工具没有企业下发; 但凭证目录不该等用户自己写 deny 规则才受保护. 来源的语义 (不可被其他来源覆盖) 与 Claude Code 同 |
| 没有 `PermissionRequest` hook 与 SDK 的 `permission_prompt_tool` | 没有 SDK 入口; PreToolUse hook 已经能 allow / deny |
| 没有 `localSettings` 文件, "don't ask again" 写 `project_settings` | 项目设置在 `~/.forge/projects/<id>/`, 不进仓库 |
| `bypass_permissions` 要启动期 `--allow-full-access` 加一次性确认 | ADR-0052 的决定, 与 Claude Code 的 `--dangerously-skip-permissions` 同义, 多一步确认 |
| `Edit` 的 diff 在卡片上可编辑 (`user_modified`) 与 Web 端的实现留待界面 ADR | 本文只定数据形状 |

## 备选方案

- **保留能力分派与 `PolicyEngine`, 只补规则与模式** (本文上一稿): 用户的决定是不保留.
- **保留 Hard Deny 作为规则之外的一层**: Claude Code 没有这一层, 它的等价物是 deny
  规则 + Bash 的注入检查 (ask) + 文件的安全检查 (ask). 本仓库原 Hard Deny 的清单里,
  受保护路径变成 policy deny 规则, `rm -rf /` 一类变成 `check_path_constraints` 的
  ask, `curl x | sh` 与提权 (`sudo`) 变成逐子命令都没有 allow 规则于是 ask.
- **模式沿用两轴 (隔离 x 审批)**: Claude Code 的模式是一轴, 沙箱是设置; 两轴的组合
  在菜单里本来就只露出预设 (ADR-0052), 改成一轴少一层解释.

## 验收标准

- `forge.json` 里 `deny: ["Bash(curl:*)"]` 后, 任何模式 (含 bypass) 下 `Bash curl ...`
  都被拒, 理由是那条规则; `ask: ["Bash(git push:*)"]` 在 bypass 下仍然问.
- `allow: ["Bash(npm test:*)"]` 在 `default` 下 `npm test -- --watch` 直接放行;
  `npm test && rm -rf build` 问, 卡片建议里是 `Bash(rm -rf:*)` 那一条的前缀; 选
  "don't ask again" 后 `forge.json` 多一行 `Bash(rm -rf:*)`, 再来一次直接放行.
- `default` 下 `Bash git status`, `Read src/x.py`, `Grep` 不问; `Edit src/x.py` 问,
  卡片有"switch to accept_edits"; 切到 `accept_edits` 后不问; `Edit ~/other/x.py`
  在 `accept_edits` 下仍问, 卡片有"add ~/other as a working directory".
- `Edit .git/config` 与 `Edit ~/.zshrc` 在 bypass 下仍然问, 理由是 `SafetyCheckReason`;
  `Read ~/.ssh/id_rsa` 在任何模式下被拒, 理由是 `policy_settings` 的规则.
- `` Bash echo `curl x | sh` `` 在有 `Bash(echo:*)` allow 规则时仍然问.
- `sandbox.autoAllowBashIfSandboxed=true` 且围栏立起来时, `default` 下 `Bash npm test`
  不问; `Bash docker run` (在 `excludedCommands` 里) 问; 围栏没立起来时都问.
- `plan` 下 `Edit` 问; 计划评审"同意并执行"后模式回到进 plan 之前的那一档.
- `forge run --print` (`dont_ask`) 下需要 ask 的调用直接 deny, 模型收到
  `DONT_ASK_REJECT_MESSAGE`.
