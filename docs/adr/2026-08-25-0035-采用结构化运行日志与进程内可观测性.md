# ADR-0035: 采用结构化运行日志与进程内可观测性

## 状态

Proposed

## 日期

2026-08-25

## 背景

到 ADR-0034 为止, Forge 已经有相当完整的**对外**记录: 会话事件 (`events.jsonl`),
工具审计, 恢复点, 运行事件流 (ADR-0016), usage 计量. 但它们都是产品语义的记录 ——
给用户看, 给 `/resume` 重建历史, 给恢复层还原工作区.

对开发者来说, 这套记录有四个够不着的地方.

### 1. 进程里一行日志都没有

`grep -rn "getLogger" src/` 的结果是零. 整个 `src/forgecli` 没有任何一个 logger.
排查一次异常行为只有三条路: 加 print, 读事件日志, 或者上 debugger. 前者要改代码
再改回来, 中间那条只有产品语义的事实, 最后一条对"跑了二十步之后才出问题"无能为力.

### 2. 事件流记的是"发生了什么", 不是"为什么"

`AgentRunEvent` 是给终端渲染用的, 字段刻意收窄: `ToolQueuedPayload.arguments` 经过
`scrub_arguments` 脱敏 (免得一屏 base64 把过程刷没), `ModelCompletedPayload` 只有
`text_chars` 而没有正文. 这些取舍对屏幕是对的, 对排查是不够的 —— "模型为什么这么
理解这个文件"要看它实际收到的那段内容, 而那段内容在任何现有记录里都不存在.

### 3. 异常在几个边界上被吃掉

有三处把异常归一成了一个状态值, 而 traceback 随之消失:

- `ToolRuntime.execute` 把工具异常归一为 `ToolResult(status=TOOL_ERROR)`;
- `ProjectRuntime._execute_turn` (Web 后台线程) 把异常压成 `TurnRun(status="failed")`;
- `AgentTurnService._obtain_outcome` 把异常写进 `diagnostic` 字段 —— 这一处还留着
  完整 traceback, 但要去翻 `events.jsonl` 才看得到.

后台线程那一处最糟: 页面上只有一行错误文案, 终端上什么都没有.

### 4. 已有的指标没人读

`InProcessGatewayMetrics` (ADR-0012 §9) 已经在按 provider/model 聚合调用数, 错误
分类, 延迟分桶与 cache 命中, 装配也接上了. 但 `snapshot()` 至今没有任何一个消费方 ——
它的注释写着"展示接入属调用方切片", 而那个切片一直没做. 于是"一轮跑了 40 秒, 时间
花在哪"没有任何读数可查.

配置面同样有一个悬空的东西: `config_keys.SCHEMA` 里的 `logging.level` 自 ADR-0005
就在, 但 `EffectiveConfig` 不收它, 也没有任何代码读它.

## 决策

### 决策 1: 在关键位置写日志, 事件名是被测试钉住的

日志覆盖一次请求从进程启动到子进程退出的完整链路. 事件名用 `域.动作` 形式, 由
`tests/observability/test_runtime_trace.py` 断言 —— 改名等于让所有按事件名写的
grep 失效, 所以它是需要一次显式修改的.

| 位置 | 事件 |
|---|---|
| 进程入口 | `forge.start` `forge.stop` `forge.refused` `project.resolved` `runtime.ready` |
| 一轮对话 | `turn.received` `turn.ok` / `turn.error` `turn.answer` `turn.driver_failed` |
| 提示词 | `prompt.compiled` `prompt.text` (debug) |
| 循环 | `loop.start` `loop.stop` 与四道闸 (`loop.repeat_call_rejected` `loop.blocked_call` `loop.barren_streak` `loop.tools_closed`) |
| 模型 | `model.request` `model.response` `model.failed` `model.malformed_tool_call` |
| 网关 | `llm.complete` `llm.stream` `llm.completed` `llm.failed` `llm.cache_hit` `llm.rate_limited` `llm.auth_failed` `llm.transport_retry` `llm.context_overflow` |
| HTTP | `http.request` `http.response` `http.error` `http.timeout` `http.stream.*` |
| 工具管线 | `pipeline.start` `pipeline.prepared` `pipeline.decision` `pipeline.denied` `pipeline.rejected` |
| 审批 | `approval.requested` `approval.wait.*` `approval.resolved` `approval.binding_changed` `approval.rule_learned` |
| 执行 | `tool.execute.*` `tool.exception` `tool.failed` `tool.output` (debug) |
| 子进程 | `shell.spawn` `shell.exited` `shell.spawn_failed` `shell.output` (debug) |
| 上下文 | `context.compaction_needed` `context.downgraded` `context.summarized` `context.over_allowance` |
| 记忆 | `memory.written` `memory.rejected` `memory.forgotten` |
| 会话 | `session.event` (debug) `session.write_failed` |
| 人工 Shell | `manual_shell.enter` `manual_shell.launch` `manual_shell.exit` |
| Web | `web.request` `web.denied` `web.turn.started` `web.turn.failed` |

背景第 3 条的三处吞异常, 各补一条带完整 traceback 的记录: `tool.exception`,
`web.turn.failed`, `turn.driver_failed`. 另有两个 `excepthook` (主线程与线程) 接住
彻底没人处理的异常.

### 决策 2: 一条记录一行, `事件名 键=值`, 运行上下文自动注入

`Log.info("shell.exited", argv=[...], exit_code=1)` 渲染成:

```text
2026-08-25T15:04:03.128 INFO  infrastructure.execution.local_command_executor \
  [MainThread] shell.exited session=sess_a1 turn=turn_0007 step=4 inv=inv_9c2 \
  tool=shell.run argv=["bash","-lc","pytest -q"] exit_code=1 duration_seconds=12.310
```

三条约束:

- **一条记录一行.** 含换行的值 (文件内容, stderr, 模型回复) 走 `json.dumps` 转义.
  跨行的记录 `grep` 出来永远是半截.
- **上下文自动带上.** `session / turn / step / req / inv / tool` 由 `RunContext`
  (contextvars) 挂在当前执行流上, 调用点不为了写日志在方法签名上多带参数. 选
  contextvars 而不是 threading.local: Web 的 turn 跑在后台线程, SSE 推送跑在 asyncio
  任务, 后者 threading.local 做不到隔离.
- **同名时调用点的值赢, 且只出现一次.** 否则工具链路会打出 `tool=x tool=x`.

`Log.span(...)` 给一段执行计时, 产出 `event.start` / `event.ok` / `event.error`,
收尾行带 `elapsed_ms`, 同时把耗时记进决策 5 的指标.

级别的分工是固定的: **INFO 是一次运行的骨架** (启动, turn 起止, 模型调用, 工具裁决
与执行结果), **DEBUG 是正文** (整段提示词, 模型回复原文, 工具输出, HTTP payload,
transcript 全文), WARNING 是"能继续但结果可能不对"(重试, 降级, 截断, 预算闸),
ERROR 是"这一步失败了". 正文一律走 DEBUG: 它们每条几千字, 放进 INFO 会把文件淹掉.

写之前先 `isEnabledFor`: 级别没开时一个字符串都不构造.

### 决策 3: 默认只写文件, 一次运行一个文件

写在 `~/.forge/logs/forge-<时间戳>-<pid>.log`, 另有 `forge-latest.log` 符号链接指向
本次运行 (供 `tail -f`), 保留最近 20 个文件.

- **不写终端.** CLI 的 REPL 与 Rich Live 区独占终端 (ADR-0016 §8.1), 往 stderr 打
  日志会把正在渲染的活动区戳花. 配置项 `logging.console` 可以打开.
- **一次运行一个文件, 而不是按大小切分的共享文件.** `~/.forge` 跨项目共享, 而
  `forge.lock` 只锁到项目一级 —— 两个项目同时跑时, 共用文件的切分会互相截断.
- **写不了日志不阻止启动.** 建目录或开文件失败时退回"没有文件 handler", 打一行到
  stderr 就继续.

级别取 `logging.level` 配置 (`debug` / `info` / `warn`, 默认 `info`), 收进
`EffectiveConfig` 并挂进 `/config` 菜单与 Web 设置页: 一个只能靠改配置文件才能打开的
debug 开关, 等于要求用户在最需要日志的那一刻先去找那个文件.

**2026-08-28 修订: 运行期开关全部改为配置项.**

原方案把 `FORGE_LOG_LEVEL` `FORGE_LOG_CONSOLE` `FORGE_LOG_DIR` `FORGE_LOG_MAX_VALUE`
`FORGE_LOG_HTTP` 定为"运行期开关, 不进配置文件", 理由是"临时开一次 debug 跑一遍不该
要求先改配置文件再改回来".

这条理由站不住: 环境变量**在设置面板里看不见, 也改不了**. 用户要打开一次 debug 日志,
得先知道有这么个变量名, 再在启动命令前面拼上去 —— 而 Forge 的入口是一个 Web 控制面.
更糟的是 `FORGE_LOG_LEVEL` 压在配置项上, 于是"面板显示 info, 实际按 debug 在写"这种
状态没有任何界面能解释.

现在它们各是一条 `logging.*` 配置项 (见 domain/config/config_keys.py), 在 `/config`
的"常规配置"与 Web 设置页里各占一行. `shared/observability/configure` 不再读环境变量,
改由 `interfaces/runtime/logging_wiring` 读配置后传参 —— 那也更符合分层: 一个住在
shared 的模块本来就不该知道 Forge 主目录在哪。

### 决策 4: 日志不脱敏, 唯一例外是凭证的值

工具入参, 子进程 argv 与环境变量, 模型请求与回复原文, HTTP payload 与错误体全部
原样写. 它与终端脱敏 (`scrub_arguments`) 不冲突: 屏幕上要防的是刷屏, 日志里要的是
"它到底收到了什么". 信任假设与会话事件, 恢复快照同级 —— 都在本机 `~/.forge` 下.

唯一的例外是 API key 的**值**. 日志记它的引用名与 sha256 前 8 位
(`credential=OPENAI_API_KEY credential_fingerprint=3f9a1c04`): 排查"用的是哪一把 key"
要的是身份而不是那串字符, 而日志文件是最容易被整份贴进 issue 的东西. 指纹取哈希前缀
而不是"头 4 位 + 尾 4 位", 后者泄漏真实字符.

单个值默认截断到 4000 字符并标出丢掉多少 (`...(+82 chars)`); 配置项
`logging.max_value_chars` 填 `0` 关掉截断 (留空表示用内置上限). 这是"够看清一次调用"
与"一行不至于把编辑器拖死"之间的取舍, 不是脱敏.

### 决策 5: 进程内指标, 纯内存, 无采样

**2026-08-28 修订: 采集由 `telemetry.enabled` 控制, 默认关闭.**

原方案让 `METRICS` 无条件采集, 而配置项 `telemetry.enabled` 从提出到现在**没有任何
消费者** —— 打开或关掉它, agent 的行为一模一样. 一个改了不生效的开关比没有这个开关更糟:
用户以为自己关掉了度量.

现在 `Metrics` 可以整体关掉, 关掉时 `count` / `observe` 是空操作 (不是"照记但不展示":
记录点遍布工具流水线与每次模型调用, 不想被度量的用户不该还为此付内存和锁), 并清空已经
攒下的读数. `/diagnostics` 单独报一行采集状态, 否则"没有阶段耗时"会被读成"这次运行什么
都没干"。

`METRICS.count(name, **labels)` 与 `METRICS.observe(name, ms, **labels)` 聚合成
`名字{标签}` 的计数器与耗时序列 (count / total / avg / min / p50 / p95 / max, 分位数
取最近 1024 个样本). `Log.span` 自动记, 也可以手动记.

刻意不做采样, 不做导出: Forge 是本机单进程 CLI, 没有需要抽样的量级, 也没有可以推送
指标的服务端. 想看就现场 dump, 进程退出即丢弃.

与 `InProcessGatewayMetrics` 并存而不是合并: 那份是冻结字段的网关调用样本
(ADR-0012 §9), 这份是任意阶段都能记的通用计数. 两份都进决策 6 的读模型.

### 决策 6: `/diagnostics` 与 `GET /api/v1/diagnostics` 读同一个函数

`interfaces/runtime/diagnostics.py` 拼出四段: 进程 (版本 / Python / pid / 运行时长),
日志装配 (**级别与文件路径** —— 排查的第一步永远是先找到日志), 阶段耗时与计数,
模型调用读数. CLI 与 Web 各自渲染, 但数字来自同一个函数: 两个入口给出不同的数字,
排查时就得先判断该信哪一个.

`/diagnostics --reset` 清零计数与耗时 (不动日志文件): 一次会话跑了两小时之后, 累计
数字反映的是整段历史, 而想优化的往往只是刚刚那一次慢调用.

Web 接口在 session cookie 之后 —— 它会吐出日志路径与调用读数, 不能匿名可读.

### 决策 7: 住在 `shared/observability`, 任何层都能 import

日志是横切的: `domain` 之外的每一层都要写. 放进 `shared` 让它对所有层都是合法依赖,
而它自己只依赖标准库 `logging` —— `scripts/check_arch.py` 的层间方向与框架隔离两条
规则都不会被它破坏.

"写到哪个目录, 用哪个级别"是 infrastructure 的知识 (Forge home + 应用配置), 所以
装配留在 `interfaces/runtime/logging_wiring.py`, 只往 `configure_logging` 传一个目录
和一个级别字符串.

包门面 `shared/observability/__init__.py` 不转导出任何东西: `configure` 依赖 `log`,
门面再急切 import `configure` 就构成 `observability <-> configure` 的 import 环
(见 `scripts/check_arch.py` 的环检查).

## 备选方案

- **方案 A: 继续靠 `events.jsonl` 排查, 不引入日志.** 优点是不新增机制. 缺点是它
  的字段是产品语义的, 且刻意脱敏与收窄 (背景 2), 而"改一改让它多记一点"会把一份
  用户可见, `/resume` 要重放的记录变成排查草稿本 —— 两种读者的需求会持续打架.
- **方案 B: 用 structlog / loguru.** 优点是开箱有结构化输出与丰富 sink. 缺点是
  `domain` 与 `application` 至今零第三方依赖 (`check_arch.py` 的框架隔离), 而日志
  是这两层里唯一要横切每个文件的东西 —— 为它开一个第三方口子, 那条规则就名存实亡.
  标准库 `logging` 加一个 150 行的门面已经覆盖全部需求.
- **方案 C: 直接上 OpenTelemetry, 导出 trace 与 metrics.** 优点是分布式追踪与现成
  的后端生态. 缺点是本机单进程 CLI 没有 collector 可推, 装一套 SDK 只为把 span
  打进本地文件, 复杂度与收益完全不成比例. 决策 2 的 `RunContext` 已经提供了
  trace 语义里真正有用的那部分 (把一次故障顺着 id 串起来读).
- **方案 D: 把日志级别做成纯环境变量, 不进配置.** 优点是少一个配置项. 缺点是
  `logging.level` 从 ADR-0005 起就在 SCHEMA 里悬空了三个月, 保留一个永远不生效的
  配置项比删掉它更糟.

## 影响

**收益.** 一次故障可以顺着 `turn_id` / `inv_id` 从"用户说了什么"一路读到"子进程
退出码是多少", 中间每一步的完整入参与产出都在. 三处被吞掉的异常都留下 traceback.
`/diagnostics` 回答"时间花在哪". `InProcessGatewayMetrics` 从此有了消费方.

**代价.**

- 日志文件会很大. DEBUG 级别下一轮带几次工具调用的对话可以写出几 MB —— 这是决策 4
  的直接后果, 也是它的目的. 缓解手段是默认 INFO, 单值截断, 保留最近 20 个文件.
- 每个被插桩的调用点多一行代码. `isEnabledFor` 保证关掉时没有字符串构造开销, 但
  函数调用本身还在.
- 日志内容是**未脱敏**的本机文件. 贴日志给别人之前要自己看一眼 —— 凭证值不在里面,
  但工作区里的文件内容在.

**约束.**

- 事件名进了测试, 改名要一次显式修改.
- `configure_logging` 只在两个进程入口调用. 业务代码只 `get_log(__name__)` 然后写,
  不碰 handler —— 一个模块自己加 handler, 另一个模块的日志就会写两份.
- `context.update()` 没有还原点 (推进式流程没有 with 块罩得住), 靠外层 `bind` 的
  `ContextVar.reset(token)` 收口. 直接驱动 `BuiltinAgentLoop` 而不经 `AgentTurnService`
  的调用方 (目前只有测试) 要自己清, `tests/conftest.py` 已经做了.

## 验收标准

- `tests/observability/` 覆盖: 记录格式 (单行, 键值, 上下文注入, 截断, 关级别不构造
  字符串), `bind` / `update` 的作用域, 指标聚合与分位数, 装配 (文件, 级别优先级,
  重复装配不写两份, 目录写不了也能启动), 诊断读模型.
- `tests/observability/test_runtime_trace.py` 断言关键位置确实留痕: 一次带工具调用
  的 turn 至少产出 `loop.start` / `model.request` / `model.response` / `tool.requested`
  / `tool.observed`; 工具入参未脱敏; `loop.stop` 带停止原因与工作量; DEBUG 关掉时
  正文行不出现.
- `tests/web/test_diagnostics_endpoint.py` 断言 Web 与 CLI 同源, 无激活项目时不报错,
  且需要 session cookie.
- `make ci` 通过 (含 `scripts/check_arch.py` 的层间方向, 框架隔离与无环检查).
