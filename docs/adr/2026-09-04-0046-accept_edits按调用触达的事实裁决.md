# ADR-0046: accept_edits 按调用触达的事实裁决, 不按"它是不是 shell"

## 状态

Proposed

本 ADR 只改 `accept_edits` 这一档的自动放行判据. `auto` 与 `full_access` 的行为不变,
Hard Deny, Mandatory Ask, 恢复屏障与 UNCONFINED 回退全部不变.

## 日期

2026-09-04

## 背景

### 现状: accept_edits 下每一条命令都要点头, 与它做什么无关

`ApprovalPolicy.ALWAYS` 的注释写着"文件工具照常自动, Shell 必须点头". 落地是这样的:

```text
fence_for:  automatic_shell = mode.approval is not ApprovalPolicy.ALWAYS   -> accept_edits 为 False
budget:     _AUTOMATIC_SHELL = {EXECUTE_SHELL, EXECUTE_SCRIPT, NETWORK_ACCESS}
            只在 confined and fence.automatic_shell 时进放行集
分析器:      EXECUTE_SHELL 由 shell_analyzer._capabilities_of 第一行**无条件**加上
```

于是 `shell_run` 的每一次调用都带着 `EXECUTE_SHELL`, 而它在 accept_edits 下永远不在
放行集里. 实测两次会话:

| 会话 | 模式 | shell 调用 | 审批次数 |
| --- | --- | --- | --- |
| forge-20260904-110706 | `workspace_write/always` (accept_edits) | 1 | 1 |
| forge-20260904-133236 | `workspace_write/auto` (auto) | 60 | 0 |

### 分析器其实算得很准, 那份精度一直没被用上

判据不是"分析不出命令内容". 实测跑一遍 `ShellCapabilityAnalyzer`, 12 项上界收缩成:

| 命令 | 收缩后的能力 | 目标集合 |
| --- | --- | --- |
| `cat README.md` | `execute_shell, spawn_process, workspace_read` | forge_expanded |
| `cat ~/.ssh/id_rsa` | `execute_shell, spawn_process, **external_read**` | forge_expanded |
| `sed -i '' 's/a/b/' README.md` | `execute_shell, spawn_process, **workspace_write**` | forge_expanded |
| `rm -rf build` | `execute_shell, spawn_process, **workspace_delete**` | forge_expanded |
| `npm test` | `**execute_script**, execute_shell, spawn_process, workspace_read, workspace_write` | forge_expanded |
| `curl https://x.com` | `execute_shell, **network_access**, workspace_read, workspace_write` | forge_expanded |
| `cat $SOMEVAR` | `execute_shell, spawn_process` | **dynamic** |
| `echo hi > /tmp/x/a.txt` | `execute_shell, **external_write**, spawn_process` | forge_expanded |

读工作区与读凭证被区分开了, 写工作区与写工作区外被区分开了, 看不透要跑什么的
(`npm test`) 也被标了出来. **这些结论算完之后, 在 accept_edits 下全部作废** —— 因为
`EXECUTE_SHELL` 恒在, 而它一项就足以让整次调用落 ASK.

### 原判据当初是对的, 是它的前提没了

"文件工具照常自动, Shell 必须点头"是一个**代理判据**: 那时 `fs_find`, `find_definition`,
`git_read`, `fs_read`, `search_text`, `fs_apply_patch` 六个专用工具覆盖了日常动作,
`shell_run` 是"其余情况"的出口, 于是"是不是 shell"约等于"是不是我们没看清的动作".

ADR-0044 之后专用工具只剩四个, 检索, 列目录与 git 查询都回到了 `shell_run`. 代理与
被代理的东西从此不再重合: 现在最常见的一条 shell 命令是 `cat` 和 `grep`.

## 决策

### 1. accept_edits 的判据换成"这次调用触达了什么"

自动放行需要同时满足四条, 缺一即 ASK:

1. 围栏确实立起来了 (`confined`, 来自 Provider 行为自测, 不是"装了就算");
2. 这一档允许自动启动看得清的 Shell (`fence.automatic_shell`);
3. **本次的目标集合已经封闭** (`ToolPlan.target_resolution.closed`);
4. 收缩后的能力集合全部落在围栏放行集内 —— 这一条由 `capabilities_requiring_approval`
   的减法自然成立, 不需要新代码.

判据里没有工具名, 也没有命令名.

### 2. `FencePolicy.automatic_shell` 拆成两个字段

```python
automatic_shell: bool            # 已解析清楚的 Shell 命令        accept_edits 起
automatic_opaque_execution: bool # 看不透要跑什么的执行, 以及网络   auto 起
```

对应 `budget` 里的两组:

```python
_TRANSPARENT_SHELL = {EXECUTE_SHELL}
_OPAQUE_EXECUTION  = {EXECUTE_SCRIPT, NETWORK_ACCESS}
```

`EXECUTE_SCRIPT` 是分界线, 因为它恰好标的就是"Forge 看不见接下来要跑什么":
有脚本正文的, `runs_arbitrary_code` 的 (`java -jar`, `docker run`, `vim -c`), 以及
`indirectly_executes` 的 (`find -exec`, `xargs`). 这是一条**按事实**画的线, 不是按
命令名画的.

`automatic_shell` 取自隔离档 (`sandbox is not READ_ONLY`) 而不是审批档, 这是全模块唯一
一处不按"自主性来自审批档"走的地方: 它是**下界**不是自主性决定 —— read_only 档的语义
就是只看不改, 那里自动起子进程没有用例. 目录能力门本来就不给 plan 档 `shell_run`, 但
围栏策略自己也要说得通: 一道门的正确性不该靠另一道门兜着.

### 3. 目标封闭这一条只加在 accept_edits, 不加在 auto

`auto` 的语义是 ADR-0030 决策 1 的"有围栏时不必猜", 它照旧不看目标封闭度.

差别落在 `cat $SOMEVAR` 上: 它的目标推不出来, 于是分析器连 read 能力都 derive 不出,
能力集合是 `{execute_shell, spawn_process}` —— **看上去比 `cat README.md` 还干净**.
只看能力集合的话, 恰恰是这一类会溜过去. 所以"看得清才放行"必须把"目标封没封闭"也算进
判据, 否则它只是"能力集合小才放行", 而那两件事在这里正好相反.

实测代价接近零: 日志里模型真实发过的命令形状 (`cat X`, `grep -rn X src`,
`find . -maxdepth 3 | head`, `cat src/**/*.py`, `git log --oneline -5`, `sed -i`,
`mkdir -p`) 全部是 `forge_expanded`.

### 4. 三条边界不动

- **auto 与 full_access**: 行为一个字不变.
- **UNCONFINED**: 两组都在 `if confined:` 里面, 没有围栏时一律落回 ASK (ADR-0030 决策 5).
- **恢复屏障**: `RecoveryFlow.begin` 按 `plan.mutates_workspace` 触发, 与裁决结论无关.
  自动放行的写入照常先落快照 (ADR-0015).

### 5. 结果矩阵

`confined=True` 下实测:

| 命令 | accept_edits | auto | accept_edits (无围栏) |
| --- | --- | --- | --- |
| `cat README.md` | **allow** | allow | ask |
| `grep -rn foo src` | **allow** | allow | ask |
| `sed -i '' 's/a/b/' README.md` | **allow** | allow | ask |
| `mkdir -p build/x` | **allow** | allow | ask |
| `rm -rf build` | **allow** | allow | ask |
| `echo hi > out.txt` | **allow** | allow | ask |
| `cat $SOMEVAR` | ask | allow | ask |
| `cat ~/.ssh/id_rsa` | ask | ask | ask |
| `npm test` | ask | allow | ask |
| `python3 -c 'print(1)'` | ask | allow | ask |
| `find . -name '*.py' -exec rm {} +` | ask | allow | ask |
| `curl https://x.com` | ask | allow | ask |
| `echo hi > /tmp/x/a.txt` | ask | ask | ask |

accept_edits 从此是一句可以对用户讲清楚的话: **工作区里看得清的改动自动做, 越界的,
联网的, 以及我看不透要跑什么的, 问你.**

## 备选方案

- **方案 A: 让 accept_edits 与 auto 合并, 删掉一档.** 拒绝. 两档的差别在本 ADR 之后是
  实的 (上表有六行不同), 而"看不透要跑什么的要不要先问"是一个真实的产品选择.
- **方案 B: 只把 `EXECUTE_SHELL` 加进 accept_edits 的放行集, 不要目标封闭那一条.**
  拒绝. `cat $SOMEVAR` 会因为能力集合更小而被放行, 判据方向反了.
- **方案 C: 保持"是不是 shell"的判据, 改为恢复被删掉的专用文件工具.** 拒绝. 那是让
  安全判据反过来决定工具集, 而 ADR-0044 删掉那四个的理由 (它们换不来 shell 给不了的
  东西) 与安全无关.
- **方案 D: 按命令名白名单放行 (`cat`, `grep`, `ls` 自动).** 拒绝. ADR-0024 已经拒绝过
  同一条: 名字不是事实, `cat` 可以是 Agent 自己写进 PATH 的一个文件, 而
  `executable_binding` 正是为此存在.

## 影响

### 收益

- accept_edits 恢复成一档可用的模式: 日常的读, 改, 删, 建目录不再逐条打断.
- 分析器已经算出来的那份精度第一次被用上. 加一条新的能力推导, 现在会直接改变裁决结果,
  而不是被 `EXECUTE_SHELL` 盖掉.
- 判据里不再有工具名. ADR-0044 那样再删或再加工具, 不会让某一档模式的语义跟着变.

### 代价

**这是一次真实的安全边界放宽, 不是等价重构.** accept_edits 下, 一条目标封闭且只触达
工作区的命令现在直接执行, 中间没有人.

风险落在**推导的正确性**上, 而不再落在"人会看一眼"上:

- `effect_kind_of` 把一条其实会写的命令判成只读时, 写入会无人值守地发生. 边界由围栏的
  写 allowlist 兜住 (只能写工作区), 由 ADR-0015 的快照兜住 (可回滚), 但确实不再有人看.
- 目标展开漏掉一条路径时同理.

不受影响的几处要写清楚, 否则这一段会被读成比实际更宽:

- 读工作区外的路径仍然 ASK (`EXTERNAL_READ` 在 `_NEVER_AUTO`, 不在任何放行组里).
- 写工作区外仍然 ASK. 读凭证与不可逆操作仍然是 Mandatory Ask.
- Hard Deny 在这一切之前就返回了.

### 已知边界

- ADR-0030 那条"读只能 denylist, 漏一条就是凭证暴露"的风险, 在 accept_edits 下从
  "被逐条审批挡在外面"变成"与 auto 同级". 本 ADR 不缩小它; 缩小它要靠 Linux 上的
  mount namespace, 或者一份更完整的受保护路径表.
- `_TRANSPARENT_SHELL` 只有 `EXECUTE_SHELL` 一项, 因此"看得清"的判据实际上是
  `EXECUTE_SCRIPT` 有没有被推出来. 那一项推漏了 (一个会跑任意代码但
  `runs_arbitrary_code` 不认识的程序), accept_edits 就会自动放行一次不透明执行.
  方向上这与 auto 的既有风险同源, 但 accept_edits 此前没有这条敞口.
- `curl` 在 accept_edits 下仍然 ASK, 而围栏本来就 `(deny network*)` —— 用户点了同意
  之后命令照样失败. `budget._OPAQUE_EXECUTION` 的注释把这称为"答案不起作用的问题",
  在 auto 档已经按那条理由放行了. accept_edits 要不要跟进, 本 ADR 不决定.

## 验收标准

- 上表十三行逐行有用例 (`tests/security/test_accept_edits_budget.py`).
- auto 档在 `targets_closed` 为真与为假时结论相同 —— 它不看这一项.
- `confined=False` 时 accept_edits 与 auto 都对 `EXECUTE_SHELL` 落 ASK.
- `SandboxLevel.READ_ONLY` 编译出的围栏 `automatic_shell` 为假.
- `accept_edits` 与 `auto` 的 `policy_hash` 不同 —— 切档使旧授权失效.
- 恢复屏障在自动放行的写入前照常建立.
- `make ci` 通过.
