# ADR-0013：采用分层 Shell 命令安全决策架构

## 状态

Proposed

## 日期

2026-07-29

## 背景

ForgeCLI 的 Agent 需要执行 Bash 或其他 Shell 命令。原始 Shell 复合形式具有较高效率，模型可以
一次生成如下命令，减少多次工具调用和模型往返：

```bash
cd project && pytest && git diff
```

但原始 Shell 同时具备管道、重定向、命令替换、子 Shell、脚本解释器和间接执行等能力。不能将模型
生成的字符串直接交给宿主 Shell，也不能只通过命令名称白名单判断安全。

Agent 在完成任务后经常会生成测试脚本，再通过 `python3`、`pytest`、`npm test` 或 heredoc 执行。
测试框架和脚本种类无法完全穷举，因此安全架构不能依赖测试命令专用白名单，而应识别更通用的
`EXECUTE_SCRIPT` 能力。

macOS 和 Linux 可以通过沙箱限制脚本的实际影响范围；Windows 非 WSL2 环境可能没有等价的统一
沙箱能力，需要在规则引擎之外使用脚本风险分类和更严格的自动执行策略。沙箱的能力探测、实例创建
和运行期目录授权另见 ADR-0014。

## 决策

### 1. plan mode 只暴露 PlanTool 和只读工具

`plan` mode 在能力门阶段就限制模型可见的工具目录，只包含：

```text
PlanTool
ReadFileTool
SearchTool
ListDirectoryTool
GitReadTool
```

写文件、编辑、删除、Shell、脚本和 Git 写操作工具不得进入 `plan` mode 的 `ToolCatalog`。

`PlanTool` 只负责创建、更新和记录计划，不执行外部副作用，也不能间接调用 `ShellTool`。

如果模型绕过工具目录直接提出 Shell 请求，应用层应返回结构化的
`tool_unavailable_in_mode` observation；这只是防御性兜底，不能替代从工具目录中移除 ShellTool。

### 2. ShellTool 是唯一的 Shell 执行入口，但不是安全决策者

Agent 不得直接调用宿主 Shell 或绕过安全管线执行 `subprocess.run(..., shell=True)`。

所有 Shell 请求必须通过统一的应用层协调器和 `ShellTool`：

```text
Agent / AgentLoop
  ↓
ToolRequestCoordinator
  ↓
Capability Gate
  ↓
CommandSecurityService
  ↓
ShellTool
  ↓
SandboxProvider / NoSandboxProvider
  ↓
Shell 进程
```

`CommandSecurityService` 完成能力门、Shell 解析、规则匹配、模式判断、风险分类和审批；通过后才
调用 `ShellTool`。`ShellTool` 只负责接收已批准的执行请求、调用执行 Provider、收集 stdout/stderr/
退出码和产物，不负责判断命令安全性，也不调用 LLM 分类器。

没有可用沙箱时也必须经过同一条执行路径，只是选择受限的 `NoSandboxProvider`，不能出现隐藏的直接
执行分支。所有未来入口（AgentLoop、slash command、resume 或其他 workflow）都必须经过
`ToolRequestCoordinator`，避免通过其他调用路径绕过安全验证。

安全验证失败时，应用层返回结构化 observation，而不是普通异常：

```json
{
  "type": "policy_denied",
  "reason_code": "protected_path",
  "message": "命令尝试写入受保护路径",
  "can_retry": false
}
```

LLM 可以根据 observation 改用安全实现或请求用户在 Forge 外部执行；Hard Deny 不得通过改写、编码
或拆分命令进行重试绕过。

### 3. 原始 Shell 是首选交互形式，结构化表示是内部安全模型

系统支持两类请求：

1. 结构化 `argv` 请求：直接执行，不经过 Shell 解释器。
2. 原始 Shell 请求：使用对应的 Shell Parser 转换为 AST 或 `CommandPlan` 后再执行。

原始 Shell 保留用户和 Agent 的高效交互形式；AST 只用于安全分析、授权和审计，不要求将每个子命令
拆成多个模型调用。

### 4. 规则引擎输出 ALLOW、DENY 和 ASK

最终裁决结果为：

- `ALLOW`：允许执行。
- `DENY`：拒绝执行。
- `ASK`：暂停并请求用户确认。

规则类型为 `allow`、`deny` 和 `ask`。安全优先级为：

```text
Hard Deny > Ask > Allow
```

Hard Deny 是任何模式、普通用户确认和风险分类器都不能覆盖的底线，包括但不限于：

- 破坏性删除、格式化、块设备写入和卷销毁。
- 提权执行。
- 从网络内容直接交给 Shell 或脚本解释器执行。
- 写入凭证、系统路径、启动配置、Git hooks 等受保护目标。
- 明确的反弹 Shell、关键进程破坏或生产级外部副作用。

无法解析、无法确定或分类器失败不等于 Allow：

```text
UNKNOWN / UNSUPPORTED / PARSE_ERROR / CLASSIFIER_ERROR → ASK
```

### 5. Allow 必须匹配命令语义，不得只匹配命令名

可信 Allow 必须同时考虑：

```text
executable
subcommand
arguments
read_paths
write_paths
network_targets
child_processes
dynamic_execution
workspace_scope
```

例如，`cat` 只有在目标为普通工作区文件且没有其他副作用时才可以自动允许；命令名为 `cat` 不能
自动授权读取凭证或系统文件。

Hard Allow 只能证明请求满足约束，不能覆盖 Hard Deny。

### 6. Shell 必须解析为 AST，并对整个 CommandPlan 预检

Parser 至少需要处理：

- `&&`、`||`、`;`、换行。
- 管道 `|` 和 `|&`。
- 子 Shell、命令替换和进程替换。
- 输入、输出和追加重定向。
- heredoc 和 here-string。
- 函数、循环、条件和复合命令。
- `sh -c`、`bash -c`、`eval`、`xargs`、`find -exec` 等间接执行结构。

例如：

```bash
cat a.txt | grep b && rm -rf /
```

可以提取出以下分析单元：

```text
cat a.txt
grep b
rm -rf /
```

但授权和执行都以整条 `CommandPlan` 为单位。第三个单元命中 Hard Deny 时，必须在启动任何子进程
前拒绝整条命令，不得先执行前两个单元。

解析单元是分析结构，不代表 Agent 要把管道拆成多次执行；通过后仍应以保持 Shell 语义的方式执行
完整命令。

### 7. Heredoc 和解释器统一归类为 EXECUTE_SCRIPT

以下请求都属于 `EXECUTE_SCRIPT` 能力，而不是依赖具体测试框架分类：

```bash
python3 test.py
pytest tests/
npm test
bash verify.sh
python3 - <<'PY'
print("check")
PY
```

对于 heredoc，解析结果必须包含：

```text
executable: python3
stdin_mode: heredoc
script_language: python
script_content: ...
```

并提取脚本可能使用的文件、网络、子进程、动态执行和资源能力。

测试不是安全信任来源。`pytest`、`npm test` 和 `python3 test.py` 都可能调用任意项目代码，统一按
脚本执行能力处理，避免维护无法穷举的测试框架白名单。

### 8. 四种模式逐步扩大能力预算

模式定义当前请求可使用的能力预算，不得取消 Hard Deny：

| 模式 | 自动允许范围 | 默认需要询问的范围 |
|---|---|---|
| `plan` | PlanTool 和普通只读工具 | 写入、Shell、脚本、网络和外部路径 |
| `accept_edits` | 工作区内普通编辑 | Shell、脚本、网络和工作区外操作 |
| `auto` | 受控工作区命令和满足环境条件的脚本 | 中高风险、未知和外部副作用 |
| `full_access` | 更广泛的本地和网络能力 | 高影响但未达到 Hard Deny 的操作 |

具体的 `EXECUTE_SCRIPT` 规则由执行环境决定：

- `accept_edits`：脚本执行默认 `ASK`。
- `auto + STRONG_SANDBOX`：满足沙箱执行策略时可以自动执行脚本。
- `auto + PARTIAL_SANDBOX`：脚本需要风险评估，必要时 `ASK`。
- `auto + NO_SANDBOX`：新脚本、变更脚本和未知脚本必须经过 Background Safety Classifier。
- `full_access`：可扩大资源范围，但仍不能绕过 Hard Deny。

### 9. 无沙箱 auto 使用 Background Safety Classifier

在没有强沙箱的执行环境中，确定性规则无法充分判断 Python、Node、Shell 等脚本的实际破坏力。
`auto` 对新脚本、变更脚本或未知脚本必须调用分类器，评估：

- 文件读写范围。
- 是否访问工作区外路径或凭证。
- 是否启动子进程。
- 是否使用 `shell=True`、`eval`、`exec` 或动态导入。
- 是否访问网络、下载代码或调用外部服务。
- 是否产生部署、远程写入或其他不可逆外部副作用。
- 是否符合用户原始意图。

只有以下条件同时满足时才能自动执行：

```text
Hard Deny 未命中
脚本风险为低
意图匹配
能力在 auto 范围内
分类器置信度达到策略阈值
```

分类器超时、异常、输出非法或无法确定时进入 `ASK`。

### 10. 分类器负责分析，不拥有最终授权权

分类器只能输出结构化风险事实和建议，不得直接修改策略或调用工具：

```json
{
  "risk_level": "low",
  "intent_alignment": "aligned",
  "capabilities": ["workspace_read", "child_process"],
  "network": false,
  "external_side_effect": false,
  "dynamic_execution": false,
  "confidence": 0.91,
  "recommendation": "allow"
}
```

最终结果仍由本地策略引擎产生。脚本内容、仓库文件和命令输出必须作为不可信输入传给分类器，不能
改变分类器的系统策略。

### 11. 使用内容哈希缓存脚本风险分析

为避免每次执行测试脚本都调用 LLM，分类结果可以基于以下内容缓存：

```text
script_content_hash
related_config_hash
dependency_hash
command
working_directory
policy_version
execution_profile
```

以下变化必须使缓存失效：

- 脚本或 heredoc 内容变化。
- `package.json`、`pyproject.toml`、`Makefile` 等入口配置变化。
- 依赖变化。
- 执行目标、工作目录或网络权限变化。
- 策略或执行环境版本变化。

缓存是效率优化，不是安全边界；缓存命中仍必须重新执行 Hard Deny 和当前策略检查。

### 12. 用户意图是约束，不等于无限授权

每次请求绑定：

```text
原始用户消息
turn_id
当前模式
工作区根目录
已授权资源
主模型生成的命令
```

“运行测试”可以说明测试脚本与任务相关，但不能自动授权生产部署、远程写入、数据库破坏或读取凭证。

### 13. 所有裁决必须可审计

至少记录：

- 原始请求摘要及哈希。
- AST / `CommandPlan` 摘要。
- 读路径、写路径、网络目标和能力集合。
- 命中的规则及版本。
- 当前模式和执行环境等级。
- 分类器版本、结果和置信度。
- 最终裁决及理由。
- 用户审批结果。
- 执行结果和退出状态。

不得记录明文凭证和不必要的敏感脚本内容。

## 备选方案

### 方案 A：穷举测试框架并建立专用执行路径

优点是常见测试命令体验较好。

缺点是无法覆盖自定义框架、临时脚本、heredoc 和项目脚本间接执行，维护成本高。

不采用。

### 方案 B：所有脚本每次执行都调用 LLM

优点是判断上下文充分。

缺点是成本和延迟高，重复执行相同测试时产生大量无意义调用。

不采用，改用静态特征提取、强沙箱和内容哈希缓存。

### 方案 C：所有原始 Shell 直接交给宿主执行

优点是实现简单且执行快速。

缺点是绕过统一安全边界，无法进行整体预检，不能接受。

### 方案 D：在 ShellTool 内部实现安全决策

优点是工具自身看起来具有完整的安全保护。

缺点是把执行机制与策略、模式、审批和 LLM 分类耦合；未来的 slash command、resume 或其他工具
调用路径容易出现不一致，也不利于替换执行后端。

不采用。安全决策由应用层统一协调器负责，ShellTool 只执行已批准请求。

### 方案 E：原始 Shell + AST + 分层规则 + 环境感知脚本策略

优点是保留 Shell 效率，兼容未知测试框架，根据沙箱能力决定是否需要 LLM，并可缓存脚本分析结果；
同时让 PlanTool、策略决策和 Shell 执行职责清晰分离。

缺点是需要 Shell Parser、统一 ShellTool、风险分类器和跨平台执行适配器。

采用。

## 影响

### 收益

- 保留原始 Shell 复合命令的执行效率。
- 不需要穷举 pytest 等测试框架。
- 强沙箱环境下可以减少脚本执行的人工打断。
- 无沙箱环境下可以通过 LLM 补足脚本语义判断。
- 复合命令和 heredoc 具备统一的预检和审计模型。

### 代价

- 必须实现可靠的 Shell Parser 和脚本能力提取器。
- 无沙箱 auto 依赖分类器的成本、延迟和可用性。
- 沙箱和非沙箱平台的自动执行能力不完全一致。
- 内容缓存必须正确处理脚本、依赖和策略变化。

## 验收标准

- `plan` mode 的 `ToolCatalog` 只包含 `PlanTool` 和只读工具。
- `plan` mode 下模型提出 Shell 请求时返回 `tool_unavailable_in_mode` observation。
- 所有 Shell 执行只能通过 `ToolRequestCoordinator`、`CommandSecurityService` 和 `ShellTool`。
- `ShellTool` 不包含安全决策逻辑，不调用 LLM 分类器。
- 安全拒绝返回结构化 `policy_denied` observation。
- 支持复合命令、管道、重定向、命令替换、子 Shell 和 heredoc 分析。
- 复合命令在任何子进程启动前完成整体预检。
- `python3 - <<'PY'` 被识别为 `EXECUTE_SCRIPT` 并提取脚本内容。
- 测试框架不依赖穷举白名单。
- `accept_edits` 下脚本执行默认进入 `ASK`。
- 强沙箱 auto 可以按执行环境策略自动执行脚本。
- 无沙箱 auto 对新脚本或变更脚本调用分类器。
- 分类器异常或低置信度时进入 `ASK`。
- 脚本分析缓存能在脚本、依赖或策略变化时失效。
- Hard Deny 不能被模式或分类器覆盖。
