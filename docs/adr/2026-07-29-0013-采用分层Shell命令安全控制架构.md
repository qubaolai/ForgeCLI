## 背景

ForgeCLI 的 Agent 需要执行 Bash 或其他 Shell 命令。原始 Shell 复合形式具有较高效率，模型可以
一次生成如下命令，减少多次工具调用和模型往返：

```bash
cd project && pytest && git diff
```

但原始 Shell 同时具备管道、重定向、命令替换、子 Shell、脚本解释器和间接执行等能力。不能将模型
生成的字符串直接交给宿主 Shell，也不能只通过命令名称白名单判断安全。

Agent 在完成任务后经常会生成测试脚本，再通过 `python3`、`pytest`、`npm test` 或 heredoc 执行。
测试框架和脚本种类无法完全穷举，因此安全架构不能依赖测试命令专用白名单，而应识别更通用的
`EXECUTE_SCRIPT` 能力。

macOS 和 Linux 可以通过沙箱限制脚本的实际影响范围；Windows 非 WSL2 环境可能没有等价的统一
沙箱能力，需要在规则引擎之外使用脚本风险分类和更严格的自动执行策略。沙箱的能力探测、实例创建
和运行期目录授权另见 ADR-0014。

安全决策还必须覆盖 Windows 原生 `cmd.exe`、PowerShell 和非 POSIX 路径语义。解析器如果只能处理
Bash，会把大量命令降级为未知并增加 LLM 分类器调用，也可能因为错误解析而产生安全漏洞。因此解析
必须按 Shell 方言选择语法模型，不能使用一个弱化的通用分词器代替完整预检。

## 决策

### 1. plan mode 只暴露 PlanTool 和只读工具

`plan` mode 在能力门阶段就限制模型可见的工具目录，只包含：

```text
plan.read / plan.write
todo.read / todo.write / todo.set_status
fs.read_file
fs.list_files
search.text
git.read
```

> 2026-08-17 修订: 首版这里写的是 `PlanTool / ReadFileTool / SearchTool /
> ListDirectoryTool / GitReadTool`. 计划工具按 ADR-0022 拆成计划与待办两组共五个,
> 其余按实际工具名对齐. 清单本身的判据没有变化: 见下.

这份清单不是一张手工维护的白名单, 而是能力门谓词的结果 —— 凡 `declared_capabilities` 与
`MUTATING_CAPABILITIES` 有交集的 `ToolSpec` 都不进 `plan` mode 的 `ToolCatalog`. 因此
写文件, 编辑, 删除, 移动, Shell, 脚本, 网络和 Git 写操作 (`git.write`) 全部不可见, 而新增
一个窄上界的只读工具会自动出现在这里, 不需要改这份清单.

计划与待办工具只维护计划与清单本身, 不执行工作区之外的任何写入, 也不能间接调用
`ShellTool`. 它们的目标集合由 Forge 计算而非模型指定, 因此不触发 ask (ADR-0022 决策 5).

如果模型绕过工具目录直接提出 Shell 请求，应用层应返回结构化的
`tool_unavailable_in_mode` observation；这只是防御性兜底，不能替代从工具目录中移除 ShellTool。

### 2. ShellTool 是唯一的 Shell 执行入口，但不是安全决策者

Agent 不得直接调用宿主 Shell 或绕过安全管线执行 `subprocess.run(..., shell=True)`。

所有 Shell 请求必须通过统一的应用层协调器和 `ShellTool`：

```text
Agent / AgentLoop
  ↓
ToolRequestCoordinator
  ↓
ToolAuthorizationService
  └─ EXECUTE_SHELL → ShellCapabilityAnalyzer
  ↓
审批后重验（ASK 且人类批准时）
  ↓
WorkspaceMutationCoordinator（需要真实工作区写入时）
  ↓
ExecutionAuthorizationEnvelope
  ↓
ShellTool
  ↓
SandboxProvider / NoSandboxProvider
  ↓
Shell 进程
```

`ToolAuthorizationService` 是所有工具共用的授权入口。它只依赖 `ToolPlan`、能力词汇和策略上下文，
并按能力分派分析器。Shell 解析、可执行文件解析和目标集解析由
`ShellCapabilityAnalyzer` 处理；规则匹配、模式判断、风险分类和审批由通用授权流程编排。通过且完成
执行前重验后，服务产生不可变的 `ExecutionAuthorizationEnvelope`，再由
`ToolRequestCoordinator` 调用 `ShellTool`。授权信封至少绑定规范化 `CommandPlan`、可执行文件
身份、目标集合、网络/远端目标、模式、执行环境画像、审批和策略版本。

`ToolAuthorizationService` 负责“是否允许”的分析、裁决和授权签发，但不拥有恢复点、沙箱策略、
沙箱实例或 Provider 生命周期。`WorkspaceMutationCoordinator` 独立判断真实工作区写入是否具备
恢复保障；`SandboxProvider` 独立限制获准进程实际能够触达的宿主资源。规则 `ALLOW`、恢复保障和
沙箱隔离必须同时满足各自适用的约束，任何一层都不能替代或覆盖另外两层。

`ShellTool` 只负责验证授权信封与当前执行实例一致、调用执行 Provider、收集 stdout/stderr/退出码
和产物，不负责判断命令安全性，也不调用 LLM 分类器。

没有可用沙箱时也必须经过同一条执行路径，只是选择受限的 `NoSandboxProvider`，不能出现隐藏的直接
执行分支。所有未来入口（AgentLoop、slash command、resume 或其他 workflow）都必须经过
`ToolRequestCoordinator`，避免通过其他调用路径绕过安全验证。

安全验证失败时，应用层返回结构化 observation，而不是普通异常：

```json
{
  "type": "policy_denied",
  "reason_code": "protected_path",
  "message": "命令尝试写入受保护路径",
  "can_retry": false
}
```

LLM 可以根据 observation 改用安全实现或请求用户在 Forge 外部执行；Hard Deny 不得通过改写、编码
或拆分命令进行重试绕过。

### 3. 原始 Shell 是首选交互形式，结构化表示是内部安全模型

系统支持两类请求：

1. 结构化 `argv` 请求：直接执行，不经过 Shell 解释器。
2. 原始 Shell 请求：使用对应的 Shell Parser 转换为 AST 或 `CommandPlan` 后再执行。

原始 Shell 保留用户和 Agent 的高效交互形式；AST 只用于安全分析、授权和审计，不要求将每个子命令
拆成多个模型调用。

### 4. 规则引擎输出 ALLOW、DENY 和 ASK

最终裁决结果为：

- `ALLOW`：允许执行。
- `DENY`：拒绝执行。
- `ASK`：暂停并请求用户确认。

规则类型为 `allow`、`deny` 和 `ask`，另有不可被普通 Allow、学习规则或模式绕过的
`MANDATORY_ASK` 能力门。安全优先级为：

```text
Hard Deny > Mandatory Ask > Ask > Allow
```

Hard Deny 是任何模式、普通用户确认和风险分类器都不能覆盖的底线，包括但不限于：

- 破坏性删除、格式化、块设备写入和卷销毁。
- 提权执行。
- 从网络内容直接交给 Shell 或脚本解释器执行。
- 写入凭证、系统路径、启动配置、Git hooks 等受保护目标。
- 明确的反弹 Shell、关键进程破坏、凭证外泄，或无法解析真实目标和影响范围的外部灾难性操作。

无法解析或无法确定不等于 Allow，但也不直接等于 Ask。`UNKNOWN`、`UNSUPPORTED`、
`PARSE_ERROR` 和 `OPAQUE` 必须先经过不依赖完整 AST 的 Hard Deny 预扫描，再进入
Background Safety Classifier，由本地策略引擎结合分类结果、当前模式和执行环境产生最终裁决：

```text
UNKNOWN / UNSUPPORTED / PARSE_ERROR / OPAQUE
  → Hard Deny Pre-Filter
  → Background Safety Classifier
  → RiskReport 返回主 Agent
  → Agent 放弃 / 重写 / 主动请求审批 / 提交执行请求
  → Local PolicyEngine
  → ALLOW / ASK / DENY

CLASSIFIER_ERROR / LOW_CONFIDENCE / INVALID_OUTPUT → ASK
```

`ASK` 是阻塞状态，不是返回错误后让主模型自行决定是否重试：

- `ToolAuthorizationService` 创建待审批的 `ApprovalRequest`，不得调用 `ShellTool`。
- 只有人类明确确认后，普通 `ASK` 才能转为一次性 `ALLOW`；Hard Deny 仍不能被确认覆盖。
- 主模型可以根据风险报告放弃、重写请求或主动把请求升级为 `ASK`，但不能把本地策略产生的
  `ASK` 或 `DENY` 降级为执行；重写后的请求必须重新走完整安全管线。
- 主模型收到 `approval_required` observation 后可以解释原因或等待用户，不得代替用户确认。
- 非交互环境中保持 pending、取消或超时拒绝，任何超时都不能转为 Allow。
- 分类器超时、异常、输出非法、内容不完整或置信度不足，统一进入 `ASK`。

#### 4.1 外部不可逆或高影响副作用必须强制逐次审批

新增独立能力类：

```text
EXTERNAL_IRREVERSIBLE_EFFECT
```

它表示不可逆、难以可靠回滚，或会修改共享/生产状态的外部操作，包括但不限于：

- `git push --force`、强制更新或删除远端 branch/tag。
- `npm publish`、`unpublish`、修改共享 dist-tag。
- `docker push`、覆盖共享 tag 或发布制品。
- `terraform apply`、`terraform destroy` 和其他基础设施变更。
- 数据库 migration、drop、truncate 和生产数据批量修改。
- 云部署、生产配置变更、远程删除和共享制品覆盖。

`EXTERNAL_IRREVERSIBLE_EFFECT` 不是 Hard Deny，因为人类可以明确批准；但它在 `plan`、
`accept_edits`、`auto` 和 `full_access` 下都必须产生 `MANDATORY_ASK`，并满足：

- 只能创建与当前请求严格绑定的一次性审批，不支持 session、workspace 或 always。
- 分类器和风险缓存可以复用分析事实，但缓存命中不能满足或跳过本次审批。
- 学习式 Allow、历史批准、模式和主 Agent 的“用户已经授权”声明都不能满足该门。
- 审批后命令、内容、凭证范围、远端目标或执行计划发生变化时，旧审批立即失效。
- 非交互环境没有本次明确审批时保持 pending 或拒绝，不能自动放行。

审批前必须解析真实远端目标，不能只展示 `origin`、默认 registry、`production` 等别名：

```text
git: remote_url + source_commit + refspec + force/delete flags
npm: registry + package + version + dist_tag
docker: registry + namespace/image + tag/digest
terraform: backend + workspace + plan_file_hash + resource change summary
database: host + database + schema + migration_ids + destructive statement types
```

凭证值必须脱敏，但凭证类型、身份范围和凭证将被发送到哪个目标必须展示。`terraform apply` 等具有
独立计划产物的操作，应优先审批并执行已经生成且绑定 hash 的计划，不能在审批后重新生成不同计划。

#### 4.2 人类批准后必须重新验证

`ApprovalRequest` 只表示人类同意审批界面展示的事实快照，不是
`ExecutionAuthorizationEnvelope`，也不能直接交给 `ShellTool`。人类批准后，
`ToolRequestCoordinator` 必须在签发授权和执行前重新验证至少以下绑定事实：

> 2026-08-20（ADR-0027）修订：`approval_presentation_hash` 已并入
> `ApprovalBinding`，批准后只比较一份绑定对象；Shell 解析结果通过 AnalysisFindings 直接交给
> ScriptAnalyzer，不再二次解析。可执行文件与脚本文件身份进入 ToolPlan，并由 ToolRuntime 在
> perform 前复核。

```text
ToolSpec / spec_hash / plan_hash
规范化 CommandPlan / 命令或脚本内容 hash
executable identity / interpreter chain / runtime config hash
目标集合 / target_set_hash / cwd / 文件系统视图
网络与真实远端目标 / 凭证作用域
mode / policy_version / ProtectedPathPolicy
execution_profile_hash / sandbox_policy_version
```

如果任一事实变化，旧批准立即失效，请求必须重新经过 `prepare`、能力分析、Hard Deny、规则匹配和
必要的新一轮审批。不得只重验命令字符串，不得把变化后的目标或环境静默附加到原批准，也不得因用户
刚刚批准而跳过新的 Hard Deny。只有重验通过、恢复绑定建立且执行画像冻结后，
`ToolAuthorizationService` 才能签发一次性 `ExecutionAuthorizationEnvelope`。

#### 4.3 拒绝之后循环怎么走: 按拒绝的来源分流, 不按 mode 分流

一次请求没能执行, 可能有三种来源. 它们对"接下来该发生什么"的含义完全不同, 必须分开处理:

| 来源 | 含义 | 后续 |
|---|---|---|
| 人类在审批界面点了 deny | 人做了决定 | **本轮不再派发任何工具** |
| 无人可裁决 (非交互环境, EOF, 无 TTY) | 这个环境里没有人 | **本轮不再派发任何工具** |
| 策略 DENY (Hard Deny, 规则引擎, 恢复层不可用) | 机器说这条路不通 | 允许换一条路, 但计入本轮拒绝预算 |

判据是**谁说的不行**, 不是当前处于哪个 mode. 用 mode 分流会同时开两个口子: `auto` 不等于
"不问人" (§9 / §10 里 auto 是更宽的允许预算, 脚本仍然过分类器仍然可能 ASK), 所以 auto 下
也会出现人类明确拒绝; 而 `accept_edits` 下同样会触发策略 DENY, 这时换个合法做法恰恰是对的.

**人类拒绝必须终止本轮的工具派发.** 理由不是"这次操作不合理", 而是: 人类拒绝的是**意图**,
不是那一条命令. 如果模型在 `rm -rf build/` 被拒后改用 `find build -delete`, 它绕过的不是一条
规则, 是人刚刚做出的那个决定. 只要"拒绝"等价于"换个说法再试", 审批提示就是摆设 —— 足够执着
的模型总能绕过去, 而用户还以为自己有否决权. 这条性质比任何单条规则都重要: 规则可以有漏洞,
而"人说不就是不"如果失效, 整个人机边界就不存在了.

**终止的粒度是本轮, 不是永久禁止.** 拒绝往往针对的是命令里的某个细节 (写错的路径, 过宽的
范围), 人类希望模型改对了再来. 本轮终止之后 turn 结束, 人类给出下一句输入, 新一轮不受任何
限制 —— 这正是 turn 的语义: 人说一句, 模型做一轮. 一句话概括: **人类拒绝之后, 下一句话应该
是人说的.**

**终止不等于硬中止.** 收掉的是工具目录, 不是整轮. 模型仍须产出一次最终回答, 说明它原本想做
什么以及为什么停下 —— 否则用户面对的是一片空白.

**收掉目录必须在派发处强制, 而不是靠"不给模型看".** 把工具目录置空只是不再向模型声明它们;
模型幻觉出一个工具名, 或者供应商重放上一条 tool call, 请求照样会到达派发环节. 实现必须在
派发前检查"本轮工具是否已关闭", 关闭后收到的工具请求一律不执行, 也不写进对话 transcript
(写进去就欠一份配对的 tool result, 而本轮不会再有执行).

**策略 DENY 允许换路, 但要计数.** 换一条合法的路正是我们希望模型做的 —— 网络被拒就改读本地
文件, 路径越界就改到工作区内. 但一直撞墙不是. 本轮累计被拒达到上限后同样收掉工具目录.

计数按**本轮累计**而不是连续: 连续计数会被任何一次成功调用重置, 模型只要在两次被拒之间插一个
无害读取, 计数器就永远到不了上限.

这道闸与"重复调用闸" (同一工具 + 同一参数) 不重叠, 两者都需要: `rm -rf build/` 与
`find build -delete` 是签名不同的两次调用, 重复调用闸放行它们.

**达到上限后的动作是"停下来告诉人", 不是"请人裁决".** 这两件事看起来像, 安全含义相反.
Hard Deny 按 §4 不能被人类批准覆盖; 如果撞墙 N 次就弹出审批框, 等于给了一条路径: 故意触发
N 次 Hard Deny 换取一次人类审批 —— 而人在连着看过几次拒绝之后, 第 N+1 次点同意的概率恰恰
最高. 升级只能升级为"终止并说明", 不能升级为"征求批准".

**"没人回答"不是"拒绝".** 非交互环境下审批保持 PENDING (§4 已规定超时绝不转 Allow), 但重试
永远还是 PENDING. 把它与人类拒绝混为一种结论, 模型会对着一个不会有人应答的提示空转烧 token;
把它当作可重试的策略拒绝同样如此. 它应当立即终止本轮工具派发.

### 5. Allow 必须匹配命令语义，不得只匹配命令名

可信 Allow 必须同时考虑：

```text
executable_identity
subcommand
arguments
read_paths
write_paths
delete_paths
move_sources_and_targets
network_targets
external_effects
child_processes
dynamic_execution
workspace_scope
target_resolution
target_set_hash
```

例如，`cat` 只有在目标为普通工作区文件且没有其他副作用时才可以自动允许；命令名为 `cat` 不能
自动授权读取凭证或系统文件。

Hard Allow 只能证明请求满足约束，不能覆盖 Hard Deny 或 Mandatory Ask。

#### 5.1 所有 Allow 都必须绑定可执行文件身份

`executable_identity` 不是命令名称字符串，而是至少包含：

```text
requested_token
absolute_path
realpath
file_identity
content_hash_or_signature
trust_zone
writable_by_agent
interpreter_chain
```

所有普通 Allow、Hard Allow、缓存命中、人工审批和学习规则都必须在裁决前把 executable 解析为绝对
realpath，并绑定文件身份和内容 hash/平台签名；执行前再次校验，路径、File ID、hash、签名或解释器
链发生变化时旧授权失效。

工作区、临时目录和其他 Agent 可写目录中的 executable、shim 或解释器不得仅凭命令名命中普通
Allow。它们仍可以作为 `EXECUTE_SCRIPT` 进入内容分析、分类器和沙箱策略，不能因为名称与系统工具
相同而获得系统工具的授权。例如 `./cat`、被修改的 `venv/bin/python` 和
`node_modules/.bin/*` 都必须解析其真实内容、shebang、shim 目标和解释器链。

解释器身份不足以单独证明运行时不变。Python `.pth`/`sitecustomize`、Node shim/package 入口、
动态库、项目配置和依赖等会改变行为的输入必须进入 `runtime_config_hash`、`dependency_hash` 和
`effective_environment_hash`。可执行文件和这些运行时输入的任一变化都会使相关授权与缓存失效。

人类确认可以选择渐进式授权范围：

```text
once → session → workspace → always
```

`always` 不是无条件放行，而是创建一个受限的结构化 Allow 规则。规则至少绑定命令 AST 指纹、
`executable_identity`、参数约束、读写路径范围、网络目标、工作区身份、模式、沙箱状态、运行时
配置和脚本内容 hash。以下情况不能创建或命中 `always` 规则：Hard Deny、Mandatory Ask、受保护
路径、提权、任意网络、下载后执行、远程写入和无法确定的动态执行。

学习式授权只能由人类在审批界面中明确选择，LLM 不得创建、扩大或选择 `always` 规则。脚本内容、
依赖、工作区、策略或执行环境变化时规则必须失效或重新确认，并且规则必须支持列出、撤销、过期和
审计。宽泛的“允许所有 Python/PowerShell/pytest”不得作为合法的渐进式授权规则。

### 6. Shell 必须解析为 AST，并对整个 CommandPlan 预检

Parser 至少需要处理：

- `&&`、`||`、`;`、换行。
- 管道 `|` 和 `|&`。
- 子 Shell、命令替换和进程替换。
- 输入、输出和追加重定向。
- heredoc 和 here-string。
- 函数、循环、条件和复合命令。
- `sh -c`、`bash -c`、`eval`、`xargs`、`find -exec` 等间接执行结构。

例如：

```bash
cat a.txt | grep b && rm -rf /
```

可以提取出以下分析单元：

```text
cat a.txt
grep b
rm -rf /
```

但授权和执行都以整条 `CommandPlan` 为单位。第三个单元命中 Hard Deny 时，必须在启动任何子进程
前拒绝整条命令，不得先执行前两个单元。

解析单元是分析结构，不代表 Agent 要把管道拆成多次执行；通过后仍应以保持 Shell 语义的方式执行
完整命令。

#### 6.1 按 Shell 方言解析，递归处理嵌套解释器

请求必须携带明确的 `shell_kind`，或由执行环境选择受支持的默认方言；不能把 Windows 命令按 POSIX
语法猜测。至少需要独立覆盖：

- POSIX Shell：`&&`、`||`、`;`、管道、重定向、子 Shell、命令替换、进程替换、heredoc、函数、
  循环、`eval`、`xargs` 和 `find -exec`。
- `cmd.exe`：`&`、`&&`、`||`、管道、括号块、重定向、`%VAR%`、延迟变量和 `^` 转义。
- PowerShell：对象管道、脚本块、子表达式、`;`、`&` 调用运算符、点源加载、`Start-Process`、
  `Invoke-Expression`、重定向、`-File` 和 `-EncodedCommand`。

包装器必须递归解析：

```text
sh -c ...
bash -c ...
cmd /c ...
powershell -Command ...
pwsh -EncodedCommand ...
python -c ...
```

PowerShell 编码命令必须先按规范编码解码后分析；解析过程不得执行解码后的内容。所有方言都输出
统一的 `CommandPlan` 和能力事实。确实不支持的语法标记为 `OPAQUE`，按决策 4 进入 Hard Deny
预扫描和 Background Safety Classifier；不得因为通用解析器无法理解就直接 Allow，也不得把 LLM
输出伪装成确定性的 Shell AST。

结构化 `argv` 请求同样必须生成 `CommandPlan` 并经过包装器、脚本和能力分析。`argv` 只表示不需要
宿主 Shell 做第一层字符串展开，不代表 `bash -c`、`python -c`、`cmd /c` 或被调用程序本身天然
安全。

#### 6.2 直接写入真实工作区前必须封闭目标集合

写入、删除和移动请求必须记录目标解析状态：

```text
STATIC          目标可从结构化请求直接确定
FORGE_EXPANDED  Forge 已按固定上下文展开并冻结目标集合
DYNAMIC         目标由 Shell、管道输入或子进程在运行时产生
UNKNOWN         无法可靠推导完整目标集合
```

直接修改真实工作区的普通 `ALLOW` 只适用于 `STATIC` 或 `FORGE_EXPANDED`。以下请求不能仅根据
命令名、字符串模式或分类器的低风险结论获得普通 `ALLOW`：

```bash
rm ./*
rm -rf "$DIR"
find . -name '*.tmp' -exec rm {} +
printf '%s\n' ... | xargs rm
```

Forge 可以对简单 glob 或变量引用执行方言感知的受控展开，但必须使用已经绑定的 cwd、环境快照和
文件系统视图，将结果规范化为完整绝对目标集合，再生成不会由 Shell 二次展开的结构化 `argv`。
裁决和授权信封必须绑定 `target_set_hash`、相关父目录身份及展开上下文；文件系统、变量、cwd 或
目标身份变化时重新展开和裁决，不能复用旧授权。

`find -exec`、`xargs`、命令替换、运行期生成路径等不能安全地做单步展开时，应优先改写为两阶段：

```text
只读枚举候选目标
  ↓
规范化并冻结完整目标集合
  ↓
重新运行路径、恢复点、模式和审批策略
  ↓
使用结构化 argv 执行
```

如果目标仍为 `DYNAMIC` 或 `UNKNOWN`，允许的执行方式只有：

- 在真实工作区只读、写入只落到 Copy-on-Write Overlay 的沙箱中执行；执行结束后根据已经固定的
  `MutationSet`，按 ADR-0015 的首次破坏性写入屏障逐项 materialize。
- 进入 `ASK`，让用户选择改写命令、启用 Overlay，或在完整、规范化的最大影响边界已经确定且
  ADR-0015 的 `FULL` checkpoint 能在进程启动前完成时，逐次批准直接执行。此审批必须把整个边界
  （通常是完整工作区）显示为“均可能被修改或删除”，不能伪装成已知目标集合，也不能创建
  session/workspace/always 规则。
- 无法提供上述边界时拒绝执行。

因此，`ASK` 不是对原始动态删除命令的空白支票，也不能把未知目标变为普通 Allow。审批界面无法
展示精确目标集合时，必须展示完整的保守上界、`target_resolution=DYNAMIC|UNKNOWN`、无法确定的
原因和 `FULL` checkpoint 结果；缺少任一项时不得直接在真实工作区运行。沙箱 Provider 的受保护
路径校验也不能替代本规则，因为它只能限制访问边界，不能证明工作区内部实际会命中哪些对象。

#### 6.3 哪些参数才是路径 (2026-08-19)

§6.2 说的是"目标集合封没封闭", 这一节补的是它的前一步: **这条命令的目标到底是哪几个参数.**

此前判据只有一句 `not arg.startswith("-")`. 实测后果:

```text
grep -r skipUrl .          -> 读取 /ws/skipUrl      搜索词被当成文件
sed -i.bak s/a/b/ f.txt    -> 写入 /ws/s/a/b        sed 表达式被当成要写的文件
tar -czf out.tgz src       -> 写入 /ws/src          tar 只读 src, 这里说它要写
find . -exec rm {} \;      -> 读取 /ws/rm /ws/{}    exec 的内层命令被当成路径
```

这些假路径一路走到审批框, 与真实目标混排成一份"读取 (6 项)". **一份掺假的清单比没有清单
更糟** —— 用户学会忽略它之后, 真正危险的那一条也跟着被忽略.

**解析器不是问题所在.** AST 一直是真的: 命令替换提取成 `origin=substitution` 单元,
`bash -c` 内层提取成 `wrapper_inner`, 子 Shell 与连接符完整保留, `curl | sh` 能被识别.
粗糙的是 AST 之上那一层 —— 每条命令的参数模型不存在.

因此新增 `domain/security/shell/arguments.py`, 与 `effects.py` 分工:

| 模块 | 回答 | 错了会怎样 |
|---|---|---|
| `effects.py` | 这条命令碰文件系统的方式是读还是写 | 漏掉一整类影响 |
| `arguments.py` | 它碰的到底是哪几个参数 | **凭空造出目标** |

模型登记四类事实: 吃值但值不是路径的选项 (`find -name`), 吃值且值是路径的选项
(`tar -f`), 前几个位置参数不是路径 (`grep` 的模式, `sed` 的脚本), 以及"位置参数一个都
不是路径" (`echo`, `sleep`). 短选项按字符登记, 因为聚合写法同样成立 (`tar -czf`).

**这不是安全白名单.** 表里有没有一条命令只影响它的参数怎么解读; 允不允许碰某个路径仍然
由受保护路径检查, 模式预算与 §6.2 的目标封闭性裁决.

##### 表外命令仍然多报

一个直觉是"不认识的命令就别编清单了". **不采用.** 少收一条的后果是
`cat ~/.ssh/id_rsa` 这类目标从受保护路径检查里消失; 多收一条的后果只是展示层要说清它是
推测. 两种错法的代价不对称, 所以默认仍然多收, 由展示层承担说明责任.

##### `find -exec` 与 `xargs` 的内层提取

`INDIRECT_EXECUTORS` 早就列了 `find` 与 `xargs`, `UnitOrigin.WRAPPER_INNER` 也现成,
`bash -c` 走的正是这条路 —— 只是 `find -exec` 一直没接上. 于是
`find . -exec rm {} \;` 只得到一个名叫 `find` 的单元, 审批框最显眼的那行写着
"删除 0 · 写入 0": **一条会删文件的命令, 用户读到的是它什么都不删.**

内层与 `nested_command_of` 走两条路: 后者把内层交回 Shell 解析器再解析一遍**字符串**,
而 `-exec` 的内层已经是分好词的 argv, 拼回字符串会在引号与 `{}` 上出错.

`{}` 是占位符, 不是路径, 在模型之外统一剔除.

##### 审批展示必须说明清单不完整

目标集合不封闭时, 每个数字都只是已知下限, 界面必须这么标 (`≥N`, 并明说"实际影响范围可能
更大"). 这条与 §6.2 末尾"不能伪装成已知目标集合"是同一条要求的界面落法 —— 此前那句话只
约束了"要展示保守上界", 没约束"计数不能读成事实".

##### 已知限制

`tar -czf out.tgz src` 仍然把 `src` 记成写入. 打包读 `src`, 解包写 `src`, 方向取决于
`-c` / `-x`, 而判错方向比多报一条更糟. 这一处保持**往安全方向多报**: 代价是恢复层多做一次
快照, 不是漏掉一次保护.

### 7. Heredoc 和解释器统一归类为 EXECUTE_SCRIPT

以下请求都属于 `EXECUTE_SCRIPT` 能力，而不是依赖具体测试框架分类：

```bash
python3 test.py
pytest tests/
npm test
bash verify.sh
python3 - <<'PY'
print("check")
PY
```

对于 heredoc，解析结果必须包含：

```text
executable: python3
stdin_mode: heredoc
script_language: python
script_content: ...
```

并提取脚本可能使用的文件、网络、子进程、动态执行和资源能力。

测试不是安全信任来源。`pytest`、`npm test` 和 `python3 test.py` 都可能调用任意项目代码，统一按
脚本执行能力处理，避免维护无法穷举的测试框架白名单。

### 8. 脚本内容先做确定性静态分析，LLM 只处理剩余不确定性

脚本请求在进入 Background Safety Classifier 前，必须尽可能收集待执行内容并运行本地
`ScriptAnalyzer`。这一步不依赖 LLM，目标是提取可验证的能力事实和硬性危险信号，而不是证明脚本
在所有运行路径上绝对安全。

内容收集规则如下：

- 临时脚本文件：读取执行前的规范化字节内容，并记录文件路径、内容哈希和依赖入口。
- heredoc/here-string：直接使用 Shell Parser 捕获的 body；`python3 - <<'PY'` 的内容必须纳入
  分析输入。
- `python3 -c`、`node -e`、`bash -c`：读取命令参数中的内联脚本。
- `python3 test.py`、`pytest`、`npm test` 等入口：读取入口脚本和可静态发现的配置、导入、脚本
  链；无法完整展开的部分标记为 opaque，而不是假设安全。

`ScriptAnalyzer` 至少提取：

```text
content_hash
language
files_read
files_written
network_access
child_process
dynamic_execution
privilege_or_system_change
credential_access
external_side_effect
resource_exhaustion_signal
opaque_constructs
evidence
confidence
```

应覆盖的确定性信号包括：删除、覆盖、改权限、系统路径和凭证访问；`subprocess`、`os.system`、
`shell=True`、`child_process.spawn`；`eval`、`exec`、动态导入；网络连接、下载后执行；启动配置、
Git hooks、crontab、Docker、SSH、云部署或远程写入；归档解压路径穿越和明显的无限资源消耗。
不同语言可以有不同规则集，但输出必须归一化为同一份能力事实。

裁决顺序为：

```text
原始请求
  ↓
Hard Deny Pre-Filter
  ↓
Shell Parser / CommandPlan
  ↓
收集脚本内容和依赖
  ↓
确定性 ScriptAnalyzer
  ├─ 命中硬性危险信号 → DENY
  ├─ 能力受控且强沙箱有效 → 可按 auto 策略 ALLOW
  ├─ 无沙箱且内容/语义仍不确定 → Background Safety Classifier
  └─ UNKNOWN / UNSUPPORTED / PARSE_ERROR / OPAQUE / 分析不完整
       → Background Safety Classifier
       → RiskReport 返回主 Agent
       → Agent 放弃 / 重写 / 主动请求审批 / 提交执行请求
       → Local PolicyEngine
```

静态分析不能替代沙箱，也不能替代无沙箱环境中的语义分类：反射、动态加载、依赖安装脚本、
运行期生成代码和间接调用都可能超出静态可见范围。分析结果必须绑定规范化内容哈希、依赖哈希、
策略版本和执行环境；执行前若内容发生变化，必须重新分析。临时脚本必须执行已经分析的内容快照，
或在启动子进程前再次校验哈希，避免分析与执行之间的 TOCTOU。对明显危险模式可以直接触发 Hard Deny，
但“未发现危险”只能表示未发现，不得直接解释为绝对安全；在 `NO_SANDBOX` 的 `auto` 下不能仅凭
静态分析为低风险就绕过 Background Safety Classifier。

Hard Deny Pre-Filter 不依赖完整 AST，至少覆盖提权入口、块设备和卷操作、明确的受保护路径写入、
下载后直接执行、反弹 Shell、关键进程破坏、凭证外泄，以及真实目标或影响范围无法解析的外部
灾难性操作。它的作用是在 Parser 失败时仍保留不可由分类器覆盖的本地安全底线；能够解析且可由
人类明确批准的外部高影响操作进入 Mandatory Ask，而不是被该预扫描一概 Deny。预扫描未命中只表示
没有发现已知硬性模式。

### 9. 四种模式逐步扩大能力预算

模式定义当前请求可使用的能力预算，不得取消 Hard Deny：

| 模式 | 自动允许范围 | 默认需要询问的范围 |
|---|---|---|
| `plan` | PlanTool 和普通只读工具 | 写入、Shell、脚本、网络和外部路径 |
| `accept_edits` | 工作区内普通编辑 | Shell、脚本、网络和工作区外操作 |
| `auto` | 受控工作区命令和满足环境条件的脚本 | 中高风险、未知和外部副作用 |
| `full_access` | 更广泛的本地和网络能力 | Mandatory Ask、动态目标和高影响操作 |

具体的 `EXECUTE_SCRIPT` 规则由执行环境决定：

- `accept_edits`：脚本执行默认 `ASK`。
- `auto + STRONG_SANDBOX`：满足沙箱执行策略时可以自动执行脚本。
- `auto + PARTIAL_SANDBOX`：脚本需要风险评估，必要时 `ASK`。
- `auto + NO_SANDBOX`：新脚本、变更脚本和未知脚本必须经过 Background Safety Classifier。
- `full_access`：可扩大本地、网络和凭证的能力预算，但仍不能绕过 Hard Deny、Mandatory Ask、
  可执行文件身份校验或目标集合封闭规则。

### 10. 无沙箱 auto 使用 Background Safety Classifier

在没有强沙箱的执行环境中，确定性规则无法充分判断 Python、Node、Shell 等脚本的实际破坏力。
`auto` 对新脚本、变更脚本、未知脚本以及 Parser 无法完整处理的请求必须调用分类器，评估：

- 文件读写范围。
- 是否访问工作区外路径或凭证。
- 是否启动子进程。
- 是否使用 `shell=True`、`eval`、`exec` 或动态导入。
- 是否访问网络、下载代码或调用外部服务。
- 是否产生部署、远程写入或其他不可逆外部副作用。
- 是否符合用户原始意图。

只有以下条件同时满足时才能自动执行：

```text
Hard Deny 未命中
未命中 EXTERNAL_IRREVERSIBLE_EFFECT
脚本风险为低
意图匹配
能力在 auto 范围内
executable_identity 已解析、可信且执行前可重验
直接真实写入的目标集合为 STATIC 或 FORGE_EXPANDED
动态目标只写入受限 Overlay，并在 materialize 前重新裁决
分类器置信度达到策略阈值
```

分类器超时、异常、输出非法或无法确定时进入 `ASK`。

`NO_SANDBOX + auto` 是基于风险评估维持任务连续性的产品策略，不等同于操作系统级 containment
保证。满足上述条件时可以自动执行，避免把 `auto` 退化为频繁审批；但本地 Hard Deny、模式能力预算
和受保护路径仍具有最终约束力。

### 11. 分类器负责分析，不拥有最终授权权

分类器只能输出结构化风险事实和建议，不得直接修改策略或调用工具：

```json
{
  "risk_level": "low",
  "intent_alignment": "aligned",
  "capabilities": ["workspace_read", "child_process"],
  "syntax_understanding_confidence": 0.94,
  "opaque_regions": [],
  "read_paths": ["./tests"],
  "write_paths": ["./.pytest_cache"],
  "delete_paths": [],
  "target_resolution": "static",
  "target_set_hash": "sha256:...",
  "network_targets": [],
  "network": false,
  "external_effects": [],
  "external_side_effect": false,
  "dynamic_execution": false,
  "executable_identity": {
    "absolute_path": "/usr/bin/python3",
    "realpath": "/usr/bin/python3",
    "content_hash_or_signature": "platform:..."
  },
  "requires_sandbox_capabilities": ["filesystem_isolation"],
  "confidence": 0.91,
  "recommendation": "allow"
}
```

最终结果仍由本地策略引擎产生。脚本内容、仓库文件和命令输出必须作为不可信输入传给分类器，不能
改变分类器的系统策略。

分类结果可以反馈给主 Agent。主 Agent 只能：

- 放弃当前请求。
- 重写为能力更小、语义更明确的请求。
- 主动请求人类审批。
- 将未修改的请求提交给本地策略引擎。

主 Agent 不能直接消费分类器的 `recommendation=allow` 调用 `ShellTool`，也不能覆盖本地策略的
`ASK` 或 `DENY`。任何重写都会产生新的请求哈希并重新解析、分析和分类。

Agent 对 RiskReport 的选择必须作为结构化 `AgentRiskResponse` 记录；只有 `submit_execution`
分支进入本地策略引擎，`request_approval` 分支只能创建审批请求，二者都不能直接调用 `ShellTool`。

Background Safety Classifier 使用独立的 LLM 调用预算和隔离的系统提示，不继承主模型的任务完成
压力，也不能接受主模型关于“用户已经授权”的自我声明。分类器本身也可能不可用或被不可信脚本内容
诱导，因此分类器结论只能作为本地规则的输入。

分类器调用必须有明确的 fail-safe 行为：

```text
timeout / transport_error / invalid_output / low_confidence / context_truncated
  → ASK
  → 阻塞 ShellTool
  → 等待人类确认或取消
```

重试次数必须有上限，不能通过重复调用分类器等待一个 Allow 结果；所有失败和人工决定都需要审计。

### 12. 使用内容哈希缓存脚本风险分析

为避免每次执行测试脚本都调用 LLM, 分类结果可以基于内容缓存. 实际的 `risk_cache_key`
由以下十项组成:

```text
script                      内容哈希 + 依赖哈希 + 语言 (ScriptFacts.cache_key)
command_hash
working_directory
policy_version
execution_profile_hash      本身还嵌着四个版本, 见 §12.1
shell_kind
script_analyzer_version
parser_version
classifier_profile_version
intent_scope_hash
```

以下变化必须使缓存失效：

- 脚本或 heredoc 内容变化。
- `package.json`、`pyproject.toml`、`Makefile` 等入口配置变化。
- 依赖变化。
- 执行目标、工作目录或网络权限变化。
- 策略或执行环境版本变化。

缓存是效率优化，不是安全边界；缓存命中仍必须重新执行 Hard Deny 和当前策略检查。

#### 12.1 版本常量与它们进入的哈希

> 2026-08-18 新增. 此前"哪个版本影响哪个缓存"这件事没有单一说明, 要回答"改了 X 会不会
> 让缓存失效"得翻三个文件.

版本常量的作用只有一个:**让"这段代码的行为契约变了"这件事传导到下游缓存**. 因此每个
常量都必须回答"我进哪个哈希". 全表如下:

| 版本常量 | 跟踪什么 | 进入的哈希 | 漏升的后果 |
|---|---|---|---|
| `POLICY_VERSION` | 策略规则表与裁决口径 | `risk_cache_key`; 学习规则匹配键 | 改完规则后旧风险结论与旧 `always` 规则继续生效 |
| `PARSER_VERSION` | Shell 解析器的公开行为 | `risk_cache_key` | 修好一个漏解析后, 基于**错误解析**算出的旧结论继续命中 |
| `ANALYZER_VERSION` | 脚本静态分析器 | `risk_cache_key` | 新增一条静态信号后, 旧结论不重算 |
| `CLASSIFIER_PROFILE_VERSION` | 分类器系统提示词与输出契约 | `risk_cache_key` | 把提示词改严之后, 之前判 `low / allow` 的脚本保持原判 |
| `ENVIRONMENT_SANITIZATION_VERSION` | `sanitize_environment` 的净化规则 | `execution_profile_hash` → 持久化的 `always` 规则 | 升级后, 按旧净化规则批准的 `always` 继续命中 |
| `path_normalization_version` | `is_within` 的路径比较规则 | 同上 | 升级后, 按旧路径判定批准的 `always` 继续命中 |
| `executable_resolution_version` | `ExecutableResolver` 的解析行为 | 同上 | 升级后, 按旧解析结果批准的 `always` 继续命中 |
| `profile_version` | `ExecutionProfile` 结构自身 | 同上 | 加了字段却不升版本, 旧规则按不完整的画像继续匹配 |
| `CAPABILITY_VOCABULARY_VERSION` | 能力闭集词汇 | `plan_hash` → 学习规则匹配键 | 改词汇后旧 `always` 规则按旧语义继续匹配 |
| `ToolSpec.version` | 单个工具的入参与能力上界 | `spec_hash` → `plan_hash` | 改工具行为后, 针对旧行为批准的 `always` 规则继续放行 |

**不进任何安全缓存键的版本**, 列在这里是为了免得有人"顺手也加进去":

| 版本常量 | 用途 | 为什么不进 |
|---|---|---|
| `MAIN_AGENT_PROMPT_VERSION` | 主 Agent 提示词 (ADR-0018) | 提示词影响模型**尝试什么**, 不影响任何一次调用的裁决结果. 它只进 `PromptSnapshot.fingerprint`, 那是诊断锚点 |
| `SessionSnapshot.schema_version` | `state.json` 落盘格式 | 存储格式版本, 与安全裁决无关 |

##### 版本号真正生效的那条路径: 持久化的学习规则

上表里 `execution_profile_hash` 那四项最容易被当成冗余删掉 —— 因为在**当前进程内**它们
确实什么都不区分. 完整的链路是:

```text
四个 profile version 字段
  -> execution_profile_hash (digest(ExecutionProfile), 全部 compare=True 字段)
  -> RuleMatch.execution_profile_hash
  -> 落进 ~/.forge/state/rules/<workspace_id>.toml 的 always 规则
  -> 下次启动时按 _MATCH_FIELDS 逐字段相等比对
```

**跨 Forge 版本是它们唯一能生效的场景, 也正是它们存在的理由.**

`ExecutionProfile` 的其余字段 (`platform`, `trusted_path`, `environment_allowlist`,
`protected_roots_hash`) 都是**数据**: 换机器, 改配置, `/add-dir` 都会让它们变. 而这四个
version 跟踪的是**算法**, 算法变了没有任何数据字段会跟着变:

> 有人把 `is_within` 的路径比较从大小写敏感改成不敏感. `trusted_path` 没变, `platform`
> 没变, `protected_roots_hash` 没变 —— `execution_profile_hash` 一个字节都不会变. 于是
> 用户半年前对某条命令点的"始终允许"继续命中, 而那条规则当初判定"这个路径在工作区内"
> 用的是旧算法.

这类改动在哈希上**完全不可见**, 只能靠人工升版本号表达. 因此这四个字段不能删, 也不能
改成从源码自动推导 (§12.4).

##### `execution_profile_hash` 的另外两个消费点当前是空转的

同一个哈希还进了两处, 在那两处它今天不产生任何区分度. 写在这里是为了免得下一个人
反过来推断"既然那两处没用, 这个哈希也没用":

| 消费点 | 当前效果 | 为什么仍然留着 |
|---|---|---|
| 学习规则匹配 | **生效**. 跨进程比对, 四个 version 在这里起作用 | —— |
| `risk_cache_key` | 空转. `RiskCache` 是进程内 LRU 且明确不落盘, 而画像由 `probe_execution_profile()` 在组合根构造一次就不再变 —— 常量对常量 | 哪天风险缓存真的落盘时, 键的形状不用回头补 |
| `ExecutionAuthorization.ensure_usable()` | 空转. 签发与执行在同一进程内, 比的是同一个常量 | ADR-0014 / ADR-0019 的沙箱 Provider 落地后画像可能在会话中途重建 (切换隔离等级), 那时这条比对才真正区分出东西 |

"当前空转"与"可以删除"是两回事: 前两处是为**已经写进 ADR 的后续切片**留的防线, 而学习
规则那一处现在就在生效.

#### 12.2 版本常量放在哪里

**常量与它描述的组件放在同一个模块里, 不集中到一个 `versions.py`.**

判据是这条机制唯一的执行方式: 改组件的人必须在同一屏里看见版本号. `CLASSIFIER_PROFILE_VERSION`
紧挨 `_SYSTEM_PROMPT`, 改提示词时版本号就在眼前; 搬进公共模块之后, 它就只是另一个文件里
的一行, 谁也不会想起.

集中还有两处代价: 那个模块会变成 `domain` 与 `application` 都要 import 的中心节点, 而
`POLICY_VERSION` 与 `CAPABILITY_VOCABULARY_VERSION` 本来各自属于自己的领域词汇; 以及版本
号不是配置, 它是代码行为契约的一部分, 该跟着代码走.

##### 归属表

| 版本常量 | 定义在 | 它守着哪段代码 |
|---|---|---|
| `POLICY_VERSION` | `domain/security/vocabulary.py` | `Decision` / `DecisionReason` / `ApprovalScope` 裁决词汇 |
| `CAPABILITY_VOCABULARY_VERSION` | `domain/tool/capability.py` | `Capability` 闭集 |
| `ENVIRONMENT_SANITIZATION_VERSION` | `domain/execution/environment.py` | `sanitize_environment` |
| `PATH_NORMALIZATION_VERSION` | `domain/workspace/boundary.py` | `is_within` 的路径比较规则 |
| `PARSER_VERSION` | `domain/security/shell/parser.py` | Shell 解析器的公开行为 |
| `PROFILE_VERSION` | `domain/execution/profile.py` | `ExecutionProfile` 结构自身 (自引用, 同文件是对的) |
| `ANALYZER_VERSION` | `application/security/analyzers/script_analyzer.py` | 脚本静态分析器 |
| `CLASSIFIER_PROFILE_VERSION` | `application/security/classifier.py` | `_SYSTEM_PROMPT` 与输出契约 |
| `EXECUTABLE_RESOLUTION_VERSION` | `application/security/executable_resolver.py` | `ExecutableResolver` 的解析行为 |
| `MAIN_AGENT_PROMPT_VERSION` | `application/prompt/system_prompt_builder.py` | 主 Agent 内置提示词 (ADR-0018) |
| `ToolSpec.version` | 各工具自己的 `_SPEC` | 单个工具的入参与能力上界 |
| `SessionSnapshot.schema_version` | `domain/session/snapshot.py` | `state.json` 落盘格式 |

##### 一个跨层例外: `EXECUTABLE_RESOLUTION_VERSION`

它守的是 `ExecutableResolver`, 而那个类在 application 层; 但消费它的
`ExecutionProfile.executable_resolution_version` 是 domain 字段,**domain 不能 import
application**. 于是它不能像 `PATH_NORMALIZATION_VERSION` 那样直接做字段默认值.

做法是**去掉默认值, 由组合期注入**: `ExecutionProfile.executable_resolution_version`
必填, 由 `infrastructure/execution/environment_probe.py::probe_execution_profile` 从
application 取值传入 (infrastructure 可以 import application, 那是既定的适配器方向).

代价是 `ExecutionProfile` 多一个必填参数, 所有构造点都要给值. 之所以仍选这条而不是把
常量塞进 `domain/security/executable_identity.py`: 后者零结构改动, 但改 resolver 的人
照样看不见常量 —— 那等于保留了病灶只换个位置, 而就近提醒正是这个常量存在的全部理由.

##### 同一个概念不得有两份定义

曾经出现过三处, 已全部消除:

- `PARSER_VERSION` 定义在 `script_analyzer.py`, 而解析器在 `domain/security/shell/parser.py`
  —— 改解析器的人看不到它, 就近提醒对这一项已经失效.
- `CommandPlan.parser_version` 另有一个字面量默认值 `"1"`, 与上面那个各自维护.
- `ExecutionProfile` 的三个 `"1"` 字面量没有常量名, 也就没有任何地方能挂"改这里要升
  版本"的提醒.

字段默认值一律引用常量, 不写字面量. 一个写死的 `"1"` 看不出它跟谁绑定, 也就没人知道
改什么的时候该动它.

#### 12.3 用测试把"改了就得升版本"钉住

就近放置只是提醒, 而漏升**不会报错** —— 它只会让缓存在本该失效时继续命中. 因此每个进
缓存键的版本都应有一条 pin 测试, 把契约钉死:

```python
def test_the_classifier_prompt_is_pinned_to_its_version() -> None:
    """改 _SYSTEM_PROMPT 必须同时升 CLASSIFIER_PROFILE_VERSION."""
    assert CLASSIFIER_PROFILE_VERSION == "1"
    assert digest_text(_SYSTEM_PROMPT) == "sha256:..."
```

改提示词 -> 指纹变 -> 测试红 -> 必须同时改版本号和指纹. ADR-0018 §15.3 对内置提示词用的
是同一个模式. 这条把约定从注释变成 CI 断言, 而且不破坏就近性.

同样适用于: `POLICY_VERSION` 对规则表, `CAPABILITY_VOCABULARY_VERSION` 对 `Capability`
枚举全集, `PARSER_VERSION` 对解析器的公开行为集.

#### 12.4 不要用源码哈希当版本号

会有人提议"直接拿模块源码哈希做版本, 就不用人工维护了". 不采用:

- 一次无关的格式化或注释改动就会作废全部缓存与全部 `always` 学习规则.
- 版本号表达的是**行为契约变了**, 而不是**字节变了**. 两者不等价, 后者只是前者的一个
  过度敏感的代理.

这不是假想. `ExecutionContextRef.filesystem_view_version` 踩过同一个坑: 它是每次调用新建
的时间戳版本, 一度被算进 `plan_hash`, 后果是 `plan_hash` 永不重复 —— 学习规则从来没有命中
过, 用户每次都被重新询问, 而且不报错. 修法是把它标成 `compare=False` 排除出哈希 (ADR-0021).

### 13. 用户意图是约束，不等于无限授权

每次请求绑定：

```text
原始用户消息
turn_id
当前模式
工作区根目录
已授权资源
主模型生成的命令
```

“运行测试”可以说明测试脚本与任务相关，但不能自动授权生产部署、远程写入、数据库破坏或读取凭证。

### 14. 审批必须呈现完整、规范化且与授权绑定的风险视图

`ApprovalRequest` 必须包含不可变的 `ApprovalPresentation`，至少向用户展示：

```text
用户意图摘要与待批准操作
原始命令和规范化 CommandPlan
Shell 方言、完整绝对 executable realpath、文件身份/hash/签名及解释器链
cwd、模式、Sandbox Provider、隔离等级和关键执行画像
完整的读、写、删除、移动源与目标集合
网络目标、协议、端口和凭证作用域
外部副作用类型及解析后的真实远端目标
触发 ASK / MANDATORY_ASK 的具体风险事实和规则
ADR-0015 恢复策略、预计保护范围和恢复点标识
审批范围、有效期以及哪些变化会使审批失效
```

审批界面可以先显示易读摘要，但危险字段不得语义截断。目标集合较大时可以分页、搜索或引用不可变
清单产物，界面仍必须提供完整清单、条目数和 `target_set_hash`；不能只显示前若干项、模糊的
“还有 N 个文件”或省略真实远端。用户批准的对象是完整规范化视图及其 hash，不是被截断的终端
字符串。若精确写入、删除或移动目标集无法生成，则必须按 §6.2 显示完整保守上界、未知原因和
`FULL` checkpoint；不能把缺失清单当作普通审批后直接执行。

凭证值、令牌和不必要的敏感内容必须脱敏，但不能隐藏凭证类型、身份范围、目标主机、registry、
repository、数据库、schema、refspec、package/version 或计划 hash。对无法安全显示的二进制内容，
应展示内容 hash、类型、大小、来源和目标。

用户确认后，`ExecutionAuthorizationEnvelope` 必须绑定 `approval_presentation_hash`。原始命令、
规范化计划、可执行文件身份、完整目标集合、网络/远端目标、凭证范围、执行模式、环境画像、恢复
策略或风险事实发生变化时，旧审批失效并重新呈现，不能在确认后静默扩大范围。

### 15. 所有裁决必须可审计

至少记录：

- 原始请求摘要及哈希。
- AST / `CommandPlan` 摘要。
- 可执行文件绝对路径、realpath、文件身份/hash/签名、解释器链和运行时配置 hash。
- 完整读、写、删除、移动目标集、目标解析状态、`target_set_hash`、网络目标和能力集合。
- 外部副作用类型、解析后的真实远端目标和 Mandatory Ask 结果。
- 命中的规则及版本。
- 当前模式和执行环境等级。
- 分类器版本、结果和置信度。
- `AgentRiskResponse` 的放弃、重写、主动审批或提交执行选择。
- 最终裁决及理由。
- `ApprovalPresentation` hash、用户实际看到的版本和审批结果。
- 审批范围（once/session/workspace/always）以及学习规则的创建、命中、失效和撤销。
- `ExecutionAuthorizationEnvelope` hash、执行前重验结果和失效原因。
- 执行结果和退出状态。

不得记录明文凭证和不必要的敏感脚本内容。

## 备选方案

### 方案 A：穷举测试框架并建立专用执行路径

优点是常见测试命令体验较好。

缺点是无法覆盖自定义框架、临时脚本、heredoc 和项目脚本间接执行，维护成本高。

不采用。

### 方案 B：所有脚本每次执行都调用 LLM

优点是判断上下文充分。

缺点是成本和延迟高，重复执行相同测试时产生大量无意义调用。

不采用，改用确定性静态特征提取、强沙箱和内容哈希缓存；只对剩余未知风险调用 LLM。

### 方案 C：所有原始 Shell 直接交给宿主执行

优点是实现简单且执行快速。

缺点是绕过统一安全边界，无法进行整体预检，不能接受。

### 方案 D：在 ShellTool 内部实现安全决策

优点是工具自身看起来具有完整的安全保护。

缺点是把执行机制与策略、模式、审批和 LLM 分类耦合；未来的 slash command、resume 或其他工具
调用路径容易出现不一致，也不利于替换执行后端。

不采用。安全决策由应用层统一协调器负责，ShellTool 只执行已批准请求。

### 方案 E：原始 Shell + AST + 分层规则 + 环境感知脚本策略

优点是保留 Shell 效率，兼容未知测试框架，根据沙箱能力决定是否需要 LLM，并可缓存脚本分析结果；
同时让 PlanTool、策略决策和 Shell 执行职责清晰分离。

缺点是需要 Shell Parser、统一 ShellTool、风险分类器和跨平台执行适配器。

采用。

## 影响

### 收益

- 保留原始 Shell 复合命令的执行效率。
- 不需要穷举 pytest 等测试框架。
- 强沙箱环境下可以减少脚本执行的人工打断。
- 确定性静态分析可以先过滤明显危险或受控脚本，减少无沙箱环境下的 LLM 调用。
- 无沙箱环境下仍可以通过 LLM 补足静态分析无法判断的脚本语义。
- 复合命令和 heredoc 具备统一的预检和审计模型。
- 外部不可逆副作用在所有模式下都保留明确的人类控制点。
- 普通 Allow、审批和执行绑定同一份可执行文件身份、目标集合和风险视图。

### 代价

- 必须实现可靠的 Shell Parser 和脚本能力提取器。
- 必须维护多语言静态分析规则，并明确其“发现风险而非证明安全”的边界。
- 无沙箱 auto 依赖分类器的成本、延迟和可用性。
- 沙箱和非沙箱平台的自动执行能力不完全一致。
- 内容缓存必须正确处理脚本、依赖和策略变化。
- 必须实现可执行身份解析、受控目标展开、完整审批清单及授权信封重验。

## 验收标准

- `plan` mode 的 `ToolCatalog` 只包含 `PlanTool` 和只读工具。
- `plan` mode 下模型提出 Shell 请求时返回 `tool_unavailable_in_mode` observation。
- 所有 Shell 执行只能通过 `ToolRequestCoordinator`、`ToolAuthorizationService` 和 `ShellTool`。
- `ToolAuthorizationService` 是所有工具共用的授权入口；Shell 请求按 `EXECUTE_SHELL` 分派给
  `ShellCapabilityAnalyzer`，安全模块不以具体工具类型分派。
- `ToolAuthorizationService` 是唯一授权签发服务；`ExecutionAuthorizationEnvelope` 是进入
  `ShellTool` 的必要条件，其他入口不能绕过。
- 规则裁决、`WorkspaceMutationCoordinator` 恢复保障和 `SandboxProvider` 隔离是三个独立层次，
  任一层的成功都不能替代或覆盖另外两层。
- `ShellTool` 不包含安全决策逻辑，不调用 LLM 分类器。
- 安全拒绝返回结构化 `policy_denied` observation。
- 支持复合命令、管道、重定向、命令替换、子 Shell 和 heredoc 分析。
- 支持 POSIX Shell、`cmd.exe` 和 PowerShell 的核心控制运算符、重定向、包装器和嵌套解释器分析。
- `UNKNOWN`、`UNSUPPORTED`、`PARSE_ERROR` 和 `OPAQUE` 先经过 Hard Deny 预扫描，再进入分类器和
  本地策略引擎，不会因静态解析失败直接 Allow，也不会无条件直接 Ask。
- 结构化 `argv` 请求同样分析嵌套解释器、脚本和能力事实。
- 复合命令在任何子进程启动前完成整体预检。
- `python3 - <<'PY'` 被识别为 `EXECUTE_SCRIPT` 并提取脚本内容。
- 临时脚本、heredoc、`-c` 内联代码和可发现的入口依赖进入确定性 `ScriptAnalyzer`。
- 明显危险的脚本能力可在不调用 LLM 的情况下命中 `DENY`；静态分析不完整时不会仅凭不完整结果
  自动放行，而是进入分类器和本地策略引擎。
- 测试框架不依赖穷举白名单。
- `accept_edits` 下脚本执行默认进入 `ASK`。
- `ASK` 在人类确认前不会调用 `ShellTool`；非交互超时不会自动 Allow。
- 人类批准后重新验证计划、内容、目标、凭证作用域、策略和执行环境；任一绑定事实变化都会使旧批准
  失效并重新进入完整安全管线，批准本身不能直接作为执行授权。
- 人类在审批界面拒绝后，本轮不再派发任何工具；模型换用其他命令或工具达成同一目的的请求
  在**派发处**被拦下，不依赖"没有向模型声明工具"这一点。终止范围是本轮，下一轮不受限制。
- 被拦下的工具请求不写入对话 transcript；已排队但未执行的 tool call 仍会收到标记为未执行的
  tool result，不会留下没有配对结果的 tool call。
- 策略 DENY 允许模型改用其他做法，但本轮累计拒绝达到上限后同样停止派发；计数按累计而非连续，
  中间穿插成功调用不重置。
- 达到拒绝上限后的动作是终止并向用户说明，**不是**弹出审批界面 —— 不存在"反复触发 Hard Deny
  换取一次人类批准"的路径。
- 非交互环境下的 `PENDING` 与人类拒绝区分为两种结论，且同样立即停止本轮派发，不会反复重试。
- `git push --force`、发布制品、基础设施 apply/destroy、数据库破坏性迁移等命中
  `EXTERNAL_IRREVERSIBLE_EFFECT`，在包括 `full_access` 的所有模式下逐次 `MANDATORY_ASK`。
- Mandatory Ask 不能由缓存、历史批准、学习规则或 always 满足；审批展示并绑定解析后的真实远端
  目标、计划/内容 hash 和凭证作用域。
- 所有 Allow、审批和缓存都将 executable 解析为绝对 realpath 并绑定文件身份、内容 hash/签名和
  解释器链；工作区和其他 Agent 可写目录中的 executable 不会仅凭名称命中 Allow。
- `rm ./*`、变量目标、`xargs` 和 `find -exec` 等目标集无法静态确定的直接真实工作区写入不能
  获得普通 Allow；简单目标由 Forge 展开并冻结，复杂目标采用两阶段枚举、Overlay 后 materialize，
  或在完整保守上界和 `FULL` checkpoint 下逐次 Ask。
- `target_set_hash`、展开上下文或目标身份变化时旧裁决和审批失效。
- 审批界面展示绝对 executable、完整写/删/移动目标集、网络/远端目标、模式、环境等级、恢复策略
  和具体风险事实；危险部分不可语义截断，完整视图 hash 与授权信封绑定。
- 强沙箱 auto 可以按执行环境策略自动执行脚本。
- 无沙箱 auto 对新脚本、变更脚本、未知脚本和解析不完整的请求调用分类器。
- 分类器异常或低置信度时进入 `ASK`。
- 分类器不能覆盖 Hard Deny，也不能接受主模型或脚本内容中的授权指令。
- 分类结果可以反馈 Agent 用于放弃、重写或主动升级审批，但 Agent 不能把 `ASK`/`DENY` 降级执行。
- Agent 的风险响应被结构化记录，只有提交执行分支进入本地策略引擎。
- 受保护路径规则覆盖平台路径别名、符号链接/junction 和 `/add-dir` 授权。
- `always` 只能创建受限、可撤销、可过期的结构化 Allow 规则。
- 脚本分析缓存能在脚本、依赖或策略变化时失效。
- Parser、ScriptAnalyzer、分类器配置或用户意图范围变化时缓存失效。
- Hard Deny、Mandatory Ask、可执行身份门和目标集合封闭规则不能被模式或分类器覆盖。
