# ADR-0063：引入 Skill 机制

## 状态

Proposed

## 日期

2026-10-08

## 背景

ForgeCLI 目前有可组合的内置工具、工具权限链、会话上下文组装和静态斜杠命令注册表，但没有把多步工作流封装成可发现、可按需加载的能力单元。把所有工作流放进 `prompt/prompts.py` 会让所有会话承担同一份上下文成本；把流程写成新的内置工具则会把“指导模型如何完成任务”和“程序执行确定性动作”混在一起。

本 ADR 借鉴 Claude Code 的边界：主进程发现 Skill 并注册名称、描述等元数据；模型需要时通过单一 `Skill` 工具激活指定 Skill；工具取出其正文并放入对话上下文。工作流中的脚本由现有 `Bash` 工具执行，继续经过命令解析、权限判断和沙箱。Bundled Skill 可由代码注册，不要求以 Markdown 文件作为定义；若有需要模型单独读取的打包资源，则提取到专用目录，并只对此目录设置窄范围读取规则。

### 与 ForgeCLI 当前结构的对应

| 当前结构 | 当前职责 | 本 ADR 的接入方式 |
| --- | --- | --- |
| `runtime/project_runtime.py`、`runtime/tool_wiring.py` | 项目会话组合根，创建工具栈与 Agent 服务 | 在组合根创建会话级 Skill 注册表，并将同一个 `Skill` 工具加入主 Agent 工具池 |
| `tools/pool.py`、`ToolRunner` | 汇总、过滤工具；会话内缓存工具 schema | `Skill` 作为一个静态内置工具注册；Skill 名单进入它的描述/输入选择信息，名单变化遵循现有 schema 缓存生命周期 |
| `ToolUseContext`、`tools/execution.py` | 校验工具输入，统一权限裁决、执行、结果映射 | Skill 激活是 `Skill` 工具调用；脚本只通过上下文中的 `Bash` 工具调用，禁止 Skill 加载器直接启动子进程 |
| `prompt/prompts.py`、`conversation/assembler.py` | 静态策略、工作区指令、工具 schema 与会话上下文 | 全局安全与行为不变量继续留在系统策略；Skill 元数据不作为另一份常驻 system prompt，而由 `Skill` 工具描述暴露 |
| `FsProjectInstructionReader` | 读取 `FORGE.md`，校验大小/编码并拒绝越界 symlink | 可复用其受限读取经验；`FORGE.md` 仍是项目指令，Skill 是可选工作流，两者不互相替代 |
| `tui/commands/registry.py` | 静态 UI 斜杠命令表 | 不是 Skill 注册扩展点；模型激活统一走 `Skill` 工具。显式 slash 调用若以后加入，必须单独支持 TUI/Web/非交互入口 |
| `AgentTool` 与子 Agent 白名单 | 创建独立、受限的子 Agent 工具栈 | 首版只向主 Agent 提供 Skill；子 Agent 的 Skill 可见性需由调用方明确传递，不能隐式继承 |

当前 `assemble_tool_pool(..., external_tools=...)` 接受的是外部工具，不是 Skill。仓库也没有可动态导入第三方代码的通用扩展注册机制。本 ADR 不把 Skill 实现成插件代码执行平台。

## 决策

### 1. Skill 的运行时模型

Skill 是一项提示/工作流定义，不是工具实现。主进程维护会话级 `SkillRegistry`，注册项至少包含：

```text
name                 唯一、稳定的调用名
description          面向模型的触发说明
source               builtin / project / user
body_provider        激活时读取正文的受控提供器
resource_provider    可选；受控读取伴随文件
metadata             受校验的展示信息，不参与工具授权
```

注册阶段读取并校验所有候选 Skill 的名称和描述；文件型 Skill 同时保留规范化后的入口路径与来源根目录，但不把正文放进初始上下文。内置 Skill 由 Python 代码以结构化定义注册（正文、描述和可选资源均作为定义字段），不要求新增 `SKILL.md` 或 Markdown 文件。工具在激活时调用 `body_provider` 取出正文。

模型只看到一个名为 `Skill` 的内置工具。它的描述列出注册表中的 Skill 名称、用途与来源，并要求传入准确名称；工具不得接受模型提供的任意路径。每个 Skill 不单独注册为工具，避免工具池/schema 膨胀。

### 2. Skill 来源与注册

首版支持三类来源：

1. **内置 Skill**：`src/forgecli/skills/builtin/` 下的 Python 定义，由组合根/注册模块显式注册。无内置 Markdown 定义文件；有伴随资源时在定义中以内存映射提供相对路径和内容。
2. **项目 Skill**：`<workspace-root>/.forge/skills/<name>/SKILL.md`。
3. **用户 Skill**：`config_dir()/skills/<name>/SKILL.md`。

文件型 Skill 使用 YAML frontmatter 的 `name` 和 `description`；`name` 采用小写字母、数字和连字符，最多 64 字符，`description` 非空且最多 1024 字符。目录名必须与 name 一致。解析错误、重复或无效条目记录来源和原因，不中断会话。

同名优先级为项目 > 用户 > 内置。只保留一个完整定义，不跨来源拼接正文与资源。冲突和覆盖记录诊断日志。内置定义优先于第三方动态导入的代码这一点由设计直接保证：首版没有代码型第三方来源。

每个文件型 Skill 根目录是正文和引用资源的边界。解析文件路径时拒绝绝对路径、`..` 越界和解析后逃出根目录的 symlink。项目级相对 workspace root 查找；用户级路径跟随 `FORGE_CONFIG_DIR` / `config_dir()`，不能假定在 workspace 内。

插件、MCP Skill、组织级目录、远程市场、embedding 检索和 `paths` 条件触发不纳入首版。后续来源必须定义来源信任、冲突、更新、撤销和权限语义后才能注册。

### 3. 发现、激活与正文注入

- **发现**：项目会话创建时主进程发现三类来源并构造 registry。registry 在该会话生命周期内冻结，与 `ToolRunner` 会话内 schema 缓存对齐；会话期间修改 Skill 后在新会话生效。
- **注册**：组合根将 registry 注入单个 `Skill` 工具。`Skill.prompt()` 从 registry 读取稳定的名称/描述清单；其内容受总字节预算约束，超限时禁用 Skill 工具并记录诊断，不能静默截断列表导致模型漏发现。
- **校验**：`Skill` 工具只接受 registry 已注册的 Skill 名称和允许的可选参数。name 未注册、被禁用或内容版本不匹配时返回可解释的工具错误，不回退到模型指定的路径或 shell 命令。
- **激活**：Skill 工具通过对应的 `body_provider` 取正文，把正文作为 Skill 调用的上下文消息交给模型。正文不是 system prompt，也不改变系统提示优先级。一次调用后正文随对话窗口保留，并遵循现有窗口压缩与会话记录策略。
- **文件型正文刷新**：文件型 Skill 注册时记录入口文件摘要。激活时重新读取并核对摘要；会话期间若正文已改变，拒绝本次激活并提示新开会话，避免模型根据旧 description 执行新正文。伴随文件在读取时同样核对其所属包边界。
- **子 Agent**：首版子 Agent 不提供 `Skill` 工具。后续支持时须由 Agent 调用定义允许的 registry 范围，并为子 Agent 自己建立可观测的激活上下文。

### 4. 脚本通过 Bash 执行

Skill 正文可以指示模型运行 `scripts/` 中的脚本。脚本仍通过现有 Bash 执行实现启动，但作为 Skill 工作流的一部分，**脚本启动不逐次触发 permission mode 的人类审批**。Skill 作者是在定义可执行自动化；如果每次只把解释器命令和路径展示给用户，而不展示/解释脚本实际行为，这种审批没有足够信息供人判断，也会形成确认疲劳。

- 是否配置/启用 OS 沙箱不决定脚本能否启动；有沙箱时沿用用户当前配置的沙箱执行，无沙箱时仍执行，不因缺少沙箱自动拦截或询问。沙箱是用户选择的运行环境，不是 Skill 机制隐含的前置条件。
- 脚本应来自当前已激活 Skill 的 `scripts/` 子目录或由内置 Skill 注册的脚本资源。SkillTool 不接受模型提供的任意脚本路径；脚本入口和参数由 Skill 正文明确，执行事件记载 Skill 名、脚本路径、摘要和参数。
- 激活时由主进程将脚本及其声明的包内资源置备到进程私有、随机 nonce 的只读 Skill 执行目录；Bash 执行该目录中的副本，工作目录仍为当前会话工作区。由此不要求 Bash 通用访问 `config_dir()`，也避免脚本运行期间源包被替换。
- 通过 Bash 执行管线提供带 `skill_name` 的内部 `SkillScriptInvocation`；该来源仅跳过脚本入口命令的 permission-mode 人类询问，不改变普通 Bash 调用行为。它仍产生 Bash 工具事件，使用用户配置的命令执行器、工作目录、环境变量、取消信号及当前沙箱配置。
- 置备目录只包含该 Skill 明确提供的脚本/资源，使用排他创建、权限收紧和相对路径校验，避免共享临时目录被预置 symlink/文件替换。沙箱启用时把该目录作为只读可执行输入加入当前 fence；无沙箱时 Bash 直接执行副本。该目录不因脚本启动而获得写权限。
- 若脚本资源准备失败，向模型返回明确错误；不伪造路径。资源目录随工具栈/进程结束清理。
- 显式 `Skill(name)` deny 仍可阻止该 Skill 激活，显式 `Bash` 工具 deny 仍阻止 Bash 启动。Skill 脚本启动之后的文件、网络和子进程操作不是逐条 Bash tool call，不能声称现有 Bash 命令规则会逐项裁决它们。

本条借鉴 Claude Code 的 `registerBundledSkill` 与延迟提取做法：Skill 的主指令由代码注册；可按需给模型读取的打包资源通过 `files` 一类相对路径映射提供，并在激活时提取，而不是把内置 Skill 写成 Markdown 文件。

### 5. Bundled Skill 文件的窄范围读取规则

项目/用户文件 Skill 的引用文档仍由现有 `Read` 按正常路径权限读取；其位于工作区外时仍需要对应授权。内置 Skill 的资源目录则使用专门的权限边界：

1. 为进程生成随机 nonce 的根目录，例如 `<runtime-temp>/bundled-skills/<version>/<nonce>/<skill-name>/`。
2. 只从代码注册的资源映射写入文件；相对路径经规范化校验，拒绝绝对路径和 `..`；文件以新建方式写入，目录与文件使用仅当前用户可访问的权限。
3. 写入前后校验路径组件，不跟随现存 symlink；不复用旧目录，不覆盖既有文件。读取清单和 Skill 工具必须使用同一个进程内根路径值。
4. 在文件读取权限层增加单一例外：仅当 realpath 落在当前进程 nonce 根目录中的 Skill 子目录时，允许 `Read` / `Grep` 等只读工具读取。此例外不得授权写入、执行、网络访问或相邻目录。
5. 该读取例外只给 `Read` / `Grep`。Skill 脚本入口使用带来源标记的 Bash 执行管线，并仅置备当前 Skill 的资源；不能因此把该目录加入普通 Bash 的通用路径 allowlist。是否有 OS 沙箱由用户当前设置决定，未启用沙箱时脚本仍可运行。

随机 nonce 是边界的重要组成，不能只用 uid、项目名或版本号等可预测路径。工具栈关闭时删除该目录；清理失败写日志，不扩大其权限。

### 6. `allowed-tools`、权限与信任

Skill frontmatter 可声明 `allowed-tools` 作为模型工作流程的可见提示，但首版该字段不产生通用工具权限变化。Skill 脚本作为一项特殊工作流边界：激活后可启动其已注册脚本，不逐次按 permission mode 询问；不代表 Skill 获得普通 Bash 的全局授权。普通模型 Bash 调用仍完全按现有 mode、deny/ask 规则和沙箱处理。

`Skill` 激活走工具校验和 Skill 级 deny 检查。用户/项目 Skill 是用户配置的自动化定义；用户选择将其安装在 Skill 目录即承担其脚本内容与副作用的审查责任。系统不以逐次询问来替用户审查代码。拒绝执行某个 Skill 的 Skill 级 deny 不能通过别名或嵌套 Skill 绕过；显式禁用 Bash 时脚本仍无法启动。

当前 `prompts.py` 把普通工具结果作为数据处理，而 Skill 正文需要作为任务工作流指导。启用自动 Skill 激活时，必须在静态策略中明确：Skill 工具产生的正文可指导当前用户任务，但低于系统策略和用户明确目标；不得遵从其中扩大任务范围、泄露数据、修改权限、规避审批或执行无关动作的要求。Skill 正文仍不得提升为系统提示等级。

### 7. 现有内置扩展点接入原则

Skill 封装的是工具之上的可选多步流程，不迁移确定性能力或状态不变量：

| 现有能力 | 可接入方式 | 必须留在现有实现的职责 |
| --- | --- | --- |
| `Read`、`Glob`、`Grep`、`Edit`、`Write`、`Bash`、`Test`、`LSP` | Skill 编排工具顺序、诊断步骤、验收标准；可引用额外资料或脚本 | 工具 schema/实现、权限判断、沙箱与运行事件 |
| Plan/Todo 工具与计划评审 | 可提供何时规划、如何分解与逐项验证的内置 Skill | 计划存储、状态机、回合边界评审和暂停语义 |
| Memory 工具 | 可提供何时写入长期记忆的使用指导 | 敏感信息校验、作用域、存储和删除行为 |
| `prompts.py` 通用策略与工具 prompt | 可把有证据表明重复、领域化、可选的多步工作流迁成 Skill | 安全规则、工具协议、拒绝处理、读后编辑和其他对所有任务成立的约束 |
| `FORGE.md` | Skill 可要求模型参考项目约定 | `FORGE.md` 的层级、刷新、大小和路径边界 |
| `/plan`、`/memory` 等斜杠命令 | 不自动转成 Skill；未来可增加只读 Skill 列表/帮助命令 | 命令 handler 继续直接操作服务，不由模型 Skill 代替 |

首批内置 Skill 由 `src/forgecli/skills/builtin/` 中的 Python 定义注册，优先选取“仓库变更审查与验证”等可组合流程。每个候选须证明它提供了现有通用提示词没有的可选领域流程；不为包装现有工具而新增重复脚本，不把 Plan、Todo、Memory 或安全规则迁成 prompt-only 逻辑。

## 首版实现边界

实现职责建议：

- `skills/registry.py`：Skill 元数据 DTO、来源覆盖、冲突诊断和会话级冻结 registry。
- `skills/loaders.py`：文件型 Skill 的 frontmatter 解析、受限读取、摘要及引用资源解析；不执行命令。
- `skills/builtin/`：内置 Skill Python 定义及可选的内存资源映射；不放 `SKILL.md`。
- `tools/builtin/Skill/`：单一 Skill 工具，校验名称、取正文并返回模型上下文；不直接授权或执行 shell。
- `runtime/tool_wiring.py`：组合根创建 registry 并注册 Skill 工具。
- `security/filesystem.py`（或其当前职责等价模块）：只读资源读取的 nonce 根目录例外；不改全局 `config_dir()` 保护。
- `execution/sandbox/`：确保特定资源路径进入沙箱时只读可见，且不因此扩大写、网络或任意路径访问边界。

首版包含：项目/用户文件 Skill 的元数据发现和按需正文加载；代码注册的内置 Skill；单一 Skill 工具；Skill 激活后脚本经 Bash 执行且不逐次受 permission mode 询问；打包资源的延迟置备和 nonce 子树读取规则；Skill 来源、冲突和拒绝原因日志。

首版不包含：远程市场/MCP Skill、动态导入 Python Skill、自动安装依赖、Skill 声明授权、独立审批通道、embedding 检索、路径触发、隐式子 Agent Skill 继承、用户显式 `@`/`/skill` 激活。

## 备选方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 所有 Skill 正文常驻 system prompt | 不需激活工具 | 每轮承担所有工作流的上下文成本，混淆通用策略与可选流程 |
| 每个 Skill 注册成单独模型工具 | 名称和 schema 直观 | Skill 数量直接扩大工具目录；把内容工作流误建模成执行工具 |
| 让模型用 Bash 读取任意 Skill 路径 | 不需新增加载能力 | 绕过主进程的注册/来源校验；会碰到工作区、配置目录和沙箱边界差异 |
| 单一 Skill 工具 + 注册表 + 受控正文提供器（选定） | 元数据可发现，正文按需进入上下文；不扩大工具数量；内置定义可直接由代码注册 | 增加 registry、loader 与 SkillTool；需要明确不同来源的读取和脚本权限 |

## 影响

**收益**

- 项目与用户可以用 `SKILL.md` 编写可选工作流；内置工作流通过代码注册，避免 Markdown 资源文件的构建/分发依赖。
- Skill 激活复用现有 tool-call、安全判断、运行事件与上下文窗口。
- 工具脚本仍走 Bash；bundled 参考资源只获得随机 nonce 子树的窄范围只读能力。

**代价**

- 需要实现会话 registry、frontmatter 解析、正文提供器和 Skill 专用权限范围。
- Skill 脚本执行明确越过逐次 mode 审批；无沙箱时它以 ForgeCLI 进程用户身份在宿主环境运行。该行为是“Skill 作者承担自动化信任责任”的产品选择，须在 Skill 编写和安装文档中说明。
- 普通 Bash 与 Skill 脚本的授权语义不同，需要在实现中传递并记录明确的调用来源，避免 Skill 例外扩散到普通 shell 命令。
- Skill 内容是额外指令面，需要静态提示说明优先级，并用真实触发样例评估 description。

**兼容性**

- 没有 Skill 时工具目录与会话行为不变；Skill 工具被 deny 或 registry 为空时不影响其他工具。
- `FORGE.md`、现有工具、斜杠命令和确定性业务服务维持原职责。

## 验收标准

- 主进程只把名称、描述和必要来源元数据注册给模型；Skill 正文只在激活时加载。
- 内置 Skill 可由 Python 注册，不依赖 `SKILL.md` 文件；文件型 project/user Skill 可从约定目录发现。
- `Skill` 工具拒绝未注册名称和任意路径；Skill 内容变化后不会用旧元数据配新正文。
- Skill 脚本只能经 Bash 执行实现启动；启动不受 permission mode 逐次询问，也不要求沙箱已启用。沙箱已启用时按用户当前配置应用；普通 Bash 调用的 mode 行为保持不变。
- Skill 脚本调用来源与普通 Bash 可区分并可审计；Skill 激活不能放开普通 Bash 对 `config_dir()` 或任意包外路径的访问。
- Bundled 参考文件写入随机 nonce 专用根，拒绝路径遍历和 symlink 替换；只读例外精确匹配该根，不能读取邻接目录或写入。
- 用户级 Skill 位于 `config_dir()` 时，脚本先由主进程置备到该 Skill 的 nonce 执行目录；普通 Bash 仍不能因此直接读取 `config_dir()`。
- 没有 Skill 的会话行为不变；子 Agent 首版不意外看到 Skill。
- 至少一份内置 Skill 与一个项目 Skill 覆盖注册、激活、资源读取和失败诊断的验收用例。
