# ADR-0047：采用操作系统文件事件感知并向 LLM 发送结构化变更

## 状态

Proposed

## 日期

2026-09-04

## 背景

Agent 运行期间，工作区可能同时被三类参与者修改：本 Agent 调用的工具、其他 Agent，
以及人类。Agent 如果只依赖工具返回值，就看不到工具通过 Shell 间接产生的文件变化，也
看不到并发参与者的变化；如果只在模型调用前扫描整个工作区，又会产生与工作区规模成正比
的重复 I/O，并且无法及时发现模型生成期间的变化。

文件系统事件可以告诉 Forge 某个目录树中的路径发生了新增、修改、删除或移动，但事件
通常不包含文件正文、行号、diff，也不包含“哪个进程是作者”这一语义。因此需要把事件监听、
内容差异计算和来源归因设计成三个明确分离的步骤。

## 决策

### 决策 1：Agent session 启动时订阅工作区目录的操作系统文件事件

Agent/session 启动时创建工作区变更监控器，并在第一个 turn 开始前监听当前
`workspace_roots`。监听器在多个 turn 之间持续运行，直到 Agent session 结束。监听器
覆盖所有工作区根目录，遵守现有的逻辑工作区范围与忽略规则，不监听 `.git`、依赖目录、
缓存目录等不属于模型工作范围的内容。

监听器通过 application 层定义的端口接入，具体的 macOS、Linux、Windows 机制由
infrastructure adapter 提供。优先使用成熟的跨平台事件库（首选 `watchfiles`），由其
调用操作系统原生能力；application 和 domain 不直接依赖 `kqueue`、`inotify` 或 Windows
API。除业务上没有合适实现的部分外，不手写跨平台 watcher、平台事件解析或线程调度器。

监听器运行在后台，不阻塞 Agent Loop。事件先进入有界队列，并允许短时间 debounce；同一
路径在一次 debounce 窗口内的多次事件可以合并，最终以稳定的路径顺序交给 application。

一个 Agent session 只创建一套 watcher、事件队列和 diff worker。每个 turn 结束、取消或
异常时，执行一次有明确线性化点的监控 reset：清理本 turn 已消费的变更批次，丢弃 reset
之前仍未交给 LLM 的旧批次，以 reset 时的工作区内容建立新基线，然后继续使用同一个
watcher 监听。这里的“重置”只重置监控状态，不回滚、不删除也不覆盖工作区文件。

reset 完成后到下一 turn 开始前发生的人类或其他 Agent 修改，仍然进入同一个 session 的
事件队列，并在下一 turn 的第一次模型请求前交付；它们不能因为处于 turn 间隙而丢失。reset
期间无法确定属于哪一侧的并发事件标记为 `unknown`，或触发重同步。

reset 使用事件序号和 generation 做线性化：监控器在锁内切换到新的 generation，记录旧
事件序号上界，丢弃旧 generation 的待交付 batch，并以当前内容建立新 generation 的基线；
之后才允许新的 batch 进入交付队列。事件到达顺序无法与这个切换点建立可靠关系时，不
静默归入新旧任一 turn，而是标记 `unknown` 或触发重同步。

Agent session 结束、取消或异常退出时才停止 watcher、停止 diff worker、释放队列并清理
session 级状态。若宿主复用进程开始新的 session，必须新建完整监控器，不能复用旧实例。

上一 turn 的 `workspace_changed` 消息可以作为历史审计记录保存在事件流中，但不能作为
下一 turn 的当前工作区变化再次注入 LLM。下一 turn 只接收 reset 之后新观测到的变化，
包括 turn 间隙内已经进入队列的变化。不同 session 之间不得共享 watcher、队列、基线、
diff 缓存或 operation id；结构化记录必须带 `session_id` 与 `turn_id`，防止事件串线。

### 决策 2：OS 事件只作为提示，文件内容 diff 作为模型事实

事件到达后，application 以事件涉及的路径为候选集合，读取变更前后内容并生成
`WorkspaceFileChange`。监听器启动时保存每个候选文件的基线元数据和必要的文本内容；
消费事件时读取当前内容，与基线比较后更新基线。文件内容的逐行比较使用 Python 标准库
`difflib.unified_diff`，hash 使用标准库 `hashlib`；不重新实现成熟库已经提供的 diff
算法或 hash 算法。

因此，OS 事件本身不负责回答“哪些行改动了”。行级信息由内容 diff 算法产生：

```json
{
  "path": "src/forgecli/example.py",
  "kind": "modified",
  "source": "agent",
  "content_kind": "text",
  "before": {"line_count": 28, "sha256": "..."},
  "after": {"line_count": 31, "sha256": "..."},
  "hunks": [
    {
      "old_start": 10,
      "old_count": 2,
      "new_start": 10,
      "new_count": 5,
      "lines": [
        "  old line",
        "-removed line",
        "+added line"
      ]
    }
  ],
  "diff_truncated": false
}
```

`created`、`deleted`、`modified` 是最小文件变更类型。移动如果能被底层事件可靠关联，
可携带 `renamed_from`；无法关联时规范化成一个 `deleted` 与一个 `created`，不凭路径
相似度猜测重命名。

为控制内存、读取和上下文成本，正文和 diff 采用上限。超过上限时仍发送路径、类型、
行数、hash、受影响行范围以及 `diff_truncated: true`，并要求模型重新读取文件；二进制、
无法解码或已不可读的文件发送 `content_kind` 与原因，`hunks` 为空而不是伪造行号。

### 决策 3：向 LLM 发送封闭的结构化变更消息

每组已消费的文件变化形成一个 `workspace_changed` 结构化消息，作为下一次模型请求的
USER 消息追加到当前 turn 的只追加窗口。消息必须经过统一 serializer 生成 JSON，不能只
发送散文，也不能让 prompt 模板自行拼接字段。turn 间隙产生的变化在下一 turn 交付时绑定
到该 turn 的 `turn_id`，同时保留真实的 `observed_at`。事件总线同时发布同一语义的
`WORKSPACE_CHANGED` payload，供终端、Web 和 trace 使用。

结构化消息带有 `session_id`、交付时的 `turn_id` 和 session 内单调递增的 `batch_id`。
`batch_id` 不跨 session 复用；turn reset 会截断上一 turn 的未交付批次，但不会截断
reset 之后产生的批次。跨 turn 的事件流可以保存完整历史，但上下文组装器不得把历史事件
当成下一轮的工作区当前状态。

消息至少包含：

- `event_id`、`observed_at`、`step_index`：定位一次变化及其在 turn 中的位置。
- `changes[]`：每个文件一条记录。
- 每条记录的 `path`、`kind`、`source`、`content_kind`、前后 hash 与行数。
- `hunks[]`、行号范围和 `diff_truncated`；无法计算时明确给出 `diff_unavailable_reason`。

模型收到变化消息后，不得继续假定变更前的读取结果仍然有效；涉及这些路径的后续判断
必须重新读取或验证当前内容。变更消息只提供事实，不替模型决定是否回滚、覆盖或接受
他人的修改。

### 决策 4：采用后台事件采集线程与串行 diff worker

文件事件监控必须异步运行，不能让 Agent Loop 在等待操作系统事件或读取文件时卡住。
线程边界固定如下：

```text
OS watcher thread
        |
        | 只做事件过滤、编号、入队，不读取文件、不调用 LLM
        v
bounded raw-event queue
        |
        | 单一 diff worker: debounce/coalesce、读取内容、计算 diff、更新基线
        v
thread-safe change batch queue
        |
        | Agent Loop 在明确边界原子地 drain
        v
structured message + WORKSPACE_CHANGED event
```

watcher callback 只负责把原始事件写入有界队列。diff worker 是单线程或等价的串行执行
器，保证同一路径的基线更新有序；禁止多个 worker 并发更新同一份基线。Agent Loop 通过
锁或线程安全队列一次性 drain 已完成的 change batch，再把 batch 追加到窗口，避免半个
diff 被模型看到。

队列满、worker 失败、文件读取跨越原子替换或 watcher 状态不确定，都必须生成显式的
`resync_required` 状态。正常路径不能退回到每轮完整扫描；重同步由一个受控 worker 执行，
完成后用新的基线替换当前基线。

### 决策 5：来源归因采用“工具执行窗口 + 不确定性”模型

操作系统事件不提供可靠的业务级作者信息，Forge 不能仅凭事件声称“这个文件一定由本
Agent 修改”。来源字段定义为：

| `source` | 含义 | 归因依据 |
|---|---|---|
| `agent` | 最可能由本 Agent 触发 | 事件发生在本 Agent 工具执行窗口内，且工具返回前后被消费 |
| `external` | 未归属于本 Agent 工具窗口 | 事件发生在 Agent 工具执行前、模型思考期间或工具窗口之外 |
| `unknown` | 无法安全归因 | 监听器溢出、事件延迟，或本 Agent 与外部参与者并发修改 |

当存在并发或事件延迟时，宁可使用 `unknown`，不把它强行标成 `agent`。必要时增加
`attribution_basis` 和 `confidence` 字段，让 UI 和模型知道这是时间窗口推断，不是操作
系统提供的作者证明。`external` 的展示文案应解释为“其他 Agent 或人类等外部参与者”，
而不是声称已识别出具体操作者。

工具执行窗口的起止由统一工具协调管线提供，不由某个文件工具自行上报；这样 Shell、
批处理脚本和未来的复合工具都遵循同一归因规则。窗口状态以及 watcher 事件的接收序号
必须通过线程安全的状态对象传给 diff worker。

事件接收和工具边界之间存在不可消除的时间窗口：文件已经写入但 OS 事件还没有送达时，
Forge 无法知道实际写入时刻；工具启动的子进程也可能在工具返回后继续写文件。因此不得
把“事件在工具返回后才被消费”当成外部修改的证明。若事件序号或时间戳不能确定它属于
哪个窗口，使用 `unknown`，并在记录中写明 `attribution_basis`；只有事件接收时明确落在
本 Agent operation 窗口内，才允许归为 `agent`。

### 决策 6：事件丢失时执行一次显式重同步

OS watcher 可能因为队列溢出、目录被替换或权限变化而丢失事件。adapter 必须把 overflow、
watch failure 或无法确认的路径状态转换为 `resync_required`，而不是静默继续。

收到该状态后，application 对逻辑工作区执行一次完整重同步，并将无法逐事件还原的变化
标为 `unknown`。重同步是事件系统的故障恢复路径，不是正常循环中的轮询机制。

## 事件到模型的时序

```text
Agent session start
      |
      v
start OS watcher --------------------------------------+
      |                                                |
      v                                                v
turn reset <---- event queue <---- watcher thread ---- diff worker
      |                                                |
      +--> next turn request <-- change batch ----------+
```

工具执行完成后先消费一次事件队列并归因，再把工具 observation 写回窗口；模型请求前还要
消费一次，以覆盖模型生成期间、工具派发前以及 turn 间隙的外部修改。turn 完成时执行
reset，但不停止 watcher；检测到变化时，不把旧内容的直接回答当作最终答案，而是追加
结构化变化消息并重新请求模型。

## 备选方案

- **继续在检查点扫描完整快照**：实现简单且容易恢复，但正常成本与工作区规模成正比，
  不能及时接收变化，也不能表达事件丢失；保留为 overflow 后的重同步手段。
- **只使用 OS 事件并直接把事件转给 LLM**：成本低，但没有行号、正文 hash 或前后 diff，
  同一个编辑器的临时文件与原子替换也难以解释，不能满足模型重新判断的需要。
- **由每个文件工具主动上报修改**：可以得到较好的本 Agent 归因，但 Shell、脚本、
  外部 Agent 和人类修改不可见，并且把工作区事实分散给工具作者，不能作为全局事实源。
- **直接读取 Git diff**：能得到部分行级差异，但未跟踪文件、非 Git 工作区、暂存区外的
  中间状态和其他根目录都可能丢失，且不能替代实时文件事件。

## 影响

- 正常路径不再按 turn 扫描整个工作区，监听器和队列增加了后台线程、生命周期管理以及
  adapter 依赖。
- 事件通知能提供路径、类型、hash、行数和受影响行范围；是否包含 diff 正文受大小与
  编码限制，模型始终可以通过工具重新读取当前文件。
- 来源字段是可审计的时间窗口归因，不是操作系统级作者证明；并发场景必须允许
  `unknown`。
- Agent Loop、运行事件、消息 serializer 和前端展示需要共享同一个领域 schema，避免
  UI 与 LLM 各自解释事件。
- ADR-0030 的工作区边界与忽略规则继续有效；本 ADR 不扩大 Agent 的读写权限，也不改变
  工具安全裁决。
- 现有“快照差异”算法可以迁移为事件丢失后的重同步算法，不能继续作为正常变更感知的
  唯一机制。

## 验收标准

- Agent turn 启动后能订阅并停止所有工作区根目录的 OS 文件事件，且监听不阻塞 Agent Loop。
- Agent session 结束时 watcher、队列、基线、diff 缓存和归因状态都被释放；每个 turn
  完成时只 reset 监控内容并建立新基线，watcher 持续运行。
- reset 后到下一 turn 开始前的人类或其他 Agent 修改能够进入下一 turn；上一 turn 的旧
  批次不会进入下一 turn。
- reset 具有可测试的事件序号/generation 线性化点；切换期间无法排序的事件不会静默丢弃。
- 创建、修改、删除和编辑器原子替换都能转换为稳定的结构化文件变化记录。
- 文本修改记录包含前后 hash、行数、受影响行范围和受限 unified diff；二进制与超大文件
  明确标记不可用或截断。
- LLM 下一次请求收到 canonical JSON 形式的 `workspace_changed` 消息；事件总线和 UI
  消费同一个 payload 语义。
- 本 Agent 工具窗口内的变化、窗口外的变化和无法归因的并发变化分别有测试覆盖，并验证
  session/turn 之间不会串入 watcher 状态。
- watcher callback、diff worker 和 Agent Loop 之间的线程安全边界有测试覆盖；同一路径的
  连续事件按顺序合并，不会产生半个 diff 或基线倒退。
- watcher overflow、权限变化、reset 竞态和停止失败不会静默丢失事实，会触发
  `resync_required` 和 `unknown` 归因的重同步。
- 正常事件路径不执行完整工作区扫描；完整扫描只出现在启动基线和显式重同步路径。
