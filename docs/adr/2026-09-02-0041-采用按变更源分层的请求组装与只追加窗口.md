# ADR-0041: 采用按变更源分层的请求组装与只追加窗口

## 状态

Proposed

## 日期

2026-09-02

## 背景

ADR-0018 把系统提示词编译成块序列, 用 `cacheable` 划出稳定前缀; ADR-0032 用预算驱动
去重, 降级与摘要三条通路. 两份 ADR 各自在自己的范围内决定"内容怎么排", 而决定成本的
是**整条序列化请求上的位置**.

本 ADR 只做第一阶段: 把请求的分层与窗口的增长治住. 结构化状态 (台账) 留到 ADR-0043,
判据是本阶段跑出来的实测数 (见验收标准的三个指标).

### 1. 块内部的缓存分区买不到任何东西

请求是线性的: `[tools][system][messages]`. `_assert_cache_partition` 保证
`cacheable=False` 的块排在 `PromptSnapshot` **内部**靠后, 但整个 system prompt 都排在
messages 之前. 于是 `RUNTIME_FACTS` / `PLAN_STATE` / `TODO_STATE` / `MEMORY_STATE` 任何
一块变化, 全部历史退出缓存.

接 Anthropic 那种显式断点也解决不了: 断点只划得出 system 内部的前缀, 易变尾部仍在
messages 之前.

`cacheable` 与 `_assert_cache_partition` 因此是 ADR-0028 规则 C 说的**摆着不生效的
字段**. blocks.py 给它写的第二条理由 (为无 system role 的 Provider 重排) 同样没有消费方.

### 2. 三条压缩通路里有两条是中段改写

`transcript.rewrite` 按位置改写工具结果正文, 去重与降级都走它.

dedup.py 在 2026-09-01 记下过实测: 一次 `fs_apply_patch` 之后 17,154 输入里 7,298 未命中,
占 20%; 改文件密集的那一轮三次改写合计 79,321, 占 57%, 净亏五到十倍. 那次修订把变更通知
挪到了尾部, 但去重与降级仍然在改中段.

结论应该更彻底: **窗口只追加, 任何回头改写它的机制都是负收益.**

### 3. 窗口增长的主项是 body, 而现在没有人按上下文口径管它

每一步进窗口的东西里, assistant 文本 + tool_calls + 结果摘要合计约 300 token, 稳定且可
预测. 全部方差来自工具结果正文.

`ArtifactPolicy.max_inline_bytes` 缺省 16 KiB (约 4k token), `ResourceGovernor` 全局上限
64 KiB (约 16k token). 溢写机制本身是对的, 但这两个数来自 ADR-0014 的执行资源治理,
回答的是"一次调用能占多少内存和磁盘", 不是"这条正文值不值得在往后每一轮都重发一遍".

按每三步一次文件读取算, 现在的窗口增长约 1k token/步; 正文不进窗口则约 300/步. 一次
100 步的会话是 100k 与 30k 的差别.

### 4. 逐条滑动是最贵的淘汰策略

"保留最近 N 条"每轮从头部丢一条, 而头部就是前缀的开头 —— 每一轮都在付整段重算的钱.
同样的平均窗口长度, 分段批量淘汰把作废频率降到每若干十步一次.

### 5. `ToolResult.text` 把结构化字段拍平

`text` 属性把 `content_parts` 与 `error.message` 拼成一段文本. 于是下游想知道"这次调用
做了什么"只能重新解析散文, 而 `status` / `metrics.exit_code` / `provenance.mutated_paths`
在拼接的那一刻就丢了. `ToolObservation.digest_line` 现在的做法就是从拼接结果里取第一行.

`coordinator.py:623` 的注释已经在抱怨同一件事: "result.text 会把所有内容块拼成一整段,
一次大文件读取就是几 MB".

### 6. 水位按窗口比例算, 大窗口模型会得出一个没有意义的数

`ContextBudget.compact_ratio` 现在是 0.75, 而它的理由 (模块说明里) 是**防溢出的机械
余量** —— 留给摘要调用的空间, 加上估算偏差. 它不是注意力阈值, 两者只是数字接近.

真正的注意力约束是**绝对 token 数**, 不是填充比例: 同样 30k 内容放在 200k 窗口 (15%)
与放在 32k 窗口 (94%) 里, 模型对那 30k 的处理能力基本一样, 后者的区别只是快撞硬限了.
位置效应 (开头与结尾的召回明显高于中间) 同样是位置的函数, 与填充率无关.

于是"标称窗口"这一个数不足以定水位: 按比例算, 一个 200k 的模型会得出 150k 的高水位,
而那远超任何模型能可靠工作的长度.

### 7. 分层的判据是变更源, 不是内容类别

现有分层按内容分 (身份 / 工具 / 运行事实 / 计划 / 待办 / 记忆), 而缓存只认变更频率.
两个判据不一致, 于是一块每轮变的内容可以合法地排在几十轮不变的内容中间.

## 决策

### 决策 1: 请求按变更源分六层, 顺序即层号

| 位置 | 层 | 生命周期 | 变化触发 | 归属 |
|---|---|---|---|---|
| [1] | 工具目录 | 模式级 | 换档 | `ToolCatalog` |
| [2] | 内置静态策略 | 包版本级 | 升级 | `application/prompt` |
| [3] | 工作区指令 | 会话级快照 | 会话开始 | `application/prompt` |
| [4] | 运行上下文 | 模式级 | 换档 / `/add-dir` | `application/context` |
| [5] | 会话窗口 | 只追加 + 罕见批量淘汰 | 每步 / 撞水位 | `application/context` |
| [6] | 当前状态帧 | 每轮重建 | 计划 / 待办 / 记忆变更 | `application/context` |

[1]-[4] 同属缓存前缀, 一起命中或一起失效. [5] 只在尾部增长. [6] 每轮重建, 但它是整条
请求的**最后一个内容块**, 后面没有任何东西会被它作废. **用户输入不是独立一层**,
它是 [5] 里的一条普通消息.

顺序由 `AssembledContext.system_prompt` 与 `to_request_messages()` 两个函数表达
(请求在协议上就有 system 与 messages 两个槽), 不散落在调用方.

**[6] 原本打算留到 ADR-0043 的台账一起做, 落地时提前了**: 计划, 待办与记忆是提示词里
仅有的每轮可变内容, 而它们没有别的去处 —— 塞进 [4] 会让决策 2 那条"它的变化是 [1] 的
子集"当场不成立, 不做又是一次没人批准过的行为回退 (模型看不见自己的待办清单).

提前的代价很小: 三份模板换个目录, `AssembledContext` 多一个字段, 一个渲染函数. 收益是
缓存的全部好处现在就拿到 —— 一次 `todo_write` 不再作废整个窗口. ADR-0043 只需换掉填充
[6] 的东西 (台账视图顶掉计划待办记忆), 不用再动位置.

### 决策 2: 运行上下文进前缀, 不进尾部

mode / cwd / workspace_roots / 隔离级别 / 能力边界的变化源只有换档与 `/add-dir`, 都是
罕见的离散事件.

关键理由: **它的变化是工具目录变化的子集** —— mode 一变, `catalog_for(mode)` 跟着变,
而目录在位置 [1], 整条请求已经作废. 把运行上下文放进前缀, 额外成本恰好为零; 放到尾部
则是每轮重建约 400 token 换不来任何东西.

`current_time` 是例外: 每轮变的时间戳绝不能进前缀. 本阶段只放会话起始日期 (会话内稳定).

未闭合的审批与评审状态本阶段归运行上下文渲染; ADR-0043 引入台账后改归 `OPEN` 条目.

### 决策 3: 工具目录的生命周期是模式级, 不是 turn 级

现在按 turn 重算 (`catalog_for(mode)`) 是实现事实, 但把它**描述**成 turn 级是危险的:
它排在整条请求最前面, 一变就没有任何东西能幸免, 而 turn 级的说法会让"每轮换一批工具"
看起来是合法的设计空间.

加一条可测的不变量:

> 同一模式下, 相邻两轮的 `catalog_snapshot_hash` 必须相同.

这条同时把将来的工具检索挡在门外: 要做, 必须先推翻这条不变量.

### 决策 4: 窗口只追加, 删掉中段改写的机制入口

`transcript.rewrite` / `Slot` / `slots_of` 整体删除. 留着它就等于留着退回去的路 ——
而"回头整理一下历史"永远是看起来合理的.

去重与降级两条通路随之删除. 它们各自的能力有了写入期的替代 (决策 6).

### 决策 5: 批量水位淘汰, 绝不逐条滑动; 水位是导出的, 不是常量

窗口设高水位与低水位. 平时只追加; 撞到高水位时**一次性**淘汰到低水位, 之后若干十步
不再动.

**两个上限分开表达** (背景 6):

```text
硬限  context_window - reserved_output_tokens   超了供应商报错
软限  effective_context_tokens                  超了不报错, 只是模型开始漏读
```

软限是模型特性, 推不出来, 与 `context_window` / `max_output_tokens` 并列进
`ModelCatalogEntry`. 未知时取 `context_window` —— 那让它退化成无操作, 由硬限兜底,
而不是拿一个猜出来的数去砍窗口.

```text
request_high_water = min(
    effective_context_tokens,
    (context_window - reserved_output_tokens) × compact_ratio
)
request_low_water  = request_high_water × 0.4
```

`compact_ratio` **从 0.75 提到 0.80**. 它保留原来的职责 —— 自动压缩的触发阈值, 兼防
估算偏差 —— 但不再需要那么保守, 理由有二: 软限现在承担了"别让上下文长到伤注意力"这件事;
而摘要那次调用的输入是被淘汰区间, 是当前窗口的**子集**, 它必然放得下, 原来为它留的
那份余量是多算的.

估算偏差方向也已经查过, 是安全的: `ApproximateTokenEstimator` 对 CJK 按一字符一 token,
拉丁与代码按 3 字符一 token (实测 deepseek 3.05 / GLM 3.89, 取 3 不会少算), 且已把
`tool_calls` 的参数算进去. 它系统性**高估**, 提到 0.80 之后真实占用仍在硬限之下.

**水位管的是整条请求, 不是只管窗口** —— 注意力与硬限都是对整条请求而言的. 窗口的份额
是减出来的:

```text
window_allowance = request_high_water − ([1] 工具目录 + [2] 静态策略
                                          + [3] 工作区指令 + [4] 运行上下文)
```

低水位取高水位的 0.4: 这个比值决定**淘汰频率**. 贴太近就变成每几步淘汰一次 (前缀反复
作废, 退化成决策 5 要避免的滑动); 压太低就一次丢掉过多. 0.4 意味着每次回收约六成,
按每步约 300 token 算, 淘汰间隔在数十步量级.

淘汰点必须落在 `safe_split_points` 给出的位置上: 从 tool call 配对中间切开, 供应商会
拒掉整个请求.

三条附加规则:

- **用户消息永不淘汰.** 它占窗口不到 2%, 一次会话十几条, 而用户约束是摘要最容易丢
  且丢了最贵的东西. 被淘汰区间里的用户原话逐字提到摘要块里.
- **淘汰区间做一次模型摘要** (决策 7).
- **最小保留步数 K ≥ 3**, 且由决策 8 的不变量在构建期保证它放得下.

### 决策 6: 工具结果分三段, body 是否进窗口逐工具声明

```text
summary   一行, 必填          "读了 fs_read.py, 92 行, 未截断"
data      结构化小字段, 必进   {"path": ..., "lines": 92, "sha": "3f9a…"}
body      不限长, 默认不进     溢写 artifact, 窗口里留 handle
```

`ToolSpec.body_in_window: bool = False`. 改代码之前的读取要进 (`fs_read`), 一次目录扫描
不进 (`fs_find`).

`ArtifactPolicy.max_inline_bytes` 缺省从 16 KiB 收到 8 KiB, `ResourceGovernor` 全局上限
从 64 KiB 收到 16 KiB. 机制不变, 变的是这两个数按什么口径定.

**去重与变更通知随之内建到写入期.** 同一路径同一状态被读第二次时, 工具在产出那一刻就
知道 (`source_state` 相同), 直接回 `body=""` + handle + 一句"内容与第 N 步相同". 确定性,
不改写历史, 不需要一个跨消息的 pass.

一个产不出简短 `summary` 的工具本身就是设计得不好. 这个约束把质量压力推到它该在的地方.

`shell_run` 一类跑任意命令的工具是明确的例外: 它给不出有意义的 `data`, 退化成
`summary` (命令 + 退出码 + 输出规模) + `body`, 不硬编一份 schema.

### 决策 7: 摘要保留, 但触发从"快溢出"改成"撞水位"

ADR-0032 的二级摘要**不删**. 本阶段没有台账, 被淘汰的区间里除了工具结果还有 assistant
的自然语言 (取舍理由, 承诺, 对用户约束的复述), 那些提取不出来, 丢了就是丢了.

改的是三处:

- **触发点**: 从"压不下去了"改成"窗口撞高水位". 高水位 30k 对 200k 窗口, 摘要不再是在
  上下文已经吃紧时跑 —— 那时候摘不好就没有第二次机会.
- **产出位置**: 摘要块是淘汰后窗口的**第一条消息**, 里面含逐字保留的用户原话. 淘汰本来
  就改了前缀, 摘要放这里不额外增加成本.
- **可信度**: 摘要块里转述的 assistant 说法标注为未经验证; 用户原话那一节标注为逐字.
  模型说过"我接下来会重构 X", 摘要之后不能读起来像已经做完了.

`CONTEXT_COMPACTED` 事件保留 (摘要不可复现, 必须落 payload), ADR-0037 的计量保留.

### 决策 8: 预算的硬序与构建期不变量

**硬序**: `[1] 工具目录` + `[2] 静态策略` + `[3] 工作区指令` + `[4] 运行上下文` +
最近 K 步是不可压层. 它们放不下就停下并交回用户 —— 这不是管道故障, 是"你手上要带的
东西比装得下的还多"这个结论.

**构建期不变量**, 不留给运行期去撞:

```text
max_inline_bytes × 最小保留步数 K  <  window_low_allowance
```

其中 `window_low_allowance = request_low_water − 前缀`. 8 KiB × 3 ≈ 6k, 对一个软限 64k
的模型成立; 对软限 32k 的模型不成立, 于是那台机器上的配置在**构建期**就被拦下 ——
要么关掉 `body_in_window`, 要么收 `max_inline_bytes`. 小窗口模型的配置问题不该留到
运行期去撞.

**超长用户输入**按工具结果同样处理: 存 artifact, 窗口留 summary + handle, 并明确告诉
用户内容已存为 X 会按需读取. 不静默截断.

### 决策 9: `ToolResult.text` 拆成两个出口, 不删除

查过消费方: `fence_hint` (安全围栏), 协调器日志, `ToolObservation.digest_line` 与
`render` —— 四处, 跨安全与展示两层. 直接删会伤到围栏.

```text
render_for_model()   summary + data + (可选 body), 给窗口用
raw_output()         原始输出全文, 给 fence_hint 用
```

围栏检的是命令**实际输出**里有没有越界痕迹, 拿 summary 去检等于把这道防线关掉.
`digest_line` 正好改成直接取 `summary` —— 它本来就是在从拼接文本里猜一个摘要.

### 决策 10: 每轮未命中的 input token 是回归指标

`ModelUsage.cached_input_tokens` 已由 adapter 归一化. 未命中量应当约等于本轮新增内容量.

把它做成可回归的量, 而不是靠人事后翻日志: 一次固定脚本的会话跑完, 未命中总量有上限用例.
这条比任何 review 都更能挡住"顺手往前缀里加一句"的回归 —— 那种回归不报错, 只是变贵.

## 实施清单

### domain/context/

**重写 `budget.py`** —— `ContextBudget` 保留 `context_window` /
`reserved_output_tokens` / `compact_ratio` (缺省从 0.75 改为 **0.80**), 新增
`effective_context_tokens`; 删除 `needs_compaction` / `over_allowance`, 新增派生属性
`request_high_water` / `request_low_water` 与方法
`window_allowance(prefix_tokens: int) -> int`.

同时修掉一处**过期的模块说明**: 现在写着"`ApproximateTokenEstimator` 按 4 字符折 1
token", 而估算器的实际常数是 3, 且 CJK 单列按一字符一 token 算. 一句已经不成立的理由
会让下一个读它的人照着不存在的行为去调阈值.

**新增 `window.py`**

| `WindowPolicy` (frozen) | `high_water_tokens` / `low_water_tokens` / `min_steps`; 由 `ContextBudget` 与前缀实测值导出, 不手写; `__post_init__` 校验决策 8 的不变量 |
| `Window` (frozen) | `messages` / `evicted_count`; 方法 `append` / `needs_eviction` / `plan_eviction` |
| `EvictionPlan` (frozen) | `split_index` / `dropped_messages` / `preserved_user_messages` |

**保留 `compaction.py`** —— `CompactionDraft` 保留, `CompactionLevel` 收敛为单值
(`SUMMARY`), 因为 `DOWNGRADE` 那一级随决策 4 消失.

### application/context/

**保留并改写 `summarize.py`** —— `summarize()` 的签名加 `preserved_user_messages`,

`effective_context_tokens: int | None = None`, 与 `context_window` /
`max_output_tokens` 并列. `None` 表示未知, 取 `context_window` 退化为无操作.

这是本阶段唯一动到 `domain/model` 的地方, 但绕不开: 有效上下文长度是**按模型不同**的
事实, 与窗口大小不成比例, 除了模型目录没有别的地方可放.

### domain/tool/

**重写 `result.py`**

- `ToolResult` 新增 `summary: str` (非空校验) 与 `data: Mapping[str, object]`;
- `ToolResult.text` 改名拆分为 `render_for_model()` 与 `raw_output()` (决策 9);
- `ResultProvenance` 保留全部字段, `dedupable` 属性保留 —— 决策 6 的写入期去重仍然用
  `(source_path, source_state)` 这对判据, 只是判定点从 `ContextManager` 挪到工具内部.

**重写 `spec.py`**

- `ToolSpec` 新增 `body_in_window: bool = False`;
- `ArtifactPolicy.max_inline_bytes` 缺省 16 KiB → 8 KiB.

### domain/conversation/

**`message.py` 不动.** 原计划把 `ToolResultBlock` 拆成
`tool_call_id` / `summary` / `data` / `body` / `handle`, 落地时判断为**本阶段的冗余设计**:

正文进不进窗口的闸门是 `ToolObservation.render()` —— 那是唯一需要做这个决定的地方, 而
它下游全是字符串管道 (`LoopObservation.content` -> `ToolResultBlock.content` -> provider
的 role=tool 消息). 在块上再拆一次, 就有了**第二个组装点**: 同一段文本, 一处按 include_body
拼, 一处按字段拼, 两处迟早不一致.

本阶段也没有消费方需要那个拆分 —— token 估算, 缓存指纹与 adapter 序列化要的都是"发出去的
那一段字". 拆分的价值在 ADR-0043: 台账要按段建条目. 到那时它有了真实的消费方, 再拆.

`domain/agent/actions.py` 的 `LoopObservation` 仍要加一个字段: `handle`. 它不是为了拆分,
是给 `_track_progress` 用的 —— 正文移出窗口之后 `content` 变短, 两次不同的调用更容易撞出
同一段文字, 而句柄是内容寻址的.

## 不在本阶段的范围

台账 (结构化事实 / 失败签名 / stale 标记 / 来源分档) 留到 ADR-0043. 它解决的是**正确性**
(用过期读数, 打转, 淘汰后失忆), 与本阶段解决的**成本**是两个问题.

是否要做由本阶段的三个实测数决定:

- 一次典型会话有没有触发淘汰? 没有 → "熬过淘汰"这个价值为零;
- 重读率高不高? 低 → stale 标记的价值有限;
- 打转发生频率? 低 → 失败归并可以先不做;
- **位置**: 本阶段之后, "用户最初要什么"仍然躺在窗口中段 —— 而位置效应最弱的正是中段
  (背景 6). 台账视图作为整条请求的最后一个内容块, 是把当前状态从中段搬到末尾的手段.
  这一条与前三条不同, 它**不是成本论证**: 成本可以靠水位缓解, 位置不能.

第四条也说明了本阶段的边界: 它解决成本, 对注意力的改善只是副产品 (body 不进窗口 →
高度相似的干扰项变少). 位置问题留到 ADR-0043.

先写台账再量, 就是拿一份 469 行的设计去赌一个还没测过的问题.

## 备选方案

- **方案 A: 保留三条压缩通路, 只调水位.** 优点是改动最小. 缺点是去重与降级都是中段改写,
  背景 2 的矛盾原样保留.
- **方案 B: 滑动窗口 (保留最近 N 条).** 行业默认做法. 缺点见背景 4: 前缀缓存下它每一轮
  都在付整段重算的钱.
- **方案 C: 运行上下文放到请求尾部.** 优点是它确实每轮可能变. 缺点见决策 2: 它的变化是
  工具目录变化的子集, 放尾部换不来任何东西, 只多 400 token/轮.
- **方案 D: 一并把台账做了.** 优点是一次到位. 缺点是它把成本问题与正确性问题绑在一起,
  而后者需要前者的实测数才能定范围.
- **方案 E: 删掉摘要.** 优点是全链路无不可复现状态. 缺点是本阶段没有台账, 被淘汰的
  assistant 自然语言 (取舍理由, 用户约束的复述) 提取不出来, 丢了就是丢了.

## 影响

**收益.**

- 每轮未命中的 input 从"整段历史"降到"本轮新增内容"; 淘汰只在罕见的水位事件上发生.
- 窗口增长从约 1k/步 降到约 300/步, 一次 100 步会话从 100k 量级降到 30k 量级.
- 去重与降级两条通路及其占位措辞消失; `application/context` 显著变小.
- 下游第一次能直接拿到结构化结论, 不必解析散文.

**代价.**

- 每个内置工具都要补 `summary` / `data` / `body_in_window`. 这是本阶段的主要工作量.
- `ToolResultBlock` 换形状牵动四个下游 (token 估算, 缓存指纹, adapter 序列化, 构造点),
  其中缓存指纹漏改不会报错.
- 工具结果上限收紧后 `artifact_read` 调用次数上升. 这是有意的取舍: 一次按需取回, 换掉
  往后每一轮的重发.
- 只追加买到了缓存稳定, 代价是**失去选择性丢弃**: 同一文件改前改后的两份正文都躺在窗口
  里, 而前一份已经过期. 缓解手段只有写入期的两条 (收 body 上限; `fs_read` 默认读行段).

**约束.**

- 窗口只追加. `transcript.rewrite` 删除之后这条是机器守得住的.
- 同一模式下相邻两轮的 `catalog_snapshot_hash` 必须相同.
- `max_inline_bytes × K < low_water` 在构建期校验.
- 淘汰点必须落在 `safe_split_points` 上.

## 验收标准

- 一个回合内连续两次模型调用, `[1][2]` 两层与已有消息序列**逐字节相同**; 用例直接断言
  相等, 不是只看 usage.
- 回合结束时循环交出的是**完整窗口**含工具往返, 驱动方原样接过去 —— 跨轮重建一份不一样
  的历史本身就是一次中段改写.
- 同一模式下相邻两轮 `catalog_snapshot_hash` 相同, 有用例.
- 淘汰只在撞高水位时发生; 一次固定脚本会话里淘汰次数有上限用例.
- 淘汰后窗口首条是摘要块, 其中含被淘汰区间的全部用户原话逐字.
- 淘汰点落在 `safe_split_points` 上; 构造一个末尾欠着 tool result 的 transcript,
  断言不会从中间切开.
- `WindowPolicy.assert_fits` 在低水位装不下**一条**满额工具结果时给出诊断, 且它有真实
  调用方 (`WindowManager` 导出水位之后调一次) —— 一条没人调的校验就是 ADR-0028 规则 C
  说的摆着不生效的字段.
- 判据取"一条"而不是"最小保留步数条": 只有 `fs_read` 把正文带进窗口, 而 `max_inline_bytes`
  是上限不是常量. 按每条都满额去算会拒掉一个完全正常的 64k 模型, 而一条不该响的警报比
  没有警报更糟. 正反两个用例都要有.
- 这条**只记不抛**: 抛出去等于让一个偏紧的配置直接判死一轮, 而淘汰在那种配置下仍然有用.
  它也不能是纯构建期检查 —— 水位跟着当前模型走, 而用户随时可以换模型.
- 水位由 `ContextBudget` 导出: `effective_context_tokens` 为 `None` 时退化为
  `(context_window − reserved) × 0.80`; 给定时取两者较小值. 两条分支各有用例.
- 同一份 transcript 在 200k 与 32k 两个模型条目下得出不同水位, 有用例 —— 防止水位被写死。
- 每个内置工具的 `summary` 非空, 用例对全部工具参数化.
- `fence_hint` 收到的是 `raw_output()` 而不是 `render_for_model()`, 有用例.
- 逐字保留的用户原话**有上限且不复利**: 一段全是用户消息的窗口, 淘汰完必须真的降到高
  水位以下 (落地时实测过一次相反的结果: 高水位 4000, 淘汰后 16212 —— 交接说明本身走
  user 角色, 下一次淘汰会把它整段再抄一遍). 两条回归用例分别守住上限与不复利.
- `application/context` 下无 `Slot` / `rewrite` 导出; `transcript.py` 只导出
  `safe_split_points`.
- 一次固定脚本会话跑完, 未命中 input 总量有上限用例.
- `make ci` 通过.
