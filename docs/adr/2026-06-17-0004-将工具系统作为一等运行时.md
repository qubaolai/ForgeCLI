# ADR-0004: 将工具系统作为一等运行时

## 状态

Accepted (2026-07-31 细化修订)

细化部分与 ADR-0013 / ADR-0014 / ADR-0015 组合生效. 这三份仍为 Proposed, 但工具系统的契约
必须先于它们冻结: 安全, 沙箱和恢复三层都是工具契约的消费者, 不是工具系统的内部实现.

## 日期

2026-06-17 (2026-07-31 细化修订)

## 背景

工具是 CLI Agent 执行真实动作的核心入口, 涉及文件, shell, git, 测试, MCP 和外部系统. 如果工具
仅作为 infrastructure 细节, 会削弱权限控制, 审计和统一扩展能力.

原始版本只确定了"工具是一等运行时"这个方向, 没有定义工具系统对外暴露什么接口. 07-29 之后引入的
ADR-0013 (命令安全决策), ADR-0014 (沙箱与执行画像) 和 ADR-0015 (工作区恢复) 都需要在工具执行
之前介入, 这暴露了四个必须解决的问题:

1. **旧验收标准把策略调用写进了工具执行路径.** 原文要求"工具执行必须经过 ModePolicy 和
   ApprovalService", 而 ADR-0013 决策 2 明确 `ShellTool` 不是安全决策者, 方案 D 也明确否决了
   在工具内部实现安全决策. 同时 ADR-0009 已废弃, `ModePolicy` 的旧口径不再成立.
2. **安全模块与工具实现之间存在耦合风险.** 如果 `ToolAuthorizationService` 需要认识 `ShellTool`,
   `FileTool` 等具体类型, 那么每新增一个工具都要同步修改安全模块, 而漏改的默认后果是"没有规则
   匹配", 即静默放行. 反过来, 如果工具需要认识模式, 审批和分类器, 那么每条安全策略变更都会扩散
   到全部工具实现.
3. **工具来源是异构的.** builtin, MCP 和 skill 引用的工具在 schema 质量, 可信度和可分析程度上
   差异很大. MCP server 返回的 name, description 和 schema 属于不可信输入, 不能与内置工具共享
   同一套隐式信任.
4. **可选授权会形成安全旁路.** 如果 `ToolSpec` 允许通过 `requires_authorization=false` 跳过授权,
   那么工具能力升级, MCP schema 变化或新增调用入口时都可能继续复用旧的免授权路径. "只读"也不能
   作为例外: 读取凭证, 工作区外文件或企业数据仍然需要策略裁决. 授权必须是执行运行时的不变量,
   而不是由单个工具自行声明的开关.

此外还需要在同一份契约里覆盖: 长输出与产物, 并发与冲突, 取消与超时, 崩溃后未知结果的恢复, 以及
工具输出作为不可信内容回填模型的问题.

因此本次细化的目标是: **工具系统只提供机制, 安全模块只提供策略, 两者通过 `domain/tool` 中的
稳定契约通信, 互不 import 对方的实现.**

## 决策

### 1. 工具系统是机制层, 不是策略层

工具系统拥有:

```text
ToolSpec 定义与注册
ToolRegistry 与 ToolCatalog 视图
工具入参 schema 校验与规范化
ToolPlan 生成 (把入参变成结构化, 可裁决, 可执行的计划)
授权信封的绑定校验
工具执行, 取消, 超时和资源回收的机制
ToolResult 归一化, 截断和产物落盘
调用级事件与工具侧审计字段
```

工具系统不拥有:

```text
mode 语义与能力预算
allow / deny / ask 规则匹配
Hard Deny 与 Mandatory Ask
审批流程与审批展示
Background Safety Classifier 与风险缓存
沙箱策略, 实例生命周期和受保护路径判定
工作区恢复点与 MutationSet 决策
```

判定原则: **凡是"要不要做"的判断都不属于工具系统; 凡是"怎么做"的机制都属于工具系统.**

工具实现代码中不得出现 mode 判断, 规则匹配, 审批调用和分类器调用. 这不是编码风格建议, 而是
可以被静态检查的硬约束, 见决策 13.

### 2. 统一调用契约: describe → prepare → execute

所有工具都只暴露三段接口 (将来接入外部来源时同样适用):

```text
ToolRegistry.describe(name) -> ToolSpec
ToolRegistry.list(query)    -> ToolCatalog

Tool.prepare(ToolInvocationRequest, ExecutionContext) -> ToolPlan | PreparationError

ToolRuntime.execute(ExecutionAuthorization, CancelToken) -> ToolResult
```

完整链路为:

```text
AgentLoop 产出 request_tool 意图
  ↓
ToolRequestCoordinator (application, 唯一装配点)
  ↓
ToolRegistry.describe / Tool.prepare        工具系统: 事实
  ↓
ToolPlan
  ↓
ToolAuthorizationService.evaluate (ADR-0013) 安全模块: 分析并裁决
  ↓
AuthorizationDecision
  ├─ DENY  → policy_denied
  ├─ ASK   → ApprovalService 阻塞等待人类决定
  │            ├─ 拒绝 → approval_denied
  │            └─ 批准 ─┐
  └─ ALLOW ────────────┘
  ↓
ToolRequestCoordinator.revalidate            重验计划, 策略与执行环境
  ↓
WorkspaceMutationCoordinator (ADR-0015)     恢复层: 可恢复性
  ↓
ToolAuthorizationService.issue              签发绑定恢复与执行画像的授权
  ↓
ExecutionAuthorization (含 effective_plan)
  ↓
ToolRuntime.execute                         工具系统: 机制
  ↓
SandboxProvider / NoSandboxProvider (ADR-0014, 仅进程类工具)
  ↓
ToolResult + Artifact + Event
```

`ToolAuthorizationService` 是所有工具共用的授权入口. 它按 `ToolPlan.capabilities` 分派能力分析器;
Shell Parser 与 ScriptAnalyzer 是其中针对 `EXECUTE_SHELL` / `EXECUTE_SCRIPT` 的分析组件, 不是
全局入口. 通用入口的命名和接口不得退化为只覆盖 Shell 或某一种具体工具.

规则引擎, 恢复系统和沙箱是三个独立层次:

- `ToolAuthorizationService` 根据能力事实, mode, 规则和审批判断"是否允许".
- `WorkspaceMutationCoordinator` 判断真实工作区变更"是否具备恢复保障".
- `SandboxProvider` 根据已经冻结的执行画像限制进程"实际能够触达什么".

安全 `ALLOW` 或人类批准都不能替代恢复点与沙箱约束; 沙箱存在或恢复能力充足也不能覆盖 `DENY` /
`ASK`. 三者由 `ToolRequestCoordinator` 顺序装配, 不互相拥有对方的策略或生命周期.

关键约束:

- `prepare` 只读, 不产生任何真实副作用. 允许通过受限的只读规划视图访问路径元数据和安全分析所需
  的本地内容, 用于路径规范化, 目标展开和能力提取, 但必须使用 `ExecutionContext` 中已经冻结的
  cwd, 环境快照和文件系统视图. `prepare` 不得启动进程, 访问网络, 修改文件或外部状态, 也不得把
  规划阶段读取的敏感内容直接放入面向模型的 `PreparationError` 或其他 observation.
- `prepare` 失败返回结构化 `PreparationError`, 直接回填模型, 不进入安全裁决.
- `execute` **只接受授权信封中的 `effective_plan`**, 不重读原始入参, 不重新解析用户或模型提供的
  字符串. 这消除了"裁决对象"与"执行对象"之间的 TOCTOU 缺口.
- **所有**进入 `ToolRuntime.execute` 的调用都必须携带本次调用的有效授权, 包括 pure, 只读和
  `PLAN_ONLY` 工具. 普通工作区只读可以由安全模块通过快速路径自动 `ALLOW`, 但仍须签发授权信封.
  系统授权不等于人工审批; 只有裁决为 `ASK` 时才进入人类审批流程.
- 没有有效授权时 `ToolRuntime` 直接拒绝执行并返回 `authorization_missing`, 属于 fail closed.
  不存在"未配置安全模块就直接执行"的默认分支, 也不存在按工具配置的免授权执行通道.

### 3. ToolSpec 声明的是能力上界, 不是放行证明

`ToolSpec` 字段:

```text
name                        命名空间化的稳定名, 如 fs.read_file / mcp.github.search_issues
version                     工具实现版本
spec_hash                   由全部字段规范化后计算, 跨模块契约锚点
title / description         面向模型的说明, 不参与裁决
input_schema                JSON Schema, 运行前强制校验
output_schema               结果结构约束
declared_capabilities       能力上界集合 (决策 5 的闭集词汇)
target_declaration_ability  static / expandable / opaque, 声明该工具能否封闭目标集合
default_timeout_seconds
artifact_policy             输出溢写阈值与产物类型
```

规则:

- 授权不是 `ToolSpec` 的可选能力, 因此不提供 `requires_authorization` 字段. 是否需要授权不能由工具
  作者, MCP server 或配置决定; 所有工具执行统一遵守 `ToolRuntime.execute` 的强制授权前置条件.
  真正不需要安全裁决的内部纯函数不得注册为工具, 也不得进入 `ToolRuntime`.
- `declared_capabilities` 是**上界**. 运行期若 `ToolPlan` 出现超出上界的能力, `ToolRuntime`
  必须 fail closed 并返回 `spec_capability_violation`, 不得放行, 也不得自动扩大 spec.
- 上界只用于目录过滤 (决策 7) 和完整性校验, **不能作为放行证明**. "spec 里只声明了
  `WORKSPACE_READ`"不构成本次调用安全的证据, 本次调用的事实以 `ToolPlan` 为准.
- 移除旧设计中作为裁决输入的 `risk_level`. 静态风险等级无法表达"同一个工具读工作区文件与读凭证
  文件"的差异, 保留它会诱导安全模块按等级而不是按事实裁决. 如需在 UI 中排序或提示, 可由能力集合
  推导展示值, 不进入决策路径.
- `spec_hash` 变化会使 ADR-0013 的风险缓存, `always` 学习规则和待审批请求失效.

### 4. ToolPlan 是工具系统与安全模块之间唯一的事实载体

```text
plan_id
tool_name
spec_hash
capability_vocabulary_version
normalized_input            通过 schema 校验并规范化后的入参
capabilities                本次调用实际请求的能力集合
effects
  read_paths
  write_paths
  delete_paths
  move_pairs
  network_targets
  external_effects
  child_process
  dynamic_execution
target_resolution           STATIC / FORGE_EXPANDED / DYNAMIC / UNKNOWN
target_set_hash
expansion_context           展开时使用的 cwd, 环境快照 id, 文件系统视图版本
workspace_scope             in_workspace / added_dir / outside
analysis_subject            供能力分析器深入分析的原始材料, 见决策 5
declaration_confidence      declared / derived / opaque
execution_context_ref       cwd, 环境画像 hash, 工具链选择
plan_hash                   以上全部字段的规范化哈希
```

规则:

- **声明只能缩小信任, 不能证明安全.** `effects` 为空或 `declaration_confidence=opaque` 不等于
  无副作用, 只表示工具无法自证. 该情形按 ADR-0013 的 `UNKNOWN` / `OPAQUE` 路径处理.
- `target_resolution` 的口径与 ADR-0013 §6.2 完全一致. **谁能证明目标集合, 谁就负责冻结它**:
  - `fs.*` 这类自己理解参数语义的工具, 在 `prepare` 中完成规范化与受控展开, 输出
    `STATIC` 或 `FORGE_EXPANDED` 并绑定 `target_set_hash`.
  - `shell.run` 无法在工具层证明目标集合, 输出 `UNKNOWN` 加 `analysis_subject`, 由安全侧的
    Shell 能力分析器产出 `CommandPlan` 与展开后的目标集合, 并通过 `effective_plan` 回写.
  - 两条路径必须产出同构的证据字段, 下游不区分冻结发生在哪一侧.
- `prepare` 的展开必须与执行使用同一份 `ExecutionContext`; 上下文变化时计划失效重算.

### 5. 能力词汇表是闭集, 安全模块按能力分派分析器

这是解耦的核心机制. 安全模块**不认识任何具体工具类型**, 只认识能力:

```text
PLAN_ONLY
WORKSPACE_READ
WORKSPACE_WRITE
WORKSPACE_DELETE
PATH_MOVE
EXTERNAL_READ
EXTERNAL_WRITE
CREDENTIAL_ACCESS
EXECUTE_SHELL
EXECUTE_SCRIPT
SPAWN_PROCESS
NETWORK_ACCESS
EXTERNAL_IRREVERSIBLE_EFFECT
MODEL_CALL
UNKNOWN
```

分派方式:

```text
ToolPlan.capabilities
  ↓
CapabilityAnalyzerRegistry (安全模块内部)
  ├─ EXECUTE_SHELL   → Shell Parser / CommandPlan 分析器 (ADR-0013 §6)
  ├─ EXECUTE_SCRIPT  → ScriptAnalyzer (ADR-0013 §8)
  ├─ WORKSPACE_*     → 路径规范化与受保护路径检查 (ADR-0014 §5.1)
  ├─ NETWORK_ACCESS  → 网络目标与凭证作用域检查
  └─ UNKNOWN         → Hard Deny 预扫描 + Background Safety Classifier
```

由此得到两个方向的独立演进:

- **新增工具不需要修改安全模块.** 只要声明能力和产出 `ToolPlan`, 既有分析器与规则自动适用.
- **新增安全规则不需要修改工具.** 规则作用于能力和 effects, 不作用于工具名.

词汇表的约束:

- 词汇表是闭集, 带 `capability_vocabulary_version`. 新增词汇需要 ADR 或显式版本升级, 并使旧缓存
  和学习规则失效.
- 工具声明了当前版本无法识别的能力时归一为 `UNKNOWN`, 走未知路径, 不得因无法识别而跳过.
- 能力不是按工具名的白名单. 任何工具声明 `EXECUTE_SHELL` 都会进入同一套 Shell 分析路径.

`analysis_subject` 是能力相关的补充材料, 结构由能力决定而不是由工具决定, 例如:

```text
EXECUTE_SHELL   { shell_kind, raw_command, cwd, env_snapshot_ref }
EXECUTE_SCRIPT  { language, script_source | script_path, entry_config_refs }
NETWORK_ACCESS  { url_or_host, method, credential_scope_ref }
```

### 6. ExecutionAuthorization 对工具系统是不透明凭证

授权信封由安全模块生成, 工具系统只做绑定校验, 不解析其策略含义:

```text
authorization_id
plan_hash                   必须与待执行计划一致
effective_plan              可能是被安全层改写后的计划
execution_profile_hash      ADR-0014 §4.1
recovery_binding            ADR-0015 的恢复点标识 (适用时)
issued_at / expires_at
single_use                  是否一次性
revocation_state
```

`ToolRuntime` 在执行前统一校验: 信封未过期, 未撤销, `plan_hash` 与 `effective_plan` 一致,
执行画像与当前实例一致. 校验失败返回 `authorization_invalid` 或
`execution_environment_changed`, 请求重新进入 `ToolAuthorizationService`.

授权信封是 `ToolRuntime.execute` 的必需参数, 不能为 null, 不能由工具自行伪造, 也不能因为工具是
pure, 只读或来自 trusted provider 而省略. `describe`, `list` 和受限只读的 `prepare` 不属于执行
阶段; 如果某项内部行为确实不需要裁决, 它应保留为普通领域或应用服务, 而不是免授权工具.

#### 6.1 人类批准后必须重新验证再签发授权

`ApprovalRequest` 绑定的是等待人类决定时的事实快照, 不是可直接执行的授权信封. 人类批准后,
`ToolRequestCoordinator` 必须在调用恢复层和签发 `ExecutionAuthorization` 前重新验证:

```text
tool_name / spec_hash / plan_hash
capability_vocabulary_version / catalog_snapshot_hash
normalized_input / effective_plan / target_set_hash
cwd / 文件系统视图 / executable identity / 脚本或内容 hash
网络与远端目标 / 凭证作用域
mode / policy_version / 受保护路径策略
execution_profile_hash / sandbox_policy_version
```

任一绑定事实发生变化时, 旧批准立即失效. 请求必须回到 `prepare → analyze → policy decision`,
必要时创建新的 `ApprovalRequest`; 不得把新事实静默附加到旧批准, 也不得只重验其中一部分.
重验通过后才建立适用的恢复绑定, 冻结执行画像并由 `ToolAuthorizationService.issue` 签发一次性
授权. 因此"用户已批准"只是裁决输入之一, 不等于已经获得可执行授权.

改写规则 (安全层只能收缩, 不能放大):

- `effective_plan` 必须是同一 `tool_name` 与同一 `spec_hash`.
- 能力集合必须是原 `ToolPlan` 能力集合的子集.
- 允许把 `UNKNOWN` / `DYNAMIC` 收紧为 `FORGE_EXPANDED` 的结构化 argv (对应 ADR-0013 §6.2).
- 不允许新增能力, 不允许更换工具, 不允许扩大目标集合.

该校验集中实现在 `ToolRuntime`, 而不是在每个工具内部重复. 这满足 ADR-0013 §2 对 `ShellTool`
"验证授权信封与当前执行实例一致"的要求: 约束由承载工具的运行时统一施加, 工具本体保持无策略,
也避免了 N 个工具各写一份校验带来的偏差.

### 7. ToolCatalog 是外部谓词计算出的视图, 注册表不认识 mode

```text
ToolRegistry.list(CatalogQuery) -> ToolCatalog
CatalogQuery = { predicate: (ToolSpec) -> bool, reason_tag }
ToolCatalog  = { entries, catalog_snapshot_hash }
```

- 谓词由 application 层根据当前 mode 能力预算构造, 注册表只负责过滤和快照.
- ADR-0013 §1 的 `plan` mode 能力门表述为一个谓词: 只保留 `PLAN_ONLY` 与只读能力的工具.
  能力门的实现位置在 application, 不在注册表, 也不在工具内部.
- `catalog_snapshot_hash` 进入模型请求记录, 事件和授权信封. 目录变化必须可追溯, 避免"模型看到的
  工具集"与"审计记录的工具集"不一致.
- 模型请求了目录外的工具时, 由 `ToolRequestCoordinator` 返回 `tool_unavailable_in_mode`
  observation. 这是防御性兜底, 不能替代从目录中移除工具.

### 8. ToolResult 归一化, 错误分类与不可信输出

```text
invocation_id
tool_name
status        ok / invalid_input / tool_error / timeout / cancelled / unavailable / partial
content_parts 结构化结果片段, 每片带 media_type 与 provenance
artifacts     产物引用 { artifact_id, path, size, hash, truncated }
metrics       duration, exit_code, bytes_out, child_process_count
error         { code, message, retryable }
```

规则:

- **策略结果不是 `ToolResult`.** `policy_denied`, `approval_required`,
  `execution_environment_changed` 由 `ToolRequestCoordinator` 生成为 observation. 工具系统的
  错误码空间与安全裁决的结果空间保持分离, 避免模型把"被拒绝"与"工具坏了"混为一谈而反复重试.
- **工具输出一律标记为不可信内容.** 文件内容, 命令输出和 MCP 响应可能包含针对模型的指令.
  归一化时必须打 `provenance=tool_output` 且 `trust=untrusted`, 并且工具输出不得改变工具目录,
  策略, 授权状态或触发新的授权.
- 超过阈值的输出溢写到 artifact store, 事件中只保留引用, 大小和哈希; 回填模型的部分必须带明确
  截断标记与产物引用, 不做静默截断.
- 文件修改优先使用 patch 语义, 便于审计与恢复 (与 ADR-0015 的 MutationSet 对齐).

### 9. 调用生命周期与崩溃后的结果未知

事件顺序 (写前事件不可省略):

```text
tool_requested   { invocation_id, tool_name, spec_hash, plan_hash, authorization_id }
  ↓
执行
  ↓
tool_completed   { invocation_id, status, metrics, artifact_refs }
```

写前事件的意义在于**事后能分辨三种状态**: 没有 `tool_requested` = 确定没执行; 两条都有 =
确定执行完; 只有 `tool_requested` = 结果未知. 顺序反过来写的话, 后两种在日志上无法区分.

**resume 不重放任何调用.** 会话恢复的语义是"回到之前的对话", 不是"回到之前的执行状态":
用户重新说一句要做什么即可, 而工作区的实际状态模型下一轮读一遍就知道 (写入本身是原子的,
不会留下半个文件). 结果未知的调用因此只是一条记录, 不触发任何自动动作.

授权信封默认一次性. 重试是新的请求, 产生新的 `plan_hash` 与新的授权.

### 10. 取消, 超时与资源治理

- **MVP 串行执行工具**, 因此不设 `supports_parallel` 与 `conflict_domain`. 并行的价值主要是墙钟
  时间, 而它在模型延迟面前很小; 真正需要并发地读代码库时, 引入 sub-agent 比工具并行更划算 ——
  后者只省时间, 前者同时省上下文预算. 将来接入并发时, 冲突域按 `ToolPlan.effects` 的写, 删除和
  移动目标集合计算, 目标集合为 `DYNAMIC` / `UNKNOWN` 时视为与所有写调用冲突.
- `CancelToken` 贯穿 `execute`; 取消后必须回收子进程, 临时文件和沙箱实例, 并写入
  `status=cancelled` 的结果.
- 超时, 输出上限, 子进程回收和平台资源限制由 ADR-0014 的 `ResourceGovernor` 提供,
  `ToolRuntime` 通过执行服务句柄消费其能力, 不在工具系统内重新实现平台机制.

### 11. 首版只提供本地内置工具

MVP 不接入 MCP server, 也不引入 skill: 工具全部是进程内的本地实现, 因此 `ToolSpec` 不设
`provider` 与 `source_trust_zone` —— 只有一种来源时, 声明来源没有信息量.

这不是说外部工具的安全约束不重要, 而是说**现在写下来的约束没有执行者**. 真正接入 MCP 时,
以下几条必须同时落地, 缺一条就不该合入:

- 命名空间前缀 (`mcp.<server>.<tool>`), 连接管理, schema 转换, 超时与错误归一化.
- **保守的能力声明**: 无法从 schema 证明的能力一律 `UNKNOWN`, 目标声明能力一律 `opaque`.
- server 返回的 name, description, schema 与结果都是**不可信输入**: 不能覆盖本地能力声明,
  不能改变工具目录, 不能携带针对模型的指令.
- `spec_hash` 变化 (server 更新 schema) 使相关学习规则, 缓存与待审批失效.

### 12. 跨模块契约锚点与失效传播

以下值是工具系统对外的稳定锚点, 变化必须向下游传播失效:

```text
spec_hash
plan_hash
capability_vocabulary_version
catalog_snapshot_hash
tool_runtime_contract_version
```

任一锚点变化时, ADR-0013 的风险缓存, `always` 学习规则和未完成审批必须失效并重新裁决. 工具系统
负责稳定地产出这些值, 不负责判断失效之后的策略行为.

### 13. 依赖方向是硬约束, 由 CI 检查

```text
interfaces -> application
application -> tools
application -> security
security   -> domain/tool (契约)
tools      -> domain/tool (契约)
tools      -> infrastructure adapters
```

禁止事项:

- `tools` 不得 import `application`, 不得 import 安全模块, 不得读取 mode, 不得调用审批服务,
  不得调用 LLM 分类器.
- 安全模块不得 import 任何具体工具实现, 只依赖 `domain/tool` 中的 `ToolSpec`, `ToolPlan`,
  能力词汇和 `ExecutionAuthorization`.
- 二者之间不存在直接调用. 唯一装配点是 application 层的 `ToolRequestCoordinator`.

该依赖方向必须由 import 静态检查纳入 `make ci`, 不依赖人工评审保证.

#### 14.1 `fs.read_file` 支持按行读 (version 2)

新增 `offset` (1 起的行号) 与 `limit` (行数); 开了窗就附一句这一段在全文里的位置.

动机是一个**工具做不到导致的硬回退**: 首版只有 `max_bytes`, 大文件一截断模型就只能改用
`shell.run` 跑 `sed -n '100,200p'` 或 `head`. 这与提示词无关 —— 无论怎么引导, 工具给不出
文件中段, 模型就只能换 Shell.

> 2026-08-20 实现记录: 本节写下时没有落地, `version` 一直是 1, 只有 `max_bytes`. 现已
> 实现, 但有两处与原文不同, 都是实现时才看清的:
>
> 1. **输出不带行号.** 带行号读起来方便, 代价却落在 `fs.edit_file` 上 —— 模型会照抄带
>    行号的那几行去拼 `old_string`, 而文件里没有行号, 逐字比对必然失败. 一个"更好读"的
>    输出换来一整类改不动文件的失败, 不划算.
> 2. **位置说明是独立的 `ContentPart`, 不拼进正文.** 同一个理由: 拼进去, 模型照抄一段
>    内容时会把说明一起抄走.
>
> 越界的 `offset` 报**请求的那个数**而不是夹紧后的值 —— 让用户看到一个自己没写过的行号,
> 只会让他以为工具算错了.

#### 14.1b 检索工具的可发现性与生成目录过滤 (2026-08-19)

> 触发这条修订的是一次真实任务: 47 次工具调用里 22 次是 `fs.list_files`, 22 次是
> `shell.run`, `fs.read_file` 只有 3 次, `search.text` 一次都没成功调用过. 模型逐层遍历
> 了一条 Java 包路径, 13 次调用只为走到 `com/citict/mis/`.

**`fs.list_files` version 2**: 能力没变, `description` 变了. 首版写的是"按 glob 列出目录
下的文件. pattern 默认 '*'", 一个字没提 `**` 递归 —— 而 `expand_glob` 走的是 `Path.glob`,
`**/*.java` 本来就成立. 缺的不是能力, 是模型看不见这个能力.

`description` 是模型唯一能看到的工具说明 (提示词的工具表只渲染 `title` 与 `name`, 见
ADR-0018 §4). 因此它必须写明: 默认值只列一层, `**/` 前缀递归整棵树, 并给出按后缀与按
文件名两种写法的例子.

**`search.text` version 3**: 两处改动.

1. `description` 写明它**默认递归** (`pattern` 默认 `**/*`), 不需要先列目录再搜。与
   `fs.list_files` 默认只列一层正好相反 —— 两个默认值不一致本身就是陷阱, 所以两边都必须
   写明自己的默认值。
2. 新增生成目录过滤, 与 `fs.list_files` 共用 `builtin/base.py::filter_globbed`.

第 2 点原本是个更硬的缺陷: `search.text` 有 2000 个文件的扫描上限, 而它此前不过滤任何
目录. 一个 Maven 项目的 `target/` 或一个前端项目的 `node_modules/` 就能把额度吃光, 于是
"这个词不在代码里"这个结论建立在压根没扫到源码上. **一个假的空结果比没有结果危险得多** ——
模型会据此下判断, 而它看不出这个空结果是假的.

两个工具共用同一份忽略清单而不是各写一份: 走偏的后果是同一个仓库在两个工具眼里有不同的
形状, 模型据此得出的结论互相矛盾. 逃生通道有两条, 都保留: `include_ignored=true`, 或者把
`path` 直接指进那个目录 (过滤按路径段判定, 段的起点是 `path` 本身).

两个 `version` 变化都会改 `spec_hash`, 使基于它的学习规则与风险缓存失效. 同 §14.1, 这是
正确行为.

#### 14.2 `git.write`: 只写 `.git`, 不动工作树

`git.read` 是只读白名单, 因此**所有** git 写操作 (`add` / `commit` / `branch`) 此前都只能
走 `shell.run`. `git.write` 补上这一段, 白名单只收写 `.git` 而不碰工作树的形状:

| 子命令 | 允许形状 |
|---|---|
| `add` | 自由 pathspec; `-A --all -u --update -n --dry-run`; 拒 `-p` (交互式) |
| `commit` | **必须**带 `-m/--message` 或 `-F/--file`; `-a --all --amend --allow-empty -s --signoff`; 拒一切会拉起 `$EDITOR` 的形状 |
| `branch` | `branch <name>` 与 `branch <name> <start-point>`; 拒 `-d -D -m -M --force -u` |
| `switch` | **必须**带 `-c/--create` 与名字 |
| `checkout` | **必须**带 `-b` 与名字; 位置 pathspec 一律拒 |
| `tag` | 位置新名字; 拒 `-d -f --delete --force` |

白名单校验与 `git.read` 的 `_ReadOnlyForm` / `_reject_args` 共用同一份实现. 那段参数走查
本身就是两个工具的安全边界, 两份实现一定会走偏.

**被排除的子命令与理由**:

- `restore` / `reset` / `clean` / `checkout -- <path>` / `stash push` 都会动工作树. 它们的
  目标集合是整个工作区, 会让 `target_resolution` 变 `DYNAMIC`, 进而让
  `WorkspaceMutationCoordinator` 走 `FULL` 策略做全工作区 preimage, 大概率撞
  `RecoveryPolicy` 预算变成 `RecoveryUnavailableError`. 留给 `shell.run` 走 ASK 是更诚实的
  结果 —— 一个"看着有专用工具其实每次都失败"的工具比没有更糟.
- `push` / `pull` / `fetch` 需要 `NETWORK_ACCESS` + `EXTERNAL_IRREVERSIBLE_EFFECT`, 按
  ADR-0021 §6 必须逐次 mandatory ask. 那是另一个工具和另一次决定.
- `remote add` / `set-url` / `config` 写 `.git/config` 或全局配置, 不收.

**git hooks 必须关掉.** `git commit` 会执行 `.git/hooks/pre-commit` 与 `commit-msg`, 那是
工作区里的任意脚本. 一个只声明 `{WORKSPACE_WRITE, SPAWN_PROCESS}` 的工具却能跑任意脚本,
正是 §3 禁止的低声明 —— 声明只能缩小信任, 不能证明安全. 做法是在 argv 里注入
`-c core.hooksPath=<Forge 状态目录下的空目录>` 与 `--no-pager`; `--no-verify` 不够,
`post-commit` 照跑. 工具的 `description` 必须说明 hooks 不会运行, 否则模型会把"提交成功"
误报成"lint 通过了".

将来若要支持 hooks, 正确做法是 `prepare` 在该次调用额外声明 `EXECUTE_SCRIPT`, 从而走
`ScriptExecutionAnalyzer` 与安全分类器 —— 这正是 §5 的按次声明模式, 不是给工具开例外.

**`/undo` 不覆盖 `git.write`.** 一次 commit 除 `.git/index` 与 `.git/HEAD` 之外还会写
`.git/refs/heads/<branch>` 或 `packed-refs`, `prepare` 无法可靠枚举. 把一个目录声明成
`write_paths` 会造出一个"标着可恢复其实什么都没护住"的检查点 —— 目录进不了 preimage.
因此决策是显式声明撤销由 git 自己负责 (`git reset --soft HEAD~1`, `git branch -d`), 并写进
工具 `description` 与 ADR-0015 的已知限制, 而不是静默铸一个恢复不了的检查点.

#### 14.3 计划与待办工具

五个 `PLAN_ONLY` 工具由 ADR-0022 决定, 此处只记录它们在本 ADR 契约下的位置:

- 它们的 `input_schema` 里**没有路径字段**, 写入位置由 Forge 从 `project_id` 与 `plan_id`
  算出. 目标集合在机制上封闭, 因此没有可裁决的内容 —— 这是它们不触发 ask 的真正理由,
  而不是"计划不重要".
- `PLAN_ONLY` 是 `MUTATING_CAPABILITIES` 之外的能力, 因此它们在四档模式的目录里都可见,
  也都在模式预算内自动放行.
- 不经审批不等于不记审计: 它们照常经 `ToolRequestCoordinator`, 照常写 `tool_requested` /
  `tool_completed`, 照常受 §3 的上界校验与 §6 的授权信封约束.

首版的 `plan.update` 把"计划"与"执行状态"合并成一张带 status 的步骤表, 状态挂在工具实例
上不落盘, 且**零消费方零测试**. ADR-0022 把这两个概念拆开并持久化之后它没有位置, 予以

#### 14.5 本节此前与实现不一致的两处

记录下来以免再次漂移:

- **`artifact.write` 从未实现, 也不应实现.** 超阈值输出的落盘由 `ArtifactStore` 在工具
  内部完成 (§8 的产物策略), 不是一个模型可调用的工具. 模型能自行决定往产物区写什么,
  等于绕开 `ArtifactPolicy` 的尺寸与生命周期约束. 从清单移除.
- **`fs.delete` 的目标声明能力必须是 `expandable`.** 它在 `prepare` 里把目录展开成逐个
  文件与目录并输出 `FORGE_EXPANDED`, 而 `STATIC` 只允许 `STATIC` (§3 的 `permits` 规则), 声明成
  `static` 会让删除目录在协调器处 fail closed. 本表保持 `expandable`; 实现若与此不符,
  以本表为准.

#### 14.6 新建与修改分成两个工具 (2026-08-20)

`fs.write_patch` 拆成 `fs.create_file` 与 `fs.edit_file`, 前者要求目标**不存在**, 后者
要求目标**存在**, 两条前置条件都在 `prepare` 判定并给出指向另一个工具的错误信息.

拆的理由不是命名整洁, 是一次真实的绕行. 旧设计里新建文件靠"把 `old_string` 传空串"表达
—— 一个没写在名字上的隐藏约定. 实际发生的事情是: 模型要建新文件, 在工具表里找不到叫
"建文件"的东西, 自己编了一个 `fs.write_file` 调过去, 拿回"工具未注册", 转头用 `shell.run`
写文件. 于是这次写入绕开了恢复层的 preimage 与逐路径裁决, 变成一次目标集合 `UNKNOWN` 的
脚本执行 —— §14 开头那条"专用工具应当存在且够用"在这里失守了, 而失守的原因仅仅是**名字里
没有这个能力**. 工具名就是模型的检索键.

同时补上的还有两条:

- **`fs.edit_file` 的 `old_string` 没命中时给出诊断.** 只说"找不到", 模型唯一能做的是换
  个写法再试一次, 而失败几乎总是同一类原因: 缩进宽度, 制表符, 行尾空白 —— 这些差别在
  模型自己的上下文里根本看不出来. 现在会分别指出"去掉首尾空白后能命中", "忽略空白差异后
  能唯一命中", 或者"第 N 行与你给的首行开头相同".
- **`old_string == new_string` 直接拒绝.** 放行等于消耗一次审批去写回一模一样的内容,
  而模型会把"成功"当成"改动生效了".

##### 14.6a 片段定位: 容忍不携带信息的差异 (2026-08-20)

逐字符匹配一条就够用的前提是模型手里那份 `old_string` 与文件逐字节相同, 而它们之间隔着
一层模型看不见的东西: 文件用 CRLF 还是 LF, 行尾有没有多余空格, 它复述这段代码时把整块的
基准缩进带上了没有. 三样都不改变代码含义, 却都足以让比对失败 —— 而失败之后模型没有任何
证据能看出差在哪, 只能换个写法再试, 或者绕去 `shell.run`. 后者正是 §14.6 刚堵上的那条路.

所以定位分三档 (`builtin/text_edit.py`):

1. **逐字符命中** —— 原样替换, 不做任何加工.
2. **按行对齐命中** —— 只容忍行尾空白, 换行符, 以及**整块统一**的缩进偏移. 命中之后:
   - 同样的偏移施加到 `new_string` 上. 不施加的话, 对齐了匹配位置却把 `new_string`
     原样贴进去, 产出的是缩进错乱的代码 —— 模型是用同一套缩进写出 old 与 new 的.
   - 替换文本的换行改成文件在用的那种. 模型永远写 `\n`, 直接贴进 CRLF 文件, 改动的那
     几行就成了 LF, 文件从此混着两种换行, git diff 里整块都算改过.
   - 未被替换的部分逐字节不变: 按行切分时保留每一行原本的行尾符, 而不是统一成一种再
     写回去 —— 后者等于顺手改了整个文件里压根没打算碰的那些行.
   - 结果连同一句"做了什么容差"回给模型, 提醒它手里那份已经过期.
3. **只在忽略一切空白后才命中** (制表符对空格, 或块内相对缩进不同) —— **拒绝**, 因为按
   偏移硬贴会写出缩进错乱的代码, 在 Python 与 YAML 里那就是改坏了. 这一档把文件里对应的
   原文带行号逐字符引回给模型, 让它照抄. 引原文而不是描述差异: 描述完模型仍然要猜是几个
   空格还是制表符, 而它刚猜错过.

唯一性不因容差放宽: 对齐后命中多处仍然要求 `replace_all`. 敢做容差的前提是替换结果最终
进 `ToolPlan.content_previews`, 人在审批界面上看到的始终是"文件会变成什么样".

`fs.create_file` 不允许覆盖已存在的文件. 允许了, 它就成了"全文覆盖"的后门: 模型没读全
文件就能把它整段换掉, 而丢掉的那部分没人看得见.

#### 14.7 `fs.scan_tree`: 认识一个陌生目录 (2026-08-20)

`fs.list_files` 回答"哪些路径匹配这个 glob" —— 一个平铺的路径清单, 前提是已经知道要找
什么. `fs.scan_tree` 回答"这个目录长什么样".

§14.1b 记录的那次任务 (47 次调用里 22 次 `fs.list_files`) 只解决了一半: 加上 `**` 的说明
之后, 模型确实会递归了, 但它拿回的是几千行绝对路径, 每行重复同一个前缀, 上下文被冲掉,
而"哪里是源码, 哪里是测试"这个真正的问题仍然没有答案. 缩进树把同样的信息压缩了一个数量
级, 深度到头的目录只报一行"还有多少项未展开", 由模型自己决定往哪儿走.

两条与展示无关但必须的性质:

- **排序固定** (目录在前, 同类按名字). 同一个目录扫两次必须给出同一棵树, 否则 `plan_hash`
  随目录项的返回顺序变化, 上一次批准绑不住下一次调用.
- **超预算要说自己不完整.** 悄悄截断的话, 模型会把一份残缺的树当成完整结构去推断.

#### 14.8 内置工具的执行不变量 (2026-08-20)

本节把分散在单个工具中的防御收敛成公共契约。工具可以因为资源上限而拒绝或返回部分结果，
但不能成功返回一个看似完整、实际残缺的结论。

- JSON Schema 中已经声明的 `minimum` / `maximum`、`minLength` / `maxLength`、
  `minItems` / `maxItems` 必须真正执行；写在 schema 里但运行时忽略，比没有声明更危险。
- 计划、文件、移动与删除在 `prepare` 记录路径状态，`perform` 在副作用或读取前复核；对象被
  替换后旧计划失效。`plan_id` 只能是单个目录段，存储层另做一次 plans root 约束。
- 文件变更工具拒绝符号链接。创建与移动采用 no-replace 语义，目标竞争出现时由内核拒绝，
  不得覆盖；编辑超过完整读取上限的文件直接失败，不得拿前 4 MiB 拼出一份“完整”新文件。
- `fs.create_file` 与 `fs.move` 不再隐式创建父目录。新增 `fs.create_directory`，每次只创建
  一个父级已存在的空目录；一次文件授权不能顺带产生未声明、无法撤销的目录树。
- `fs.delete` 的恢复集合包含目录本身与空子目录；preimage 保存文件内容以及文件/目录 mode。
  移动完成后同时记录“源已删除”和“目标已创建”的 postimage，undo 才不会复制出两份文件。
- `fs.read_file`、`fs.list_files`、`search.text` 与 `fs.scan_tree` 的字节、文件数、命中数和条目
  上限一律在输出开头或独立 `ContentPart` 中说明。未扫描大文件尾部、跳过符号链接或达到上限
  时不得使用“确定的空结果”。glob 枚举本身最多收集 10,001 个候选，不先把整棵巨型目录树
  装进内存再截断输出。
- `search.text` 的 Python 正则只接受无分组、分支、反向引用和花括号量词的安全子集；Python
  `re` 没有可中止的匹配超时，高级正则走受进程超时约束的 `shell.run` / `rg`。
- `shell.run.shell_kind` 只能与执行画像一致。`git.read` 不接受会访问网络和凭证帮助器的
  `remote show`，执行时强制关闭 pager、terminal prompt、可选锁、fsmonitor、外部 diff 与
  textconv。
- stdout 与 stderr 共用 `max_output_bytes`，artifact 上限按 UTF-8 字节而不是 Python 字符数
  计算。底层已截断时，提示必须位于内联输出前部，不能只落在同样残缺的 artifact 末尾。

上述变化均提升对应 `ToolSpec.version`，使旧审批、学习规则和基于 `spec_hash` 的缓存失效。

### 15. 工具侧审计只记录机制事实

工具系统记录: `invocation_id`, `tool_name`, `spec_hash`, `plan_hash`, `authorization_id`,
`catalog_snapshot_hash`, 状态, 耗时, 退出码, 产物引用与哈希, 截断情况, 取消与超时原因.

裁决理由, 命中规则, 分类器结论, 审批展示与范围由 ADR-0013 §15 记录. 两侧通过
`plan_hash` 与 `authorization_id` 关联, 不重复存储同一事实, 也不互相依赖对方的日志格式.

不得记录明文凭证和不必要的敏感内容.

## 备选方案

### 方案 A: 工具内部实现安全裁决

优点是单个工具看起来自洽, 调用方无需理解安全管线.

缺点是策略与执行耦合, 每个工具都要重复实现模式, 审批与分类器接入, 且新增调用路径 (slash
command, resume, sub-agent) 极易出现不一致.

不采用. 与 ADR-0013 方案 D 结论一致.

### 方案 B: 安全模块按具体工具类型特例分派

优点是实现直接, 针对 `ShellTool` 可以写出最精确的分析逻辑.

缺点是新增工具必须同步修改安全模块, 而漏改的默认后果是"无规则匹配"即静默放行. 安全模块还会
反向依赖工具实现, 破坏两侧的独立演进.

不采用.

### 方案 C: 工具只暴露原始入参, 由安全模块自行解析每种工具的参数语义

优点是工具实现最薄.

缺点是安全模块必须跟随每个工具 (包括 MCP 动态工具) 的 schema 演进, 解析责任错配; 且解析结果与
工具执行时的理解可能不一致, 产生"裁决的是一个语义, 执行的是另一个语义"的缺口.

不采用.

### 方案 D: 两段式调用 (无 prepare), 直接执行并事后审计

优点是链路短, 延迟低.

缺点是副作用已经发生后审计没有意义, 无法支持 ASK 阻塞, 无法支持 ADR-0015 的执行前恢复点.

不采用.

### 方案 E: describe / prepare / execute 三段式 + 闭集能力词汇 + 不透明授权信封

优点是工具只提供事实与机制, 安全模块只消费能力与 effects; 两侧可独立演进, 新工具默认进入
最保守路径而不是默认放行; 裁决对象与执行对象由 `plan_hash` 绑定, 消除 TOCTOU.

缺点是调用链路更长, 需要维护能力词汇表和哈希锚点, 每个工具都要实现 `prepare`.

采用.

## 影响

### 收益

- 工具系统与安全, 沙箱, 恢复三层完全解耦, 后续安全规则引擎只通过 `ToolSpec`, `ToolPlan`,
  能力词汇和授权信封与工具交互.
- 新增工具无需修改安全模块; 新增规则无需修改工具实现.
- 未声明, 未知和无法自证的调用默认进入最保守路径, 而不是默认放行.
- 裁决, 审批与执行绑定同一 `plan_hash`, 安全层的改写 (受控展开) 有明确的合法通道.
- 所有工具共享同一审计, 归一化和不可信输出模型.
- 工具运行时只有一条授权后执行路径, 不会因只读标记, provider 信任级别或配置错误产生旁路.

### 代价

- 每次工具调用增加 `prepare` 阶段和授权校验开销.
- pure 和普通工作区只读调用也需要签发一次性授权; 安全模块需要提供不触发分类器和人工审批的
  确定性快速 `ALLOW` 路径.
- 必须维护能力闭集词汇表和五个哈希锚点的失效传播.
- MCP 工具因保守声明会更频繁地进入分析器与审批路径.
- 依赖方向需要静态检查工具支撑, 否则约束会随时间腐化.

### 后续约束

- 工具实现中出现 mode, 审批或分类器调用视为架构违规.
- 安全模块 import 具体工具实现视为架构违规.
- 通用授权入口命名为 `ToolAuthorizationService`; Shell 与脚本安全能力作为分析器注册到
  `CapabilityAnalyzerRegistry`, 不另设按具体工具类型分派的全局入口.
- 人类批准后必须完成全量绑定重验, 再建立恢复绑定和签发执行授权.
- 规则裁决, 工作区恢复和沙箱隔离保持独立组件与生命周期, 仅由 application 层装配.
- 能力词汇表变更需要 ADR 或显式版本升级, 并触发缓存与学习规则失效.
- `docs/02-detailed-design.md` §1.1, §3.6, §3.7 和 §8 需按本 ADR 同步; §8.2 中引用已废弃
  ADR-0009 的裁决表以 ADR-0013 为准.

## 验收标准

- 所有工具通过 `ToolRegistry` 暴露, 不存在未注册的执行通道.
- 工具执行统一经过 `describe → prepare → execute`; `execute` 只消费授权信封中的
  `effective_plan`, 不重读原始入参.
- `ToolSpec` 不包含 `requires_authorization` 或任何等价的免授权开关.
- pure, 只读和 `PLAN_ONLY` 工具在执行前同样取得本次调用的授权; 普通工作区只读可以自动
  `ALLOW`, 但不能绕过授权信封.
- `ToolRuntime` 的执行接口要求非空授权信封; 缺少有效授权时 fail closed 并返回
  `authorization_missing`.
- 授权信封的 `plan_hash`, 执行画像, 有效期和撤销状态在执行前统一校验, 失败返回
  `authorization_invalid` 或 `execution_environment_changed`.
- 安全层改写只能收缩能力集合, 不能更换工具, 新增能力或扩大目标集合.
- 工具实现中不含 mode 判断, 规则匹配, 审批调用和分类器调用.
- 安全模块不 import 任何具体工具实现; 依赖方向由静态检查纳入 `make ci`.
- 所有工具的通用安全入口为 `ToolAuthorizationService`; `EXECUTE_SHELL` /
  `EXECUTE_SCRIPT` 通过能力注册表分派给 Shell / Script 分析器, 不按 `ShellTool` 类型分派.
- 人类批准后重验 `ToolSpec`, 计划, 内容, 目标, 策略和执行环境; 任一事实变化都会使旧批准失效并
  重新进入完整安全管线.
- `ExecutionAuthorization` 只在批准后重验通过、适用的恢复绑定建立且执行画像冻结后签发.
- 规则 `ALLOW`, 恢复保障和沙箱隔离互不替代; 恢复层和 Sandbox Provider 不参与 mode、规则匹配
  或人工审批.
- `ToolPlan` 超出 `ToolSpec.declared_capabilities` 上界时执行被拒绝.
- 能力词汇为闭集; 未识别能力归一为 `UNKNOWN` 并进入 ADR-0013 的未知路径, 不被跳过.
- 安全模块按能力而不是按工具名分派分析器; 新增声明 `EXECUTE_SHELL` 的工具自动进入 Shell 分析
  路径, 无需修改安全模块.
- `fs.*` 类工具在 `prepare` 中输出 `STATIC` / `FORGE_EXPANDED` 与 `target_set_hash`;
  `shell.run` 输出 `UNKNOWN` 与 `analysis_subject`, 由安全侧分析器冻结目标集合.
- `prepare` 不启动进程, 不访问网络, 不修改文件或外部状态; 展开使用与执行同一份
  `ExecutionContext`, 规划阶段读取的敏感内容不进入面向模型的错误或 observation.
- `ToolCatalog` 由外部谓词计算, 注册表不含 mode 语义; `plan` mode 目录只保留 `PLAN_ONLY`
  与只读工具, 目录快照哈希进入事件与授权.
- 目录外工具请求返回 `tool_unavailable_in_mode` observation.
- 策略拒绝不表现为 `ToolResult` 错误, 而是独立的 observation 类型.
- 工具输出标记 `trust=untrusted`, 不能改变工具目录, 策略或授权状态.
- 超阈值输出溢写 artifact, 回填带显式截断标记与产物引用.
- 计划的 `target_resolution` 不得弱于 spec 声明的 `target_declaration_ability`; 违反者在
  prepare 之后立即 fail closed, 且标记为不可重试 (工具实现与声明不一致, 重试结果相同).
- `tool_requested` 为写前事件, 落盘之后才允许执行; 据此能分辨"没执行", "执行完"与"结果未知"
  三种状态. resume 不重放任何调用.
- 工具串行执行; 不提供 `supports_parallel` / `conflict_domain` 声明 (§10).
- 取消与超时能够回收子进程, 临时文件和沙箱实例.
- 首版只有本地内置工具; 接入 MCP 的前置条件见 §11, 未全部落地前不合入;
  MCP 不能绕过 `ToolRegistry` 与 `ToolRuntime`.
- `spec_hash`, `capability_vocabulary_version`, `catalog_snapshot_hash` 变化会使 ADR-0013
  的缓存, `always` 规则与待审批失效.
- 工具侧审计记录机制事实, 与 ADR-0013 的裁决审计通过 `plan_hash` 关联且不重复存储.
