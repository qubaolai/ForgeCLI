# ADR-0057：采用显式权限模式状态与回合边界切换

## 状态

Proposed

## 日期

2026-09-16

## 背景

ForgeCLI 需要提供类似 Claude Code 的模式体验：模式不只是提示词中的一句话，而是同时影响工具目录、工具自身检查、人工确认、沙箱和计划流程的运行时状态。

源码验证显示当前处于迁移中：

- `core.mode.SessionMode` 仍是运行时入口使用的“沙箱档位 × 审批档位”模型，拥有 `manual`、`plan`、`accept_edits`、`auto`、`full_access` 五个预设。
- `ProjectRuntime.set_mode()` 已统一 TUI、Web 和 `/mode` 的入口，并在 turn 运行期间拒绝切换；`SessionService.set_mode()` 当前只改变内存快照，不写会话事件或 `state.json`。
- `tools.pipeline.catalog_predicates` 按 `SessionMode` 过滤只读模式下的变更工具，`CoordinatorToolDispatcher` 将同一个 `SessionMode` 传给目录、围栏和权限管线。
- 新增的 `core.permissions.PermissionMode`、`ToolPermissionContext`、`transition_permission_mode()` 和工具 `check_permissions()` 已形成 Claude Code 式权限模型的雏形，但当前真实执行链仍是 `ToolRequestCoordinator -> ToolAuthorizationService -> PolicyEngine -> ToolRuntime`；新权限上下文没有成为 ProjectRuntime 的唯一模式事实。
- 当前工作树源码可编译且核心导入冒烟通过，但 lint、架构检查、mypy 和 pytest 尚未通过/尚无用例。因此本 ADR 是迁移目标，不宣称 0055 已经接线完成。

## 决策

### 1. 以单一权限模式作为“自主性”轴，沙箱作为独立安全轴

最终模式状态由两部分组成：

1. `PermissionMode`：决定规则、工具自检和人工确认如何协作。
2. `SandboxPolicy`：决定操作系统和工作区围栏允许触达什么资源。

两者正交。权限模式不能扩大沙箱；`bypass_permissions` 也不能绕过 hard deny、沙箱无法提供的资源或必须有人在场的安全检查。现有 `SessionMode` 在迁移期间作为兼容读写模型，不能继续同时承担第二套权限事实；完成迁移后，所有模式入口、目录生成、工具裁决和提示词运行事实都从同一份 `ToolPermissionContext` 读取。

### 2. 固定五种规范模式及其能力

| 模式 | 规范含义 | 工具目录 | 人工确认 |
|---|---|---|---|
| `default` | 规则优先，工具自行判断具体调用，无法确定时询问 | 可见工具按当前沙箱/deny 过滤 | ask 进入统一人机通道 |
| `accept_edits` | 工作区内文件编辑可自动接受，其余行为仍按规则和工具检查 | 与 default 基本相同 | 越界、命令风险和安全检查仍可询问 |
| `plan` | 只调查、分析和生成计划，不执行工作区变更 | 隐藏或硬拒绝变更能力，保留读取、搜索、计划和提问能力 | 计划评审是回合终态，不是普通工具审批 |
| `bypass_permissions` | 在启动时获得明确授权后减少常规询问 | 不因常规 allow/ask 规则移除 | hard deny、内容级 ask、安全检查和必须在场的工具仍可询问/拒绝 |
| `dont_ask` | 无人值守策略；任何本应 ask 的调用直接拒绝 | 目录仍按 deny 和沙箱过滤 | ask 不创建人机提示，转换为 deny |

旧名称只作为输入兼容层：`full_access` 映射到 `bypass_permissions`，`dontAsk` 映射到 `dont_ask`，`auto` 的映射必须明确记录为 `accept_edits` 的兼容语义，不能因为名称相似而扩大权限。

### 3. 模式切换必须经过一个显式转换服务

以下入口都只能提交 `PermissionUpdate(type=SET_MODE, ...)` 或等价的领域命令，由同一个转换服务完成校验和状态替换：

- 启动参数、用户/项目默认设置；
- TUI `/mode` 和快捷键循环；
- Web 模式 API；
- 计划评审后的后续动作；
- 人工审批卡片中的“本会话切换模式”建议。

转换服务负责：

- 检查 `bypass_permissions` 是否在启动阶段获得可用许可，以及是否被设置 kill switch 禁用；
- 进入 `plan` 时记录 `pre_plan_mode`，离开时按显式目标或既定计划评审策略恢复；
- 拒绝无法识别的模式，不把未知值降级成更宽松模式；
- 返回新的不可变权限上下文，由组合根写回 `AppState`；
- 发布带有 from/to、原因、来源和上下文指纹的运行审计信息。

模式切换不是模型文本，不进入 system prompt 的原始历史，也不由模型通过普通工具参数直接改变。工具只能返回权限建议；实际模式改变必须经过人类选择或启动配置。

### 4. 模式以回合边界生效

- turn 开始时冻结有效权限模式、沙箱策略、工具目录和执行上下文；该 turn 中的模型调用、工具队列和审批重验使用同一份快照。
- 忙碌期间的 TUI/Web 切换请求返回明确冲突，不静默改变队列中后续工具的权限含义。
- 计划评审是一个合法的回合终态；用户选择“继续执行”后先完成模式转换，再以新的 follow-up turn 重新组装 prompt、工具目录和围栏。
- 新模式从下一个 turn 的上下文组装开始可见。模式变化使运行上下文和工具目录指纹失效，但不改写历史消息。

这样避免了“同一批模型 tool call 中前几个按旧模式、后几个按新模式”的不可审计状态，也与 ADR-0056 的上下文刷新边界一致。

### 5. 权限裁决采用“全局硬约束 + 工具局部判断”

工具可以通过 `check_permissions(input, context)` 返回调用特有的 allow、ask、deny 或 passthrough，但工具不能自行跳过以下约束：

1. 整工具 hard deny；
2. 必须有人在场的交互要求；
3. 工具自身返回的 deny；
4. 内容级 ask 规则和安全检查；
5. 沙箱与执行环境一致性检查；
6. `dont_ask` 对 ask 的安全收紧。

工具自判只负责“这个具体输入的机制事实”，不能成为新的全局授权引擎，也不能把模型提供的描述直接当成安全事实。未来接入 MCP 时，MCP 适配层可以单独管理连接、服务器和外部工具权限，但最终调用仍必须转换为同一套模式、规则、沙箱和人机确认边界。

## 备选方案

- **继续使用 `SessionMode` 的两个轴和所有预设。** 能兼容当前实现，但同一件事同时存在 `SessionMode` 与 `PermissionMode` 两套语义，工具作者和入口很容易接错；不作为最终方案。
- **只在 system prompt 中告诉模型当前模式。** 提示词不能构成执行约束，模型仍可直接请求隐藏工具或改变参数；不采用。
- **每次工具调用都读取最新模式。** 看似响应快，但一个模型批次内会产生不同权限语义，审批绑定和审计无法解释；不采用。
- **模式切换直接写普通会话消息。** 会污染任务历史，恢复时还可能被模型当作用户要求；不采用。

## 影响

收益是模式名称、能力、切换时机和权限责任单一且可审计；Plan、非交互模式和 Full Access 不再依赖提示词自律。代价是需要完成 `SessionMode` 到 `PermissionMode` 的兼容迁移，并让工具目录、围栏、审批和 Agent turn 共享回合快照。

模式仍是运行时授权状态，不因 `/resume` 自动继承上一次的高权限档位；恢复后的会话从安全默认模式开始，除非用户再次显式选择。该点延续 ADR-0052，避免把一次性授权变成跨会话授权。

## 验收标准

- 所有模式入口最终调用同一个转换服务；未知模式、未启动授权的 bypass 和 busy turn 都有明确失败结果。
- 一个 turn 内工具目录、沙箱和权限上下文指纹稳定；切换只影响下一个 turn，历史窗口不被改写。
- `plan` 无论模型是否直接请求变更工具，都不能产生工作区变更；计划评审能以新的 follow-up turn 进入执行模式。
- `accept_edits` 只对声明的工作区编辑自动放行，越界、脚本/联网和安全检查不会因模式名称被泛化放行。
- `bypass_permissions` 不绕过 hard deny、执行环境复核、沙箱和必须有人在场的检查；`dont_ask` 不创建悬挂的人机提示。
- 工具 `check_permissions()` 异常按 fail-closed 处理；工具局部判断不能直接写全局权限状态。
- 权限状态变化有可关联的运行审计，但不进入模型历史；MCP 接入时能复用相同的最终裁决边界。
- 完成迁移后，补齐模式状态机、回合冻结、Plan 越权、bypass 安全检查、dont_ask 和 TUI/Web 一致性的测试；当前质量门禁失败项必须先收敛，不能由本 ADR 豁免。
