# ADR-0036: 工具名从点号分段改为下划线分段

## 状态

Proposed

## 日期

2026-08-25

## 背景

ADR-0004 给工具定了"命名空间化的稳定名", 形式是点号分段: `fs.read`, `shell.run`,
`mcp.<server>.<tool>`. ADR-0029 按动作重组时改过一轮名字 (`fs.read_file` -> `fs.read`),
但没有动分隔符.

点号在两处碰壁.

### 1. 供应商拒收带点的函数名

OpenAI 的 function calling 规定工具名匹配 `^[a-zA-Z0-9_-]{1,64}$` —— 点号不在里面.
ForgeCLI 唯一的 adapter 是 OpenAI 兼容协议 (`infrastructure/llm/adapters/
openai_compatible.py`), 工具名原样进 `tools[].function.name`. 严格执行这条约束的兼容
端点会把**整条请求** 400 掉: 不是某个工具不可用, 是这一轮根本发不出去. 而工具目录是
每次调用都带的, 所以这不是偶发失败, 是这个 provider 完全用不了.

### 2. 与同类工具的形状不一致

主流 code agent 的工具名都不带点. 模型在预训练与后训练里见到的工具名就是这个形状,
跟着对齐比自创一套划算 —— 工具名是模型每一轮都要复述一遍的东西, 形状越常见, 它拼错
的概率越低.

## 决策

### 决策 1: 分隔符改成下划线, 段的语义不变

14 个内置工具全部改名. 分段结构与归属不变, 只换分隔符:

| 旧 | 新 |
|---|---|
| `artifact.read` | `artifact_read` |
| `fs.find` | `fs_find` |
| `fs.read` | `fs_read` |
| `fs.apply_patch` | `fs_apply_patch` |
| `git.read` | `git_read` |
| `search.text` | `search_text` |
| `shell.run` | `shell_run` |
| `memory.write` / `memory.forget` | `memory_write` / `memory_forget` |
| `plan.read` / `plan.write` | `plan_read` / `plan_write` |
| `todo.read` / `todo.write` / `todo.set_status` | `todo_read` / `todo_write` / `todo_set_status` |

MCP 工具随之变成 `mcp_<server>_<tool>`.

### 决策 2: 校验正则重新收紧, 保住"至少两段"

`ToolSpec._NAME_PATTERN` 改成 `^[a-z][a-z0-9]*(_[a-z0-9]+)+$`.

`+` 而不是 `*` 是这条决策的全部内容: 把点号换成下划线时, 一个看似等价的写法
`^[a-z][a-z0-9_]*(_[a-z0-9_]+)*$` 其实退化成了 `^[a-z][a-z0-9_]*$` —— 因为头部的
`[a-z0-9_]*` 已经吃掉了下划线, 后面那个可选组匹配不匹配都一样. 它会放行单段名
(`shell`), 双下划线 (`fs__read`) 与尾部下划线 (`fs_read_`).

"至少两段"不是洁癖: 名字要自带归属. 一个叫 `run` 的工具和一个叫 `read` 的工具摆在
同一张工具表里, 模型分不出谁管什么, 而工具表是它选工具的唯一依据.

### 决策 3: 历史 ADR 不改名

本仓库的约定是 ADR 记录**那一天的决定**, 不是当前状态的说明书: ADR-0004 至今写着
`fs.list_files` / `fs.create_file`, 而那些名字 ADR-0029 就删掉了. 沿用这个约定 ——
把旧 ADR 里的名字改成今天的, 等于让记录说了一句它当时没说过的话.

跟着改的只有**描述当前状态**的文档: `docs/02-detailed-design.md`,
`docs/03-delivery-plan.md`, `docs/06-code-reading-guide.md`, 以及尚未实现的提案
ADR-0034 (它描述的是将来要写的代码, 不是已经做过的决定).

### 决策 4: 已学到的 always 规则全部作废, 不做迁移

`tool_name` 进 `ToolPlan.plan_hash`, 而 `plan_hash` 是 always 学习规则的匹配键
(ADR-0013 §5.1). 改名之后, `~/.forge/state/rules/<workspace>.json` 里此前学到的规则
一条都匹配不上.

**不写迁移**. 迁移意味着把一条用户在"批准 `shell.run xxx`"这个措辞下同意过的规则,
自动改写成对另一个名字生效 —— 而规则的全部意义就是"用户看着那份视图点过同意".
不迁移的后果是回落到 ASK, 用户再点一次; 迁移写错的后果是一条没人复核过的 ALLOW.
方向不对称, 所以选前者.

`tests/memory/test_memory_prompt_and_tools.py` 里那个钉住的 `plan_hash` 因此变了.
那条用例的注释写着"哈希变了必须是有人明确决定要做" —— 这里就是那次明确决定.

## 备选方案

- **方案 A: 保留点号, 在 adapter 里把 `.` 转成 `_` 发出去, 回来再转回来.** 优点是
  内部名字不动. 缺点是从此存在两套名字: 日志, 审批界面, 学习规则, 事件流里是点号,
  模型看到的是下划线, 而用户排查时对着的是模型的输出. 一次翻译写错方向不会报错, 只会
  让规则匹配不上 —— 正是决策 4 想避免的那类静默失效.
- **方案 B: 只给出问题的那个 provider 做转换.** 缺点同上, 而且判据是"哪个 provider
  严格", 那件事会随对方版本变.
- **方案 C: 干脆去掉命名空间, 用 `read` / `run` / `find`.** 优点是最短. 缺点是丢掉
  归属 (决策 2 的理由), 而且 MCP 工具本来就来自不同 server, 没有归属就会重名.

## 影响

**收益.** 严格执行 OpenAI 函数名约束的兼容端点可以用了. 工具名与主流 code agent 同形.

**代价.**

- 已学到的 always 规则全部作废 (决策 4), 用户要重新批准一轮. 失败方向是 ASK, 安全.
- 提示词正文变了, `PROMPT_TEXT_VERSION` 8 -> 9, 两处指纹快照同步更新. 模型行为可能
  随之有细微变化, 这是 ADR-0018 §15.3 要求显式承认的那种变化.
- 历史会话的 `events.jsonl` 里留着旧名字. 它们只是文本, `/resume` 重建 transcript 不
  受影响; 但按旧名字 grep 老日志时要记得名字换过.

**约束.**

- 新工具名必须过 `^[a-z][a-z0-9]*(_[a-z0-9]+)+$`, 且至少两段.
- Web 侧那份"连 prepare 都没走到时按名字兜底分类"的清单 (`web/src/runModel.ts` 的
  `NAME_CATEGORIES`) 只收当前真实存在的工具名. 它上面那段注释警告过"名字清单会悄悄
  过期", 而它自己确实过期了 —— 这次一并清掉了 ADR-0029 删除的那些名字.

## 验收标准

- `ToolSpec` 拒绝单段名, 双下划线与尾部下划线; 14 个内置工具与 `mcp_<server>_<tool>`
  形式全部通过.
- `make ci` 通过, 含 `scripts/check_prompt_text.py` 与两处指纹快照.
- 提示词里模型看到的工具表全部是下划线名 (`tests/prompt/test_system_prompt_builder.py`
  的编排快照).
- `web/tests/runModel.test.mjs` 断言按名字兜底时只认当前存在的工具.
