# ADR-0051: 采用双层循环, 每次调用现组上下文, 外层用时读依赖

## 状态

Accepted (2026-09-14 实现)

本文取代下面几处早先的决定. 这些决定当时各有理由, 本文逐条说明为什么不再成立:

- ADR-0010 §2: "循环只产出意图, 不执行任何工具, 真实执行由 AgentTurnService 完成".
- ADR-0018 §6: "按 turn 冻结与失效" 整节.
- ADR-0041 决策 1: 六层表里各层的变更频率标签 ("包版本级", "会话级", "模式级"), 以及
  "一轮之内不换前缀"的说法. 保留的只有一句: 请求按"稳的在前, 变的在后"排.
- ADR-0048 决策 1: 用 `reconfigure` 换依赖的机制.

ADR-0049 的规则与时机一个字不改; 它里面沿用 ADR-0010 §2 的几处口径跟着本文改.

## 日期

2026-09-14

## 背景

### 1. 今天是三层, 中间那层是一次握手

```
想一次   BuiltinAgentLoop._advance     规则 -> 调模型 -> 规则 -> 写消息 -> 交出意图
一轮     AgentTurnService._run_loop    拿意图 -> 执行工具 -> observe 喂回 -> 直到 LoopStop
会话     ProjectRuntime / SessionService  后台线程, 取消, 运行状态, 存储, 恢复
```

循环每想一次就把意图 (`AnswerAction` / `ToolRequestAction`) 交给驱动方, 驱动方执行完
用 `observe()` 喂回去, 循环再想下一次. 连"回答已产出"都要驱动方 `observe(answer_delivered)`
一次才算结束. 为了这次握手, 域里有 `LoopAction` / `AnswerAction` / `ToolRequestAction` /
`LoopStepResult` 四个类型, 循环有两个"等待中"的状态, 驱动方有一个带 `isinstance` 分发
和步数上限 `_DEFAULT_MAX_LOOP_STEPS` 的 `for`.

### 2. 握手的理由不成立

ADR-0010 §2 给的理由是安全: 循环拿不到 `ToolRegistry` 和 `ToolRuntime`, 想绕过协调器在
循环里做不到. 但这条保证**来自循环拿到的是什么对象, 不来自它在哪一层**:

- 驱动方今天调的是 `CoordinatorToolDispatcher.dispatch`. 它对外只有这一个执行入口,
  每次现造 `PolicyContext`, 取围栏, 走 `ToolRequestCoordinator.handle`, 没有第二条路.
- `check_arch.py` 对 `agent_loop` 只禁了两件事: 不认识网关实现, 不认识记忆. 没有禁它
  认识 `tool_request`.

把 dispatcher 交给循环, 循环能做的跟驱动方能做的一样. 再退一步, 循环连 dispatcher 都
不必认识: 驱动方把自己那个"执行一次工具"的方法当成函数交给循环, 循环只会调它.

### 3. 按轮冻结防的是不会发生的事, 却推迟了该发生的事

ADR-0018 §6.2 要求一轮之内不重读 FORGE.md, 不换工具目录, 不重编 system prompt, 理由是
"换了之后模型为什么突然改了行为就对不上任何一条事件".

但一轮之内会话是 busy 的: 模式、根目录、模型配置都改不了 (`reload_llm` 与切模式都
先查 busy). 一轮之内唯一能变的输入是**模型自己**改了 FORGE.md, 写了记忆, 或者改了
计划与待办. 这三件事立刻生效本来就是对的: 它改了指令文件, 指令就该变; 事件日志里有
那次工具调用, 不存在对不上. 冻结防的是一个不会发生的变化, 顺便把三个该发生的变化推迟
到了下一轮 —— 阅读线路 §5.1 专门解释过"这轮调了 `todo_set_status`, 待办状态帧要下一轮
才更新"这个别扭.

### 4. 六层的标签背后没有代码

ADR-0041 决策 1 把请求分六层, 给每层标了变更频率: 工具目录"模式级", 静态策略"包版本级",
FORGE.md "会话级", 运行事实"模式级", 窗口"只追加", 状态帧"每轮重建". 这些标签没有一个
对应任何代码 —— 静态策略是几个模板常量, 给常量贴一个"包版本级"什么都没换到.

六层真正要的只有一件事: 前缀缓存. 供应商按字节前缀命中缓存, 所以稳的放前面, 变的放
后面. 这一句话就够, 不需要六个标签.

### 5. `reconfigure` 是做了一半的用时读

`reload_llm` 重建网关、工具栈、窗口管理器, 然后调 `AgentTurnService.reconfigure` 换五样
东西: `context_budget`, `context`, `memory`, `planning`, `tools`. 注释写着"调用方必须整套
传, 少传一个就会出现半旧半新的组合, 而那种组合不会报错".

同一段注释的下半句说 `loop_factory` 与 `runtime_facts` **不在里面**, 因为"它们是读组合根
当前字段的闭包, 换掉 `self.llm` 之后自己就指向新的". 也就是说七个依赖里有两个已经是
用时读的, 剩下五个不是 —— `reconfigure` 是为那五个存在的. 而五个里的 `context`
(`WindowManager`) 在 `AgentTurnService` 里存了却没用过一次.

### 6. 常见的形状是两层

内层是一次查询的完整生命周期: 组上下文, 调模型, 解析, 执行工具, 结果进历史, 直到模型
不再要工具. 外层是一轮对话的生命周期: 持久化, 终态, 以及它上面的会话层: 要不要继续,
中断的发起. ForgeCLI 的三层比它多的那一层, 只是把内层从中间切开了.

## 决策

### 决策 1: 循环自己执行工具, 一次 `run()` 跑到底

```python
class BuiltinAgentLoop:
    def run(
        self,
        loop_input: LoopInput,
        *,
        execute: ToolExecutor,
        assemble: ContextAssembly,
    ) -> LoopResult: ...

ToolExecutor = Callable[[ToolRequest], LoopObservation]
ContextAssembly = Callable[[], AssembledContext]
```

内层的形状:

```
while True:
    ctx = assemble()                       # 决策 2
    规则 before_model  (压缩用 ctx 估算)
    调模型 (ctx.system_prompt, ctx.tools, 窗口 + ctx.state_frame)
    规则 after_model -> 写 assistant 消息
    没有 tool_calls -> 停 (FINAL_ANSWER, 带回答)
    for call in 这批:
        规则 before_dispatch (Deny 就补结果跳过)
        observation = execute(call)
        回填工具结果 -> 规则 after_observe (停 / 收工具则跳出这批 / 攒提醒)
    写攒着的提醒 -> 回到顶上
```

`execute` 由外层给, 就是今天 `AgentTurnService._run_tool_and_watch_planning`: 经
`CoordinatorToolDispatcher.dispatch` 走完整条安全管线, 顺带比对计划有没有变. 循环拿到
的只是一个函数, 认识不到 dispatcher, 更认识不到注册表与运行时. 单一入口由 dispatcher
的类型守着, 跟谁调用无关.

`LoopResult` 是一轮的产出: 停止原因, 回答文本, 中断时的部分回答, 结束时的窗口, 用量
草稿, 压缩记录. 外层只读它, 不再持有循环实例.

`CloseTools` 从今天的"回调 `_advance`"变成"跳出这批, 回到 while 顶上". 这是唯一要重新
想的控制流, 其余是搬.

### 决策 2: 每次调模型前现组整份上下文

`assemble` 也由外层给: 读 FORGE.md, 运行事实, 工具目录, 围栏, 预算, 计划, 待办, 记忆,
编译 system prompt, 渲染状态帧, 返回一份 `AssembledContext`. 内层每次调模型前调它一次.
循环不认识提示词编译器、计划服务与记忆服务, 拿到的是组好的材料.

请求的顺序保持**稳的在前, 变的在后**: system prompt (策略块 + FORGE.md + 运行事实)
-> 工具 -> 窗口 -> 状态帧. 一轮里输入没变, 前面那段每次组出来都是同样的字节, 缓存照样
命中; 模型真改了 FORGE.md, 那一次不命中, 应该的.

这一改换到的: 模型这轮调了 `todo_set_status`, 下一次调模型就看到新的待办; 写了记忆,
下一次就看到; 改了 FORGE.md, 下一次就按新指令走. 今天这三件都要等下一轮.

`AssembledContext` 从"一轮冻结的材料"变成"一次调用的材料". `LoopInput.context` 删掉,
只剩初始窗口. `prompt_fingerprint` 从每轮记一次变成每次调用记一次, 变了能看见.

工具目录也是每次调用现算. 它进审计的快照哈希在一轮里输入不变时是同一个; 若不是同一个,
那是今天就有的问题, 只是今天一轮只算一次看不出来.

### 决策 3: 外层只管一轮的生命周期

`AgentTurnService.handle_user_message` 收成:

```
组 execute 与 assemble 两个闭包 (绑定本轮的 mode, session_id, turn_id, 用户原话)
记 user 消息
result = loop.run(input, execute=execute, assemble=assemble)
记 assistant / usage / compaction, 接窗口
映射终态 (COMPLETED / FAILED / PLAN_REVIEW)
```

`_run_loop` 的 `for` 与 `isinstance` 分发删掉, `_DEFAULT_MAX_LOOP_STEPS` 删掉: 它兜的是
握手次数, 握手没了, 一轮的上限就是 `ModelBudgetRule` 那个模型调用次数.

会话层 (`ProjectRuntime`: 后台线程, 取消源, `TurnRun`, 存储, 恢复) 不动.

### 决策 4: 中断与预算, 内层能停, 外层算账, 会话层发起

内层跑到底之后, 外层在一轮中间插不进手. 这不是两层设计的缺陷, 是各做各的那一半:

- **中断**: 一轮可能跑五十次工具, Ctrl-C 必须能停在中间. 取消令牌仍随每次模型调用进
  网关, 循环把 `ModelCancelledError` 收成 `USER_CANCELLED`; 外层拿到这个停止原因, 决定
  记什么 (部分回答加取消标记); 会话层 `ProjectRuntime.cancel` 置令牌、放开待答队列.
- **预算**: 窗口是在一轮中间撑爆的, 所以压缩 (`context_fit`) 与调用计次 (`model_budget`)
  仍是内层调模型前的规则. 会话级的花费统计是外层 `record_usage` 与网关的花费守卫.

如果将来要让外层在一轮中间叫停 (比如累计花费到线), 内层每圈开头多问一句外层给的
`should_continue()`. 现在没有这个需求, 不加.

### 决策 5: 外层随模型配置换的依赖改成用时读, 删 `reconfigure`

把背景 §5 做了一半的事做完. `AgentTurnService` 今天收的五样会随 `reload_llm` 换的东西
(`context_budget`, `context`, `memory`, `planning`, `tools`), 改成跟 `loop_factory` 与
`runtime_facts` 一样: 组合根交进来的、调用时读它当前字段的函数.

```python
AgentTurnService(
    session,
    loop_factory=...,          # 已是闭包
    runtime_facts=...,         # 已是闭包
    instructions=..., prompt_builder=..., run_bus=...,   # 不随模型配置换, 照旧
    context_budget=lambda: self.llm.context_budget(),
    memory=lambda: self.tools.memory,
    planning=lambda: self.tools.planning,
    tools=lambda: self.tools.dispatcher,
)
```

`context` (`WindowManager`) 从 `AgentTurnService` 删掉: 它在那里没用过. 压缩用的那一份
由组合根交给 `context_fit` 规则, 今天就是这么接的.

`reconfigure` 删掉. `reload_llm` 只剩: 建新的 `llm` 与 `tools`, 一起换上. 换完所有东西
自动指向新的, 没有"少传一个"的坑.

**不引入全局取.** 依赖仍写在签名上, 测试仍直接构造, `check_arch.py` 仍看得见 import.
一个谁都能 import 的 `runtime.current()` 会让所有机器守的边界失明: 循环里写一句
`current().memory.write(...)` 就绕过了记忆禁令, 检查脚本一个字都看不见. 组合根是唯一
知道"现在是哪一个"的地方, 别人拿到的是"去问它"的函数, 不是它字段的副本.

轮内的东西 (循环, 规则表, 账本, 取消令牌) 照旧显式传, 它们每轮都是新的, 不是"当前的
那一个".

### 决策 6: 删掉握手的词汇

`domain/agent/actions.py` 删去 `LoopAction` / `AnswerAction` / `ToolRequestAction` /
`LoopStepResult`, 加 `LoopResult`, `ToolExecutor`, `ContextAssembly`. 留 `ToolRequest`
(dispatcher 的入参), `LoopObservation` / `ObservationSource` / `ObservationDisposition`
(dispatcher 的返回, 规则看它), `LoopStop`. `observe()` 删掉. `LoopPhase` 收成三个:
没开始, 在跑, 结束.

## 实施清单

按下面顺序, 每步单独提交, 每步之后 `make ci` 通过. 第 1 到第 3 步动循环与域, 第 4 步动
外层, 第 5 步动组合根; 前三步做完测试就该全过, 后两步是接线.

1. **域类型** (`domain/agent/actions.py`, `phase.py`): 按决策 6 增删. `AssembledContext`
   留在 `domain/agent/state.py`, 说明改成"一次调用的材料"; `LoopInput` 删 `context`,
   加 `initial_window`.
2. **循环** (`application/agent_loop/builtin_loop.py`): `start` / `observe` / `_advance` /
   `_dispatch_next` / `_observe_tool` 合成 `run` / `_think_and_act` / `_run_batch` /
   `_execute`. `_build_request` 改为用 `assemble()` 的返回值. `_close_tools` 不再回调
   循环. 规则表, 账本, 事件发布, `_stop`, `_abandon_pending`, `_remember_assistant`
   不动. `LoopView` 的 `system_prompt` / `tools` / `budget` 改从这次的 `ctx` 取.
3. **测试** (`tests/agent_loop/`): 驱动器改成给循环一个假 `execute` 与一个固定的

   场景一个不减. 加一个场景: 同一轮里 `assemble` 第二次返回不同的状态帧, 第二次模型

   记忆、目录、围栏; `_outcome_from_stop` 改读 `LoopResult`; 删 `max_steps`; 五个依赖
   改成 `Callable[[], ...]`, 用处改成 `self._memory()` 这种; 删 `reconfigure`, 删
   `_context`.
5. **组合根** (`interfaces/runtime/project_runtime.py`): `_build_agent_turn` 按决策 5 传

6. **文档**: ADR-0010 §2, ADR-0018 §6, ADR-0041 决策 1, ADR-0048 决策 1 各标注被本文
   取代; ADR-0049 里"循环只产出意图"的几处改口径; 阅读线路 §1.1, §2.4, §3.2, §4, §5.1
   重画.

## 备选方案

- **保持三层握手.** 握手换来的"循环可以脱离工具系统测试", 用一个假 `execute` 同样能
  换来; 握手本身多四个类型、两个等待态、一层分发和一个兜底常量. **不采用.**
- **循环直接持有 dispatcher 与六个服务, 自己组上下文、自己执行.** 单一入口一样有保证,
  但循环认识了 `tool_request`, `context`, `prompt`, `memory`, `planning` 五个包, 构造参数
  多六个, `check_arch.py` 的记忆禁令要改. 交两个函数更省: 循环知道的是节奏, 不是配方.
  **不采用.**
- **保留按轮冻结, 只把状态帧改成每次重渲染.** 能换到待办即时可见, 但 FORGE.md 与
  记忆仍要等下一轮, 而且要解释"为什么第六层例外"—— 解释的内容就是背景 §3, 既然那段
  理由对六层都成立, 就没有理由只放开一层. **不采用.**
- **全局取依赖 (`runtime.current()`).** 见决策 5 最后一段. **不采用.**
- **一个小容器替手写组合根接线.** 容器解决的是"谁来 new", 不解决"换了之后谁指向新的";
  后者才是这里的痛点, 而闭包已经解决了它. 引一个依赖换不来东西. **不采用.**

## 影响

**好处.**

- 一个循环而不是两个半. 域里少四个类型, 循环少两个等待态和一次"回答已送达"的往返,
  外层少一个 `for` 加分发和一个兜底常量, 少一个 `reconfigure` 和一个没用的字段.
- 内层读起来就是"想, 做, 记, 直到不再要工具"; 外层读起来就是"记, 跑, 记".
- 模型在同一轮里看到自己刚改的待办、记忆与指令.
- 换模型之后所有东西自动指向新的, 没有"少传一个"的坑.
- 六层模型收成一句话, 少三份 ADR 里的机制说明.

**代价.**

- 四处早先的决定要标注取代, ADR-0049 几处口径要改, 阅读线路五节要重画.
- 38 个测试里 28 个基线用例在 `start/observe` 边界上, 全部要改断言对象, 场景不变.
- 每次调模型多读三个本地文件 (计划, 待办, 记忆) 和一次 FORGE.md. 都是小文件, 一次
  模型调用是几秒, 这点读取看不见.
- 模型一轮里改了 FORGE.md, 那一次前缀缓存不命中. 应该的.

**兼容性.** 会话事件, 运行事件, 安全管线, 规则与时机, Web 与 TUI 都不受影响.
`ToolRequestCoordinator` 一行不动.

## 验收标准

- `domain/agent/actions.py` 里没有 `LoopAction` / `AnswerAction` / `ToolRequestAction`
  / `LoopStepResult`.
- `BuiltinAgentLoop` 没有 `observe` 方法; `run` 每轮只能调一次; 一轮里 `assemble` 被调
  的次数等于模型调用次数.
- `builtin_loop.py` 不 import `tool_request`, `context.assembler`,
  `prompt.system_prompt_builder`, `prompt.project_instruction_reader`, `memory`,
  `planning`. (通知模板 `prompt.template_renderer.render_notice` 不算: 循环补配对结果
  要用它, 一直如此.)
- 同一轮里 `assemble` 第二次返回不同的状态帧, 第二次模型请求的末尾是新的; system
  prompt 与工具没变时, 两次请求的前缀字节相同.
- `AgentTurnService` 里没有 `_DEFAULT_MAX_LOOP_STEPS`, 没有 `reconfigure`, 没有对动作
  类型的 `isinstance`, 没有 `_context` 字段.
- `reload_llm` 之后不调任何 `reconfigure`, 下一轮用的是新网关与新工具栈.
- 38 个场景在改造后全过, 新增的"状态帧轮内更新"场景过; mypy 与三个架构检查通过.
