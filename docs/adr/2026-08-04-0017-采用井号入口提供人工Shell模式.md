# ADR-0017：采用井号入口提供人工 Shell 模式

## 状态

Superseded by ADR-0025（Web 不提供人工终端；受控 `shell.run` 不受影响）

## 日期

2026-08-04（2026-08-05 按实现回填：新增 `# 命令` 一次性执行、`FORGE_SHELL` 标记，
并把 §8.1 的实现选择写实）

## 背景

ForgeCLI 运行期间，用户仍会需要临时执行熟悉的 Shell 操作，例如检查 Git 状态、运行测试、调整
环境变量、切换目录、查看进程或打开交互式程序。如果用户必须先退出 Forge、执行命令、再重新启动并
恢复会话，会破坏 conversation-first 体验，也使终端上下文切换变得频繁。

Agent 生成的 Shell 命令与人类亲自在终端输入的命令具有不同信任主体：

- Agent Shell 是模型提出的执行请求，必须遵守 ADR-0013 定义的能力分析、策略裁决、HITL、恢复
  和审计边界。
- 人工 Shell 是当前 OS 用户主动接管终端后的直接操作。用户拥有与未启动 Forge 时相同的宿主权限，
  Forge 不应把这类操作再次包装成 Agent 工具请求并要求用户批准自己刚输入的命令。

如果两类入口共用 `ToolRequestCoordinator`，人工 Shell 会受到 mode、HITL、输出截断和非交互
子进程语义影响，无法使用 `cd`、`export`、补全、job control、全屏程序和原生 Shell 历史。如果完全
退出 Forge，则当前 session、项目锁、终端状态和对话连续性都要重新建立。

因此需要一个明确、不可由 Agent 伪造的人工终端接管入口，在保留 Forge 进程和 session 的同时，
临时运行真实交互式子 Shell。

## 决策

ForgeCLI 采用单独输入 `#` 进入人工 Shell 模式，并作出以下决策：

1. 只有空闲 Forge 主提示符从真实交互式 TTY 读取、清洗后的输入才能进入人工 Shell，且分两种
   形态：严格等于 `#` 开一次完整交互式会话；`#` + 空格 + **单行**内容执行一条一次性命令。
   两种形态信任语义完全相同，界面不同（见 §4）。

   > **本条在 2026-08-05 修订。** 原文是"`# 文本` 仍是普通自然语言输入"。改动理由：为一条
   > `clear` 开一整个会话太重，而一次性命令与会话的信任主体本来就是同一个人。代价是**单行**
   > `# 标题` 会被当成命令执行（多半得到 command not found，界面据此提示去掉井号）；多行
   > 输入不受影响，粘贴 markdown 文档仍是自然语言。
   >
   > 前缀字符曾在 `#` 与 `$` 之间权衡：`$ ` 的碰撞面更小且能直接粘贴 README 里的
   > `$ npm install`，但最终选择保持 `#` 与会话入口一致。字符定义在
   > `application/intent_router.py::ONE_SHOT_PREFIX` 一处，改动只需一行。
2. 人工 Shell 是独立信任通道：跳过 LLM、AgentLoop、mode policy、HITL、
   `ToolRequestCoordinator`、`ToolAuthorizationService`、`ShellTool` 和工作区恢复机制，只受当前
   OS 用户权限约束。
3. Forge 在进入前暂停自身输入与渲染，使用平台交互式终端 Provider 启动用户 Shell，并把
   stdin、stdout、stderr、终端尺寸、信号和 job control 临时交给子 Shell。
4. `exit`、Ctrl-D 或 Shell 结束后返回同一个 Forge 进程和 session；Ctrl-C、Ctrl-Z 等终端信号在
   Shell 模式内优先交给子 Shell 或其前台任务。
5. 每次进入创建一个新的交互式子 Shell。`cd`、`export`、alias 和 shell option 在该次 Shell 会话
   内保持，退出后不反向修改 Forge 父进程的 cwd、环境或 workspace root。
6. Shell 内的命令、输入和输出默认不进入 Forge conversation history、LLM context、工具审计或
   artifact。Forge 最多记录不含命令内容的 entered/exited 生命周期摘要。
7. 返回 Forge 后，所有可能受人工文件变更影响的缓存、文件系统视图、待执行 ToolPlan 和审批绑定
   必须失效；下一次 Agent turn 重新构造执行上下文和工作区上下文。
8. 项目进程锁在 Shell 模式期间保持。人工 Shell 可以像普通终端一样修改工作区或启动后台进程，
   这些文件与进程的变更归属于用户，不归属于 Agent，也不承诺由 Forge RecoveryStore 恢复。
9. 本 ADR 修订 ADR-0013 中“所有 Shell 执行只能经过 ToolRequestCoordinator”的范围：该不变量
   继续约束 Agent、slash command、resume、workflow、MCP 和其他应用内自动化入口；人工 TTY 用户
   显式进入的 Shell 模式是唯一例外，且不得暴露为 Agent 可调用工具。

## 备选方案

- ~~使用 `# command` 每次执行单条命令~~：**已改为与会话并存**（决策 1，2026-08-05）。原判断
  "每条命令都是新子进程，形不成真实连续会话"仍然成立，所以它没有**取代**会话入口；但它作为
  会话之外的补充是划算的——`clear`、`git status`、`ls` 这类一次性操作根本不需要连续会话，
  而为它们开一个会话再退出的仪式感比命令本身还重。
- 一次性命令用 `-c` 而不是 `-i -c`：省掉每次 source rc 的开销，但用户的 alias、函数和 rc 里
  配的 PATH 全部失效，`# ll` 会报 command not found。用户抱怨的"重"是进入退出的仪式，不是
  几十毫秒，因此选择 `-i -c`。
- 使用 `/shell` 进入：与现有 slash command 一致，但 `#` 更短、更像终端模式切换；slash command
  体系主要面向 Forge 应用能力，人工终端接管属于不同交互层。
- 一次性命令改用 `$ ` 前缀：碰撞面确实更小（`$ ` 开头的自然语言几乎不存在，而单行 `# 标题`
  是合理输入），且 `$ ` 是全世界文档里 shell 命令的写法。放弃它是为了让两个入口共用一个字符，
  少一样要记的东西。127 退出码提示（§4）承担了误伤的兜底。
- 在人工 Shell 里改写用户 prompt 以标示"当前在 Forge 内"：最直观，但会打坏 powerlevel10k /
  starship 这类自己拼提示符的配置，且各 shell 注入点不同。改为注入 `FORGE_SHELL` 环境变量
  （§6.4），与 `VIRTUAL_ENV` / `IN_NIX_SHELL` / `TMUX` 同一套做法。
- 退出 Forge 后使用宿主 Shell：语义最纯粹，但中断对话和工作状态，用户需要重新启动和恢复。
- 将人工命令包装为 `shell.run`：可以复用工具管线，但会把用户直接操作误判为 Agent 行为，无法
  提供原生交互式 Shell 体验。
- 在 Forge 中实现 Shell 解析器和内建命令：可以控制状态，但等于重新实现 zsh/bash/PowerShell，
  复杂度、兼容性和行为差异不可接受。

## 影响

- IntentRouter 增加 `ManualShellIntent`，但只有 CLI 的 TTY 输入适配器可以构造该意图。
- application 层新增 `ManualShellService`，以及 `InteractiveShellProvider`、
  `InteractiveShellResolver`、`TerminalLease`、`ManualShellObserver` 四个端口。
- CLI 新增 `TerminalLease`，统一暂停和恢复 prompt_toolkit、Rich Live、终端模式与前台进程组。
- infrastructure 分平台实现终端交接：POSIX 用前台进程组，Windows 用控制台句柄继承
  （两者都不介入字节流，理由见 §8.1）。
- 人工 Shell 不受 Forge mode 和 Agent 安全策略保护；这是用户直接控制宿主终端的明确产品语义。
- 人工修改不会进入 RecoveryStore，Agent 后续必须把工作区视为可能已被外部修改并重新取事实。
- 需要新增伪终端 E2E 测试，普通 StringIO 单元测试不足以覆盖信号、job control 和终端恢复。
- `IntentRouter.route` 增加 `origin` 参数，默认 `PROGRAM`；所有既有调用方语义不变。
- `AgentTurnService` 增加失效屏障依赖：屏障未清干净时拒绝开始下一轮。

## 设计细节

## 1. 目标与非目标

### 1.1 目标

- 用户无需退出 Forge 即可获得接近普通交互式 Shell 的体验。
- 一次性命令（`clear`、`git status` 这类）不必为它开一整个会话再退出。
- Shell 模式支持 `cd`、环境变量、alias、补全、历史、管道、重定向、前后台任务和全屏程序。
- Shell 结束后可靠恢复 Forge 输入框、状态栏、终端属性和当前 session。
- 在架构上严格区分“人类终端接管”与“Agent 请求执行 Shell 命令”。
- 人工 Shell 行为不进入 LLM 上下文，也不隐式授权 Agent 执行相同命令。
- 人工修改后 Agent 不复用过期文件、计划、审批或执行环境事实。
- 用户能判断自己当前是否处于 Forge 启动的 Shell 内。

### 1.2 非目标

- 不为人工 Shell 命令执行 Forge 的风险分类、HITL 或恢复保护。
- 不捕获、解析、脱敏、截断或持久化人工 Shell 的每条命令和输出。
- 不让 Agent 通过工具调用、模型文本或提示注入进入人工 Shell 模式。
- 不在 Forge 父进程中解释 `cd`、`export`、alias 或其他 Shell builtin。
- 不让一次人工 Shell 会话对 Forge 父进程环境进行反向同步。
- 不保证 Shell 退出后清理由用户启动的后台任务；遵循所选 Shell 的正常 job/exit 语义。

## 2. 两类 Shell 信任边界

```text
Agent / application 发起
  -> ToolRequest
  -> ToolRequestCoordinator
  -> policy / HITL / recovery
  -> ShellTool
  -> 受控执行 Provider

TTY 用户在空闲主提示符输入 #  或  # 命令
  -> ManualShellIntent(command="" 或 命令)
  -> ManualShellService
  -> TerminalLease
  -> InteractiveShellResolver -> InteractiveShellProvider
  -> 用户交互式 Shell（会话或一条命令）
```

两种形态走**同一条**路径, 因为它们的信任主体是同一个人。差别只在 argv（`-i` 还是 `-i -c`）
与界面（打不打边界提示），不在裁决。

两条路径不得互相调用或降级：

- `ManualShellService` 不接受 `ToolRequest`，不注册进 ToolCatalog，也不实现 MCP tool。
- AgentLoop、slash command handler、resume service 和 hook 不得构造 `ManualShellIntent`。
- `ShellTool` 不得以“需要交互”为由转发到 `ManualShellService`。
- 人工 Shell 中执行过某条命令不能作为 Agent 的 approval、allow rule 或用户意图证明。
- `#` 的特权来自输入 provenance，而不是字符本身。只有当前前台 TTY 输入适配器可以标记
  `InputOrigin.TTY_USER`。

## 3. 输入解析与状态机

输入解析优先级：

```text
空输入
  -> 忽略

origin == TTY_USER 且 trim(input) == "#"
  -> ManualShellIntent(command="")        开一次完整会话

origin == TTY_USER 且 trim(input) 以 "# " 开头且不含换行
  -> ManualShellIntent(command=剩余部分)   执行一条一次性命令

input starts with "/"
  -> SlashCommand

其他输入
  -> UserMessage
```

两道形态限制各挡一类东西，缺一条误伤面就明显变大：

| 限制 | 挡掉的东西 |
| --- | --- |
| `#` 后必须有空格 | `#!/bin/sh`、`#include <stdio.h>`、`#define X`、`#123`、`#tag`、`## 二级标题` |
| 必须是单行 | 粘贴进来的 markdown 文档：`# 标题\n\n正文…` |

剩下的误伤只有一种：**单行 `# 标题`**。它会被当成命令执行。这是决策 1 明确买下的代价，
兜底是 §4 的 127 退出码提示。实现里有一条测试专门断言这个行为
（`test_a_single_line_heading_is_the_accepted_casualty`），把代价钉住，避免有人以为是 bug
顺手"修好"从而无声地废掉一次性命令。

`#` 只有在 Forge 处于 `PROMPT_IDLE` 时有效：

```text
PROMPT_IDLE
  -> SHELL_PREPARING
  -> SHELL_ACTIVE
  -> SHELL_RESTORING
  -> PROMPT_IDLE
```

如果未来 REPL 支持后台 Agent turn，进入人工 Shell 前必须确认没有前台审批、终端工具或仍可能写工作区
的 Agent 动作。MVP 单线程 REPL 在读取 `#` 时天然处于 turn 之间，不能增加“暂停一半 Agent turn 后
进入 Shell”的隐式路径。

## 4. 用户体验

### 4.1 完整会话

进入时只显示一条边界提示，不执行二次确认：

```text
forge› #

进入 Shell 模式 · zsh · cwd=/workspace/ForgeCLI
输入 exit 或 Ctrl-D 返回 Forge · 环境变量 FORGE_SHELL=1

user@host ForgeCLI % git status
user@host ForgeCLI % cd ..
user@host workspace % export DEBUG=1
user@host workspace % vim README.md
user@host workspace % exit

返回 Forge · shell exit 0
forge›
```

规则：

- Shell 使用自己的原生 prompt、配色、历史、补全和启动脚本；Forge 不伪造 Shell prompt。
- Forge 不在每条命令前显示 mode、workspace、HITL 或工具状态。
- `exit` 和 Ctrl-D 结束人工 Shell；Ctrl-C 只中断 Shell 当前前台任务。
- Shell 启动失败时显示一条可行动错误并返回 Forge，不进入半初始化状态。
- Shell 由信号或崩溃结束时显示 exit code 或 signal 摘要，但不把它标记成 Agent tool failure。
- 返回后的 Forge prompt 必须完整重绘，不能遗留 raw mode、alternate screen 或破损光标状态。

### 4.2 一次性命令

**成功时 Forge 一个字都不打**：

```text
forge› # git status
On branch feat/mvp
nothing to commit, working tree clean
forge›
```

这不是省事，是这条路径成立的前提。`# clear` 之后再打一行"返回 Forge"，刚清干净的屏幕就又有
东西了——而用户要的正是那块干净屏幕。同理，进入提示（`进入 Shell 模式 · …`）对一次性命令
也不打。

只有三种情况出声，因为那时用户需要知道出了什么事：

| 情况 | 输出 |
| --- | --- |
| 启动失败 | `未能进入 Shell: <原因>` |
| 被信号终止 | `命令被信号 15 终止` |
| 非零退出 | `命令退出码 2`，不加解释——那是用户自己的命令，他比 Forge 清楚 |

退出码 127（cmd.exe 是 9009）额外替换成一句可自我纠正的提示：

```text
forge› # 这句其实是想说给模型听的
zsh:1: command not found: 这句其实是想说给模型听的
命令未找到. 如果这句是想说给模型听的, 去掉开头的 "# " 再发一次.
```

这条提示是 §3 那处已知误伤的兜底，把"莫名其妙报错"变成"哦我该去掉那个井号"。

**只看退出码，不看输出。** 退出码是一个整数，不是内容；解析 stderr 去判断"是不是 command
not found"会直接违反 §9 的不捕获约束。

## 5. 应用端口

```text
ManualShellRequest
  shell_executable
  argv
  cwd
  environment
  terminal
  command            一次性命令; 空串表示完整会话
  interactive        = not command

ManualShellResult
  started_at
  finished_at
  exit_code?
  signal?
  start_error?

ManualShellContext          Forge 这边的事实, 每次进入现取
  cwd
  environment
  terminal
  command

InteractiveShellResolver
  resolve(context) -> ManualShellRequest

InteractiveShellProvider
  open(request) -> ManualShellResult

TerminalLease
  acquire() -> ContextManager       用上下文管理器表达, 保证 release 走 finally

ManualShellObserver
  entered(request)
  exited(result)

ManualShellService
  enter(intent, context) -> ManualShellResult
```

`ManualShellService` 负责：

- 校验请求来自空闲 TTY 用户输入。
- 从 execution profile/用户环境解析交互式 Shell。
- 获取 `TerminalLease`，调用平台 Provider，并在 `finally` 中释放终端。
- 将 entered/exited 生命周期通知发送给观察者。
- 无论成功或失败都触发返回 Forge 后的上下文失效。

三条实现层面的约束：

- **`enter` 收的是 `ManualShellIntent` 而不是裸字符串。** 意图对象的构造函数已经拒绝了非
  `TTY_USER` 来源（§2），换成字符串参数等于把那道校验丢掉。
- **`observer` 是必填参数，没有默认值。** §4.1 与 §6.2 把进入提示（尤其那行 cwd）定成硬性
  要求，而那行字是 observer 打的。给它默认值意味着漏接的后果是"界面少一行"这种没人会注意到
  的静默降级。真不需要通知的调用方显式传 `NullManualShellObserver`。
- **`command` 在 request 里是因为非有不可**（不放进 argv 就跑不了），但它绝不能流向审计、
  事件或模型上下文。`ManualShellResult` 因此一个能装命令或输出的字段都没有——这是类型层面的
  保证，不是纪律。observer 实现同样不得持久化 `request.command`。

它不负责：

- 解析 Shell 内命令。
- 捕获 stdout/stderr。
- 安全裁决或创建审批。
- 写 Agent 工具审计。
- 将 Shell 内容转成 conversation message。

## 6. Shell 选择、cwd 与环境

### 6.1 Shell 选择

POSIX 默认选择顺序：

1. Forge 启动时可信用户环境中的绝对 `$SHELL`，且文件存在并可执行。
2. execution profile 探测到的用户 Shell。
3. 平台保守 fallback，例如 `/bin/sh`。

Windows 默认选择当前配置的 PowerShell、`pwsh` 或 `COMSPEC`。Shell 路径只用于启动人工会话，
不是 Agent executable allowlist，也不进入 ToolAuthorizationService。

默认启动普通 interactive non-login shell；例如 zsh/bash 使用 `-i`。不默认增加 login 参数，避免重复
执行 login profile。用户可在后续配置中显式选择 shell executable 和启动参数。

一次性命令在同一个 Shell 上追加 `-c`：

| Shell | 完整会话 | 一次性命令 |
| --- | --- | --- |
| sh / bash / zsh / ksh / dash / fish | `-i` | `-i -c <命令>` |
| pwsh / powershell | （无） | `-Command <命令>` |
| cmd | （无） | `/c <命令>` |

一次性命令**保留 `-i`**：没有它就不 source rc，用户的 alias、函数与 rc 里配的 PATH 全部失效，
而 `# ll` 正是最常见的用法之一。代价是每次多 source 一遍 rc（几十到几百毫秒），但决策 1 要解决
的"重"是进入退出的仪式，不是这点延迟。

`$SHELL` 只接受**绝对路径**。相对值（`SHELL=zsh`）需要靠 PATH 查找，而人工 Shell 用的是用户
环境快照里的 PATH——那份 PATH 里可能包含 Agent 可写目录。解析不出可用 Shell 时按 §12 报错，
不静默回退到一个用户不认识的 Shell。

### 6.2 cwd

初始 cwd 是 Forge 当前交互上下文的 cwd，默认等于 primary workspace root。人工 Shell 内可以
`cd` 到任意 OS 允许的位置；退出后 Forge cwd 和 workspace roots 保持不变。

进入提示必须显示初始 cwd，避免用户误以为继承了上一次人工 Shell 的目录。再次输入 `#` 创建新会话，
仍从 Forge cwd 开始。

### 6.3 环境

人工 Shell 继承 Forge 启动时的用户环境快照以及终端必要变量，不使用 Agent ToolRuntime 的净化环境。
Shell 启动脚本可以按用户正常配置进一步修改环境。

人工 Shell 内 `export`、`unset` 和激活虚拟环境只影响该子 Shell及其后代。退出后不尝试解析或同步环境
差异；需要改变 Forge/Agent 配置时使用对应 Forge 配置入口。

### 6.4 "我现在是不是在 Forge 里"

人工 Shell 用的是用户自己的 prompt，因此它和一个普通终端长得一模一样——用户滚上去几屏之后就
分不清自己是在 Forge 的子 Shell 里还是在别的窗口，`exit` 会不会把整个 Forge 关掉也说不准。

Forge 注入两个环境变量：

```text
FORGE_SHELL=1
FORGE_SHELL_CWD=<进入时的 cwd>
```

**不改写用户 prompt。** §4.1 要求"Forge 不伪造 Shell prompt"，而往别人的 `PROMPT`/`PS1` 里插
东西会打坏 powerlevel10k、starship 这类自己拼提示符的配置，且各 shell 的注入点都不同。环境变量
是这类"我在某个子环境里"的通行做法（`VIRTUAL_ENV`、`IN_NIX_SHELL`、`TMUX`、`STY`）：Forge 只
负责把事实摆出来，怎么显示由用户决定。进入提示（§4.1）会告诉他这个变量存在。

`FORGE_SHELL` 还有第二个用处：在人工 Shell 里再启动 forge 时能据此认出嵌套，§11 的项目锁报错
可以说得更准。

**这只解决了一半。** 变量要用户自己配进 prompt 才看得见，开箱即用仍然分不清。真正开箱即用的
做法是用 `ZDOTDIR` / `--rcfile` 生成临时 rc，先 source 用户原 rc 再追加一段标记（nix-shell 的
做法）。那是分 shell 的实打实工作量，且需要重新界定"不伪造 prompt"的边界，本次未做。

## 7. 终端所有权与信号

`TerminalLease` 是 Forge 内所有交互式终端接管的唯一协调点：

```text
停止或清空 Rich Live
  -> 暂停 ForgePrompt/status renderer
  -> 保存 termios/console mode、光标和 screen 状态
  -> InteractiveShellProvider 取得前台终端
  -> 子 Shell 运行
  -> 回收子进程
  -> 恢复 termios/console mode、光标和 screen 状态
  -> 重绘 ForgePrompt/status renderer
```

必须在 `try/finally` 中恢复，覆盖正常退出、启动失败、Shell 崩溃、信号退出和 Forge 自身终止路径。

信号规则：

- Shell 活跃时，Ctrl-C、Ctrl-Z、Ctrl-\ 和窗口尺寸变化由子 Shell/前台进程组处理。
- Forge 不把 Shell 内 Ctrl-C 解释为 Agent cancel 或 REPL quit。
- POSIX Provider 管理 controlling TTY 和前台 process group，并在退出后把前台控制权交还 Forge。
- Forge 收到进程终止请求时，先按平台语义通知/结束人工 Shell，再尽力恢复终端并执行正常关闭。
- Shell 退出后必须回收直接子进程，不能留下 zombie；后台 job 是否继续由 Shell 自身决定。

## 8. 跨平台 Provider

### 8.1 POSIX

`PosixInteractiveShellProvider` 使用 PTY 或等价的前台进程组交接，至少支持：

- controlling terminal。
- interactive shell 和 job control。
- 原始字节 stdin/stdout/stderr 直达（转发或直接继承均可）。
- SIGWINCH 尺寸同步。
- Ctrl-C/Ctrl-Z 等信号语义。
- alternate screen、颜色和全屏程序。
- 子 Shell 退出码和信号收集。

不能仅使用带 `stdin=PIPE` 的 `subprocess.run` 模拟交互式 Shell；这会丢失 job control、终端探测、
补全和全屏程序行为。

#### 实现选择：前台进程组交接，不开 PTY

上面两条路径本 ADR 都允许，实现选了后者。理由是在**本场景下** PTY 严格更弱：

开 PTY 意味着 Forge 坐在用户和 Shell 中间，每个字节都要经 Forge 转发一次。那是"需要观察或改写
流"时的做法——而 §9 恰恰**禁止**观察：不捕获 stdin/stdout/stderr，不记录 history。既然一个字节
都不许看，转发就只剩代价：多一层缓冲会打乱全屏程序时序，SIGWINCH 要手工同步，信号要手工翻译，
而且 Forge 进程里凭空多出一份用户输入。

Forge 的 stdin/stdout **本来就是**用户的真实终端（bootstrap 已拒绝非 TTY 启动），直接交出去，
用户拿到的就是原生终端，中间没有任何一层：

```text
subprocess.Popen(..., process_group=0)   子进程进入独立进程组
  -> os.tcsetpgrp(fd, child_pgid)        把它设为前台, 于是它拥有 controlling terminal
  -> 等它结束                             job control / 补全 / 全屏程序全部原生可用
  -> os.tcsetpgrp(fd, forge_pgid)        交还 Forge
```

两处不能省：

- **独立进程组 + `tcsetpgrp`。** 只 `Popen` 不设前台的话，子 Shell 与 Forge 同组，Ctrl-C 会
  同时打到两边——而 §7 要求"Forge 不把 Shell 内 Ctrl-C 解释为 Agent cancel"。
- **两次 `tcsetpgrp` 期间临时忽略 SIGTTOU。** 从非前台进程组调用 `tcsetpgrp` 会收到 SIGTTOU
  把自己停住，结束后原样恢复。

`tcsetpgrp` 整段是 best effort：拿不到前台控制权（例如 Forge 自己就在后台）时不阻止 Shell 启动，
但**终端交还必须走 `finally`**。

将来若需要在非前台场景（如后台 Agent turn 期间）接管终端，PTY 路径仍然是正确答案，届时替换
`InteractiveShellProvider` 的实现即可，端口不变。

### 8.2 Windows

`WindowsInteractiveShellProvider` 使用 ConPTY 或当前 Windows Console 的受控交接，至少支持：

- PowerShell/pwsh/cmd 的交互输入输出。
- console mode 保存与恢复。
- Ctrl-C/Ctrl-Break。
- 窗口尺寸同步。
- UTF-8/Unicode 输入输出。
- 子进程退出后可靠返回 Forge。

同样不开 ConPTY，理由与 §8.1 一致：Windows 控制台子进程默认继承父进程的控制台句柄，而 Forge 的
控制台就是用户的控制台。ConPTY 是"把控制台**嵌进**另一个程序的窗口"时才需要的东西，这里没有第二
个窗口。进程组在 Windows 上没有对应物（Ctrl-C 由控制台按前台进程路由），但必须在人工 Shell 期间
摘掉 Forge 自己的 SIGINT 处理，否则 Forge 会把用户中断命令的那次 Ctrl-C 当成对自己的。

平台暂不支持所需终端能力时应明确拒绝进入并给出诊断，不能静默降级成无法交互的管道子进程。

> **Windows 实现未经实测。** 当前只在 POSIX 上验证过。若实际行为与本节不符，按本节末句处理
> ——明确拒绝并给出诊断，而不是降级。这也是本 ADR 暂不转 Accepted 的唯一原因。

## 9. 会话、隐私与事件

人工 Shell 内容默认不属于 Forge session transcript：

- 不写 `user_message` 或 `assistant_message`。
- 不写 `tool_requested`、`tool_completed` 或 `policy_decision`。
- 不捕获 Shell history、stdin、stdout 或 stderr。
- 不加入下一次模型请求的 messages/context package。
- 不因人工命令成功而创建 learned allow rule。

可以选择记录以下不含内容的生命周期事件：

```text
manual_shell_entered
  shell
  initial_cwd
  entered_at

manual_shell_exited
  exit_code?
  signal?
  duration
```

生命周期事件不得包含命令、输出、Shell history、环境变量值或子进程参数。MVP 可以完全不落盘，
只在进程内用于终端恢复和诊断（当前实现即如此：只有进程内的 observer，没有 session event）。

**一次性命令带来一处需要点明的边界。** `ManualShellRequest.command` 里装着用户敲的那条命令
——非有不可，不放进 argv 就跑不了。它因此会经 `ManualShellObserver.entered(request)` 传给观察者。
约束是：

- `ManualShellResult` **在类型上**没有任何能装命令或输出的字段，所以退出摘要、生命周期事件与
  未来的落盘路径天然带不出内容。
- observer 实现**不得持久化** `request.command`。当前的 `ConsoleManualShellObserver` 只读
  `descriptor`（Shell 的 basename）与 `cwd`，且对一次性命令根本不打字。
- 想给生命周期事件加落盘时，只能取 shell 名、初始 cwd、退出码/信号与时长。

用户敲进终端的命令本来就显示在他自己屏幕上，Forge 不需要再存一份；而存了那一份就会进日志、
进审计、最终进模型上下文。

## 10. 返回 Forge 后的失效屏障

人工 Shell 可以在 Forge 不可观察的情况下修改工作区、依赖、可执行文件和配置。返回 Forge 后必须执行
一次 `ManualMutationBarrier`：

```text
人工 Shell 退出
  -> 丢弃 filesystem view / directory snapshot
  -> 清空脚本分析和依赖内容缓存
  -> 失效尚未执行的 ToolPlan / target expansion
  -> 失效未消费的 approval / authorization binding
  -> 标记 context package 需要重建
  -> 下一次工具调用重新生成 ExecutionContext
  -> 下一次模型调用重新收集工作区上下文
```

规则：

- 不尝试通过命令记录推断哪些文件改变；Forge 没有捕获人工 Shell 内容，应按可能发生任意外部变更处理。
- 已完成的历史审计事件保持不变，但不能证明人工 Shell 退出后的当前状态。
- 进入 Shell 前存在的未消费一次性授权必须撤销或因 execution/workspace snapshot 变化而失效。
- 返回后不自动触发 LLM 总结或扫描整个工作区；在下一次需要事实时惰性重建。
- 人工修改与编辑器、Git GUI、其他终端进程造成的外部修改语义相同，不纳入 RecoveryStore。

### 10.1 实现范围与今天的实际覆盖

`ManualMutationBarrier` 用**注册制 + 单调 generation** 落地：持有缓存的组件在装配期注册一个
清理函数，屏障逐个调用；generation 单调递增，供任何想跨人工 Shell 复用事实的地方当失效键。

用注册制而不是让屏障去认识每一个缓存：后者意味着新增一处缓存要记得改屏障，而"忘了改"是静默的。

上面那张清单里，**今天真正注册进去的只有 `RiskCache` 一处**。其余各项不是漏了，是当前架构下
它们本来就不存在跨轮状态：

| 清单项 | 今天的实际情况 |
| --- | --- |
| filesystem view / directory snapshot | `context_factory` 每次调用现建 `OsFileSystemView`，本来就不复用 |
| 脚本分析与依赖内容缓存 | 即 `RiskCache`，**已注册** |
| 未执行的 ToolPlan / target expansion | per-call 产生并立即消费，无缓存 |
| 未消费的 approval / authorization binding | 协调器内联阻塞审批，不留跨轮待消费项 |
| context package 重建标记 | 工作区上下文收集器尚不存在（系统提示词模块未做） |

所以注册表与 generation 主要是**给将来的缓存留判据**。新增任何跨轮缓存时，同时注册一个清理
函数是硬性要求。

屏障有两条不能改的行为：

- **在 `finally` 里 trip。** 启动失败的 Shell 也可能已经跑过 rc 文件，"没进去"不等于"什么都
  没发生"。租约抛异常时同样触发。
- **清不掉就阻止下一轮。** `AgentTurnService.handle_user_message` 在屏障 blocked 时直接拒绝，
  并说清是哪个钩子失败的。清不掉缓存就无法证明后续裁决基于当前事实。

## 11. 进程锁与并发

- Forge 项目进程锁在人工 Shell 活跃期间继续持有，保证当前 Forge session 没有第二个 Forge 进程并发
  操作同一项目状态。
- 人工 Shell 启动另一个同项目 Forge 时，后者按现有锁策略拒绝；本 ADR 不增加递归 Forge 特例。
- 人工 Shell 可以启动普通后台进程。Forge 返回后不拥有这些进程，也不把它们加入 Agent job manager。
- MVP 只允许在没有运行中 Agent turn 时进入；未来并发 Agent 模式必须先实现显式 pause/barrier，
  不能只暂停终端渲染而让 Agent 在后台继续修改文件。

## 12. 错误与恢复

| 场景 | 行为 |
| --- | --- |
| Shell 不存在或不可执行 | 显示启动错误，恢复 Forge prompt |
| 无 TTY | 不创建 `ManualShellIntent`，保持普通输入规则 |
| 有 TTY 但拿不到控制终端 | 明确报错，不降级为 pipe 模式（§8.2） |
| 会话 exit 0/非 0 | 显示返回摘要，恢复 Forge |
| 一次性命令 exit 0 | **不显示任何内容**（§4.2） |
| 一次性命令非 0 退出 | 显示 `命令退出码 N` |
| 一次性命令 exit 127 / 9009 | 显示"命令未找到"并提示去掉开头的 `# ` |
| Shell 被 signal 终止 | 显示 signal 摘要，恢复 Forge |
| 全屏程序破坏终端状态 | `TerminalLease.finally` 恢复并完整重绘 |
| Forge 在 Shell 期间退出 | 终止/交接子 Shell，释放终端和项目锁 |
| 失效屏障失败 | 禁止开始下一次 Agent turn，给出可行动诊断 |

终端恢复失败是交互基础设施错误，不应伪装为 Shell 命令失败。若无法证明终端和工作区上下文已经恢复，
Forge 应安全退出，而不是在未知状态继续接收 Agent 指令。

## 15. 测试策略

实现落在 `tests/manual_shell/`，7 个文件。其中两个真的 `pty.fork()` 起子进程跑 `/bin/sh`
（`test_posix_pty_e2e.py`、`test_repl_entry_e2e.py`），因为下面 15.2 / 15.3 的断言 StringIO
给不了。两者都用 `pytest.importorskip` 在 Windows 上整体跳过。

### 15.1 路由与信任边界

- 单独 `#`、单行 `# 命令`，且来源为前台 TTY 时才产生 `ManualShellIntent`。
- LLM 文本、工具输出、事件重放和非 TTY 输入不能进入人工 Shell——包括来源为 PROGRAM 的
  `# rm -rf /`。
- `#!/bin/sh`、`#include`、`#123`、`## 二级标题`、多行 markdown 仍是自然语言。
- `ManualShellIntent(origin=PROGRAM)` 构造即抛错。
- 人工 Shell 路径不调用 LLM、AgentLoop、ToolRequestCoordinator、policy、HITL 或 RecoveryStore
  ——除 `check_arch.py` 的静态规则外，另有一条测试直接 AST 扫描 `application/manual_shell/`
  的 import，给"忘了跑 make arch"兜底。
- 人工 Shell 历史不能满足 Agent approval 或 learned allow rule。
- 单行 `# 标题` **确实**被当成命令：这条不是在断言正确行为，是把决策 1 买下的代价钉住，
  防止有人当成 bug 顺手"修好"从而无声废掉一次性命令。

### 15.2 Shell 行为

- `cd`、`export` 和 alias 在当前子 Shell 内持续有效。
- 退出后 Forge cwd、环境、workspace roots 和 session id 不变。
- `exit`、Ctrl-D、非零退出和 signal 终止均返回 Forge。
- Ctrl-C 中断 Shell 前台任务而不是取消 Forge session。
- 交互程序、颜色、补全、历史、管道、重定向和 job control 可用。

### 15.3 终端恢复

- termios/console mode、光标、alternate screen、前台进程组和窗口尺寸正确恢复。
- Provider 在各个生命周期点抛错时 `TerminalLease` 都执行 release。
- Shell 退出后 Forge prompt 和状态栏只重绘一次，无残留输入和重复 banner。

### 15.4 隐私与失效

- 命令、输入、输出和环境值不进入 session event、日志、artifact 或模型上下文。
- `ManualShellResult` 的字段集合被测试锁死，加一个 `captured_output` 会立刻失败。
- 进入提示只含 Shell basename 与 cwd：环境变量名与值、完整 Shell 路径都不出现。
- 可选生命周期事件只含 shell、初始 cwd、exit/signal 和 duration。
- 人工 Shell 修改文件、脚本、依赖或 executable 后，旧缓存、计划和审批均不能复用。
- 屏障在 `finally` 里 trip：启动失败与租约异常同样触发（rc 文件可能已经跑过）。
- 失效屏障失败时下一次 Agent turn 被阻止，且拒绝理由说得出是哪个钩子失败。

### 15.6 一次性命令

- 成功时终端输出为**空串**——这是 `# clear` 能用的全部前提。
- 非零退出、信号终止、启动失败各有一条可区分的提示。
- 退出码 127 给出"去掉开头的 `# `"提示。
- 一次性命令不打进入提示。
- `-i -c` 与 `-i` 两种 argv 各有断言。

### 15.5 跨平台

- POSIX 覆盖 zsh/bash/sh、controlling terminal 可见性、独立前台 process group、
  `cd`/`export` 会话内持续、非零退出与 signal 终止可区分。真 pty，非 StringIO。
- Windows 覆盖 PowerShell/pwsh/cmd、Console mode、Ctrl-C 和 Unicode。**当前缺失**，
  是本 ADR 转 Accepted 的唯一阻塞项。
- 平台能力缺失时明确失败，不退化为伪交互 pipe。

## 16. 验收标准

| 标准 | 状态 |
| --- | --- |
| 用户在空闲主提示符输入单独 `#` 后进入真实交互式 Shell | ✅ 真 pty E2E |
| 单行 `# 命令` 执行一条命令后返回；成功时 Forge 无输出 | ✅ |
| `#` 开头但不带空格的输入、多行输入仍作为自然语言发送给 Agent | ✅ |
| Shell 模式不触发 mode policy、HITL、ToolRequestCoordinator、ShellTool 或 LLM | ✅ 静态规则 + AST 扫描 |
| Shell 支持原生 prompt、历史、补全、`cd`、`export`、管道、重定向、job control 和全屏程序 | ✅ POSIX 实测（全屏程序未单独构造用例） |
| `exit` 或 Ctrl-D 返回同一个 Forge 进程和 session，Ctrl-C 不退出 Forge | ✅ 独立进程组 |
| 每次进入是新 Shell；退出后 Forge cwd、环境和 workspace roots 不变 | ✅ |
| 人工 Shell 命令和输出不进入 conversation history、模型上下文、Agent 审计或 learned allow rule | ✅ 结果类型上装不下 |
| 所有退出和错误路径都恢复终端状态、前台进程组、Forge prompt 和项目锁 | ✅ `finally` + 用例覆盖 |
| 返回 Forge 后执行失效屏障，旧事实不再复用 | ⚠ 见 §14 阶段 4：目前只有 `RiskCache` 一处真缓存 |
| Agent、工具、MCP、slash command、resume 和自动化入口无法构造或调用人工 Shell 通道 | ✅ 三道锁（§2） |
| ADR-0013 的统一 Shell 安全管线继续约束所有非人工 TTY Shell 入口 | ✅ 未改动 |
| 用户能判断自己当前处于 Forge 的人工 Shell 内 | ⚠ `FORGE_SHELL` 已注入，但需用户自行配进 prompt（§6.4） |
| POSIX 和 Windows 平台行为有对应测试 | ❌ **Windows 未实测** |

`make ci` 通过（340 个测试）。**转 Accepted 的唯一阻塞项是最后一行**：Windows 平台需要在真实
Windows 控制台上验证 PowerShell/pwsh/cmd、Ctrl-C、窗口尺寸与 Unicode，或者显式把 Windows 支持
降级为"暂不支持并明确拒绝"再转。
