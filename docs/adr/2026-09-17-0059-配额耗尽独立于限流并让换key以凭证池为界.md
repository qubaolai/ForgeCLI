# ADR-0059: 配额耗尽独立于限流, 并让换 key 以凭证池为界

## 状态

Proposed (2026-09-17; 工作区里有一版实现, 分支 `refactor/claude-code-tools`, 未提交)

修订 ADR-0011 §5 / §7 / §12 / §16 与 ADR-0012 §2 里关于"换凭证受 `max_retries` 约束",
"冷却状态不落盘"与"`credential_refs` 只支持手写"的三句. 其余 (绝不切换 provider/model, 凭证只来自环境变量, 明文 key
不进配置与日志) 不变.

## 日期

2026-09-17

## 背景

2026-09-17 09:47 的日志 (`forge-20260917-090807-65945.log`, session
`20260917T092712-0448b813` turn_0005): 阿里云 dashscope 对 `qwen/glm-5.1` 回 429, 错误体
是 `insufficient_quota` ("You exceeded your current quota"), 没有 Retry-After 头. 重试环
按 ADR-0012 §2 走了"冷却这把 key, 换下一把", 而 `~/.forge/llm.json` 里 qwen 只有一个
`api_key_env`, 于是第二轮 `get_credential` 报"全部凭证均在冷却期内", 重试环把原始 429
上抛, 一轮跑了 21 步的工作停在 `model_error_blocking`. 同一 session 09:32 还有一次 403
`AllocationQuota.FreeTierOnly` ("Free quota exhausted"), 走认证失败分支, 结局相同.

顺着这条线看到的几件事:

1. **配额耗尽和限流在代码里是同一个错误.** 两者 HTTP 上长得一样 (多半都是 429), 区别
   只在错误体. 限流是"这一秒发得太多", 退避几秒就过去; 配额耗尽是"这个账号今天 / 这个月
   没有了", 要么充值, 要么换一个账号的 key. 现在两者都冷却 30 秒 (无 Retry-After 时的
   缺省), 30 秒后再选中这把 key 只是把同一个错误再报一遍; 给用户的提示也是同一句
   "触发限流: 请稍后重试", 对配额耗尽是误导.
2. **换 key 的次数被 `max_retries` 锁死.** ADR-0012 §2 让短等重试与换凭证都计入
   `max_retries` (默认 2), 一次调用最多三次尝试 —— 配了五把 key 也只轮到前三把, 而这条
   限制在配置界面上看不出来. 换 key 与"同一把 key 上再试一次"是两件事: 前者以池的大小
   为自然边界, 后者才需要一个人为的上限.
3. **全部 key 冷却时报的是认证失败.** `get_credential` 在"未配置", "全部冷却", "全部解析
   失败"三种情况下都抛 `ModelAuthError`, 用户看到的是"请检查 API Key 环境变量" —— 对
   后两种是错的.
4. **Retry-After 只认秒数.** RFC 9110 §10.2.3 允许 HTTP 日期, 那种写法现在被当成 None.
5. **冷却只在进程内.** ADR-0011 §7 / §12.1 把这一条写成了决策. 对秒级的限流冷却这没有
   问题; 对小时级的配额耗尽, 每次启动 forge 都会先拿那把没额度的 key 撞一次.

同时要说清一件事: 这次日志里两个错误都是**账号级**的配额耗尽. 同一个阿里云账号下再开一把
key 共享同一份配额, 换了照样 429; 只有来自不同账号的 key 才有意义. 本文改的是"有第二个
账号时能不能自动用上", 不是"没有第二个账号时能不能变出额度来".

## 决策

### 1. 配额耗尽是一种自己的错误: `ModelQuotaExhaustedError`

继承 `ModelRateLimitError`. 继承而不是并列: 上层"这是不是一个该换凭证的错误"的判断
(`isinstance(exc, ModelRateLimitError)`) 不变, 变的只有冷却多久与给用户的提示.

adapter 从错误体认它 (`_QUOTA_EXHAUSTED_MARKERS`, 与 `_CONTEXT_OVERFLOW_MARKERS` 同一种
做法: 措辞表, 因为 OpenAI 兼容协议没有约定错误码):

| 状态码 | 判据 | 结果 |
|---|---|---|
| 402 | 无条件 | 配额耗尽 (DeepSeek 的 "Insufficient Balance") |
| 403 / 429 | 错误体命中措辞表 | 配额耗尽 (阿里云 `insufficient_quota` / `AllocationQuota.*` / `Arrearage`, OpenAI `insufficient_quota`, 智谱 "欠费" / "余额不足") |
| 403 / 429 | 未命中 | 照旧: 认证失败 / 限流 |

措辞表刻意不收单独的 "quota": 有些供应商的**限流**消息也带这个词 ("quota per minute"),
归成配额耗尽会让一把好 key 被冷却一小时.

### 2. 配额耗尽的冷却是小时级, 由 `[llm.retry].quota_cooldown_seconds` 定

默认 3600. 与 `wait_threshold_seconds` 同一段配置, 同样经 `RetrySettings` ->
`ProviderRuntimeSettings` 现读, 所有 provider 共用, `/config` 网关页与 Web 设置页各加一行.

凭证池加 `mark_exhausted(ref, cooldown)`, 与 `mark_failed` 分开: 后者的冷却由 Retry-After
或 30 秒缺省定, 只在进程内; 前者的冷却由配置定, 并落盘 (决策 5).

### 3. 换凭证以凭证池为界; `max_retries` 只约束同一把凭证上的重试

重试环 (`CredentialRetryLoop.run`) 从 `for _ in range(max_retries + 1)` 改成两条互不相干
的界:

- **换凭证**: 每把 key 在一次调用里至多被冷却一次. 环自己记一张"本次调用冷却过的 key"
  的表 —— 池按冷却截止时刻选 key, 而截止时刻可能在试别的 key 的这几秒里过去
  (`Retry-After: 0` 甚至立刻过去), 只靠池会把同一把 key 再选一次, 环就没有界了.
  全部冷却过 (池抛"全部冷却") 就把最后那个 provider 错误上抛.
- **同凭证重试**: 429 短等与超时 / 连接失败共用一份 `max_retries` 预算. 换 key 对这两类
  没有帮助 —— 超时是服务的事, 不是 key 的事.

`RetryCounts` 三个计数不变, `raw_metadata` 的重试摘要不变.

### 4. 池在"无可用凭证"时按原因抛不同的错误

| 原因 | 错误 | 提示 |
|---|---|---|
| 未配置 / 全部解析失败 | `ModelAuthError` | 检查环境变量 |
| 全部在冷却期 | `ModelRateLimitError`, `retry_after` = 最短剩余秒数 | 建议 N 秒后重试 |
| 全部在冷却期且全是配额耗尽 | `ModelQuotaExhaustedError` | 充值, 或在 `credential_refs` 配另一个账号的 key |

重试环取凭证那一步的 `except` 从 `ModelAuthError` 放宽到 `ModelGatewayError`: 本次调用
里已经有 provider 错误的, 仍然上抛那一个; 没有的 (第一轮就取不到 key) 原样上抛池的错误.

### 5. 配额耗尽的冷却落盘

`~/.forge/state/credential_cooldowns.json`, 内容是 `环境变量名 -> 墙钟截止 (epoch 秒)`.
环境变量名本来就写在 `llm.json` 里, 这里没有多暴露任何东西; 明文 key 从不经过这个类.

- 池启动时读一次, 按"还剩多少秒"换算成自己的单调钟; 过期的条目丢掉.
- `mark_exhausted` 写, `mark_succeeded` 清. 每次写先重读再合并: 同一台机器上可能有几个
  forge 进程, 各自只该改自己知道的那一条.
- 读坏了 (JSON 语法错, 权限问题) 当作空表并记一条警告, 不让一次模型调用因为一份状态
  文件失败: 最坏的结果只是多撞一次配额耗尽的 key, 而那正是没有这个文件时的行为.
- 秒级的限流 / 认证失败冷却**不**落盘: 它们活不过一次进程启动的时间.

ADR-0011 §12.1 "熔断状态只存在于进程内运行时"不变: 熔断是 provider/model 级的服务
可用性, 与这里的凭证级配额状态正交.

### 6. Retry-After 两种写法都认

秒数, 或 HTTP 日期 (`email.utils.parsedate_to_datetime`). 日期折成"距现在多少秒", 过去的
时刻算 0 而不是负数: 负的等待时长传到重试环里会被当成"不必等"直接放过阈值判断, 而
供应商的本意是"现在就可以了".

### 7. `credential_refs` 进 /config 供应商菜单

`ProviderConfig.credential_refs` 带上菜单标签 ("API Key 环境变量池 (逗号分隔)"), 位置紧跟
`api_key_env`. TUI 与 Web 的供应商表单都从 `PROVIDER_FIELDS` 派生 (ADR-0040 决策 4.2),
所以两端各自动多一行, 不另写.

- 菜单字段类型多一种: `tuple[str, ...]` 折成 `list`, 表单里是逗号分隔的一行文本,
  `coerce_provider_field` 拆开, 各项去空白, 空项丢掉 ("A, B," 是手误不是第三个空名字).
- 留空即清除: 写路径把键从文件里删掉 (`drop_provider_field`), 不把 `[]` 固化进去 ——
  与模型字段"默认值不回写"同一条. 清除后回落到 `api_key_env` 派生的单条.
- 语义不变: 设了池就**只**用池, `api_key_env` 不再自动算进去; 要它也在池里就把它写进
  列表, 位置由用户定. 字段注释与 ADR-0011 §16 写明这一点.
- 可用性 ("已就绪 / 缺少 XXX") 改按池判: `EnvProviderAvailability` 从
  `LlmConfigProviderSettingsSource` 取网关真正会用的那几个环境变量名, 任一设了就算就绪;
  "缺少"后面列全池. 原先按注册表的默认名判, 配了池的供应商会被显示成"缺少 QWEN_API_KEY"
  哪怕它能正常调用. TUI 与 Web 三处各自算 "就绪" 的地方收成一个 `providerReady`.
- `settings_for` 改成先读配置再查注册表: 用户自建的供应商是读配置那一刻登记的, 原先的
  顺序在本进程第一次读配置之前会把它判成"未知".

## 备选方案

- **不分配额耗尽, 只把无 Retry-After 时的缺省冷却调长.** 限流也会没有 Retry-After
  (这次的阿里云就没有), 调长会让一把只是被瞬时限流的 key 闲置一小时. 否决.
- **`ModelQuotaExhaustedError` 与 `ModelRateLimitError` 并列而不是继承.** 要改所有
  `isinstance(exc, ModelRateLimitError)` 的地方, 而它们关心的正是"该不该换凭证", 对
  两者答案相同. 否决.
- **换凭证的上限 = `max(max_retries + 1, len(credential_refs))`.** 仍然把两件事揉在一个
  数字里, 只是把揉法改得不那么显眼. 否决.
- **冷却状态全部落盘, 包括秒级的.** 一次进程启动的时间就够它过期, 落了也读不到. 否决.
- **`credential_refs` 在菜单里用多行 / 逐项添加的控件, 而不是逗号分隔的一行.** 菜单
  框架 (`_menu` / `DraftForm`) 只有单行文本与下拉两种控件, 为一个字段加第三种控件不值;
  环境变量名里不会有逗号. 否决.
- **可用性 = 池里的环境变量全都设了.** 池的用途正是"设了哪个用哪个", 全设才算就绪会让
  只配了一把的用户看到"缺少", 而那把能用. 否决.

## 影响

- **用户可见**: 配额耗尽时提示从"触发限流: 请稍后重试"变成"配额已用尽: 请充值, 或在
  credential_refs 里配置另一个账号的 API Key"; 全部 key 冷却时提示带剩余秒数, 不再说
  "检查环境变量". 配了多把 key 的, 一次调用能把它们全试完.
- **配置**: `[llm.retry]` 多一个 `quota_cooldown_seconds` (默认 3600). 旧配置文件不用改.
  供应商菜单多一行 `credential_refs`; 已手写了这个字段的配置原样读出.
- **状态文件**: 多一个 `~/.forge/state/credential_cooldowns.json`, 只在有 key 被判配额
  耗尽时出现.
- **日志**: 多一个事件 `llm.quota_exhausted` (带 `cooldown_seconds` 与凭证指纹).
- **不变**: 绝不切换 provider/model; 凭证只来自环境变量; 明文 key 不进配置, 日志, 状态
  文件; adapter 不枚举或切换 key.

## 验收标准

- 429 / 403 错误体命中措辞表, 或 402, 抛 `ModelQuotaExhaustedError`; 未命中的 429 / 403
  仍是限流 / 认证失败.
- `max_retries = 0` 且配三把 key, 前两把 429 (无 Retry-After), 第三把成功: 三把都被试到.
- 单 key 永远回 `Retry-After: 0`: 环在 `1 + max_retries` 次后终止.
- 超时: 同一把 key 试 `1 + max_retries` 次, 不换 key.
- 配额耗尽后同进程内该 key 不再被选; 新进程从状态文件读回, 同样不选; `mark_succeeded`
  清掉文件里的条目; 状态文件是坏 JSON 时当空表.
- 全部冷却: `ModelRateLimitError` 带最短剩余秒数; 全部配额耗尽: `ModelQuotaExhaustedError`.
- Retry-After 为过去的 HTTP 日期 -> 0; 未来的 -> 剩余秒数; 垃圾 -> None.
- 菜单: `PROVIDER_FIELDS` 里 `credential_refs` 紧跟 `api_key_env`, kind 为 list;
  " A , B, " 写成 `["A", "B"]`; 留空把键删掉并回落 `api_key_env`; str 字段留空仍拒绝.
- 可用性: 配了池 `[A, B]` 而只设了 `QWEN_API_KEY` -> 不可用, "缺少 A / B"; 设了 B ->
  可用; 未知供应商 -> 空池.
