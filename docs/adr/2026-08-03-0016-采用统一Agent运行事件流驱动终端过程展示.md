# ADR-0016：采用统一 Agent 运行事件流驱动终端过程展示

## 状态

Proposed

## 日期

2026-08-03

## 背景

ForgeCLI 已通过 `AgentTurnService`、`BuiltinAgentLoop`、`LlmGateway`、
`ToolRequestCoordinator` 和 `ToolRuntime` 形成受控 ReAct 闭环：一次用户输入可以触发多次
模型调用，模型可以请求一个或多个工具，工具结果经安全裁决和执行后作为 observation 回填，
直到模型产出最终回答。

当前终端只消费 LLM 的文本增量。运行期间即使已经发生模型请求、工具排队、安全裁决、审批、
工具执行和再次思考，用户通常只能看到笼统的“处理中”。现有 `LoopEvent` 也只覆盖循环的粗粒度
生命周期，尚不能表达整个 turn 内的模型流、工具流、安全流和终端状态；如果继续直接扩展
`StreamingTranscript.feed(str)`，CLI 将逐渐依赖 AgentLoop、Provider 和工具运行时的内部结构，
并出现以下问题：

- 同一 turn 的多次模型调用共享一个文本缓冲区，中间说明与最终回答难以分界。
- 工具名称、参数摘要、等待审批、执行状态、耗时和失败原因无法进入统一时间线。
- thinking 配置只表示模型是否启用推理能力，不等于供应商会返回可展示的思考内容。
- 原始 chain-of-thought、凭证、系统提示词或未脱敏工具输出可能被误送到终端或事件日志。
- Rich `Live`、审批输入和普通 `console.print` 可能成为多个终端写入者，导致覆盖、重复或错位。
- 将流式 delta 直接持久化会显著放大事件日志，并混淆“运行时展示”与“恢复审计事实”。

ADR-0010 已决定 hooks 可以影响控制流、events 只做观察；ADR-0011 已决定 gateway 输出统一
stream chunk，且 `AgentTurnService` 是会话事件和 usage 的写入边界。本 ADR 在这两个边界上补充
“整个 Agent turn 如何形成可展示、可测试且安全的运行时间线”。

## 决策

ForgeCLI 采用统一 `AgentRunEvent` 运行事件流驱动终端过程展示，并作出以下决策：

1. 将 ADR-0010 §7.2 的观察事件范围从 `AgentLoop` 扩展到整个 Agent turn。现有
   `LoopEventBus` 演进为 `AgentRunEventBus`，生产装配不保留两套并行事件总线。
2. `AgentRunEvent` 是进程内、只读、按 turn 排序的运行通知，不改变控制流，也不替代
   `events.jsonl + state.json` 持久化真相源。
3. AgentLoop、模型流、工具协调器、安全裁决和审批只发布语义化事件；CLI 只订阅事件，
   不读取 Provider 私有响应、ToolPlan 或 AgentLoop 内存状态。
4. `TerminalRunRenderer` 是一次 turn 内唯一的终端输出协调者。Rich `Live` 只显示当前活动状态，
   已完成内容采用 append-only 方式提交到终端滚动历史。
5. 每次模型调用以 `request_id` 独立分组。中间模型输出、工具调用和最终回答不得再拼进同一个
   无边界字符串缓冲区。
6. thinking 默认只展示状态和安全摘要：优先使用供应商明确声明为用户可见的 reasoning summary，
   否则使用 ForgeCLI 自己生成的 `LoopDecision.reason_summary`；不得展示、推导或持久化 raw
   chain-of-thought。
7. 工具默认展示名称、安全参数摘要、目标、状态、耗时、结果计数和错误摘要，不直接展开完整文件
   内容、stdout/stderr 或任意 Provider/MCP 原始响应。
8. HITL 确认采用固定, 面向动作的视图, 依次呈现: 当前模式与完整工作区目录列表, 待执行的原始命令,
   完整脚本内容 (执行脚本时), 目标集合, 最后是选择方式. 计划 hash, 目标集合 hash, 风险标签,
   执行画像和批准失效字段继续参与内部授权绑定与审计, 但不进入默认人类确认界面; 原始命令与
   脚本内容必须逐字完整展示, 不得由 hash, 条目数或摘要替代.
9. 目标集合**按后果显示**: 纯读取的调用不列 (命令与脚本已经逐字看过, 再列一遍读了哪些文件
   只是噪音); 只要存在写, 删除, 移动, 网络或外部副作用目标, 或目标集合未封闭, 就必须列全,
   不得截断. 这一档由 `HitlApprovalView.consequential` 判定.
10. HITL 的 `always` 只创建工作区范围的学习规则, 映射为 `ApprovalScope.WORKSPACE`;
    `ApprovalScope.ALWAYS` 与 `ApprovalScope.SESSION` 不由默认确认界面产出. 选项顺序为
    `once -> always -> deny`, `once` 是默认项.
11. MVP 保持工具串行执行。未来并行工具仍使用同一事件协议，通过 `parent_event_id` 和 `lane_id`
    表达并发关系，不允许多个工具直接并发写终端。
12. 同一 chunk 多 tool call delta 丢失与工具审计 `turn_id` 未绑定是两处既有正确性缺陷,
    先行独立修复, 不纳入本 ADR 的迁移阶段; 本 ADR 只把修复结果当作前提.

## 备选方案

- 继续扩展 `StreamingTranscript`，在字符串回调中识别工具和思考状态：改动最少，但字符串没有
  request、step、tool call 和安全语义，最终会让 CLI 反向理解 application 内部状态。
- 让 CLI 分别订阅 `LlmGateway`、`ToolRuntime`、审批服务和安全审计：能够获得更多数据，但无法
  形成单调有序的 turn 时间线，也会让 interfaces 层依赖多个内部组件。
- 所有运行事件先写入 `events.jsonl`，终端再 tail 事件文件：天然可重放，但流式 delta 会放大日志，
  写盘延迟影响交互，且把短暂 UI 状态错误地提升为恢复事实。
- 使用全屏 TUI 展示固定面板：信息密度高，但破坏终端原生 scrollback、管道友好性和简单审批流程，
  对 MVP 成本过高。
- 原样透传 Provider 的 reasoning、tool delta 和 raw metadata：实现直接，但供应商协议不统一，
  可能暴露私有推理、凭证、系统提示词和恶意 ANSI 控制序列。

## 影响

- application 层新增统一的运行事件词汇、事件总线和安全展示 payload。
- `BuiltinAgentLoop` 的 `on_delta: Callable[[str], None]` 将被结构化流事件替代。
- `ToolRequestCoordinator` 需要独立的运行观察端口；该端口与持久化 `ToolAuditSink` 分离，
  避免把 UI 展示当作安全审计。
- CLI 将以 `TerminalRunRenderer` 替代只处理回答文本的 `StreamingTranscript`。
- `ApprovalPresentation` 继续保存授权重验需要的完整事实，但新增独立的 `HitlApprovalView` 作为
  人类确认 DTO，避免 renderer 直接打印内部计划、hash 和风险分类字段; 原始命令, 脚本内容和
  完整目标集合仍进入该 DTO, 不因 "简化确认界面" 被裁掉.
- 本 ADR 依赖两处先行独立修复的既有缺陷: 供应商流式 chunk 的多 tool call delta 归一化,
  以及工具审计 sink 的 `turn_id` 绑定. 二者是执行与审计正确性问题, 不属于终端展示范围,
  修复后本 ADR 才能得到可信的工具事件序列.
- Provider adapter 需要区分普通文本、用户可见 reasoning summary、tool call delta、usage 和收尾块；
  不支持 reasoning summary 的 Provider 保持能力缺失，不做猜测或伪造。
- 终端输出更透明，但事件与 renderer 的测试矩阵增加，需要覆盖多模型调用、工具、审批、取消、
  错误、长输出、窄终端和非 TTY 降级。
- 现有会话存储格式无需因流式展示而迁移；只在后续决定持久化新的安全摘要事件时增加事件类型。

## 设计细节

## 1. 目标与非目标

### 1.1 目标

- 在终端连续展示一轮 Agent 的模型调用、可展示思考摘要、工具调用、安全裁决、审批和最终回答。
- 保证同一 turn 内事件全序、跨模型调用和工具调用可关联。
- 保持 CLI、AgentLoop、LLM gateway、工具、安全与会话存储之间的分层边界。
- 保持终端原生 scrollback，长回答不会因为 `Live` 高度限制被裁剪或反复重印。
- 让终端展示可通过确定性事件序列和 Rich record console 测试。
- 保证展示失败不影响 Agent 执行，展示配置不改变权限、工具目录或控制流。

### 1.2 非目标

- 不展示模型的 raw chain-of-thought。
- 不把终端事件流作为 session resume 的唯一恢复源。
- 不在本 ADR 中引入工具并行执行。
- 不在 MVP 中实时透传任意 shell stdout/stderr；首版只展示工具生命周期和受控结果摘要。
- 不建设全屏 TUI、Web 调试器或远程 tracing 服务。
- 不改变 ADR-0004、ADR-0013、ADR-0015 定义的授权、审批和恢复顺序。

## 2. 架构位置

统一链路如下：

```text
Provider Adapter
  -> ProviderStreamChunk
  -> LlmGateway / ModelStreamChunk
  -> BuiltinAgentLoop
       -> AgentRunEventBus
       -> AgentTurnService
            -> ToolRequestCoordinator
                 -> policy / approval / recovery / ToolRuntime
                 -> AgentRunEventBus
            -> SessionService（只写持久化事实）
       -> TerminalRunRenderer（只读 subscriber）
       -> TraceSubscriber（可选，只读 subscriber）
```

模块建议：

```text
src/forgecli/domain/agent/run_events.py
  AgentRunEventKind
  AgentRunEvent
  各类安全 payload 值对象

src/forgecli/application/agent_run/events.py
  AgentRunEventSubscriber
  AgentRunEventBus
  AgentRunContext / sequencer

src/forgecli/interfaces/cli/run_renderer.py
  TerminalRunRenderer
  DisplayDensity
```

约束：

- domain 事件不 import Rich、prompt_toolkit、Provider SDK、filesystem 或 shell。
- application 事件总线不写终端、不写会话文件，也不返回控制信号。
- Provider adapter 只做协议归一化，不直接发布终端事件。
- CLI subscriber 只消费安全 payload，不重新读取原始请求或工具结果补全显示。
- 权限审批仍由 `ApprovalService` 控制；renderer 只能展示和协调终端占用，不能批准或拒绝请求。

## 3. 统一事件信封

每个事件使用统一信封：

```text
AgentRunEvent
  event_id
  kind
  turn_id
  sequence
  occurred_at
  step_index?
  request_id?
  tool_call_id?
  invocation_id?
  parent_event_id?
  lane_id?
  payload
```

规则：

- `event_id` 在进程内唯一，便于测试、trace 和父子关联。
- `sequence` 在单个 turn 内从 1 单调递增，由 `AgentRunEventBus` 统一分配，发布者不得自填。
- `occurred_at` 使用单调时钟计算耗时；面向用户的绝对时间仅在 debug 模式按需展示。
- 模型事件必须带 `request_id`；工具意图必须带 `tool_call_id`；真实执行事件必须带
  `invocation_id`。
- payload 使用冻结、封闭的值对象联合，不使用任意 `dict[str, object]` 作为长期公共契约。
- `parent_event_id` 表达模型调用产生工具、工具产生审批等因果关系；MVP 串行执行时可以为空。
- `lane_id` 为未来并行工具预留，MVP 固定为 `main`，不改变事件顺序语义。

事件总线同步发布，以保持当前单线程 REPL 的确定顺序。subscriber 按注册顺序执行；subscriber
抛出的异常必须隔离记录，不能向 Agent 主循环传播。renderer 应保持轻量，耗时操作不得放在
`on_event` 中。

## 4. 事件词汇

### 4.1 Turn 与步骤

| 事件 | 必要摘要 | 终端语义 |
| --- | --- | --- |
| `TURN_STARTED` | mode、工具数量 | 建立本轮显示状态 |
| `STEP_STARTED` | step index、phase | 切换“思考/工具/回答”等当前状态 |
| `DECISION_SUMMARY` | 安全 reason summary | 展示 ForgeCLI 可审计决策摘要 |
| `TURN_COMPLETED` | 状态、总耗时、调用计数 | 提交本轮汇总 |
| `TURN_CANCELLED` | partial、阶段 | 标记取消并保留已提交内容 |
| `TURN_FAILED` | 错误类别、可行动提示 | 提交失败说明 |

### 4.2 模型调用

| 事件 | 必要摘要 | 终端语义 |
| --- | --- | --- |
| `MODEL_STARTED` | request id、序号、provider/model | 显示正在调用模型 |
| `MODEL_OUTPUT_DELTA` | sequence、visible text | 逐步提交模型可见输出 |
| `MODEL_REASONING_STATUS` | started/completed/unavailable | 显示“正在思考”等状态 |
| `MODEL_REASONING_SUMMARY_DELTA` | user-visible summary | 展示供应商明确返回的安全摘要 |
| `MODEL_COMPLETED` | finish reason、耗时、tool count | 关闭当前模型调用块 |
| `MODEL_USAGE` | input/output/reasoning/cached | normal 汇总或 debug 详情 |
| `MODEL_FAILED` | 归一化错误、retryable | 展示安全错误提示 |

### 4.3 工具、安全与审批

| 事件 | 必要摘要 | 终端语义 |
| --- | --- | --- |
| `TOOL_QUEUED` | tool name、参数摘要、队列位置 | 展示模型请求的工具 |
| `TOOL_PREPARED` | 目标/能力摘要 | debug 展示已归一化计划 |
| `POLICY_RESOLVED` | allow/ask/deny、reason | 展示安全裁决 |
| `APPROVAL_REQUESTED` | 动作、风险、目标数 | 暂停 Live 并进入审批界面 |
| `APPROVAL_RESOLVED` | approved/denied/pending | 恢复运行时间线 |
| `TOOL_STARTED` | invocation id、tool name | 显示正在执行 |
| `TOOL_PROGRESS` | 受控进度摘要 | 后续可选，不透传任意 stdout |
| `TOOL_COMPLETED` | status、耗时、结果摘要 | 提交成功或失败结果 |
| `TOOL_CANCELLED` | 阶段、是否已产生副作用 | 标记取消或未知结果 |

`POLICY_RESOLVED` 是运行展示，不替代持久化 `policy_decision`；`TOOL_STARTED` 也不替代
ADR-0004 要求的写前 `tool_requested` 审计。安全审计写入失败的处理仍按安全 ADR 决定，不能因为
终端已经显示“开始”就认为写前审计已经落盘。

## 5. 模型流与多次调用边界

当前字符串回调升级为带通道的流式结构：

```text
ProviderStreamChunk
  output_text_delta?
  reasoning_summary_delta?
  tool_call_deltas[]
  usage?
  finish_reason?

ModelStreamChunk
  request_id
  sequence
  provider
  model
  output_text_delta?
  reasoning_summary_delta?
  tool_call_deltas[]
  usage_delta?
  finish_reason?
  interrupted
```

规则：

- 一个供应商 chunk 可以携带多个 tool call delta，不能只保留列表中的第一项。这一条是**前置缺陷
  修复**, 不由本 ADR 的迁移阶段承担: 只保留首项会让并行工具调用整体消失, 模型随后收到残缺的
  结果集, 属于执行正确性问题而非展示问题. 本 ADR 假定 `tool_call_deltas[]` 已是列表.
- tool call 参数在累积为完整合法 JSON 前不发布 `TOOL_QUEUED`，更不能执行或展示半截参数。
- 每次模型调用有独立 accumulator 和独立 renderer block；request 结束时必须明确收尾。
- 模型在请求工具之前产生的普通可见文本作为该 request 的中间输出显示，不能与后续最终模型调用
  的文本拼成一个持久化 assistant message。
- `AgentTurnService` 仍只把最终 `AnswerAction` 保存为本轮 assistant message；运行展示不能改变
  conversation transcript。
- 流式中断时提交已收到的可见文本，并发布 `MODEL_FAILED` 或 `TURN_CANCELLED`，不得把半截
  tool call 当成可重试执行请求。

## 6. Thinking 与推理内容边界

`thinking=on`、`reasoning_effort` 和 `reasoning_tokens` 分别表示启用配置、强度配置和用量计数，
都不能证明 Provider 返回了可展示的思考内容。

ForgeCLI 将三类内容严格区分：

```text
MODEL_REASONING_STATUS
  ForgeCLI 自己知道的运行状态，例如 started / completed / unavailable

MODEL_REASONING_SUMMARY_DELTA
  Provider 明确标记为 user-visible reasoning summary 的文本

DECISION_SUMMARY
  ForgeCLI 根据结构化 LoopDecision 生成的可审计行动摘要
```

约束：

- Provider 未提供 reasoning summary 时只显示“正在思考”，不从回答、token 数或工具请求推导思维链。
- adapter 对供应商私有字段采用显式 allowlist；只有语义被供应商定义为用户可见 summary 的字段
  才能映射为 `reasoning_summary_delta`。
- raw reasoning、hidden thoughts、encrypted reasoning、签名推理块和 Provider 私有内部 trace 一律不
  映射到运行事件。
- reasoning summary 默认只存在于进程内终端事件；不写 session transcript，不进入下一轮模型上下文。
- `DECISION_SUMMARY` 可以按 ADR-0010 的安全摘要规则进入审计，但必须与 Provider reasoning 分开命名。
- `debug` 模式可以显示 reasoning token 数，不能显示被禁止的 reasoning 内容。

## 7. 工具展示与输出治理

### 7.1 安全参数摘要

`TOOL_QUEUED` 不携带任意原始 arguments。每个 ToolSpec 或工具类别应提供安全展示策略，将参数转换为：

```text
ToolDisplaySummary
  title
  target_labels[]
  operation
  item_count?
  redacted_arguments[]
  risk_hint?
```

无法证明安全的字段显示为 `[redacted]`。shell 命令、URL、文件路径和搜索表达式可以在策略允许时显示，
但必须执行长度限制、控制字符剥离和 Rich literal escaping。凭证、Authorization header、环境变量值、
系统提示词和 Provider 私有选项不得进入摘要。

### 7.2 工具结果

默认 `TOOL_COMPLETED` 只展示：

- 成功、失败、拒绝、待审批、取消或结果未知。
- 耗时、退出码、匹配数、读取行数、写入文件数、输出字节数等机制摘要。
- 截断状态和 artifact id；不自动读取 artifact 内容回显。
- 经过归一化且长度受限的错误说明。

MVP 不实时显示任意 shell stdout/stderr。后续若实现 `TOOL_PROGRESS`，必须先经过
`ResourceGovernor`、输出字节上限、ANSI/OSC 控制序列过滤和 artifact 溢写；工具子进程不能直接
继承 ForgeCLI 的终端 stdout/stderr。

## 8. 终端渲染模型

### 8.1 单一写入者

`TerminalRunRenderer` 拥有 turn 期间的 Rich `Live` 和所有运行事件的输出协调权：

- 当前尚未完成的状态只在一个短 Live 区显示，例如“正在思考”或“正在执行 search.text”。
- 完成的模型文本、工具和结果通过 `console.print` 提交到 Live 上方，进入原生 scrollback。
- Live 退出前必须提交剩余半行并清空 transient 区，不能出现正文重复。
- 审批开始时 renderer 暂停或清空 Live，由 `ApprovalService` 接管输入；审批结束后再恢复运行状态。
- 其他组件不得在 turn 期间直接写运行进度。普通 slash command 在 turn 外仍可使用 `RichOutput`。

### 8.2 展示密度

展示密度是 UI 配置，不属于 session mode，也不影响工具目录、权限或 Agent 决策：

| 密度 | 默认展示 |
| --- | --- |
| `compact` | 工具名称与终态、审批、错误、最终回答 |
| `normal` | 加上安全思考/决策摘要、中间模型输出、目标摘要、耗时和 turn 汇总 |
| `debug` | 加上安全 request/invocation id、provider/model、policy reason、hash 和 usage |

默认使用 `normal`。配置可以由后续 `/display compact|normal|debug` 或等价应用级设置控制，
但三种密度共享相同的 redaction、字符上限和控制序列过滤。

### 8.3 推荐终端形态

```text
› 分析登录失败，并找出相关代码
│ 思考 先定位认证入口与错误处理，再读取相关文件
│ 说明 我先搜索认证相关符号。
├─ 调用 search.text  query="login|auth" · path="src"
│  └─ 完成 12 处匹配 · 84 ms
├─ 调用 fs.read_file  src/auth/service.py
│  └─ 完成 读取 186 行 · 输出不直接展开
│ 思考 错误分支吞掉了刷新异常；继续核对调用方
● 根因在 AuthService.refresh()：刷新异常被统一转换为“登录失败”……
└─ 完成 2 次模型调用 · 2 次工具调用 · 1.8 s
```

颜色只能增强含义，不能作为唯一状态编码；成功、失败、拒绝和等待必须同时有文字或符号。窄终端下
参数摘要换行到正文列，不横向滚动，不使用固定全屏高度。

### 8.4 HITL 人类确认界面

HITL 是用户决定是否授权 Forge 执行动作的交互面，不是内部安全分析报告。确认界面使用固定信息层级，
不受 `compact`、`normal`、`debug` 展示密度影响：

1. 第一行显示当前 mode 和本次调用可见的完整 workspace root 列表。
2. 第二行使用“是否允许 Forge 执行：”展示原始命令；不能用工具名或计划摘要替代原始命令。
3. 如果命令执行脚本，换行显示“脚本内容：”和安全分析实际绑定的完整脚本内容。
4. 如果本次操作除读取外还有后果 (写, 删除, 移动, 网络, 外部副作用), 或目标集合未封闭,
   显示目标集合: 先给一行各类别计数 (含为零的类别), 再按类别逐条列全. **纯读取的调用跳过
   这一节** —— 命令与脚本已经逐字看过了, 再列一遍它会读哪些文件只是噪音, 反而把真正要读的
   两行淹掉.
5. 最后列出选择键, 英文 scope 和中文含义, 顺序 `once -> always -> deny`, `once` 为默认选项.

普通命令 (纯读取) 的标准形态:

```text
模式 accept_edits · 工作区 /workspace/forge, /workspace/shared

? 是否允许 Forge 执行：poetry run pytest tests/agent_loop -q

[1] once   仅允许本次执行（默认）
[2] always 本工作区内以后遇到相同命令直接允许
[3] deny   拒绝执行

请选择 [1/2/3]：
```

脚本命令的标准形态:

```text
模式 accept_edits · 工作区 /workspace/forge, /workspace/shared

? 是否允许 Forge 执行：python3 scripts/migrate_config.py --dry-run

脚本内容：

    from pathlib import Path

    config = Path("forge.toml")
    updated = config.read_text().replace("mode = 'edit'", "mode = 'accept_edits'")
    print(updated)

[1] once   仅允许本次执行（默认）
[2] always 本工作区内以后遇到相同脚本直接允许
[3] deny   拒绝执行

请选择 [1/2/3]：
```

有破坏性后果时, 目标集合必须出现且列全:

```text
? 是否允许 Forge 执行：rm -f logs/*.log

目标 读取 0 · 写入 0 · 删除 300 · 移动 0 · 网络 0 · 外部副作用 0
删除 (300 项):
  /workspace/forge/logs/app-0.log
  ...
```

目标解析不封闭时, 计数行改为保守上界并显式标注原因与恢复策略:

```text
目标 读 1 · 写 >=1 (上界 /workspace/forge/**) · 删除 0 · 移动 0 · 网络 0 · 外部副作用 0
未封闭原因: 写入路径由运行时变量决定, 无法静态展开
执行前将建立 FULL checkpoint
```

确认 DTO 使用独立的最小结构：

```text
HitlApprovalView
  mode
  workspace_roots[]
  raw_command
  script_content?
  target_groups[]        # (类别, 完整目标列表), 类别取读/写/删除/移动/网络/外部副作用
  target_resolution      # STATIC / FORGE_EXPANDED / DYNAMIC / UNKNOWN
  unresolved_reason?     # 仅 DYNAMIC / UNKNOWN 时出现
  recovery_strategy?     # 目标不封闭时说明将建立的 checkpoint 策略
  allowed_scopes[]
  default_scope = deny
```

显示规则：

- `workspace_roots` 必须完整显示；窄终端可以换行缩进，但不能只显示数量或省略中间目录。
- `raw_command` 必须按实际待执行命令逐字展示，并过滤 ANSI/OSC 控制序列；不能显示经过 shell escaping
  后含义不同的替代字符串。
- `script_content` 使用安全分析和授权绑定的同一份内容快照。inline `-c`、heredoc、临时脚本和脚本
  文件都先解析为该快照再显示，不能只显示脚本路径。
- 脚本较长时可以进入 pager，但必须能查看完整内容；不得只显示前若干行后要求用户授权完整脚本。
- 一旦决定展示, `target_groups` 必须逐条列全, 不得截断, 不得用 "还有 N 个文件" 或
  `target_set_hash` 替代. 目标很多时可以进入 pager 或引用不可变清单产物, 但界面必须同时给出真实
  条目数和查看完整清单的入口. 用户批准的是这份效果清单, 不是命令字符串本身 -- `rm *.log` 展开成
  3 个还是 300 个文件必须可见.
- `target_resolution` 为 `DYNAMIC` 或 `UNKNOWN` 时按 ADR-0013 §6.2 显示完整保守上界, 未知原因和
  将要建立的 `FULL` checkpoint; 缺失清单不能当作普通审批直接放行.
- 选项按 `once -> always -> deny` 排列, `[1] once` 为默认, 默认标记写在选项文案里
  (`仅允许本次执行（默认）`), 提示行只写 `请选择 [1/2/3]：`.
- **只有真正的空输入 (用户看着界面按回车) 才取默认项.** EOF (管道读到头) 与任何无法识别的输入
  一律解析为 deny: 前者说明根本没有人在回答, 后者说明用户想说的不是这三个里的任何一个, 把它们
  当成"他按了回车所以是同意"就是凭空造出一次授权. 非交互环境仍然保持 PENDING.
- `[2] always` 只创建**工作区范围**的受限学习规则, 映射为 `ApprovalScope.WORKSPACE`; 界面文案必须
  写出 "本工作区内", 不得让用户以为批准范围是全局. 措辞随内容变: 执行脚本时写"相同脚本",
  普通命令时写"相同命令" —— 两者绑定的事实不同. `ApprovalScope.ALWAYS` 与
  `ApprovalScope.SESSION` 不由默认 HITL 产出, 需要它们时走专门的规则管理界面.
- `[1] once` 只批准当前请求, 映射为 `ApprovalScope.ONCE`.
- `always` 只在 ADR-0013 允许创建受限学习规则时出现. Mandatory Ask, Hard Deny, 受保护路径和其他
  禁止学习授权的场景不提供 `always`, 界面只显示 `once` 与 `deny`.
- “相同命令/脚本”的内部判断继续绑定命令 AST、executable identity、脚本内容、工作区、模式、
  路径范围、网络目标和执行环境等事实；这些字段用于授权校验、失效和审计，不进入 HITL 默认视图。

本节修订 ADR-0013 §14 的默认终端呈现要求: `target_set_hash`, `plan_hash`, 风险事实, 执行画像和
"哪些变化会使批准失效" 不再要求显示在确认提示中 -- 它们是内部绑定字段, 对人类决策没有帮助.

**目标集合的完整呈现要求不在此列, 保持不变.** §14 关于危险字段不得语义截断, 必须提供完整清单与
真实条目数, 目标集不封闭时必须显示保守上界与 `FULL` checkpoint 的约束继续适用; 本节只是把清单
改成按类别分组的可读形式, 并取消同时打印 `target_set_hash` 的要求. ADR-0013 定义的内部完整
`ApprovalPresentation`, 批准后全量重验, Mandatory Ask, Hard Deny 和学习规则约束同样保持不变.

对 ADR-0013 §5.1 渐进式授权的收窄: 默认确认界面只产出 `ONCE` 与 `WORKSPACE` 两档. 这是有意的
取舍 -- 三键之外每多一档, 用户误选更大范围的概率就上升一分, 而 `SESSION` 与 `ALWAYS` 都可以在
专门的规则管理界面里显式选择.

## 9. 持久化、历史与审计

运行事件和会话事件是两个不同层次：

| 数据 | 运行事件流 | `events.jsonl` / state |
| --- | --- | --- |
| 当前 spinner / phase | 是 | 否 |
| 文本 delta | 是 | 否 |
| reasoning summary delta | 是，进程内 | 默认否 |
| 最终 assistant message | 完成时展示 | 是 |
| usage 汇总 | 展示 | 是，由 `AgentTurnService` 写入 |
| tool requested/completed | 展示摘要 | 是，按安全 ADR 写审计事实 |
| policy / approval / recovery | 展示摘要 | 是，按现有事件模型持久化 |

规则：

- session resume 从持久化事实恢复，不重放 spinner 和字符级 delta。
- 下一轮 conversation history 只包含规范化 user/assistant 消息及 AgentLoop 明确需要的结构化工具历史；
  不能因为终端展示了中间文本就自动加入长期 transcript。
- 同一真实工具调用的运行事件与审计事件共享 `turn_id`、`tool_call_id`、`invocation_id`，但使用不同
  event id；不得用终端事件冒充写前审计。
- 工具审计 sink 必须在每次 dispatch 前绑定当前 `turn_id`，不能依赖进程启动时的空值。这一条同样是
  **前置缺陷修复**: `turn_id` 悬空会让持久化的工具审计事件无法归属到具体轮次, 属于审计正确性
  问题而非展示问题. 本 ADR 假定运行事件与审计事件已经能通过同一 `turn_id` 对齐.
- 将来如需保存完整 trace，应增加独立、受配额和脱敏控制的 trace sink，不扩张 session 主日志。

## 10. 取消、错误与审批

### 10.1 取消

- 同一个 turn 的 `CancelToken` 必须同时传播给模型流和工具 dispatcher/runtime。
- 模型取消保留已提交可见文本，关闭当前 request block，发布 `TURN_CANCELLED`。
- 工具取消必须区分“执行前取消”“执行中已终止”“副作用结果未知”，不能统一显示为成功结束。
- 取消后 renderer 清空 Live、提交取消说明，再把终端控制权交还输入框。

### 10.2 错误

- Provider、解析、预算、安全、工具和 renderer 错误使用不同 kind，不依赖字符串匹配分类。
- 对用户显示归一化、可行动的安全错误；debug 可增加安全 id，不显示原始异常体中的秘密。
- renderer subscriber 失败被事件总线隔离；Agent turn 继续执行，最终至少由 REPL fallback 打印结果。

### 10.3 审批

- `APPROVAL_REQUESTED` 只负责结束当前活动状态并按 §8.4 展示 `HitlApprovalView`。
- 人类输入仍由 `ApprovalService` 获取，renderer 不返回 allow/deny 控制信号。
- 审批通过后的全量重验过程继续发布 policy/approval 事件；内部绑定事实变化时旧批准失效并重新进入
  HITL，但默认确认界面不打印 hash、风险标签或失效字段。
- mandatory ask、pending、denied 和 approved 必须使用不同文字，不能以颜色或空响应暗示批准。
- `ApprovalService` 将用户输入解析为 `deny`, `always` (= `ApprovalScope.WORKSPACE`) 或 `once`
  (= `ApprovalScope.ONCE`); 空输入和非法输入不得转成允许.

## 11. 迁移方案

### 阶段 0: 前置缺陷修复 (独立交付, 不属于本 ADR)

- 供应商流式 chunk 的 `tool_call_delta` 归一化为 `tool_call_deltas[]`, 覆盖同一 chunk 携带多个
  工具调用的情形.
- 工具审计 sink 在每次 dispatch 前绑定当前 `turn_id`, 消除进程启动时的空值.
- 两项各自带回归测试并先于阶段 1 合入. 本 ADR 的验收不重复覆盖它们的正确性, 只依赖其结果.

### 阶段 1：统一事件骨架

- 新增 `AgentRunEvent`、封闭 payload、sequencer、subscriber 和事件总线。
- 将现有 loop lifecycle kind 迁移到新总线，保留语义和测试。
- bootstrap 注册 `TerminalRunRenderer`，确认生产路径不再存在“创建总线但无 subscriber”。

### 阶段 2：模型流分通道

- 将 `on_delta(str)` 替换为结构化事件。
- 为每个 request 建独立 accumulator 和渲染边界。
- 接入 output、usage、finish、interrupt 和可选 reasoning summary (`tool_call_deltas[]` 已由阶段 0
  交付, 此处只消费).

### 阶段 3：工具、安全与审批

- 在 dispatcher/coordinator 注入运行观察端口。
- 发布 queued、prepared、policy、approval、started、completed 和 cancelled 事件。
- 绑定 turn/tool/invocation 三类关联 id (`turn_id` 的审计侧绑定已由阶段 0 交付, 此处只把同一 id
  接进运行事件), 并把当前 cancel token 传入工具执行链。
- 让审批与 renderer 明确交接 Live 所有权。

### 阶段 4：展示密度与治理

- 实现 compact/normal/debug。
- 增加 tool-specific display summary、统一 redaction、控制序列过滤和输出上限。
- 增加 turn 汇总、usage 展示和非流式 Provider fallback。
- 评估受控 `TOOL_PROGRESS`，MVP 验收不依赖实时 stdout。

迁移期间可以保留一个把 `MODEL_OUTPUT_DELTA` 适配到旧 `StreamingTranscript.feed` 的短期桥接器，
但生产组合根最终只能装配 `TerminalRunRenderer`，桥接器不得长期成为第二套显示协议。

## 12. 测试策略

### 12.1 事件契约

- sequence 在一个 turn 内严格递增，多个 request 和 tool call 关联 id 正确。
- subscriber 失败被隔离，其他 subscriber 与主循环继续运行。
- payload 构造拒绝 secret-like 字段、未限制文本和非法状态组合。
- 同一 Provider chunk 的多个 tool call delta 全部保留并正确累积 (该项的回归测试由阶段 0 提供,
  本层只断言事件序列按累积结果逐个发布 `TOOL_QUEUED`).

### 12.2 Agent 场景

- 单次模型调用直接回答。
- 模型输出中间说明后请求一个工具，再次调用模型给最终回答。
- 同一模型响应请求多个工具，按队列逐个展示和执行。
- policy deny、approval pending/denied/approved、批准后重验失效。
- Provider 超时、流式中断、tool error、预算耗尽、用户取消。
- 跨 turn 历史只保存最终 assistant message，不混入终端中间输出。

### 12.3 Renderer

- 使用 `Console(record=True)` 对 compact/normal/debug 做快照测试。
- 长多行回答只出现一次，最后半行正确提交，Live 退出无残留。
- 审批前后无重复 spinner、无输入提示覆盖。
- HITL 第一行完整展示 mode/workspace roots，第二行完整展示原始命令；脚本场景显示绑定内容快照。
- HITL 完整列出目标集合: 300 条写目标场景下全部条目可达 (可分页), 不出现截断或 "还有 N 个";
  `DYNAMIC` / `UNKNOWN` 时显示保守上界, 未知原因和 `FULL` checkpoint 说明.
- 纯读取的调用不出现目标一节; 一旦有写 / 删除 / 移动 / 网络 / 外部副作用或目标未封闭, 必须出现.
- 普通 ASK 按 once/always/deny 顺序展示且 once 标注为默认; Mandatory Ask 只展示 once/deny.
- 空输入解析为默认的 once; EOF 与非法输入解析为 deny, 不落到默认项上.
- `[2] always` 解析为 `ApprovalScope.WORKSPACE`, 文案包含 "本工作区内", 且脚本场景写"相同脚本"、
  命令场景写"相同命令"; HITL 不产出 `ApprovalScope.SESSION` 与 `ApprovalScope.ALWAYS`.
- HITL 快照中不出现 plan hash、target set hash、风险标签、执行画像或批准失效字段。
- 40 列窄终端下换行可读，无横向依赖。
- Rich markup、ANSI、OSC、控制字符和超长路径不会注入或破坏终端。
- renderer 抛错时 fallback 仍能打印最终回答。

### 12.4 安全

- API key、Authorization header、环境变量秘密、系统提示词和 Provider raw metadata 不进入任何密度。
- raw chain-of-thought 和未 allowlist 的 reasoning 字段不会映射为事件。
- 工具完整输出默认不回显；截断和 artifact 引用明确。
- debug 不放宽 redaction、安全策略或审批要求。

## 13. 验收标准

- 一次包含“模型 → 工具 → observation → 模型 → 最终回答”的 turn 在终端形成顺序清晰的时间线。
- 每次模型调用和工具调用均有独立边界，不发生跨 request 文本拼接。
- 用户能看到工具名称、参数/目标安全摘要、状态、耗时和失败原因。
- HITL 确认严格采用 "mode 与工作区 -> 原始命令 -> 可选脚本内容 -> 有后果时的目标集合 ->
  once/always/deny" 的信息顺序, once 为默认; 内部计划 hash, 目标集合 hash, 风险标签, 执行画像和
  失效字段不进入默认确认界面, 但原始命令与脚本内容逐字可见, 有破坏性后果时目标集合完整可见.
- `always` 仅在安全策略允许学习授权时提供, 且只创建工作区范围的学习规则
  (`ApprovalScope.WORKSPACE`); Mandatory Ask 保持逐次批准, 不能被 always 满足.
- thinking 可用时只显示供应商用户可见 summary 或 ForgeCLI decision summary；不可用时显示状态，
  不展示或伪造 raw chain-of-thought。
- `TerminalRunRenderer` 是 turn 期间唯一的运行输出协调者，长输出进入原生 scrollback。
- compact/normal/debug 三档行为有测试，且三档共享相同脱敏和输出限制。
- AgentRunEvent subscriber 失败不会改变 Agent 控制流。
- 运行事件不替代 session、tool、安全和恢复审计；resume 不依赖字符级 delta。
- 模型和工具共享同一 turn cancellation，取消状态在终端与持久化终态中一致。
- 架构检查确认 domain/application 不依赖 Rich、prompt_toolkit 或具体 Provider SDK。
- 相关单元、集成和 E2E 测试通过，`make ci` 通过后方可将 ADR 状态改为 Accepted。
