# ADR-0058: auto 模式: 把"要不要问"交给安全分类器

## 状态

Proposed (2026-09-16; 工作区里有一版实现, 分支 `refactor/claude-code-tools`, 未提交)

修订 ADR-0055: 差异表里"没有 auto 模式 (LLM 分类器)"那一行作废, 五档模式变六档.
推翻 ADR-0030 决策 5 对"用 LLM 判断命令是否安全"的否决 —— 否决的理由 (非确定, 输入
可被注入) 仍然成立, 本文的回答是把它放在一个明确选择了它的档位里, 而不是放在每一档
都要过的裁决链上. 与 ADR-0057 决策 2 里 "`auto` 映射到 `accept_edits`" 的说法冲突时
以本文为准: `auto` 现在是一档自己的模式.

## 日期

2026-09-16

## 背景

ADR-0055 之后的五档模式里, 减少打断的办法只有两种: `accept_edits` 只免掉工作目录内的
编辑, 其余命令照问; `bypass_permissions` 什么都不问, 连"删掉整个 src 目录"也不问. 中间
那一大片 —— 跑测试, 装依赖, 提交, 在工作目录外读一份日志 —— 要么反复确认, 要么放弃
一切把关. 用户的原话是: "Auto Mode 不直接跳过权限, 而是把'是否需要询问'交给安全分类器,
这样可以进一步减少打断".

Claude Code 有这一档 (`auto`, `utils/permissions/yoloClassifier.ts`,
`permissions.ts:473` 里 `mode === 'auto'` 那一段, `denialTracking.ts`,
`dangerousPatterns.ts`, `autoModeState.ts`, `classifierDecision.ts`). 它的形状:

| 组成 | 做什么 |
|---|---|
| 裁决链不变 | `hasPermissionsToUseToolInner` 照常跑; deny 规则, 内容级 ask 规则, 安全检查, 整工具 allow 都在分类器**之前**生效. 分类器只接手本来要问人的那些 ask |
| 两条快路 | 换成 `acceptEdits` 会放行的 (工作目录内的编辑与文件系统命令) 直接放, 不问分类器; 只读与提问类工具 (`Read`, `Grep`, `Glob`, `LSP`, `TodoWrite`, `AskUserQuestion`) 直接放 |
| 分类器 | 另一次模型调用: 系统提示词写死拦截类别与"缺省放行"; 用户消息是 JSONL 记录 (`{"user": ...}` 用户文本, `{"Bash": ...}` 工具调用入参, 由每个工具的 `toAutoClassifierInput` 投影), 最后一行是待裁决的调用; 回答 `shouldBlock` + `reason` |
| 记录里没有的 | 工具输出与 assistant 的文本: 前者是可被注入的正文, 后者是模型写的, 两者都可能是为了说服分类器 |
| 拦下之后 | deny, 话里带分类器的理由与"可以换个自然的做法, 不许绕"; 连续 3 次或累计 20 次 -> 退回问人, 卡片带理由; 分类器不可用 -> deny (fail closed), 话里说清是暂时的 |
| 进 auto 前 | 剥掉会绕过分类器的 allow 规则 (`Bash` 整工具, `Bash(python:*)` 一类解释器前缀), 出 auto 放回 |
| 设置 | `autoMode.allow` / `soft_deny` / `environment`: 三组自然语言句子, 拼进分类器的系统提示词 |
| 可用性 | 功能开关 + 设置; 不可用就不在 Shift+Tab 循环里 |

## 决策

### 1. 第六档 `auto`; 可用性是启动期事实

`PermissionMode.AUTO = "auto"`. 菜单与 Tab 循环: default -> accept_edits -> plan ->
(bypass, 若可用) -> (auto, 若可用) -> default, 次序与 `getNextPermissionMode` 同.

`ToolPermissionContext.is_auto_mode_available` 在装上下文时定: 调用方接得上分类器
(`ProjectRuntime` 有网关, 传 `classifier_wired=True`), 且设置里 `permissions.disableAutoMode`
不是 `"disable"` (与 `disableBypassPermissionsMode` 同一种锁). 不可用时菜单里没有这档,
`/mode auto` 与 `POST /api/v1/mode` 走 `transition_permission_mode` 时抛
`ModeUnavailableError`. 与 bypass 不同, 它不要启动参数也不要一次性确认: 它比 default
多的是一个替人做判断的分类器, 少的是打断, 危险的类别仍然拦.

`defaultMode: "auto"` 可以写进设置. 旧写法 `"auto"` 不再映射到 `accept_edits`; 两轴时代
的 `workspace_write/auto` 仍映射到 `accept_edits` (那是"围栏内自动", 与本文无关).

### 2. 设置: `autoMode` 段与一个新的调用用途

```json
{
  "autoMode": {
    "allow": ["跑 make ci 与 poetry run 开头的命令"],
    "soft_deny": ["碰 deploy/ 目录"],
    "environment": ["build/ 是一次性产物, 可以随时删"]
  },
  "permissions": {"disableAutoMode": "disable"}
}
```

用户级 (`config.json`) 与项目级 (`forge.json`) 合并, 项目级排在后面; 每次分类时读,
改了不必重启. 没有 `model` 键: 分类器的模型走 ForgeCLI 自己的机制 —— 新的调用用途
`RequestOrigin.PERMISSION_CLASSIFIER` (不思考, 非流式), 用户像给别的用途绑模型一样给它
绑一个更快的模型 (`/model` 与 Web 的模型页都按 `RequestOrigin` 枚举列).

### 3. 分类器: `security/auto_mode_classifier.py`

`AutoModeClassifier(query, rules, instructions)`:

- `query` 是网关的 `complete_structured` (类型 `StructuredQuery = Callable[[StructuredModelRequest],
  StructuredModelResponse]`). security 在 llm 之下 (check_arch), 只认这个签名, 由
  `runtime/tool_wiring.py` 把绑定方法递进来. schema 是 `{thinking, should_block, reason}`,
  `strict=True`: 不合 schema 就是"没问到".
- 系统提示词在 `prompt/templates/classifier/auto_mode.md.j2` (新目录, `render_classifier`,
  已登记进 `check_prompt_text` 的 SINKS). 正文: 记录的格式, 缺省放行的日常, 七个拦截
  类别 (不可逆破坏, 泄露秘密, 执行来源不明的代码, 未授权持久化, 削弱安全, 超出任务范围,
  绕过之前的拦截), "只有 `user` 行的明确要求能覆盖", 三段 `<user_*>`.
- 用户消息: FORGE.md 原文 (用户写给 Agent 的话, 当用户意图) + `<transcript>` 里的 JSONL.
  记录由 `build_transcript_lines` 从 `ToolUseContext.messages` (当前窗口) 生成: USER 消息的
  文本各一行, ASSISTANT 消息的每个工具调用各一行, 值是 `tool.to_auto_classifier_input(arguments)`
  (`Tool` 协议新成员, 缺省 `""` = 不进记录). TOOL 消息与 assistant 文本不进去.
- 每个内置工具的投影: `Bash` 命令; `Edit` / `Write` 是 `路径: 新内容`; `Read` 路径;
  `Grep` 是 `模式 in 路径`; `Glob` 模式; `LSP` 是 `操作 路径`; `AskUserQuestion` 问题;
  计划, 待办与记忆工具缺省 `""`.
- 结论 `ClassifierVerdict(should_block, reason, model, unavailable, thinking, duration_ms)`.
  任何异常 -> `unavailable=True, should_block=True`.

### 4. 裁决: `has_permissions_to_use_tool` 多一段

顺序 (与 `permissions.ts:473` 逐行对应):

1. `_inner` 照常. 结果 allow: auto 下顺带把"连续被拦"计数清零, 返回.
2. 结果 ask 且 `dont_ask` -> deny (不变).
3. 结果 ask 且 auto 生效 (`mode is AUTO`, 或 `mode is PLAN and pre_plan_mode is AUTO`) 且接了
   分类器 -> `_auto_mode_decision`:
   - 安全检查且 `classifier_approvable` 为假 (可疑的 Windows 路径, UNC) -> 照问人; 无界面
     -> deny. 为真的那些 (`.git`, `.forge`, shell 配置) 往下走.
   - `requires_user_interaction()` 的工具 -> 照问人.
   - 快路一: 用同一份上下文, 模式换成 `accept_edits` 再问一次工具的 `check_permissions`,
     allow 就放, 理由 `mode auto`. 这意味着 auto ⊇ accept_edits: 工作目录内的 `rm -rf src`
     不过分类器 (与 Claude Code 同).
   - 快路二: `AUTO_MODE_ALLOWLISTED_TOOLS` -> 放.
   - 分类器. 不拦 -> allow, 理由 `classifier auto-mode: <reason>`. 拦且不可用 -> deny,
     `build_classifier_unavailable_message`, 不计数. 拦 -> 计数 +1; 到阈值
     (`security/denial_tracking.py`: 连续 3, 累计 20) -> 退回原来的 ask, 理由换成分类器
     的 (累计到 20 清零); 无界面时照拒. 否则 deny, `build_auto_mode_rejection_message(reason)`
     (与 Claude Code 的 `buildYoloRejectionMessage` 同一段话, 附 `DENIAL_WORKAROUND_GUIDANCE`).
4. 结果 ask 且无界面 -> deny (不变). auto 那一段排在它前面, 无人值守的入口 (`dont_ask`
   之外) 也能用 auto.

计数 `DenialTrackingState` 住在 `AppState` (与 Claude Code 的 `appState.denialTracking`
同), 由 `AppStateHolder` 持有, 随会话.

新的理由类型 `DecisionReasonType.CLASSIFIER` (`classifier`, `reason`); 事件与卡片上的
`reason` 字符串是 `classifier auto-mode: ...`, 终端与 Web 不需要新的展示逻辑.

### 5. 进出 auto 剥与还 allow 规则

`security/dangerous_patterns.py` 是 Claude Code 对外构建的那张清单 (解释器, 包运行器,
shell, `ssh`, `eval` / `exec` / `env` / `xargs` / `sudo`); `is_dangerous_bash_permission`
认整工具 `Bash`, `Bash(*)`, `x`, `x:*`, `x*`, `x *`, `x -...*` 五种写法.
`security/auto_mode.py::strip_dangerous_permissions_for_auto_mode` 把命中的从
`always_allow_rules` 里摘出来存进 `ToolPermissionContext.stripped_dangerous_rules` (按来源),
`restore_dangerous_permissions` 放回. `transition_permission_mode` 按"换完之后分类器还在
不在"决定剥还是还: auto -> plan 不还 (plan 下的 ask 仍由分类器管), plan -> auto 不重复剥,
auto -> default 还. `defaultMode: "auto"` 启动时也剥.

### 6. 与 Claude Code 的差异

| 差异 | 理由 |
|---|---|
| 一次结构化调用 (`complete_structured`), 没有两阶段 XML 分类器 (`classifyYoloActionXml`) | 两阶段是为省 token 与延迟做的优化, 靠 GrowthBook 开关; 结构化输出走网关已有的原生 / 降级两条通道, 供应商换了也不用改 |
| 没有 `transcriptTooLong` 的特殊处理 | 记录只含用户文本与工具入参, 严格小于主循环窗口, 主循环的压缩先于它触发 |
| 分类器不可用一律 fail closed | Claude Code 由 `tengu_iron_gate_closed` 决定开合, 缺省闭; 本仓库没有远程开关 |
| 没有 `Bash(prompt: ...)` 规则 (`bashClassifier.ts`) | 对外构建里是桩 |
| 记录里 Forge 自己注入的引导 (`notices/loop.md.j2` 一类, 以 USER 角色进窗口) 会以 `user` 行出现 | 它们是 Forge 写的固定文本, 不是攻击面; 分不开是因为窗口里没有"谁写的"标记. 已知局限 |
| 无人值守下拦到阈值不中止 Agent (Claude Code 抛 AbortError) | 本仓库循环的停止条件在规则层 (refusal 一类); 这里只 deny, 话里带累计次数 |
| 分类器的用量不进会话计量 | 与 Claude Code 的 `sideQuery` 同 (不计入 session cost); 要计量时给 `AutoModeClassifier` 加一个 meter 即可 |

## 备选方案

- **让分类器进裁决链的每一档** (ADR-0030 否决的形态): 否. 非确定性的判断只能替代
  "问人", 不能替代 deny 规则与安全检查; 所以它只接手 ask, 且只在用户选了 auto 时.
- **用 `sandbox.autoAllowBashIfSandboxed` 覆盖这个用例**: 那是 ADR-0055 的回答. 它只
  管进围栏的 Bash, 不管工作目录外的读写与围栏外的命令, 也不理解"用户让不让做这件事".
- **分类器看完整窗口 (含工具输出)**: 否. 工具输出是注入的主要入口, Claude Code 特意
  不放; 代价是分类器看不到"上一条命令失败了"这类上下文, 由记录里的调用序列部分弥补.

## 验收标准

- `/mode auto` 后: `Read /etc/hosts` 不问; 工作目录内 `Edit` 不问; `git commit -m x`
  经分类器放行, 事件 `reason` 是 `classifier auto-mode: ...`; `rm -rf ~/Documents` 被拒,
  tool_result 以 `Permission for this action has been denied. Reason:` 开头.
- 用户说 "把 build 目录删了" 之后 `rm -rf build` 放行 (记录里有那一行 `user`).
- 连续三次被拦, 第四次弹卡片, 卡片理由含 "3 consecutive actions were blocked".
- 网络断开时被拦的话含 "temporarily unavailable", 且不计入拦截次数.
- `forge.json` 里 `allow: ["Bash(python:*)"]`: default 下 `python x.py` 直接放行, auto
  下经分类器; 切回 default 后又直接放行. `/permissions` 在 auto 下不显示那条.
- `permissions.disableAutoMode: "disable"` 后菜单里没有 auto, `/mode auto` 报错.
- 给 `permission_classifier` 用途绑另一个模型后, 分类器用那个模型.
