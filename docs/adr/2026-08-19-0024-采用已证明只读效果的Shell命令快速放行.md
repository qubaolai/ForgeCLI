# ADR-0024：采用已证明只读效果的 Shell 命令快速放行

## 状态

Superseded by ADR-0030 (2026-08-24)

> 实现已整体删除: `proven_read_only` 判据函数, `findings` 上的字段, `commands.py` 里
> 29 条命令名的标记, 以及 `PROVEN_READ_ONLY_SHELL` 这个裁决理由.
>
> 本 ADR 要解决的问题是真的 (一次任务里连续 20 次形状雷同的 ASK, 全是只读命令), 但
> 解法的形状不对: 它靠**八条判据证明这条命令等价于一次读取**来免掉一次确认, 于是精度
> 只能靠加判据换, 而命令的世界是开放的. 2026-08-21 修的 `find` 误判就是这个模型必然
> 会出现的一类错误 —— `find` 因为**名字**在表里被判为动态执行, 而做同样目录遍历的
> `ls -R` 与 `grep -r` 自动放行.
>
> ADR-0030 换了判据: 不证明命令只读, 而是**让它伸不出去**. 围栏内的读写一律放行,
> 因为工作区内有写时复制快照兜底, 工作区外由内核拒绝. 于是那张 29 条的表不必再追赶.

## 日期

2026-08-19

## 背景

`domain/security/modes.py` 把 `EXECUTE_SHELL` 放在 `_AUTO` 档. 因此在默认的 `accept_edits`
下, **每一条** shell 命令都要人类逐次确认 —— 包括 `ls -la`, 包括 `grep -r`.

一次真实任务里连续出现约 20 次 ASK, 全部是只读命令:

```text
ls -la <resources>/                              mode_requires_approval
grep -r "skipUrl" . --include="*.yml"            mode_requires_approval
find . -name "*.yml" -exec grep -l skipUrl {} \; unproven_executable
```

三条后果, 一条比一条严重:

1. **用户被训练成无脑回车.** 二十次形状雷同的确认之后, 第二十一次没有人在读.
2. **审批因此失去意义.** 而 ADR-0013 §6.2 的整套设计, 前提正是"人类看得懂并且真的在看".
3. **它与 ADR-0013 §6.3 修掉的那类展示缺陷叠加时最危险.** 一条 `find -exec rm` 的审批框
   曾经写着"删除 0", 而用户此时的状态是连着按了二十次回车.

**这不是一个体验问题, 是一个安全问题.** 一道从不被阅读的闸门, 与没有闸门的区别只在文档里.

### 为什么现在的档位设计会这样

模式预算把**能力**当闸门: 一个工具声明了 `EXECUTE_SHELL`, 那么它在 `accept_edits` 下就要
问人, 无论这次要跑的是 `rm -rf /` 还是 `ls`.

这个粒度对 `fs.*` 工具是合适的 —— 它们的能力上界窄, 声明即事实. 对 `shell.run` 不合适:
它的能力上界是"几乎一切", 而单次调用的实际效果可以窄到只有一次目录列举. **能力上界回答
的是"最坏能干什么", 不是"这次干了什么".**

ADR-0004 §14 已经写下相关判断: "`shell.run` 的能力上界最宽, 因此它的每次调用几乎必然进入
能力分析器; 这正是 ADR-0013 期望的路径, 而不是缺陷." 那句话仍然成立 —— 本 ADR 不改变
"每次都要分析", 只改变"分析证明了它只读时, 还要不要再问一次人".

## 决策

**模式预算按能力放行; 在此之上增加一条按已证明效果放行的快速路径.**

一条 `shell.run` 调用在下列条件**全部**成立时, 不再要求人类确认:

| # | 条件 | 不成立时说明什么 |
|---|---|---|
| 1 | `ParseStatus.OK` | 命令没被完整解析, 谈不上"证明" |
| 2 | 每个单元的可执行文件都已证实, 无 `UNPROVEN` | 有命令我们不认识它碰什么 |
| 3 | 所有单元的 `effect_kind` 都是 `READ` | 存在写 / 删 / 移动 / 跑代码 |
| 4 | 无 `substitution` / `wrapper_inner` / `process_substitution` 单元 | 有内层命令, 外层的证明不传导 |
| 5 | 无 `dynamic_execution` | `eval` 一类, 内容运行期才有 |
| 6 | `target_resolution` 封闭 (`STATIC` / `FORGE_EXPANDED`) | 目标集合本身没封闭 |
| 7 | 全部目标在 `workspace_roots` 内 | 越界读取仍是 `EXTERNAL_READ` |
| 8 | 无网络目标, 无写重定向 | `> file` 是写, 命令名看不出来 |

任何一条不成立即退回现在的 `ASK`. 判据全部取自已有事实, 不新增任何推断.

**这不是"信任 shell", 是"分析证明了这条命令等价于一次读取".** 同样一次目录列举, 走
`fs.list_files` 本来就自动放行; 走 `ls` 却要问人, 差别只在它经过了哪个工具, 而不在它做了
什么.

### 明确不改变的东西

逐条点名, 作为"这条路径只影响要不要问人"的证据:

- **Hard Deny 清单**照常先判, 快速路径在它之后.
- **受保护路径检查**照常. 条件 7 之外, `~/.ssh` 一类目标仍由 `ProtectedPathPolicy` 拦.
- **恢复层屏障** (ADR-0015) 不受影响: 只读命令本来就不触发首次破坏性写入屏障.
- **审批绑定的重验** (ADR-0004 §6.1) 不受影响: 快速路径不产生审批, 也就没有可复用的旧
  批准.
- **审计**照常. 不经审批 ≠ 不记录, `tool_requested` / `tool_completed` 一条不少.
- **模式预算本身不动.** `EXECUTE_SHELL` 仍然只在 `_AUTO` 档进自动集合; 快速路径是预算之上
  的一条独立判据, 不是把能力挪档. 这一条要写死 —— 挪档会顺带放行 `EXECUTE_SCRIPT`.

## 备选方案

- **方案 A：把 `EXECUTE_SHELL` 挪进 `_ACCEPT_EDITS`.** 一行改动, 但它放行的是**能力**而
  不是效果: `rm -rf build/` 与 `ls` 会一起自动放行. 这正是模式预算不该表达的粒度. 不采用.
- **方案 B：维护一份只读命令白名单** (`ls`, `cat`, `grep` …). 看似简单, 实则把"这条命令
  只读"从**可证明的结论**降级成**一句断言**: `cat` 在白名单里, 而 `cat a > b` 是写.
  ADR-0013 §3 已经写过为什么规则不能作用于命令名. 不采用.
- **方案 C：靠 `always` 学习规则消化.** 它已经存在 (`tty_approval` 的 `[2] always`), 但
  规则按 `command_hash` 匹配, 而模型每次换个写法就是一条新规则 —— trace 里 8 个 grep 变体
  会产生 8 条规则, 一条都复用不上. 它解决的是"同一条命令反复问", 不是"同一类命令反复问".
  保留, 但它不覆盖本 ADR 的场景.
- **方案 D：什么都不做, 靠用户自己切到 `auto` 档.** 那一档同时放行 `EXECUTE_SCRIPT`, 代价
  远大于收益; 而且它要求用户为了少按二十次回车而永久放宽一整档权限. 不采用.

## 影响

### 收益

- 只读探索不再产生审批噪音, 审批框回到"出现即值得看"的状态.
- 与 ADR-0018 §4.5 的检索顺序形成合力: 提示词让模型少用 shell 检索, 这条路径让它偶尔用到
  时也不打断用户.

### 代价

- 多一条判据链, 且它的正确性依赖 §4 那条依赖顺序. 判据链本身要有正面用例逐条钉住.
- 条件 2 与 3 依赖命令表, 表有漏项时结果是**退回 ASK**, 方向朝安全.

### 兼容性

无数据迁移. 不改变任何已持久化的规则, 缓存或授权信封的字段.

## 设计细节

### 1. 判据放在哪一层

**裁决在 `PolicyEngine`, 事实在分析器.** 这条分界不因为多一条快速路径而模糊.

具体地: 分析器只回答"这条命令的结构是不是只读"这个**事实问题** (它是唯一拿得到
`CommandPlan` 的一层), 把结论记进 `AnalysisFindings.proven_read_only`; 要不要因此免掉一次
人类确认, 由 `PolicyEngine` 决定, 与既有的 `PLAN_ONLY_FAST_PATH` 并列.

分析器**不**产出"可以放行"这种结论 —— 那是裁决. 拆法见 §8.

### 2. 失效方向

八条判据全部是"必须成立", 缺一即退回 `ASK`. 新增一种解析不出来的语法, 新增一个表外命令,
新增一种重定向形态 —— 结果都是多问一次, 不是少问一次.

### 3. 与 ADR-0020 的关系

ADR-0020 的分类器处理的是"auto 解析不完整"的情形. 本路径要求条件 1 与 2 成立, 因此**永远
不会与分类器路径重叠**: 需要分类器的调用一定不满足快速路径.

### 4. 实现顺序 (硬约束)

**必须排在 ADR-0013 §6.3 的参数模型之后.**

条件 3, 6, 7 全部建立在效果推导之上. 而在参数模型出现之前, 那套推导会把 `tar` 的 `src`
说成写入, 把 `grep` 的搜索词说成读取. **在一个已知会说假话的判断之上放宽自动放行, 比现状
更糟** —— 现状只是问得太多, 那样是问得不对.

§6.3 落地之后, 条件 3 与 7 才有可信的输入.

### 5. 可见性

自动放行的只读命令仍然进运行事件流与终端过程展示 (ADR-0016). 用户看得见它跑了什么, 只是
不必逐次点头. "不问"与"不告诉"是两件事.

### 6. 已知限制

- 命令表覆盖不到的只读命令仍然要问. 这是刻意的: 补表是一次显式改动, 而"没覆盖就放行"是一条
  静默的口子.
- 只读命令仍可能消耗大量时间或产生大量输出. 那由 `ResourceGovernor` 与超时管, 不由审批管.

### 7. 实现相对本设计的两处收紧

两处都是**更严**, 不是更松. 记下来是因为读设计的人会拿它去对代码.

**其一, 条件 4 扩成"只认最外层单元".** 设计列了 substitution / wrapper_inner /
process_substitution 三种 origin, 实现要求全部单元都是 `TOP_LEVEL`, 因而连 subshell 与
PowerShell script block 也排除掉. 多排除的两种只会让某些本可放行的命令继续问人.

**其二, `plan` 档整档排除.** 设计没提模式区分, 实现发现 `ls src` 在 plan 档也会被放行 ——
判据上没错 (那一档预算里 `EXECUTE_SHELL` 同样超支, 同样会被免掉), 但与 plan 档对用户的
承诺冲突: **起一个子进程就是执行**, 它会占用时间, 会读东西, 也会挂住.

`shell.run` 本来就不在 plan 档的工具目录里 (`catalog_query_for_mode` 按
`MUTATING_CAPABILITIES` 过滤掉了它), 所以这条判断买不到新功能. 加它的理由是**不让策略层
依赖目录过滤兜底** —— 目录是"看不看得见", 策略是"许不许可", 两层各自成立才算数.

### 8. 作用域的落法

设计写的是"八条判据全部成立才自动放行". 实现把它拆成两半:

- 分析器 (`shell_analyzer._proven_read_only`) 产出条件 1-5 与 8, 因为只有它拿得到
  `CommandPlan` —— 策略层看不见单元, 连接符与重定向.
- 策略引擎 (`policy_engine._proven_read_only`) 再验条件 6, 并只从 `over_budget` 里减掉
  `EXECUTE_SHELL` 与 `SPAWN_PROCESS`.

**条件 7 因此不需要单独实现.** 越界读取会被推导成 `EXTERNAL_READ`, 而快速路径减不掉它,
于是它自己留在 `over_budget` 里. 把这条写成"免掉全部 `over_budget`"会顺带放行
`cat ~/.ssh/id_rsa` —— 作用域的窄小本身就是这条路径的安全边界, 不是实现细节.

## 2026-08-21 收窄记录 (ADR-0028)

**八条判据一条不改。** 变的是条件 2 与 3 依赖的命令表。

原先的 `effects._KNOWN_READERS` 有 85 条命令，且它同时兼两个职责：决定位置参数按不按
读取记账（影响审批清单准不准），以及决定能不能自动放行。两个职责的错法方向相反 ——
记账漏一条是清单少一项，放行漏一条是少一道闸门 —— 混在一张表里，就只能按更宽松的那个
方向维护。

ADR-0028 规则 D 把它拆成两个字段（`domain/security/shell/commands.py`）：

- `effect=READ`：位置参数按读取记账。原 85 条命令**全部保留**，审批清单的准确度不变。
- `proven_read_only=True`：进本 ADR 的快速放行。收到 **29 条命令名 + git 只读子命令**，
  小到可以在一次代码评审里读完。

因此 `wc`、`ls`、`grep`、`find`、`cat`、`git status` 照旧自动放行，而 `sort`、`xxd`、
`uniq`、`strings` 一类退回 ASK。**这是刻意的代价**：本 ADR 的整个前提是"人类真的在看"，
而一张没人审计得动的放行表，与没有审计的区别只在文档里。

要把一条命令加进核心集是一次显式改动，需要在 PR 说明里单独指出（ADR-0028 后续约束）。

## 验收标准

- 八条判据各有一条正面用例与一条反面用例; 反面用例断言退回 `ASK`.
- `ls -la <workspace>` 与 `grep -rn foo src` 在 `accept_edits` 下不触发审批.
- `ls > out.txt`, `cat a | sh`, `grep -r foo /etc`, `find . -exec rm {} \;` 全部仍然触发审批.
- 有用例证明 Hard Deny, 受保护路径与模式预算在快速路径存在时行为不变.
- 有用例证明自动放行的调用仍然产生完整审计事件.
- 实现提交里包含一条断言: 参数模型 (ADR-0013 §6.3) 已落地.
