# ADR-0015：采用首次破坏性写入屏障与独立工作区恢复机制

## 状态

Accepted (2026-07-31 实现)

2026-08-10：ADR-0020 对本 ADR 增加窄范围例外。未获人工批准的自动真实写入仍必须建立
恢复绑定；人类在完整展示后明确“仅本次批准”的调用可以绑定审批 view hash 直接执行，
不要求 RecoveryStore，并明确不承诺可恢复。

首次破坏性写入屏障, 内容寻址 RecoveryStore, MutationSet, postimage 冲突检查, 崩溃恢复
扫描与 `/undo` `/checkpoints` `/recovery` 全部落地, 且不依赖 Git.

§7.3 的 `OVERLAY` 快照策略随沙箱一同缓期: 枚举值保留但不可选中 (`SnapshotStrategy
.available` 为 False), 当前只实现 `NONE` / `TARGETED` / `FULL`. 因此 §8.3 的
"ShellTool + OVERLAY" 路径暂不可用, 写集合未知的直接执行只能走 `FULL` 或拒绝.

## 日期

2026-07-30（2026-07-31 实现）

## 背景

ForgeCLI 的 Agent 需要在工作区内完成覆盖文件、删除旧实现、移动目录、批量重构、运行代码生成器和
清理构建产物等操作。这些操作对软件工程任务是必要能力，不能因为具有破坏性就全部设为 Hard Deny。

Git 可以辅助展示差异和恢复部分源码，但不能作为 Forge 工作区安全机制的前提：

- 用户可能在一个没有 `.git` 的普通目录中工作。
- 工作区可能包含未跟踪、被 ignore、尚未保存到 Git 或不适合进入 Git 的文件。
- 工作树可能在 Agent 执行前已经存在用户的未提交修改。
- 自动执行 `git reset --hard`、`git clean` 或 checkout 恢复会破坏用户原有状态。
- 数据文件、生成物、本地配置和临时资产不一定能从 Git 重建。

恢复点如果按 `rm`、`sed`、`python` 等危险命令清单触发，会同时产生漏判和误判：普通解释器可以
动态覆盖整个工作区，而 `rm` 也可能只删除可再生缓存。恢复机制必须根据真实文件系统变更语义触发，
而不是根据可执行文件名称猜测。

ADR-0013 负责决定请求是否允许执行，ADR-0014 负责限制进程能够触达的宿主资源。本 ADR 补充第三层
边界：当已经允许的请求需要修改真实工作区时，Forge 如何在不依赖 Git 的情况下建立可恢复性。

## 决策

### 1. 权限、隔离和恢复是三个独立层次

统一执行路径为：

```text
ToolRequest
  ↓
ToolAuthorizationService       是否允许执行
  ↓
审批后重验（ASK 且人类批准时）
  ↓
WorkspaceMutationCoordinator    真实工作区写入是否具备恢复保障
  ↓
ToolAuthorizationService.issue  签发绑定 recovery_binding 的授权
  ↓
ExecutionAuthorization
  ↓
Execution path
  ├─ FileTool
  ├─ ArtifactCollector
  └─ ShellTool → SandboxProvider（能够触达哪些宿主资源）
  ↓
RecoveryCheckpoint + MutationSet
```

沙箱限制写入范围，但不保证工作区内部变更可撤销；风险分类器评估行为风险，但不保存旧内容；Git 可以
作为可选证据源，但不拥有恢复流程。任何一层都不能替代其他层。

`WorkspaceMutationCoordinator` 不是 `ToolAuthorizationService` 或规则引擎的内部组件。规则引擎
可以根据恢复能力和执行画像作出更保守的裁决，但不创建、提交或回滚恢复事务；恢复层可以拒绝建立
恢复保障，但不能把安全层的 `ASK` / `DENY` 提升为允许。沙箱同样由独立 Provider 实施资源隔离，
不参与恢复触发和回滚裁决。三层只通过 `ToolRequestCoordinator`、授权信封中的
`recovery_binding` 和执行画像进行装配。

人类批准发生在恢复事务建立之前。批准后，`ToolRequestCoordinator` 必须先按 ADR-0004 / ADR-0013
重新验证计划、目标集合、策略和执行环境；旧批准失效时不得创建或复用恢复点。只有重验通过后才能
为本次调用建立恢复绑定并签发一次性执行授权，避免为未获准或已经变化的动作提前持有恢复事务。

### 2. 恢复触发基于破坏性变更语义，不基于命令清单

`WorkspaceMutationCoordinator` 以目标对象的操作前状态和计划变更判断是否需要恢复保护。

以下属于破坏性写入：

- 覆盖、截断或追加现有文件。
- 删除文件或非空目录。
- 将对象移动或重命名到其他路径。
- 用新文件、目录或链接替换现有对象。
- 修改权限、owner、ACL、扩展属性或其他影响访问语义的元数据。
- 修改符号链接、junction 或 reparse point 的目标。
- 对现有数据库、归档或其他复合文件执行原地修改。
- 其他会导致旧状态无法仅从执行后状态可靠推导出来的操作。

以下操作仍需记录，但不需要保存旧内容：

- 创建原先不存在的新文件、目录或链接。
- 在声明为可再生的缓存或构建输出目录中创建内容。

命令名称和脚本语言可以作为风险分析证据，但不能作为恢复点的规范触发条件。`rm` 不必然创建完整
工作区快照，`python`、`node`、自定义二进制或 MCP 工具也不能因为不在危险命令清单中绕过恢复屏障。

### 3. 每个有状态 ToolInvocation 构成一个恢复事务

默认事务边界为单个 `ToolInvocation` 或一条整体授权的 `CommandPlan`。复合 Shell 命令作为一个
事务处理，不能为管道或 `&&` 的每个分析单元分别建立互不关联的恢复点。

恢复事务状态至少包括：

```text
PREPARING
ARMED
EXECUTING
COMPLETED
FAILED
RESTORING
RESTORED
CONFLICTED
EXPIRED
```

状态语义：

- `PREPARING`：正在建立恢复元数据或保存 preimage，尚不允许真实破坏性写入。
- `ARMED`：恢复数据已经持久化，可以开始真实写入。
- `EXECUTING`：工具正在执行，新的首次触达路径可以继续追加 preimage。
- `COMPLETED`：执行结束，preimage、postimage 和变更集已经封存。
- `FAILED`：执行失败，但恢复点仍保留，用于检查或回滚部分修改。
- `CONFLICTED`：恢复时发现对象已被后续操作或外部进程修改，不能静默覆盖。

### 4. 在首次破坏性写入之前设置恢复屏障

恢复点采用写前日志语义：

```text
首次破坏性写入即将发生
  ↓
创建 RecoveryCheckpoint
  ↓
保存目标对象 preimage 和元数据
  ↓
持久化 checkpoint manifest
  ↓
状态变为 ARMED
  ↓
才允许真实写入
```

同一事务内，每个路径只在第一次被真实修改前保存一次 preimage。后续反复修改同一路径不覆盖最初
preimage，也不重复存储相同内容。新建对象记录 `existed_before=false`，恢复时依据 postimage 冲突
检查决定是否删除。

纯创建操作不需要保存内容 preimage，但仍必须在对象创建前持久化一个轻量 MutationEntry，记录
`existed_before=false`。因此事务日志在首次真实工作区变更前存在，而内容快照的昂贵部分只由首次
破坏性写入及其后续首次触达路径触发。

“首次破坏性写入触发”是领域规则，不代表所有执行后端都能在任意进程的第一个 `write()`、
`unlink()` 或 `rename()` 系统调用处暂停。不能提供运行期写屏障的后端必须在进程启动前建立等价的
目标快照、完整快照或临时写层，不能等修改已经发生后再补建恢复点。

### 5. RecoveryCheckpoint 和 MutationSet 使用明确的数据模型

`RecoveryCheckpoint` 至少包含：

```text
checkpoint_id
workspace_id
session_id
turn_id
tool_invocation_id
command_plan_hash
created_at
status
snapshot_strategy
policy_version
execution_profile_hash
manifest_hash
recoverable
incomplete_reason
retention_deadline
```

每个对象的 `MutationEntry` 至少包含：

```text
relative_path
object_type
existed_before
preimage_content_hash
preimage_metadata_hash
postimage_content_hash
postimage_metadata_hash
operation
source_path
target_path
file_identity
link_target
recoverability
conflict_status
```

`MutationSet` 是某次事务实际产生的规范化变更集合，包括 created、modified、deleted、moved 和
metadata_changed。预测写集合只用于选择快照策略，不能冒充实际变更集合。

### 6. 使用独立于 Git 的受保护 RecoveryStore

恢复数据存放在 Forge 状态根目录下，而不是工作区或 `.git` 中：

```text
forge_state_root/
  recovery/
    <workspace_id>/
      blobs/
      checkpoints/
      manifests/
```

`RecoveryStore` 必须满足：

- 使用规范化 `workspace_id` 隔离不同工作区。
- 由 Forge 进程控制，Agent、Shell、`/add-dir`、学习式 Allow 和 `full_access` 不能写入。
- 内容 blob 使用内容 hash 寻址，相同内容跨 checkpoint 去重。
- manifest 使用原子写入和完整性校验，不能先修改工作区再异步补写恢复记录。
- 保存文件内容所需的权限、类型、链接目标和平台元数据。
- 支持配额、保留期、列出、恢复、过期和显式清理。
- 不把恢复 blob 暴露给模型上下文或普通 Shell 输出。

恢复存储可能包含工作区中的敏感数据，必须使用仅当前用户可访问的文件权限；企业或高敏场景可以增加
静态加密。清理恢复数据只能由受控的 Recovery Service 执行，不能由 Agent Shell 直接删除。

### 7. 快照策略按变更能力选择

快照策略分为：

```text
NONE
TARGETED
OVERLAY
FULL
```

#### 7.1 NONE

用于确定不会破坏真实工作区状态的请求，例如纯读取，或只在隔离临时目录中产生可丢弃内容。

#### 7.2 TARGETED

用于 FileTool、已知目标的补丁、明确的移动/删除以及能够可靠提取写路径的命令。只保存预计目标在
首次变更前的 preimage。

如果执行过程中请求访问预测集合之外的真实写路径，支持写屏障的后端可以延迟补充 preimage；不支持
动态写屏障的后端必须阻止该写入或让整个请求重新裁决，不能把预测集合当作无限授权。

#### 7.3 OVERLAY

用于支持临时写层的 SandboxProvider。工作区源内容保持只读，命令只修改 Overlay；Overlay 内部写入
不触发真实工作区恢复点。执行结束后由 `ArtifactCollector` 或变更 materializer 得到确定的
`MutationSet`，在每个变更真正写回工作区前设置恢复屏障。

#### 7.4 FULL

用于无 Overlay、无运行期写拦截且写入范围无法可靠确定的直接执行。必须在启动进程前为纳入策略的
工作区内容建立完整 checkpoint。

`FULL` 不是无条件复制所有文件。实现可以使用文件系统原生 copy-on-write clone、reflink、卷快照或
内容寻址增量存储，但必须通过自测证明旧内容可以恢复。硬链接不能作为普通文件 preimage，因为原地
写入会同时改变所谓备份。

### 8. 不同执行入口采用不同恢复方式

#### 8.1 FileTool

FileTool 能确定目标路径，默认使用 `TARGETED`。写入顺序必须为：

```text
校验当前对象身份和 hash
  ↓
保存 preimage
  ↓
checkpoint ARMED
  ↓
原子写入或删除
  ↓
记录 postimage
```

#### 8.2 ArtifactCollector

临时层产物只有在 materialize 到真实工作区时才进入恢复事务。目标已存在则保存 preimage；目标
不存在则记录 `existed_before=false`。产物收集仍需遵守 ADR-0014 的链接、设备对象、路径和大小
限制。

#### 8.3 ShellTool + OVERLAY

优先使用 `OVERLAY`。Shell 可以在临时层内执行测试、生成代码和批量变更，执行后再把确定的变更集合
通过恢复屏障写回真实工作区。这是任意脚本和未知命令的首选恢复方式。

#### 8.4 ShellTool 直接写真实工作区

如果后端没有 Overlay 或系统级写拦截：

- 写路径可靠且规模受控时使用 `TARGETED`，并在启动进程前保存目标集合。
- 写路径未知或可能扩大时使用 `FULL`。
- `FULL` 超过资源预算、无法保证一致性或创建失败时，`auto` 不得直接继续，必须进入 `ASK` 或改用
  不写真实工作区的执行方案。

文件系统 watcher、执行后扫描或 SRT violation 日志只能用于发现和审计，不能替代 preimage，因为
观察到写入时旧状态可能已经丢失。

### 9. 可再生内容可以降低恢复成本，但必须显式声明

缓存和构建输出可以标记为 `regenerable`，例如项目策略明确识别的：

```text
.pytest_cache/
coverage/
dist/
build/
node_modules/.cache/
```

对可再生内容可以只记录对象原先是否存在、路径和操作，而不保存全部内容。但：

- ignore 规则不自动等于可再生。
- `node_modules`、虚拟环境或本地数据库不能仅因体积较大就默认可再生。
- 用户文件、源码、测试、配置和数据文件不能由模型自行标记为可再生。
- `regenerable` 规则只能来自 Forge 内置策略或用户显式配置，并需要审计。

### 10. 恢复预算是 auto 的执行前置条件

`RecoveryPolicy` 至少包含：

```text
max_checkpoint_files
max_checkpoint_bytes
max_checkpoint_seconds
max_total_store_bytes
retention_duration
regenerable_paths
full_snapshot_allowed
```

裁决规则：

- `NONE` 和预算内的 `TARGETED` 可以继续执行。
- 可用 `OVERLAY` 时优先使用临时层，减少真实工作区快照。
- `FULL` 在预算内且创建成功时可以继续执行。
- checkpoint 不完整、存储不可写、完整性校验失败或超出预算时，不能标记为 recoverable。
- 需要破坏性写入但恢复保障未建立时，`auto` 必须进入 `ASK`、缩小请求范围或改用 Overlay。
- `full_access` 可以扩大工作区操作范围，但不能把失败的 checkpoint 伪装成可恢复。

用户可以在审批界面明确选择一次性“无恢复执行”，但界面必须展示不可恢复范围和原因；该授权只对
当前请求有效，不能形成 `always allow`。工作区根目录、RecoveryStore 和其他受保护路径仍不能通过
此审批覆盖。

### 11. 恢复操作必须进行 postimage 冲突检查

提供以下用户接口：

```text
/undo
/undo <tool_invocation_id>
/checkpoints
/restore <checkpoint_id> --preview
/recovery status
```

恢复规则：

- 当前对象仍等于该事务记录的 postimage 时，可以自动恢复 preimage。
- 原先不存在且执行后新建的对象，只有在当前对象仍等于 postimage 时才可自动删除。
- 当前对象已经被后续 ToolInvocation、用户或外部进程修改时进入 `CONFLICTED`，不能静默覆盖。
- move/rename 必须同时校验源和目标位置。
- 冲突时生成预览，并允许恢复为旁路文件、逐项确认或取消。
- restore 本身也创建新的 RecoveryCheckpoint，使恢复操作可以再次撤销。

Forge 不自动调用 `git reset --hard`、`git clean` 或其他会覆盖用户原始工作树的命令。

### 12. 崩溃恢复和并发写入必须显式处理

工作区真实写入前，checkpoint manifest 必须已经原子持久化。Forge 异常退出后：

- `PREPARING` 表示真实写入尚不应开始，可以安全清理未完成临时数据。
- `ARMED` 或 `EXECUTING` 表示可能发生了部分修改，启动时必须比较 preimage、当前状态和已有
  postimage，向用户展示恢复选项。
- `COMPLETED` checkpoint 可以按正常保留策略管理。

Forge 对同一工作区的有状态 ToolInvocation 使用工作区级写租约，避免多个 Forge 执行事务同时覆盖
同一路径。外部进程不受该租约约束，因此每次真实写入和恢复仍需校验对象 hash、文件身份和元数据。
检测到并发变化时中止当前写入或进入冲突处理。

数据库、虚拟机镜像和其他需要应用一致性的复合文件不能仅凭字节复制宣称可安全恢复。无法获得一致
快照时，应停止相关进程、使用应用专用备份接口或将请求升级为 `ASK`。

### 13. Git 只作为可选增强

当工作区存在 Git 时，Forge 可以记录：

```text
repository_root
HEAD
branch
index_hash
dirty_paths
untracked_paths
```

这些信息可用于差异展示、冲突说明和恢复验证，但：

- checkpoint 仍保存需要恢复的非 Git 内容和用户未提交 preimage。
- 工作区是否干净不影响恢复事务的建立。
- 不假设所有文件都受 Git 跟踪。
- 不使用破坏性 Git 命令代替 `RecoveryStore`。
- `.git` 内部写入继续服从 ADR-0013/0014 的受保护路径和 Git 操作策略。

### 14. 所有恢复生命周期必须可审计

至少记录：

- checkpoint 创建原因、策略和范围。
- 首次破坏性写入屏障的触发时间。
- preimage 持久化结果和 manifest hash。
- 实际 `MutationSet`。
- checkpoint 失败、预算超限和降级原因。
- undo/restore 的发起者、预览、冲突和结果。
- 过期、配额清理和显式删除事件。

审计事件不得包含不必要的文件明文。模型可以看到路径级摘要和恢复状态，但不能直接读取恢复 blob。

## 备选方案

### 方案 A：完全依赖 Git

优点是已有 diff、commit 和 checkout 能力。

缺点是工作区可能没有 Git，且无法可靠保护未跟踪、ignore、未提交和非源码内容；自动 reset 还可能
破坏用户原始修改。

不采用。

### 方案 B：按危险命令清单创建恢复点

优点是实现简单，容易识别 `rm`、`mv` 等常见命令。

缺点是任意脚本和自定义程序可以绕过，普通命令也会被误判；命令名称不能说明目标对象的操作前状态。

不采用。

### 方案 C：每次工具调用前完整复制工作区

优点是概念简单，对未知写集合也容易理解。

缺点是大型工作区的时间、磁盘和 I/O 成本不可接受，并会让 `auto` 频繁停顿。

不作为默认方案；仅在无法使用 Overlay、无法确定写集合且 `FULL` 策略预算允许时采用优化后的完整
checkpoint。

### 方案 D：只使用文件系统 watcher 记录变化

优点是跨工具观察方便。

缺点是 watcher 通常在修改发生后才报告事件，不能保证保存 preimage，也存在丢事件、合并事件和
并发竞态。

不作为恢复边界，只用于审计和变更核对。

### 方案 E：首次破坏性写入屏障 + 分层快照 + 内容寻址 RecoveryStore

优点是与命令名称解耦，支持无 Git 工作区；FileTool 可以按路径延迟保存，沙箱脚本可以通过 Overlay
延迟 materialize，未知直接写入仍可通过 FULL checkpoint 保护；内容寻址可以降低重复存储。

缺点是需要维护事务状态、对象身份、跨平台元数据、冲突恢复、配额和崩溃恢复；没有 Overlay 或写入
拦截时，未知脚本仍可能需要较昂贵的完整 checkpoint。

采用。

## 影响

### 收益

- 无 Git 环境仍能恢复 Agent 对工作区的破坏性修改。
- 不依赖无法穷举的危险命令清单。
- 正常删除、覆盖和重构不必全部设为 Hard Deny。
- FileTool 和 Overlay 场景可以按首次真实写入延迟保存，减少 `auto` 打断。
- 恢复过程能够保护用户在 Agent 执行后的新修改。
- checkpoint、执行、恢复和清理具有统一审计模型。

### 代价

- 需要新增 WorkspaceMutationCoordinator、RecoveryStore、SnapshotProvider 和恢复冲突处理。
- 需要占用额外磁盘空间并维护配额、保留期和内容去重。
- 跨平台文件元数据和对象身份处理复杂。
- 无 Overlay 且写集合未知时可能需要完整 checkpoint 或用户审批。
- 对数据库等应用一致性数据只能提供条件性恢复保证。

### 后续约束

- 工作区恢复不得依赖 Git 存在。
- 恢复触发不得以危险命令名称作为规范依据。
- preimage 必须在真实破坏性写入前持久化。
- RecoveryStore 位于工作区外并优先于 Agent、模式和目录授权。
- checkpoint 创建失败时不能声称操作可恢复。
- `auto` 不得在需要恢复保障但 checkpoint 未建立时静默继续。
- 恢复层不参与 mode、规则匹配或人工审批，也不能把安全层的 `ASK` / `DENY` 提升为允许。
- 人类批准后必须先重新验证计划、目标集合、策略和执行环境；重验通过后才能建立本次恢复绑定并
  签发执行授权。
- undo/restore 不得覆盖已发生的后续修改。
- 工作区根目录和 RecoveryStore 删除保持 Hard Deny。

## 验收标准

- 无 `.git` 工作区能够创建、列出和恢复 checkpoint。
- `ToolAuthorizationService`、`WorkspaceMutationCoordinator` 和 Sandbox Provider 保持独立；
  恢复成功或沙箱可用不能覆盖安全层的 `ASK` / `DENY`。
- 人类批准后绑定事实发生变化时不创建或复用 checkpoint，旧批准失效并重新进入完整安全管线。
- FileTool 在首次覆盖、删除、移动或元数据修改前持久化对应 preimage。
- 新建文件记录 `existed_before=false`，undo 只在 postimage 未变化时删除。
- 同一事务多次修改同一路径只保留最初 preimage。
- 复合 `CommandPlan` 使用一个关联的恢复事务。
- 恢复点触发不依赖 `rm`、`sed`、`python`、`node` 等命令名称。
- `TARGETED`、`OVERLAY` 和 `FULL` 策略具有明确选择和降级行为。
- Overlay 内部写入不修改真实工作区，materialize 前触发恢复屏障。
- 无 Overlay 且写集合未知时，在进程启动前完成 FULL checkpoint；无法完成时 `auto` 不执行。
- watcher 或执行后扫描不被当作 preimage 保证。
- checkpoint manifest 在工作区真实写入前原子持久化并进入 `ARMED`。
- RecoveryStore 不能被 ShellTool、`/add-dir`、学习式 Allow 或 `full_access` 修改。
- 恢复存储支持内容去重、配额、保留期和完整性校验。
- 恢复前校验 postimage；存在后续修改时进入冲突流程而不是静默覆盖。
- restore 自身创建 checkpoint。
- Forge 崩溃后能识别 `ARMED`/`EXECUTING` 事务并提供恢复或冲突说明。
- Git 存在时只作为增强；不存在、dirty 或包含 untracked 文件时恢复能力仍然成立。
- 工作区根目录和 RecoveryStore 删除在所有模式下被拒绝。
- checkpoint、MutationSet、恢复、冲突、过期和清理均有审计事件。
