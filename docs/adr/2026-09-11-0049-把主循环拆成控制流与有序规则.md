# ADR-0049: 把主循环拆成控制流与有序规则

## 状态

Accepted (2026-09-11 实现, 见文末实现记录; 同日修订决策 2 与决策 3 的形状, 见"修订"一节)

本文合并了两份草稿: 2026-09-10 的 ADR-0049 初稿 (五个时机加封闭处置) 与 2026-09-11 的
ADR-0050 (显式状态机加 Effect 执行器)。ADR-0050 因此标为 Superseded, 它的内容有三类去向:

- **并入本文**: 循环所处状态改成枚举, 先写行为基线再动手, Skill 的接入边界, 子 Agent
  只读优先并返回结构化报告, 安全管线不做成插件。
- **推迟到别的 ADR**: 子 Agent 的运行身份, 审批归属, 取消传播, 预算归属。这四件事不是
  循环形状的问题, 见"与将来功能的关系"一节。
- **不采用**: 纯 reducer 内核, Effect 执行器与 Handler 注册表, 能整体替换状态的处置,
  数字顺序, 把组请求和调模型也做成规则。理由见备选方案 A 与 G。

本文只改**循环内部的组织方式**, 不改循环与外界的边界: `LoopInput` / `LoopAction` /
`LoopStop` / `LoopObservation` 四个类型一个字段都不动, `AgentTurnService` 除了读用量记录
的几行之外不动。"循环只产出意图, 不执行工具" (ADR-0010 §2) 与"谁看见的事实谁发事件"
(ADR-0016 §4.3) 两条规矩之后仍然成立, 而且从靠人看守变成靠类型看守。

ADR-0010 §7.1 画过的 `LoopHook` 在本文落地, 但形状不同: 当时是一个带四个可选字段的通用
返回值, 本文改成每个时机各自一套处置。ADR-0010 §7.1 在本文接受后标注被取代。

## 日期

2026-09-11

## 背景

### 1. `_advance` 一个方法里写死了八条互不相干的判断

`application/agent_loop/builtin_loop.py` 的 `_advance` 在 304-433 行, 共 130 行。真正属于
"调模型, 看它要不要工具, 派发或回答"的只有约 25 行, 其余 105 行是八件各自独立的事:

| 行 | 判断的是什么 | 判断依据住在哪 |
| --- | --- | --- |
| 306 | 工作区有没有被外部改过, 有就追加通知 | `WorkspaceChangeMonitor` |
| 308 | 模型调用次数到没到上限 | 本文件常量 |
| 312 | 窗口撞没撞水位, 撞了先压缩 | `WindowManager` |
| 340-364 | 五种网关错误各自怎么办 | 散在 except 链 |
| 369-374 | 模型生成期间工作区又变了, 重新问一次 | 同第一条 |
| 375 | 模型什么都没说 | 本文件 |
| 385-400 | 工具调用参数里混进了标记文本 | `transcript.protocol_markup_in` |
| 402-416 | 目录已经收了模型还在要工具 | 本文件 |

加上 `_dispatch_next` 里的重复调用判断, `_observe_tool` 里的三条 (计划评审停轮, 收工具,
空转提醒), 一轮之内一共 12 条判断。

### 2. 判断依据与它的处理隔着几百行

ADR-0048 决策 5 已经把事件发布 (`run_events`), 模型调用 (`model_invoker`) 和打转判断
(`progress`) 拆出去了。那三个拆的是"怎么做", "什么时候做, 做了之后怎么办"还留在原地。
结果同一件事被劈成两半:

- `MAX_BARREN_OBSERVATIONS` 的说明与计数在 `progress.py`, 到线之后追加提醒和发事件在
  `builtin_loop.py:551`。
- `_fit_window` (估算说放不下) 在 726 行, `_recover_from_overflow` (供应商说放不下) 在
  583 行。同一个问题的两道防线隔了 140 行, 共用一个只有读到第二处才知道存在的字段
  `_overflow_compactions`。

### 3. 26 个字段里只有 5 个是控制流自己的

`__init__` 有 9 个形参, 26 个字段。属于控制流的只有 `_window`, `_pending_calls`,
`_dispatched`, `_started`, `_finished`; 其余全是那 12 条判断的计数器
(`_malformed_responses`, `_overflow_compactions`, `_model_calls`, `_tool_calls`,
`_workspace_changes`, `_tools_closed`) 或它们要用的东西 (`_context`, `_context_budget`,
`_workspace_monitor`, `_transport_policy`)。

加一条新判断要动四处: `__init__` 加字段, 在 `_advance` 或 `_observe_tool` 里插一段 if,
想清楚它跟前后七个 if 的先后, 再决定该不该发事件。删一条同理。**难的不是行数多, 是没有
一个地方叫做"这里可以加一条判断"。**

### 4. 循环在等什么, 靠三个字段拼出来

`_dispatched is None` 有四种可能: 还没派过工具, 工具刚跑完, 回答已经产出正等驱动方确认,
本轮已经结束。要知道是哪一种, 得再看 `_started`, `_finished` 和 `_pending_calls`。这种
组合没有一个是非法的会报错的。

### 5. `_advance` 有 7 处调自己

249, 378, 489, 559, 581, 636, 665 七行都是 `return self._advance()`。一轮里连着几次工作区
变更加一次压缩就会一层套一层, 读代码时看不出现在是第几层。

### 6. 有四条先后顺序改了就坏, 但只写在代码行的前后

- 工作区通知必须在压缩之前追加: 通知先进窗口, 压缩才把它算进预算。反过来的话一次大改动
  的变更列表 (几 KB) 不进本次估算, 而它恰恰最可能把窗口顶过水位。
- 模型预算必须在压缩之前查: 本轮已经该停了, 压缩还要再调一次模型, 那次调用记进用量却
  什么也没换来。
- 参数标记检查必须在"目录已收还在要工具"之前: 一个格式坏掉的调用不该被当成"模型无视
  目录已收"的证据。
- 计划评审必须在收工具之前判: 两者都不再派工具, 但前者是"轮到人说话", 后者是"你被罚
  闭嘴", 判错了评审界面上方会多一段没人读的解释。

### 7. 将来要接的功能, 大半不落在循环上

按 `docs/02-detailed-design.md` §10.2, Skill 加载的五步全部发生在
`AgentTurnService._assemble_context`, 也就是循环 `start` 之前, 跟计划 / 记忆 / 项目指令
完全一样。`allowed_tools` 走 `ToolCatalog` 的目录筛选。**接 Skill 不需要改循环。** MCP 工具
走 `ToolRegistry` (§9), 新提示词块走 `ContextAssembler`, 新展示走 `AgentRunEventBus`, 同样
不碰循环。

真正要改循环的只有一类: 改变"下一步做什么"的判断 —— 新的卡死判断, 新的错误恢复, 预算
分档降级。本文只为这一类开口子。子 Agent 会带来一种新动作, 但它的难点不在循环里, 见
"与将来功能的关系"。

## 决策

### 决策 1: 循环所处的状态改成枚举

循环在两次被驱动之间只可能处于四种状态之一:

```python
class LoopPhase(Enum):
    NOT_STARTED = "not_started"           # 还没 start
    AWAITING_TOOL_RESULT = "awaiting_tool_result"   # 派出去一个工具, 等结果
    AWAITING_ANSWER_ACK = "awaiting_answer_ack"     # 回答已产出, 等驱动方确认送达
    FINISHED = "finished"
```

`LoopPhase` 住在 `domain/agent/phase.py`, 与停止原因并列。`start()` 与 `observe()` 先按当前
状态断言合法, 再往下走 (已结束之后再 `observe` 是错误, 抛 `RuntimeError`, 不再发一次
`turn_finished`)。`_started` / `_finished` 两个布尔字段删掉; `_dispatched` 只在
`AWAITING_TOOL_RESULT` 下有值。

只要这四个。ADR-0050 草稿里的 `WAITING_CHILD_AGENTS` 与 `WAITING_USER` 不加: 前者今天没有
生产方, 后者是一个停止原因 (`WAIT_PLAN_REVIEW`), 不是循环的状态。

### 决策 2: 五个时机, 每个时机一套封闭的处置

一条规则就是一个类, 只在它关心的时机上给意见。今天有规则的时机是五个:

| 时机 | 方法 | 允许的处置 |
| --- | --- | --- |
| 调模型之前 | `before_model` | 继续 / 改写窗口 / 停止 |
| 模型调用出错 | `on_model_error` | 继续 (不归我管) / 重问 / 改写窗口 / 停止 |
| 模型回来之后 | `after_model` | 继续 / 改写输出 / 重问 / 停止 |
| 派发一个工具之前 | `before_dispatch` | 继续 / 拒绝这个调用 / 停止 |
| 拿到工具结果之后 | `after_observe` | 继续 / 追加消息 / 收工具 / 停止 |

处置类型如下。构造出来就是合法的; 一条规则在某个时机返回了不允许的处置, mypy 直接报错。

```python
# application/agent_loop/verdicts.py

@dataclass(frozen=True)
class Continue:
    """这一步没有意见. 在 on_model_error 里表示"这个错不归我管"."""


# 停止直接用已有的 LoopStop(reason, message), 不另起一个类型.


@dataclass(frozen=True)
class Rewrite:
    """换成这个窗口, 然后照常往下走.

    调模型之前返回它: 换了窗口, 后面的规则接着看 (看到的是换过的窗口).
    模型出错后返回它: 换了窗口, 回到"调模型之前"重来一遍.
    """

    window: Window
    summary: str = ""


@dataclass(frozen=True)
class Reask:
    """这次模型输出作废, 追加几条消息, 重新问一次.

    不写 assistant 消息: 那次输出里没有一条能用的工具调用, 写进去就欠下一批永远等不到
    的工具结果.
    """

    messages: tuple[ChatMessage, ...]
    summary: str = ""


@dataclass(frozen=True)
class Replace:
    """改写模型这次的输出, 比如剥掉已经不该派发的工具调用."""

    outcome: ModelOutcome


@dataclass(frozen=True)
class Deny:
    """这一个调用不执行, 用这段文字当它的工具结果. 队列里其余的照常派发."""

    notice: str
    code: str


@dataclass(frozen=True)
class Inject:
    """追加消息. 由循环保证在整批工具结果都回填完之后才写, 插在两条工具结果中间
    供应商会拒."""

    messages: tuple[ChatMessage, ...]
    summary: str = ""


@dataclass(frozen=True)
class CloseTools:
    """收掉本轮的工具目录. 给排队中的调用补工具结果, 追加通知, 都由循环做."""

    notice: str
```

规则的基类与只读快照:

```python
# application/agent_loop/rule.py

class LoopRule(Protocol):
    name: str
    runs_before: tuple[OrderRule, ...]
    runs_after: tuple[OrderRule, ...]

    def before_model(self, view: LoopView) -> Continue | Rewrite | LoopStop: ...
    def on_model_error(
        self, error: ModelGatewayError, view: LoopView
    ) -> Continue | Reask | Rewrite | LoopStop: ...
    def after_model(
        self, outcome: ModelOutcome, view: LoopView
    ) -> Continue | Replace | Reask | LoopStop: ...
    def before_dispatch(
        self, call: ToolCall, view: LoopView
    ) -> Continue | Deny | LoopStop: ...
    def after_observe(
        self, call: ToolCall, observation: LoopObservation, view: LoopView
    ) -> Continue | Inject | CloseTools | LoopStop: ...


class LoopRuleBase:
    """五个方法默认都返回 Continue. 一条规则通常只覆写一两个."""


@dataclass(frozen=True)
class LoopView:
    """规则能看到的东西. 全部只读, 除了 ledger."""

    session_id: str
    turn_id: str
    mode: SessionMode
    phase: LoopPhase
    window: Window
    tools: tuple[ToolSchema, ...]
    tools_closed: bool
    budget: ContextBudget | None
    system_prompt: str
    model_calls: int
    tool_calls: int
    pending_calls: int        # 只给数量, 不给队列: 规则改不了派发顺序
    ledger: TurnLedger
```

`TurnLedger` 是本轮的账本: 用量草稿与压缩记录都记在这里 (`add_usage` / `record_fit` 加两个
只读属性)。它也是规则把自己看见的事实报出去的口子: `record_fit` 顺手发压缩事件,
`report_workspace_changes` 发工作区变化事件 —— 规则拿不到事件发布器的其他方法, 编不出
"本轮结束"这种它没看见的事实。它替掉循环上的 `_usage_drafts` / `_compaction_drafts` 两个
字段与对应的两个属性, 驱动方改读 `loop.ledger`; `AgentModelInvoker` 的 `on_usage` 回调
改为写它。落盘仍由 `AgentTurnService` 执行 (ADR-0037), 分工不变。

**规则拿不到 `_window` 和 `_pending_calls`。** 不然耦合只是从一个文件搬进十个文件。

**不给规则整体替换状态的能力。** ADR-0050 草稿里 `ReplaceState(LoopState)` 那种处置, 意味着
规则能改工具目录, 清空队列, 动预算 —— 那之后"规则不允许改权限和预算"就只能靠人看代码。
本文的处置每一个都只能做一件具体的事。

**不开"改工具目录"的处置。** 轮内开放工具目录与 ADR-0018 §6.2 "一个 turn 中 mode, tool
catalog 和 system prompt 必须来自同一份开始快照"直接冲突, 而工具目录是缓存前缀最外面
那一层, 换一次整段前缀作废。这要单独一份 ADR, 不能是一个顺手就能返回的值。今天只有收
目录 (`CloseTools`) 这一条路, 本文之后仍然只有这一条。

**规则的规则清单只在今天有实现的时机上开。** 将来要加时机 (本轮开始, 本轮结束, 模型一次
要了一批工具), 只是给基类加一个默认方法, 不预留。

### 决策 3: 顺序就是列表的书写顺序, 硬约束另外声明, 装配时校验

规则表是一份写在代码里的有序列表, 读列表就知道先后。硬约束由规则自己声明, 装配时校验,
挪错位置进程起不来:

```python
# application/agent_loop/rule.py

@dataclass(frozen=True)
class OrderRule:
    """一条硬顺序约束.

    `why` 必填: 写不出"违反了会怎么坏"的, 就不是硬约束, 是偏好. 偏好不声明, 由列表
    的书写顺序表达就够. 这跟 check_arch.py 里 SIBLING_BANS 的 (源, 禁止, 理由) 是同一
    个形状.
    """

    peer: str
    why: str
```

```python
# application/agent_loop/rules/workspace_watch.py

class WorkspaceWatchRule(LoopRuleBase):
    name = "workspace_watch"
    runs_before = (
        OrderRule(
            "context_fit",
            "通知要先进窗口, 这次压缩才把它算进预算. 反过来一次大改动的变更列表"
            "(几 KB) 不进本次估算, 而它恰恰最可能把窗口顶过水位",
        ),
    )
```

`validate_rule_order(rules)` 在 `RuleTable` 构造时跑 (每轮一次, 十条规则, 便宜), 违反则抛
`RuleOrderError`, 消息里带两条规则的名字和那句 `why`。另有一个测试直接校验内置规则表,
改错顺序在 `make test` 就停下, 不用等到第一轮。

四条要声明的约束 (即背景 §6):

| 声明方 | 约束 |
| --- | --- |
| `workspace_watch` | 排在 `context_fit` 之前 |
| `model_budget` | 排在 `context_fit` 之前 |
| `malformed_output` | 排在 `tools_closed` 之前 |
| `plan_review` | 排在 `refusal` 之前 |

**不用数字。** 数字之间的空隙没有含义, 下一个人该填 55 还是 150 全靠猜。Spring 的
`@Order(int)` 走的是这条路, 而 Spring Security 内部那份过滤器顺序表是写死的清单, 外部
只能说"排在某某之前" —— 后者出现的原因就是前者不好维护。

**不做拓扑排序。** Spring Boot 的 `@AutoConfigureBefore/After` 要排序, 是因为几百个自动
配置类没有一份中心清单。这里是十条规则四条约束: 排序会让剩下六条的最终顺序变成一个要在
脑子里跑一遍算法才知道的结果。约束少项多, 声明加校验; 约束多项多, 才排序。`OrderRule`
的形状与排序的输入一致, 将来规模上去了换实现不用改声明。

另有两条顺序**不需要声明**, 由时机的位置保证:

- 参数标记检查必须在写 assistant 消息之前: `after_model` 全跑完循环才写, 时机的位置就是
  这条约束。
- 空转提醒必须在整批工具结果回填完之后: 这是 `Inject` 的定义, 由循环执行, 规则说了不算。

规则在任何时机抛异常, 循环把它记成一条日志和一条运行事件, 按 `Continue` 处理, 本轮不
因此失败。这是 ADR-0010 §7.2 原有的要求。

### 决策 4: 循环只剩控制流, 递归改成显式循环

五个时机就位后, 四条"追加点东西再来一次"的路径 (收工具, 格式重试, 溢出恢复, 工作区
变更) 变成同一种处置, 7 处自递归收成一个 `while`:

```python
def _advance(self) -> LoopStepResult:
    while True:
        verdict = self._rules.before_model(self._view())
        if isinstance(verdict, Rewrite):
            self._window = verdict.window
            self._events.decision(verdict.summary)
        elif isinstance(verdict, LoopStop):
            return self._stop(verdict)

        outcome = self._call_model()          # 内含 on_model_error 分发
        if isinstance(outcome, LoopStop):
            return self._stop(outcome)
        if isinstance(outcome, (Reask, Rewrite)):
            self._apply_retry(outcome)
            continue

        after = self._rules.after_model(outcome, self._view())
        if isinstance(after, Reask):
            self._apply_retry(after)
            continue
        if isinstance(after, LoopStop):
            return self._stop(after)
        if isinstance(after, Replace):
            outcome = after.outcome

        self._remember_assistant(outcome)
        return self._dispatch_or_answer(outcome)
```

规则表怎么跑, 只有两条:

- `Rewrite` 更新快照之后**接着看下一条规则**, 后面的规则看到的是换过的窗口。
- 其余非 `Continue` 的处置, 后面的规则不再看, 循环立刻执行它。

**这些留在循环里, 不搬:**

- 派一个工具, 等结果, 回填成工具结果消息; `_abandon_pending` 给排队中的调用补工具结果。
  这是协议本身: 每个工具调用都要有配对的结果, 不然供应商拒。
- `_remember_assistant`: 写 assistant 消息的唯一入口。
- `_build_request`: 组请求。
- 窗口只追加 (ADR-0041 决策 4)。
- 一次只派一个工具: 并行要知道冲突域, 那是安全层的知识。
- 事件的发布权: 规则只交回一句 `summary`, 事件由循环在执行处置时发; 工具的裁决与执行
  事实仍由 `ToolRequestCoordinator` 发。

**组请求, 调模型, 写 transcript 不是规则。** ADR-0050 草稿把它们列进了 14 步的管线。那之后
"增删一条规则不改循环"这句话就不成立了: 删掉调模型那一步循环就不转了。

### 决策 5: 外部规则将来走另一个类型, 只能追加消息

循环今天拿不到 `ToolRegistry` 也拿不到 `ToolRuntime`, "绕过 `ToolRequestCoordinator`
直接执行"在类型层面写不出来 —— 这是 ADR-0010 §2 那条规矩真正靠得住的原因。一个不分级的
通用挂载机制会打开两个口子: 项目或用户注册的代码能返回 `Replace(outcome)` 改写模型输出,
能返回 `LoopStop(reason)` 伪造一个写进事件流的停止原因。

所以本文定一条约束, **不写接口**: 将来项目, 用户或 Skill 要往循环上挂东西时, 必须走
另一个类型, 它只允许 `Continue` 与 `Inject` 两种处置, 由一条内置规则统一驱动 (隔离异常,
限制追加长度, 给追加的正文打来源标记)。它排在内置规则之后, 内部按加载顺序 (内置 ->
项目 -> 用户), 不接受自定义排序。

今天不写这个接口: 没有一个实现的 Protocol 是 ADR-0028 规则 A 要删的东西, ADR-0050 草稿
自己也写了"不因为将来可能需要提前加没有生产方的接口"。约束记在这里, 接口等第一个外部
规则出现时再写。

### 决策 6: 安全管线不做成规则

规则只管循环层面的判断: 预算, 压缩, 重试, 打转, 目录收放。下面这些仍归安全与工具模块,
规则碰不到:

```text
工具目录筛选
Tool.prepare
授权裁决
审批绑定
执行环境复核
恢复检查点
ToolRuntime.execute
工具结果整理
```

一条规则要派工具, 唯一的出口是让循环产出 `ToolRequestAction`, 然后照常经
`CoordinatorToolDispatcher -> ToolRequestCoordinator`。

## 与将来功能的关系

| 功能 | 落在哪 | 循环要改什么 | 真正的难点 |
| --- | --- | --- | --- |
| Skill | `ContextAssembler` 加一个块, `ToolCatalog` 加一条筛选 | 0 | 轮内开工具目录与 ADR-0018 §6.2 冲突, 需要单独决定 |
| MCP | `McpClientAdapter` 把外部工具做成 `Tool` 进 `ToolRegistry` (§9) | 0 | 外部工具的风险分类, 默认该是 ASK。纯安全层的事 |
| 子 Agent (只读) | 一种新的 `LoopAction` 子类型 + 驱动方一个分支 + 子运行器 | 一种新动作, 一个新状态 | 见下 |
| 多 Agent 并发 | 调度器, 在循环之外 | 等子运行 + 汇合 | 冲突域, 租约, 共享工作区写权限。离得远 |
| 并行工具调用 | 改骨架 | 真改骨架 | 要安全层给出冲突域, 任何规则机制替代不了 |

**Skill 的边界** (吸收自 ADR-0050 决策 8): Skill 在本轮开始时编译成不可变的快照, 只能提供
触发条件, 指令正文, 输出格式, 工具建议或工具筛选, 版本指纹。它不能提供绕过
`ToolRequestCoordinator` 的执行入口, 不能改安全策略, 模式权限或审批结论, 不能直接改会话
状态, 不能直接写工作区或长期记忆。Skill 文件在本轮运行期间变了, 本轮不变, 下一轮重新读。

**子 Agent 的边界** (吸收自 ADR-0050 决策 9): 第一版只读, 不开写权限; 返回结构化报告
(摘要, 发现, 证据, 建议动作, 把握程度); 要改东西就返回建议, 由父 Agent 重新产出
`ToolRequestAction` 走同一条安全管线。循环那部分能直接复用 (每 turn 一个新实例的工厂今天
就有), 但下面四件事**不是循环形状的问题**, 规则机制一条都碰不到, 要单独一份 ADR:

1. 嵌套审批归谁: 只读工具也会撞 ASK (路径越出工作区)。ADR-0048 决策 3 把每条待答提示
   绑到 turn 生命周期, ADR-0043 的提示通道按 turn 释放。子运行要么有自己的 turn 身份,
   要么通道得认识父子关系。
2. 取消传播: `cancel_source.current()` 是按 turn 的。父轮取消时子运行阻塞在哪, 谁放开它。
3. 上下文切片与只追加窗口: ADR-0041 决策 4 之后窗口只追加, 子运行的窗口不是父窗口的
   前缀, 缓存前缀从零开始。可以接受, 但要算出来。
4. 预算归属: 子运行的用量记进父轮合计还是独立一轮, 前端每轮成本显示要跟着改。

子 Agent 要用的事件身份字段 (`run_id`, `agent_id`, `parent_run_id`) 与 ADR-0048 决策 2 同向,
在那份 ADR 里一起定, 本文不加。

**不做 Effect 执行器与 Handler 注册表。** 今天 `AgentTurnService._run_loop` 是两个分支
(回答, 派工具), 子 Agent 来了是三个。三个分支换注册表, 收益是负的。ADR-0050 草稿列的
八种 Effect 里, `RequestHumanDecision` 与 `CompactContext` 与 ADR-0043 决策 1 直接冲突
(那份 ADR 明确把提问, 审批, 压缩三项从动作表里删掉, 给了三条理由, 并已实现),
`StopLoop` 就是 `LoopStop`, `JoinChildAgents` 没有生产方。等第三种动作真的落地时再看那个
isinstance 链值不值得换。

## 备选方案

- **方案 A: 一个通用的返回值类型** (ADR-0010 §7.1 的 `HookResult`, ADR-0050 的
  `ReplaceState(LoopState)`)。12 条判断里没有一条需要在不同时机做同一种处置: 拒绝调用只在
  派发前有意义, 改写输出只在模型回来后有意义, 收工具只在拿到结果后有意义。合并省不下
  代码, 只是把 mypy 能拦的事换成运行期的 if。而且这与本仓库一路的做法相反
  (`AssembledContext.policy` 必填而不是可选加运行期检查, `LoopAction` 用密封子类型,
  `ObservationDisposition` 用枚举而不是读文字)。ADR-0050 自己的方案 B 也以"类型边界弱"
  拒绝了通用 Hook, 然后决策 4 又给了 `ReplaceState`。**不采用。**
- **方案 B: 数字顺序** (`@Order(int)`, ADR-0050 的 10..140)。见决策 3。**不采用。**
- **方案 C: 相对声明加拓扑排序。** 见决策 3。**不采用, 保留升级路径。**
- **方案 D: 洋葱式中间件 (`next()` 链)。** 这条循环在派工具与拿结果之间必须 return 给
  `AgentTurnService` 再回来, 调用栈在 `observe` 回来时已经散了, 接不回中间。ADR-0050 的
  14 步线性管线也是这个形状: 第 100 步 `EffectExecutionStage` 挂起之后, 是从第 110 步
  接着跑还是从第 10 步重来, 草稿没说。**这是硬理由, 不是风格取舍。**
- **方案 E: 只做事件订阅。** 改不了控制流, 而这 12 条判断全都要改。它已经存在
  (`LoopEventPublisher`)。**不采用。**
- **方案 F: 每个步骤一个状态类。** 真状态只有四个 (决策 1), 拆成七个类读起来更难。
  **不采用。**
- **方案 G: 纯 reducer 内核 + Effect 执行器 + Handler 注册表** (ADR-0050 决策 2, 3, 5)。
  这套形状跟今天的一样: 循环产出意图 (`LoopAction`), 驱动方执行 (`_run_loop`), 结果回填
  (`observe`) —— 只是换了名字 (`Effect`, `TurnRunner`, `reduce`)。换名字本身不是问题,
  问题是它与决策 4 的线性管线互相矛盾 (纯 reducer 不做 I/O, 管线里却有调模型那一步),
  且新增十几个类替换 `BuiltinAgentLoop` 与 `_run_loop`, 与 ADR-0048 "不以全面重写作为
  优化手段"相反。**不采用。** 它里面对的部分已并入本文。
- **方案 H: 引入 LangGraph 等第三方运行时。** 12 条判断是 Forge 自己的策略, 框架吸收不了,
  搬过去变成条件边和字符串路由, 类型反而弱化; `check_arch.py` 不许 application 层依赖
  SDK, 循环恰好在那一层; 图的 checkpoint 与 `events.jsonl` 是两份真相源, 违反 ADR-0028
  "一个事实只存一次"; `LangChain` 的模型层与 `LlmGateway` 的重试, 缓存, 计价重复。
  ADR-0040 §4 已写明"第三方 agent framework 不得隐式接管循环, 工具授权或恢复"。它真正
  强的两块 (轮内断点恢复, 并行与子 Agent 的扇出汇合) 今天不是主线。**不采用**; 若将来
  这两块成为主线, 且愿意让 checkpoint 成为真相源, 再重新评估。本文的拆分反而是那时
  换骨架的前提: 判断与骨架分开了, 骨架才换得动。

## 修订 (2026-09-11): 规则表按时机列, 列里放方法

实现完第一版之后对着代码复盘, 决策 2 与决策 3 的形状对新人不友好, 改了。原文保留, 以本节
为准。

### 第一版的问题

第一版把"规则"建模成对象: 一个 `LoopRule` 协议带五个时机方法, 一个基类给五个默认实现,
十条规则排成**一份**列表, 到了任何一个时机都把十条从头走一遍。读 `rules/__init__.py`
看到的是十个类名和几行按"主要时机"分组的注释 —— 而那几行注释是骗人的: `workspace_watch`
挂四个时机, `context_fit` 与 `malformed_output` 各挂两个。想知道"模型回来之后到底哪几条
会跑, 什么顺序", 唯一的办法是把十个文件挨个打开看谁覆写了 `after_model`。新人第一天最想
知道的恰恰是这个, 而它没写在任何一个地方。

顺带的负担: 写一条规则要先知道五个方法名和各自允许的返回类型, 要继承基类, 要给 `name`,
可能还要声明 `OrderRule`; 位置在一份列表里定, 但它同时决定五个时机的顺序。

根子上是建模建偏了: 循环关心的从来不是"规则对象", 是"这个时机上按什么顺序问哪几个函数"。
那就该按时机列。

### 改成什么样

```python
            ToolsClosedRule().after_model,
        ),
        before_dispatch=(workspace.before_dispatch, RepeatCallRule().before_dispatch),
        after_observe=(
            workspace.after_observe,
            # 先判"轮到人说话", 再判"你被罚闭嘴".
            PlanReviewRule().after_observe,
            RefusalRule().after_observe,
            BarrenStreakRule().after_observe,
        ),
    )
```

`RuleTable` 是五个有序元组, 就是这份表本身; `RuleRunner` 拿着它在每个时机上跑, 执行规矩
不变 (`Rewrite` 往下传, 其余第一个非 `Continue` 就算数, 抛异常按 `Continue` 处理)。

一条规则就是一个方法: 收只读快照加这个时机的输入, 返回这个时机允许的处置。方法叫什么、
属于哪个类都随意 (`fit.on_overflow` 比 `fit.on_model_error` 更说事); 它在哪个时机跑, 由表
决定, 不由方法名决定。同一个对象的方法出现在几列, 它就参与几个时机, 状态自然共享。

### 砍掉的

- `LoopRule` 协议, `LoopRuleBase` 基类与五个默认方法
- `OrderRule`, `validate_rule_order`, `RuleOrderError`, `runs_before` / `runs_after`
- 规则的 `name` 属性 (日志改用方法的 `__qualname__`, 如 `WorkspaceWatchRule.before_model`)
- `check_abstractions.py` 里的 `LoopRule` 登记

### 留下的 (本文真正要的东西, 一条没丢)

- 七种处置与"哪个时机允许哪几种"的封闭类型: 每一列的元素类型是
  `Callable[[...], 该时机的处置联合]`, 把 `repeat.before_dispatch` 塞进 `after_model=`, 或让
  一个方法返回不该返回的处置, mypy 在装配那一行就报错 (三种误用都试过)
- `LoopView` 只读, `TurnLedger` 唯一可写
- 执行规矩与异常隔离
- 循环本体一行没动

### 放弃的一条, 以及为什么可以放弃

"挪错顺序进程起不来"改成"挪错顺序 `make test` 停": 顺序写在表里, 理由写在旁边的注释里,
`tests/agent_loop/test_rule_table.py` 按时机逐列断言。决策 3 当初拒绝"写在注释里"的理由
是注释不会报错; 有测试守着之后这条理由不成立了, 而且约束和理由回到了同一个地方 (表的
旁边), 比散在四个规则文件里更容易看全。

### 新人现在怎么加一条判断

写一个方法, 返回它那个时机允许的处置; 在 `rules/__init__.py` 对应时机那一列里加一行,
旁边写一句为什么排在那。完。
