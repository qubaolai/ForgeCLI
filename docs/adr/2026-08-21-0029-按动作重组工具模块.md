# ADR-0029：按动作重组工具模块

## 状态

Proposed

## 日期

2026-08-21

## 背景

一次真实需求（在 Java 项目里加一个下载接口）的完整 trace：**30 次模型调用、28 次工具
调用、498k tokens、151 秒**，产出是 3 个文件各加一个方法。

按调用归类：

| 类别 | 次数 | 明细 |
|---|---|---|
| 有效编辑 | 4 | 4 个文件各改一处 |
| 必要探索 | 10 | scan_tree ×3、首次 read ×4、有效 search ×2、有效 read ×1 |
| **摩擦** | **14** | edit 失败 ×5、为修 edit 而重读 ×6、工具名猜错 ×1、search 传文件路径 ×1、只改 limit 的重复读 ×1 |

**一半的工具调用没有产出。** 而且四次成功的编辑全部是同一个模式：模型连续失败之后
把 `old_string` 缩到最小片段（小到不含嵌套缩进）才命中——**它在绕过工具，不是在用工具**。

### 现状盘点

11 个工具、34 个参数、4023 行实现：

| 工具 | 参数 |
|---|---|
| `fs.read_file` | path, offset, limit, max_bytes |
| `fs.list_files` | path, pattern, depth, include_ignored |
| `fs.scan_tree` | path, depth, max_entries, include_ignored |
| `search.text` | query, path, pattern, regex, context_lines, include_ignored |
| `fs.create_file` | path, content |
| `fs.edit_file` | path, old_string, new_string, replace_all |
| `fs.delete` | path, recursive |
| `fs.create_directory` | path |
| `fs.move` | source, target |
| `git.read` | subcommand, args |
| `shell.run` | command, shell_kind, timeout_seconds |

### 外部证据

**工具数量有可测的硬上限。** 工具选择准确率在 10–15 个之后开始下降；Berkeley Function
Calling Leaderboard 上某类任务从 4 个工具扩到 51 个，准确率从 43% 掉到 2%。失效有两种
机制：语义边界模糊导致选错工具，以及**拿 A 工具的 schema 去填 B 工具的参数**。

11 个还在安全区，但已经在边缘——**没有加法余量了**。这一条直接反驳「遇到新场景就给工具
加个参数」这条默认路径。

**四家主流实现的分歧只在三个点上：**

| | 检索 | 编辑寻址 | 长尾 |
|---|---|---|---|
| Claude Code | Glob + Grep，刻意不做语义索引 | 精确串替换 | Bash |
| Codex | shell 的 cat/grep/find | **一个 apply_patch 信封** | shell |
| Aider | tree-sitter repo map + PageRank | whole / diff / udiff / search-replace | — |
| Cline / Roo | 专用工具 + list_code_definition_names | **四个入口 + 两个废弃别名** | execute_command |

共识的部分比分歧更值得抄：

1. **一个动作一个入口。** Cline 是反面教材，它的编辑工具长期反复失败。
2. **编辑是最危险也最常失败的动作，值得单独下重注。** Codex 把读、搜、跑全交给 shell，
   唯独文件变更收进一个严格信封，逼模型产出最小外科式 diff。
3. **反馈要闭环。** SWE-agent 的 ACI 论文四条原则：动作简单、动作紧凑、反馈信息量足但
   简洁、**护栏防止错误扩散**。它们的编辑器带 linter——改完就校验，坏了立刻拒绝。论文
   的核心主张是：界面设计比模型能力更决定成败。

### Forge 的特殊约束改变了答案

**安全链按能力解耦，不认识工具名。** 所以 `shell.run "grep -rn x src"` 和 `search.text`
走的是同一套裁决；ADR-0024 之后前者还零摩擦自动放行。

**这意味着专用工具在 Forge 里买不到安全性**，只买到结构化输出和更好的审批展示。

## 决策

### 规则一：工具的重量是契约面，不是代码行数

两种「重」的成本差一个数量级：

- **契约面** = 模型每次调用都要读、要选、要选对的东西。11 个工具 / 34 个参数。
- **内部复杂度** = 模型看不见的部分。4023 行。

`fs_write.py` 865 行是全仓第二大文件，但 `fs.edit_file` 只有 4 个参数——**这 865 行
没有一行让模型的选择变难**。让模型出错的从来是契约面。

由此得到改动分级：

| 改动形态 | 是否加重 | 是否需要 ADR |
|---|---|---|
| 加工具、加参数、加模式 | **加** | **需要** |
| 改输出格式、改错误信息、改内部算法 | 不加 | 不需要 |
| 删限制、合并入口 | **减** | 不需要，鼓励 |

**工具可以变聪明，不该变宽。**

### 规则二：长尾交给 shell.run

新场景出现时，先问「`shell.run` 能不能做」。能做就不加——安全链已经覆盖它，而
ADR-0024 之后只读命令零摩擦。

**专用工具只占高频且结构化收益明显的路径。** 判据：它的结构化收益是否大于它占掉的
那一个工具位。

### 规则三：五类，六个工具

| 类 | 工具 | 存在理由 |
|---|---|---|
| A 定位 | `fs.find`、`search.text` | 结构化 `file:line` 比 stdout 省 token；强制排除生成目录 |
| B 读取 | `fs.read` | 高频，需要 offset/limit 窗口 |
| C 写入 | **`fs.apply_patch`** | 唯一危险动作，重注所在 |
| D 执行 | `shell.run` | 长尾全在这里 |
| E 过程 | `plan.write` | 已有，不动 |

#### A 类：3 → 2

`fs.scan_tree` 与 `fs.list_files` 是**同一个动作两个入口**，合并为 `fs.find`
（按路径模式定位 + 列目录）。

`search.text` 的 `path` 同时接受文件与目录。现在传文件路径直接 `target_unreadable`，
而这里没有安全理由——收一个文件就是 `files = [path]`，能力声明完全一样。**这是删一条
规则，不是加一个参数。**

`search.text` 增加结果排序：命中按「是不是源码文件」排，`.log` / `.min.js` /
`dist/` / `target/` 靠后。trace 里搜 `downloadConsole` 只回了 378 字节而候选 2000 个，
额度被日志文件吃掉了。**零参数、纯输出改进。**

#### C 类：5 → 1（本 ADR 的核心）

`fs.apply_patch` 一个信封，替掉 `create_file` / `edit_file` / `delete` /
`create_directory` / `move`。

**为什么是信封而不是第六个工具：**

- 审批界面本来就要展示「文件会变成什么样」。**一个信封天然对应一次审批、一个恢复点**；
  现在跨文件的一次逻辑改动会产生 4 次独立审批（trace 里正是如此）
- 五个工具意味着五套 prepare / plan / content_previews 逻辑，这是 865 行的由来
- **未来所有写入场景的变化都在信封的内部语法里表达，不占新工具位、不加新参数**

**信封语法自定，不抄 Codex。** Codex 那套格式的优势来自模型对它的训练，而那主要是
OpenAI 系模型的优势；Forge 走多供应商网关，对 DeepSeek / Qwen 未必成立。自定语法可以
按 Forge 已有的事实来设计——特别是让 `old_string` 的定位失败可诊断（见「不在本 ADR」）。

语法要满足的约束（具体形式留给实现）：

1. 一个信封含若干文件段，每段一种操作：新建 / 更新 / 删除 / 移动
2. 更新段内可含多处替换，每处独立定位
3. 解析失败必须指出是**哪一段的哪一处**，不能整封退回
4. 每段的产出直接进 `ToolPlan.content_previews`——审批看到的就是最终形态

**保留的安全性质一条不减**：`expected_state` / `path_state_token` 守卫照旧（计划生成
后文件变化即拒绝）；`PlanEffects` 的 write/delete/move 目标照旧逐项进恢复层；
受保护路径、Hard Deny、模式预算不变。

#### D 类：`git.read` 保留，但归到读取类；写半部留在 shell.run

> **2026-08-21 修订。** 本节原本的决策是删掉 `git.read`（2 → 1），理由两条：
> 「`git status` / `git diff` 走 proven-read-only 本来就自动放行」，以及「一张必须与
> `GIT_READ_ONLY_SUBCOMMANDS` 手工同步的表」。ADR-0030 把这两条各拆掉一条，
> 决策因此反转。

**理由一失效**：`GIT_READ_ONLY_SUBCOMMANDS` 的唯一消费方是
`domain/security/shell/effects.py:79` 的 `_git_is_read_only`，走 proven-read-only
那条路径。ADR-0030 决策 6 把 proven_read_only 整体删除，**这张表跟着消失**，重复
自然不存在。备选方案 D 里「共享要跨过 `check_arch.py` 边界」的两难也随之消解。

**理由二在 plan 档不成立**：`application/tool_request/catalog_predicates.py` 的目录门
在 plan 档移除全部带 `MUTATING_CAPABILITIES` 的工具，`shell.run` 的能力上界声明了
9 个 mutating 能力，因此**它在 plan 档不可见**。那里没有 proven-read-only 可走。
删掉 `git.read` 等于 plan 档完全没有 git——而 `git log` / `git diff` / `git blame`
正是做计划时最该看的东西。

**读写必须拆在 spec 层，这是结构约束不是偏好。** `_plan_mode_visible` 判的是
`spec.declared_capabilities` 这个**上界**，其注释写明「一个上界里带 WORKSPACE_WRITE
的工具，即使这次只想读，也不该出现在 plan 档的目录里」。所以一个统一的 `git` 工具
**不可能**在 plan 档可见。`git_read.py:270` 现在正好是
`{WORKSPACE_READ, SPAWN_PROCESS}`，已经是对的形状。

**分类摆正**：`git.read` 不属于 D 类（执行），它属于 B 类（读取）——它是一个读工具，
后端恰好是子进程。归类正确之后，plan 档可见性自动成立，不需要为它开特例。

**写半部不做 `git.write`**，三条理由：

| | |
|---|---|
| 契约面 | commit / add / checkout / branch / merge / rebase / stash / reset / tag / cherry-pick…… 结构化它要么是 `subcommand + args` 透传（等于 `shell.run` 换个名字），要么契约面爆炸。这正是规则二说的长尾 |
| 安全 | ADR-0030 下已被两道防线盖住：`git commit` 写 `.git/`，在工作区内，快照可回滚；`git push` 命中围栏外不可回滚操作表 → ASK |
| 工具数 | 6 → 7 可接受；6 → 8 开始侵蚀本 ADR 的核心论点 |

**顺带解决了 ADR-0015 显式放弃的一件事**：ADR-0015 有一节「已知限制：`/undo` 不覆盖
`git.write`」，理由是 `.git/refs/heads/<branch>`、`packed-refs` 这些写入 `prepare`
无法可靠枚举，因此「显式放弃」并注明「需要单独一个切片」。**ADR-0030 的 FULL 快照
不需要枚举**，整棵工作区快照天然包含 `.git`，那个切片不用做了。

**保留 446 行的代价**：`git_read.py` 里的 `_ReadOnlyForm` 表仍要维护，但它此后是
**唯一**一份 git 子命令知识（security 侧那份已删），不再有同步问题。

### 规则四：不做 repo map

**Aider 需要 repo map，是因为它没有 agentic 检索循环**——它必须在生成前把上下文预先
装好，所以需要一张图来决定装什么。**Forge 有工具有循环，能搜就不需要那张图。**
Claude Code 也是这个取舍。

更关键的是 trace 里的痛点根本不是符号导航：3 次 `scan_tree` 是在找 `com/citict/mis`
这个**目录**，AST 帮不上忙——一次 `find . -path '*mis*' -name '*.java'` 就到了。

而且有一条与本仓库原则直接冲突：**索引是派生事实，会过期，而 ADR-0027 整条血脉就是
「不信任过期事实」。** 一个陈旧的符号索引会让模型读到已经不存在的方法——比没有索引更糟。

**AST 真正能赢的地方也要说清楚**：找引用 vs 找文本。grep 分不清定义、调用、注释和日志。
trace 里搜 `downloadConsole` 命中的候选包含 `error.log` / `info.log` 就是这个问题。

判断是**先不做**，理由三条：

1. trace 的痛点是目录导航与编辑失败，不是符号导航
2. `find` 误判已修（2026-08-21）、提示词那句过期的话已改，**先重新量一次再定**
3. 真要做，做**按需 outline 不做常驻 index**——当场 parse、无缓存、无过期，避开与
   ADR-0027 的冲突。但它仍要占掉六个工具位里的一个

先用 `search.text` 的结果排序（零契约面）去消掉「grep 不好用所以要 AST」这个前提。

### 汇总

| 类 | 现在 | 之后 | |
|---|---|---|---|
| 定位 | scan_tree, list_files, search.text | `fs.find`, `search.text` | 3 → 2 |
| 读取 | read_file, git.read | `fs.read`, `git.read` | 2 → 2 |
| 写入 | create_file, edit_file, delete, create_directory, move | **`fs.apply_patch`** | **5 → 1** |
| 执行 | shell.run | `shell.run` | 1 → 1 |
| 过程 | plan 工具 | 不变 | 1 → 1 |
| **合计** | **11 个工具 / 34 参数** | **7 个工具** | **−36%** |

## 备选方案

- **A：维持 11 个工具，按场景加参数。** 成本最低，但这正是产生 34 个参数的那条路径，
  而外部证据说明工具数与参数量的代价是断崖式的。不采用。
- **B：全 shell-first，只留 shell.run + apply_patch（Codex 路线）。** 最少的契约面。
  但放弃结构化检索输出——`grep` 原始 stdout 比 `file:line` 结构费 token，且无法强制
  排除生成目录（trace 里 2000 个候选文件含日志正是这个问题的预演）。不采用。
- **C：做 repo map（Aider 路线）。** 见规则四。不采用，但保留为后续可选项。
- **D：保留 `git.read` 并让它与 security 侧共享同一张子命令表。** 共享要跨过
  `check_arch.py` 的 tools ⇏ security 边界，而那条边界是 ADR-0004 §2 的核心。不采用。
  （2026-08-21：ADR-0030 删除 security 侧的 `GIT_READ_ONLY_SUBCOMMANDS` 之后，
  只剩一份表，本方案的前提消失——`git.read` 按 D 类修订保留，无需共享。）

## 影响

### 收益

- 契约面从 11 个工具 / 34 参数降到 7 个工具，回到安全区中部
- 写入的所有场景变化在信封内部语法里表达，不再需要加工具或加参数
- 一次跨文件改动 = 一次审批 = 一个恢复点，而不是 N 次独立审批
- git 子命令知识收敛到一份（security 侧那张由 ADR-0030 删除），不再需要手工同步
- plan 档保住 `git log` / `git diff` / `git blame`——该档没有 `shell.run` 可用

### 代价

- **`fs.apply_patch` 是一次性大改**，五个工具的 prepare / plan / preview 逻辑要重写
- 信封语法自定意味着**没有模型训练优势**，要靠 spec description 与失败诊断补
- 信封解析本身成为新的失败点。缓解：约束 3（指出是哪一段的哪一处）
- `git_read.py` 的 446 行与 `_ReadOnlyForm` 表继续维护
- 模型已经形成的工具使用习惯要重新适应，短期内可能升高失败率

### 兼容性

工具名与参数全部变化，`spec_hash` 随之改变，因此**所有 learned allow rules 失效**
（`ApprovalBinding.plan_hash` 覆盖 `spec_hash`）。恢复点与会话记录格式不变。

## 不在本 ADR

以下几条来自同一份 trace 分析，但属于安全裁决而非工具契约，需要各自的决策：

- **从冻结环境展开 `$VAR`。** `ls $MODULE` 在 `MODULE` 已在净化环境里时仍判 DYNAMIC，
  Forge 手里有值却没用。展开它和展开 glob 是同一件事，是净收益。
- **未封闭写目标 ASK → DENY。** 理由是机械的：`_begin_recovery` 遍历
  `plan.effects.write_paths`，目标 DYNAMIC 时它是空的——checkpoint 建了但 preimage
  一个都没存，`rm -rf $BUILD_DIR` 批准之后 `/undo` 什么都还原不了。这与 ADR-0027
  决策 2 对「读不全的脚本不提供批准后继续路径」是同一条判据。
- **编辑后的闭环校验。** SWE-agent 第四条原则。trace 里四次编辑全部「成功」，但没有
  任何一步确认那个 Java 文件还能编译。加一次 post-edit 语法检查（坏了连同恢复点回退）
  不加任何参数。
- **`fs.edit_file` 失败诊断中制表符不可见。** 工具说「缩进方式不一致（制表符与空格）」
  并引出原文，而引文里制表符和空格长得一模一样——模型被要求照抄一段它看不清的东西。
  这是 5 次编辑失败的直接原因。若 C 类落地则随信息语法一并解决。

## 验收标准

- 工具目录中恰好 6 个工具；参数总数不超过 20
- 同一个动作只有一个入口（可用工具名与 `ToolSpec.description` 交叉检查）
- `fs.apply_patch` 一次调用产生一个 `ToolPlan`、一次审批、一个恢复点
- 信封解析失败时错误信息指出具体是哪一段的哪一处
- `expected_state` 守卫、`PlanEffects` 目标登记、受保护路径、Hard Deny、模式预算
  行为全部不变，有用例逐条钉住
- 拿一次同等复杂度的真实需求重跑，**摩擦调用占比从 50% 降到 20% 以下**
- `make ci` 全绿
